## 🧭 使用契约：作为「逐聚合根应用设计」技能（应用组构建 · 第②步）

> 本文件一身二用：**下半部分**是供逐个需求填写的《用户需求规格说明书》模板（第1–7部分 + 示例）；
> **本节**约定把它当作技能使用时的输入、产出与方法——以第①步产出为起点，为应用组内**每个聚合根**生成一份按本模板填写的《应用详设》。

### 技能定位（九步法 · 后端段）

```text
第①步  fde-aggregate-identification（规格见同目录《架构设计.md》）
          业务说明 → app/<组>/architecture.md（聚合根清单总表 + 聚合根卡 + 关系图）
            ↓
★第②步  本技能 · 逐聚合根应用设计
          app/<组>/architecture.md + app/<组>/brd/ → 每个聚合根一份 app/<组>/<应用名>/应用详设.md
            ↓
第③步  按 CONVENTION 生成代码（规格《应用编码.md》）
            ↓
第④⑤步  测试用例生成 → 测试执行（规格《应用测试.md》《测试执行.md》）
            ↓（契约冻结后）
第⑥–⑨步  前端设计 → 前端编码 → 前端测试用例 → 前端测试执行
          （规格《前端设计.md》《前端编码.md》《前端测试.md》《前端测试执行.md》，全景见《工具链使用说明.md》）
```

### 必给参数
- 英文应用组名 `<组>`（snake_case），逐字绑定 `app/<组>/`。
- （可选）`<应用名>`：只详设指定的某一个聚合根；缺省＝对总表内**全部**聚合根各出一份。

### 输入（两类，均位于应用组目录）
| 来源 | 位置 | 说明 |
|---|---|---|
| ① 第①步产出（**必需**） | `app/<组>/architecture.md` | **主输入**。从①聚合根清单总表确定要建哪些应用（第3列＝应用名），从②各聚合根卡读取核心属性 / 对外操作 / 关键不变量 / 引用的聚合 / 跨应用调用 / 状态机。**缺失则停下**，提示先跑第①步，不臆造。 |
| ② 组级业务设计（可空） | `app/<组>/brd/` 下**所有文件**（含子目录如 `images/`） | 补充上下文：业务背景 / 主流程 / 角色职责 / 字段细节 / 原型。文本类（md/txt/html/csv/json…）读正文；二进制（图片等）记录路径供参照。为空时仅依据 architecture.md 展开。 |

### 产出（每个聚合根一份，落同名应用文件夹）
对 architecture.md 总表中的**每一个聚合根**（应用名 `<应用名>`，snake_case）：
1. 在应用组目录下新建**同名应用文件夹** `app/<组>/<应用名>/`（不存在则创建）。遵循 CONVENTION：一个聚合根＝一个 FDE 应用＝一个同名文件夹＝一个同名类＝一个同名 SQLite 库。
2. 在该文件夹下写出 **`app/<组>/<应用名>/应用详设.md`**——一份按下方模板（第1–7部分）完整填写的《用户需求规格说明书》，**只聚焦这一个聚合根**。
- 产出文件固定名 `应用详设.md`，每个应用文件夹下唯一一份；已存在则覆盖更新。
- 只产出**详设文档**，不写代码（代码在第③步）。

### 从聚合根卡到本模板的填写映射
| 聚合根卡（来自 architecture.md） | → 本模板章节 | 产生 ID |
|---|---|---|
| 一句话定义 / 业务定义 | §1 需求概览（背景 / 范围 / 目标） | — |
| 对外操作（将成公共方法） | §2 用户故事 + §4 功能清单 / 功能详细说明 | US / FUNC |
| 核心属性（含值对象、行项目） | §3.3 业务数据 + §4.3 各功能字段表 | — |
| 关键不变量（边界）＋**本步补全的逐字段校验** | §3.2 业务规则 | BR |
| 状态机 | §3.4 状态机 | — |
| 引用的聚合 / 跨应用调用 `self.fde.call` | §4.3 特殊处理 + §7.3 外部依赖 | — |
| 角色与职责（取自 brd） | §1.4 涉及角色 + §5 权限要求 | PERM |
| 待确认清单（architecture.md ③） | §6.3 已知问题或限制 / §7.4 备注 | — |

> **第②步相对第①步的增量**：第①步只给「边界不变量」（解释为何这些实体同聚合 / 同事务）；第②步须在 §3.2 **补全逐字段校验规则**（唯一性 / 必填 / 取值范围 / 金额>0 等），形成完整 BR 集合。

### 命名与边界铁律
- 应用文件夹与产出路径中的 `<应用名>` **逐字取自** architecture.md 总表第3列（snake_case），不改写、不起别名。
- 一份 `应用详设.md` 只覆盖**一个**聚合根；跨聚合协作（`self.fde.call`）写进「特殊处理 / 外部依赖」，不在本文档替别的聚合做设计。
- **不臆造**：architecture.md 与 brd 都未说清的字段 / 规则 / 流程，标注「待确认」，不编造取值或步骤。

| 模板章节 | 章节编号 | 对应需求 ID 前缀 | ID 示例 | 赋予阶段 |
|---------|---------|-----------------|---------|---------|
| §2.1 用户故事 | 2.1.x | `US-{n}`（写在PRD章节号后） | `US-01` | PRD 编写阶段由AI自动赋予 |
| §2.1 验收场景 | 每个故事下编号条目 `US-{n}-AC{n}` | `US-{n}-AC{n}` | `US-01-AC1` | PRD 编写阶段由AI自动赋予 |
| §3.2 业务规则 | 3.2.x | `BR-{n}`（写在PRD标题前） | `BR-01` | PRD 编写阶段由AI自动赋予 |
| §4.1 功能清单 | Fxx-xx-xx（三级编号深度优先递增） | `FUNC-{n}` | `FUNC-01` | 需求分析阶段 AI 自动映射 |
| §5.1 权限矩阵 | 每行一个权限项 | `PERM-{n}` | `PERM-01` | 需求分析阶段 AI 自动赋予 |

> **重要**：`US-{n}` 、 `BR-{n}` 、`FUNC-{n}` 和 `PERM-{n}` 由 AI 在需求分析阶段自动赋予。

## 📝 使用说明

本模板旨在帮助需求分析师或产品经理**快速、准确地表达用户需求**。填写本模板后，AI将自动完成以下工作：

1. **需求分析** - 提取业务实体、实体关系、核心业务规则（OOA），根据已有的 US/BR 编号记录 ID 映射表
2. **系统设计** - 设计类结构、数据模型、接口设计（OOD）
3. **编码实现** - 生成符合规范的代码（OOP）

#### 3.2.3 规则3: 审批规则

- **适用场景**: 结算审批时
- **计算方式**: 系统根据审批流程配置，自动将结算申请路由到对应的审批人
