## B-01 双源合成静默退化成单源：客户没报数时，算好的统计基线被丢弃、最终预测归零

> **状态：已修（2026-09-15）** —— 代码按 BR-15 补齐四分支，并同步补写了《应用详设》BR-15
> 与 BR-15 的「客户侧不可用」一档。修复验证见文末「B-01 修复验证」。
> 遗留：无 —— 真库（202610）已按修复后的口径整链重算，见下文「演示环境重算」。

**严重度**：高（量级大、无任何提示、界面看不出异常）

**现象**（实测数据，版本 202610）：

| 物料 | 滚动月 | 统计基线 `base_event_qty` | 最终预测 `final_qty` | 异常标记 | 实际毛需求 | 应有毛需求 |
|---|---|---|---|---|---|---|
| `M9-BEAM` | N+1/N+2/N+3 | 1967.71 / 1962.94 / 1959.32 | 空 | 0（非异常） | 2040.14（**只剩水位层**） | 4007.85 |
| `BYD-HAN-SPARM` | N+1/N+2/N+3 | 45.30 ×3 | 空 | 0（非异常） | 84.55（只剩水位层） | 129.85 |

三个月合计 **6025.88 件的基线需求没有进入毛需求**。

**根因**（`app/psc/sales_forecast/sales_forecast.py`）：

```
377:        if base_qty is None or adj_sum is None:
379:            final_qty = adj_qty          # ← adj_qty 为空时，final 直接为空
...
388:                final_qty = adj_qty      # ← 非异常分支同样只取 adj_qty
```

`decide` 的三个分支都只取 `adj_qty`（= `orig_qty × (1 − bias)`），**从不回退到 `base_qty` /
`base_event_qty`**。客户未报数时 `orig_qty` 为空（BR-09 明确允许可空）⇒ `adj_qty` 为空
⇒ `final_qty` 为空，而 `abnormal_flag` 仍为 0 —— 系统认为这一行没有问题。

`base_event_qty`（BR-23「基线和事件合计量」）**已经算好并落在同一行上**，只是没被使用。
"双源合成"（《销售预测与库存策略说明.md》§1.1）实际退化为"单源"，且退化方式是**静默归零**。

**为什么现有测试抓不到**：演示环境的客户原始预测只覆盖 BRK/FB26/RB26/WIR 四个物料
（`宣传/导入素材/比亚迪汉_客户原始预测_202610.csv`），其余物料的 `orig_qty` 全为空。
`verify_chain_psc.py` 的用例全部围绕"有原始预测"的主链，从未覆盖"客户没报数"这一支。

**待定口径**（属于业务决策，需人工确认后再改）：

- **A（推荐）**：客户未报数时回退到基线 → `final_qty = base_event_qty`。
  符合文档 §1.1「双源合成」语义，也符合 `base_event_qty` 被专门计算并落库的用意。
- **B**：保持留空转人工，但**必须显式标记**（异常标记或告警），不得静默按 0 计入汇总。
- **C**：维持现状且不标记（等于把 0 当作正确答案）—— 应排除。

**附带的第二个口径问题**：`BYD-HAN-FB25` 的基线是**负数**（−26.60 / −56.81 / −78.42，
退坡外推所致）。若采纳 A，负基线会经「断点切换全额转移」流到 `BYD-HAN-FB26` 并**冲减**其需求。
故需同时定：**负基线钳到 0，还是视为无需求跳过**。

**旁证（非缺陷）**：`BYD-HAN-FB25` 整条不出现在 `demand` 表中，属**设计如此** ——
`demand.build_gross` 按 `md_breakpoint`（`FB25 → FB26`，`switch_time=2026-07-01`）把切换后
的需求全额转移给新件，然后 `forecast.pop(old)`。三个滚动月均晚于切换时间，故全部归属 FB26。

## B-02 两个「死适配器」：声明了外部数据来源，却从无调用点

`inventory_projection._load_in_transit` 与 `attainment._load_attainment` 均带 docstring
声明语义（"取已下工单（在途）"、"从 ERP 拉取 MAPE/bias 后逐条 upsert"），但**全仓没有任何
`self.<name>(` 调用点**。后果是该外部数据永远不参与计算，且在 stub 环境下完全隐形。

**注意 `_load_in_transit` 暴露的术语冲突**：`demand._load_in_transit`（BR-07「在途工单扣减」）
指的是 **ERP 在途工单**，而 `inventory_projection` 的「在途」（BR-04）指的是**需求池未完成补库单**

死适配器正是旧口径的化石。属 `宣传/待办.md` 第 5 项「本体 a) 同名不同义校验」要抓的问题类型，
这是第二个活体实例（第一个是 `safety_level`）。

**待定**：删除死适配器，还是补上调用点？需确认 BR-04 是否本来就**不**含 ERP 在途工单
（现文档措辞支持"不含"）。

## B-03 测试穿透力缺口：净需求的扣减公式从未在非零输入下执行过

`demand._load_open_order / _load_inventory / _load_in_transit` 是**代码写死的 stub**，
恒返回 `{}`（`app/psc/demand/demand.py:405-415`，与 `/integration` 配置无关）。
因此 `net = gross + 未发 − 库存 − 在途`（BR-04）在演示环境里恒等价于 `net = gross`——
**符号写反、单位错、取错来源，全都不可能被测出来**。实测：6 行 N+1 的扣减三层全为 0。

同类：`inventory_projection._load_inventory`（起始库存锚点，恒返回 0）与
`_load_in_work_orders`（恒返回空列表）。演示环境推移表之所以到处「击穿」，
正是因为起始库存恒为 0。

**解法（已完成，2026-09-15）**：在影子库内 monkeypatch 这几个适配器喂**非零受控值**，
再跑净需求运算 —— 见下文「已完成的检查组」中的 X-H。结论：**符号、单位、钳零、远期不扣减全部正确，
此处无 BUG**。（原 A9「扣减层非零覆盖」在真库上永远是 0 属环境使然，已从 FAIL 降为参考项，
避免留下一条常红的检查。）

| 靶点 | 结果 |

**一条口径观察（设计行为，非缺陷，但值得确认）**：
补库量是**分级补齐**的（`_replenish_qty`：击穿最低 → 补到 A；击穿安全 → 补到 A+C），

按 BR-06「产能松紧分档由 demand_pool 处理」的设计这是预期结果；
但从计划员的视角看，同一天同一个物料要下两张单，是否应合并为一张，**需业务确认**。

> 于是把上面这个设计行为报成了「重复建单」；改用「物料+**补库类型**+入库日」后消除。
> 教训与 A1/A2 同类：**判据的粒度必须与业务的真实身份对齐**，过粗的键会把设计行为当缺陷。

## B-04 `build_gross` 在无预测可合成时**声称成功**（静默降级）

## B-05 同一物料两条计算路径**结论相反**：单行 `calc` 与 `calc_batch` 对冲选型不一致

> **状态：已修（2026-09-15）** —— `calc` 不传 `customer_no` 时自动取主客户（同 `calc_batch`）。
> **无需改 spec**：BR-11 本来就写对了规则，是单行路径没实现（与 B-01 不同，那是 spec 有缺口）。

**现象**（G3 实测，影子库）：

| 路径 | `BYD-HAN-BRK` 的对冲工具与三层水位 |
|---|---|
| `inventory_strategy.calc_batch(V)` | **(速度, A=0, C=0, B=0)** |
| `inventory_strategy.calc(V, material_no)` | **(库存, A=151.64, C=9.88, B=1415.32)** |

同一物料、同一版本、同一份输入，**两个服务给出相反结论**。

## B-07 `list` 服务漏取字段 → **「键在、值恒为 None」**陷阱（两处，已修）

> **状态：已修（2026-09-15）** —— 两处 SELECT 补齐 + 检查面扩到全部应用。

**机制**：本项目的 `_to_dict` 普遍写成「固定键列表 + `row["x"] if "x" in keys else None`」。
只要某个 `list` 的 SELECT 少取了几列，那些键**照样出现在返回里、但恒为 `None`**，
而库里其实有值 —— 消费方（前端列表、智能体）会把 `None` 理解成「没有」，
与「静默降级」是同一类：**不报错、不崩溃、只是答案错**。

**实测抓到的两处**：

| 应用 | list 漏取的字段 | 后果 |
|---|---|---|
| `strategy_fitting` | `mase`、`pred_qty`、`pred_lo`、`pred_hi`、`sigma_l`、`detail_json`（**6 个**） | 库里 `pred_qty=1623.64`，经 list 变 None ⇒ 问智能体「预测量是多少」会得到「没有预测量」；`detail_json` 拿不到候选模型明细 |
| `md_material` | `sigma_l` | 安全库存 `C = z × σ_L` 正要用它；BRK 库里 `sigma_l=5.99`，经 list 变 None |

**发现方式**：G 组「list 与 get 必须同值」的判据。**关键在于把检查面从 6 个应用扩到全部
15 个有 `get` 的应用** —— 第一轮只覆盖 6 个，`strategy_fitting` 是扩面后才暴露的；
扩面后又立刻抓到 `md_material`。

**修的取舍**：`model_blob`（整个 pickle 序列化的 statsforecast 模型，单行数十 KB）
在 `md_material.list` 中**刻意省略是合理的** —— 带上它会把列表响应撑爆。
所以检查按**字段体量**自动分类：>200 字符的省略记为参考项（WARN），小字段的省略判 FAIL。
不写死字段名。

**这条与 `宣传/待办.md` 第 5 项的关系**：`_to_dict` 这种「固定键列表 + 缺键补 None」
是一种**隐式契约**（字段集靠人抄）。第 5 项的本体 a) 层（从 `schema.sql` 派生机器可读元数据）

## 分页形参名漂移：声明的 `page_size` 从未生效（2026-09-17 已修）

> 代理在补 e2e 前端用例时顺手发现的。**属"声明了但收不到"** —— 与 `_coerce` 静默忽略未知键同源，
> 也是台账主题「同名不同义/多处表达必漂」的又一实例。

**现象**：平台基座 `view/lib/shell.js::pageable()` 的 `load()` 传的是 **`{page, size}`**，
而 `app/e2e/member|task` 的 `list` 声明的是 **`page_size`** ⇒ `fde_platform/web.py::_coerce`
对**未知键静默忽略** ⇒ 形参**收不到值、也没有任何报错**，分页一直走服务默认（50/100），
而前端又按自己的 `size`（20）算页数 ⇒ **分页条与真实返回不一致**。

**范围核实（不凭代理的转述）**：扫了全仓 19 个应用的 `list` 签名 ——

| 组 | 结论 |
|---|---|
| `app/psc`（17 个应用） | **全部叫 `size`** ✓ 与基座一致，无此问题 |
| `app/e2e`（member / task） | 叫 `page_size` ✗ **只有这两个是例外** |

⇒ 代理报的"平台级口径差、PSC 同形"**不成立**（PSC 没问题）。这是**应用签名与平台基座不一致**。

**修法（选应用侧改名，不在平台加别名）**：

- `member.list` / `task.list` 的 `page_size` → **`size`**（与基座 + PSC 全组一致）；
- **`task/view.js` 里显式传的 `page_size: 200`（负责人下拉）也一并改掉** —— 它是实参，不改就又被静默忽略；
- 详设 / 前端详设 / 用例文档 / `dashboard.js` 注释同步；**契约重冻**（`_contracts.md` 已按新签名生成）。

> **为什么不选「`_coerce` 加别名容错」**：那会把命名不一致**藏起来** ——
> 本仓 `宣传/待办.md` 第 5 项要的是**消同名不同义**，不是容忍它。选应用侧改名，
> 漂移点就只剩一处（基座一个名字），谁再写错当场就是把 `size` 写成别的，一样会被下游断言抓住。

**新守卫**：e2e 链测试补 **`TC-DM-17`** —— `member.list(page=1, size=1)` 断言
`len(items) == 1` 且 `total == 2`（**分页只影响本页条数、不影响总数**，纯关系式）。
**它真能红**：把形参名改回 `page_size` 再跑 → **失败 1**（本页退回全量 2 条）；还原 → **36/36 PASS** ✓。

**顺带把 `pitfalls #41` 订正**：原写「PSC 与 e2e 同形、属平台基座口径差」——
实测 PSC 全组用的是 `size`，**只有 e2e 例外**；pitfall 已按事实改写（含"选应用侧改名"的理由）。

### 后续（2026-09-18）：改名只改了代码，**文档还写着 `page_size`**

**现象**：`app/psc/*/前端详设.md` 里 **27 处** svc 调用仍写 `{page:1, page_size:200}`，
而对应 `view.js` 里早已是 `{page:1, size:200}`（`attainment / demand_pool / inventory_strategy /
master_plan / md_project_part / sales_forecast / strategy_fitting` 7 个应用）。
**为什么一直没被发现**：`view_coverage.py` 的 V1–V7 对账的是 **VT 编号**，不看 svc 实参的**参数名**；
`_coerce` 又对未知键静默忽略 ⇒ 文档与代码各说各话，谁都不断言。

**处置**：27 处按代码改成 `size`；另外发现 `md_project_part/前端详设.md` 更离谱 ——
它写项目/物料下拉传 `{page:1, size:200/500}`，而 `view.js` 里**根本不带参数**（`{}`，取全量），
已一并按代码订正（并写明"不带分页 ⇒ 服务端返回全量 `{items,total}`"）。
`md_customer/README.md` / `HOWTOUSE.md` 里那句「分页参数名是 `size`，**不是** `page_size`」是对的，保留。

> **教训**：**"改代码"这个动作结束在文档改完、契约重冻之后**。只改代码的那一半，
> 下一个人会照文档写出错的调用 —— 而这次错的是参数名，恰好是**没有任何报错提示**的那一类错。

### 同批查出：平台把 `Optional[int]` 的类型标成了 `string`（已修）

**现象**：重冻契约时发现 `page=None:integer`（写成 `page: int = None`）与 `page=None:string`
（写成 `page: Optional[int] = None`）**并存于同一份 `_contracts.md`** —— 同名参数两种类型。

**根因**（平台层，`fde_platform/introspect.py::_json_type`）：`py_type.split("[")[0]` 对
`typing.Optional[int]` 切出 `typing.Optional`，不在 `_TYPE_MAP` 里 ⇒ **静默 fallback 成 `string`**。
这份类型不只喂契约文档，还喂 **MCP tool 定义 / Agent function-calling / Web 调用表单的 `_coerce` 强转** ——
即 `Optional[float]` 的数值参数（如 `sales_forecast.adjust(orig_qty)`、`inventory_projection.refresh(opening_stock)`）
会**一路以字符串形态**送达服务。

**当前没炸**：各应用普遍有 `_to_number` / `_to_bool` 兜底（`sales_forecast._to_bool` 连 `"False"` 也认）。
但**声明的类型是错的**本身就该修 —— 消费方无从判断该传 `true` 还是 `"true"`。

**修法**：剥 `Optional[...]` / `Union[..., None]` 取非 None 分支（真 Union 各分支基底不一致则如实回退
`string`），并顺手剥 `typing.` 前缀（`typing.Dict[...]` → `object`、`typing.List[...]` → `array`）。
两组契约一并重冻：**7 处 `page`/`size` 由 `string` → `integer`、2 处 `abnormal_flag` → `boolean`**。

## 前端「断言偏软」收敛 + 新增判据 V7「无断言步」（2026-09-17 晚）

### 量出来的：214 步里 6 步**一条断言都没有**

按 `step("…")` 切块统计 19 个脚本（214 步），发现：

| 类 | 数量 | 性质 |
|---|---|---|
| **无断言步**（整步一条 `assert` 都没有） | **6** | **无歧义缺陷**：只证明「没抛异常」 |
| **仅软断言步**（整步只有 `count() > 0` / `is not None` 这类） | **14**（按**更宽**的口径量） | ⚠ **多数是正当的**，见下 |

6 处无断言步：`demand_pool §2 物料过滤`、`md_monthly_version §4.1 回退后重新冻结` / `§4.2 重复版本号被拒`、

### 口径之争：「仅软断言」到底算不算缺陷 —— **不算，故不入闸**

先后用了两个口径量，结果差很多（14 vs 0），**差别本身就是结论**：

- **宽口径**把「断言某元素**不存在**」（`.count() == 0`）也算成软断言 ⇒ 报 14 步；
- **工具口径**（`view_coverage.py` 的 `_SOFT`）只认 `count() > 0` / `is not None` / `len() >= 1` ⇒ 报 0 步。

**工具口径是对的**：前端有一类用例的**规格本身就是计数/存在断言** ——
渲染步（`main .card > 0` 且 `.kpi == 0`）、豁免步（「按钮集合恰为 …」）、终态步（「无可见操作按钮」），

拿这个当闸会**误红**，而常红的闸会训练人绕过它 —— 与 `验证门禁.md`「闸只卡不变量、不卡答得好不好」同一口径。

| **V7 无断言步** | **入闸**（`view_coverage.py` 的 `step_assert_facts()` → `scan_structure.py`）—— 无歧义 |
| 软断言计数 | **只作报告项**（`view_coverage.py` 每次打印"断言密度"一行），供人复查，不判红 |

> **这轮自己给自己上了一课**：我先用一个更宽的私有口径量出"14 步软弱"，差点把它写进闸；
> 换工具的窄口径一量是 0。**同一件事两套口径 = 两个结论** —— 与「同一套词汇在两个工具里各认一半」

### 顺带抓到一个 **flaky 断言**（全量跑批才露头）

全量跑批 `--tier view` 里 `demand` 报 `§4 发布: 发布后缺运算净需求`，而**单跑两次都过** —— 典型 flaky。

**根因**：该步点「发布」后等的是「版本下拉选项文本变成『发布（锁定）』」，然后就去断**工具栏按钮集**；
而工具栏是**另一次渲染**才更新的 —— 全量跑批时机器更忙，按钮集还没换过来，断言当场红。

**修法**：**等你要断的那个东西** —— 补 `wait_for_selector('button:visible:has-text("运算净需求")')`
（下拉那条保留，它断的是另一件事：版本状态联动）。
> **教训归一条**：等待条件必须与断言对象**同一个**。等 A 断 B，平时侥幸过、忙时就红 ——

### 顺带记一条**未处理**的观察：影子库两种路径布局对不上

`fde_platform/shadowdb.py` 把副本按**树形**放（`<shadow>/app/<组>/<应用>/<应用>.db`），
而 `runtime.py` 在 `FDE_DB_ROOT` 下解析的是**扁平**路径（`<shadow>/<应用名>.db`）——
两者对不上。组合 `shadow_dbs(env=True, inprocess=True)`（`verify_chain_*` 用的就是默认值）时，
**平台读的是那个不存在的扁平路径，于是拿到一个空库**（"副本"其实没被读到；好在链测试本来就要空库，所以一直没坏）。
`env=True, inprocess=False`（view e2e 用）同理 —— 子进程也读扁平路径。

**影响面**：今天**没有**测试因此变红（要空库的拿到了空库、自造数的照旧自造）。但它意味着
**"在副本上跑真实数据"这个说法在 env 组合下不成立** —— 哪天有人写一个"想读演示数据、又想零风险"的检查，
会**静默拿到空库**（正是我们一路在清的那类静默）。**修法未定**（对齐两种布局 or 统一用扁平），
先记账；`verify_psc_oracles.py` 的 `shadow_sandbox()` 自己走的是**扁平**布局，**不受影响** ✓。

## 口径变更：`strategy_fitting` 库存拟合段 → 改「主数据人工维护」（2026-09-17，业务确认）

> 三要素那一层早就把它标成了**全组唯一「整段声明 > 实现」**的地方（`_inventory_fit` 的
> docstring 自己写着"简化：取默认组合"，而 BR-08~12 描述的是一整套**网格遍历 + 回放 + 成本寻优**）。
> 业务方给的口径是：**组批窗口是计划员判断"该不该组批"的结果，人工维护在主数据上，不需要系统自动运算**
> —— BRD §4.8.1 的字段表本身就写着「组批窗口：**物料主数据（经验值）**或经济批量模型计算」，取前者。

### ① 停掉"编造常量"

`_inventory_fit`（恒返回 1.65 / 28.0 / 0.95 / `len//4`）→ **`_inventory_params`**：只**回读主数据**
里人工维护的 `batch_window` / `service_level` 作镜像；**服务系数 / 安全水位 / 库存天数 / 切线次数
不再产出**（留空）——不是"没做"，是"不做"，四列留空的语义比填编造的常量诚实。

### ② 停掉"静默覆盖人工值"（**这条才是真缺陷**）

`approve` 每次复核通过都会 `set_fit_params(batch_window=拟合值, service_level=拟合值)` ——
**计划员手工维护的组批窗口与满足率目标，跑一次拟合就被静默冲掉**，而且因为"拟合值恰好是默认的
28 / 0.95"而完全看不出来。已改：

- `approve` / `rollback` **只回填预测侧**（base_method / base_params / model_blob / σ_L）；
- `md_material.set_fit_params` 的 `batch_window` / `service_level` 改为**「给了才更新」**
  （与 `import_batch` 的部分更新同一语义），快照仍记当时生效值，回滚才能原样还原。

## B-10 速度对冲件「余额 > 0 就判超储」（**已修** 2026-09-17）

> 与 B-08 同家族（`B=0` 的语义），是修 B-08 时顺带照出来的。**结论：这不是口径取舍，而是两处文档互相矛盾。**

**矛盾**：`inventory_strategy` 的 **BR-10** 说「上限（组批封顶线）= **A + C + B**；高于上限即超储」，
而 `inventory_projection` 的 **BR-08** 写的是 `balance > B → 超储`，**实现照后者写的**
（`_classify_alert` 里就是 `if balance > b`）—— 而**前端画的水位带用的正是 A+C+B**
（`get_water_level` 的 `upper`）⇒ **预警与同一屏上的带子说的不是一回事**。

对库存对冲件差别很小（RB26：`>898.26` vs `>968.21`），所以一直没暴露；对**速度对冲件**
（BR-12 规定 `C=B=0`）则退化成 `>0` ⇒ **手上有货就报超储**。

**修法**：阈值改用「水位带上限」`A + C + B`（BR-10 的正本定义，也是前端画带子用的那个值）。
不选"速度对冲件不判超储"那条路 —— 那等于对**高价值件**（最该有超储预警的品种）放弃这条预警。

## B-09 `inventory_strategy` 的版本有效性校验**只查格式、不查存在**（已修）

> **状态：已修（2026-09-17）** —— `_validate_version` 补存在性校验；同时补了**通用不变式 C11**。

**现象**（E8 实测）：

```
inventory_strategy.calc(version_no="209901", material_no="BYD-HAN-BRK")
→ 未拒绝，返回 {'version_no': '209901', 'hedge_tool': '速度', 'min_level': 0, …, }
```

`209901` 在 `md_monthly_version` 里**不存在**，但 `calc` 照样为它**写入了水位策略行**。
BR-16「版本有效性校验」声明了这道校验，而 `_validate_version` 只做了两件事：
非空 + `\d{6}` 格式与月份范围。**格式对就放行。**

**后果**：那一行成了孤儿（无版本可依），而任何"按版本查水位"的下游都会读到它；
若把版本号写错一位，系统不会报错，只会静默按一个不存在的版本算出一套水位。

**这与本项目反复出现的那一类同源**：**静默接受一个不存在的标识，比报错危险得多。**

**修法**：`_validate_version` 补 `md_monthly_version.get` 存在性校验，报错话术指明"请先创建版本"。

### 顺带补的通用不变式：C11 `version_no` 引用完整性

## 影子库隔离机制：一个「谁都不报错」的偏差 + 三处被它掩盖的旧假设（2026-09-18 已修）

> 起因：复核 e2e 组产物时发现 `shadowdb` 的**副本落盘布局**与运行期解析规则不一致。
> 修掉之后，**四处旧假设当场暴露**（其中三处是测试自身的缺陷）—— 这一整段值得留档，
> 因为它们的共同形态是「不报错、不变红，只是答案错」。

### 1. 布局不一致：复制到 A、运行期找 B ⇒ 静默跑空库

| | 位置 | 规则 |
|---|---|---|
| 复制方（旧） | `shadowdb._copy_all` | **树形**：`<影子>/app/<组>/<应用>/<应用>.db` |
| 运行期 | `runtime.py` | **扁平**：`Path(FDE_DB_ROOT) / f"{name}.db"` |
| 运行期 | `users.py` | **扁平**：`Path(FDE_CONFIG_ROOT) / "auth.db"` |
| 运行期 | `verify_psc_oracles.py` 自带 sandbox | **扁平**：`shutil.copy2(src, shadow / src.name)` |

⇒ 找不到副本，SQLite 就在扁平位置**新建空库**顶上。

**为什么长期没被发现**：① 真库确实零字节接触（安全承诺成立，"真库没变"这条证据**证明不了**"跑在副本上"）；
② 链测试 / view e2e 本来就要空表起步，**结果一样是空库**；③ 想要"读真数据零风险"的用法才会中招，
而当时那类用法（对账体检）**自带了一份扁平 sandbox**、根本没走这条路径。

**修法**：**复制方去适配运行期**（扁平落盘），不给解析器加"猜两种布局"的兼容 ——
运行期的解析规则是唯一真相，把不一致留在系统里就又是一个"同名不同义"。

**固化成三层**：① `shadow_dbs()` 入口自检（`missing_shadows`，不一致当场抛错）；
② `shadow_clear()` 找不到库时**不许静默返回 0**；③ 新增 `scripts/verify_shadow_isolation.py`
（四条判据：副本可解析 / 副本内容 == 真库 / `env` 路径下 `db_path` 全在影子目录内 / 真库 `size+mtime` 不变），
已接进 `run_gates.py` 的 **static** 层。

**判据能失败吗（变异取证）**：把 `_copy_all` 改回树形重跑 ⇒
`RuntimeError: 影子库自检失败：复制了 67 个库，但按运行期解析规则找不到 [...]（共缺 67 个）`；还原 ⇒ PASS。

### 2. 副本是「真库的拷贝」⇒ 测试必须**显式清表**（22 个 view 脚本补 `shadow_clear`）

### 6. `strategy_fitting` view 脚本偶发失败的排查结论（2026-09-18，**未定案，待决策**）

**现象**：`verify_view_psc_strategy_fitting.py` 在 `§4 VT-FORM-03 批量拟合` 那一步失败，
约 **1/2 ~ 1/3** 的跑次触发；失败后脚本**卡住**（该步之后的所有 playwright 调用都不返回），
跑手按 300s 超时判 FAIL。单跑、并在跑手 suite 里跑，概率相近。

**两种表现**（同一处、随机出现其一）：
1. `ERROR @ §4 VT-FORM-03 …: Error: Page.wait_for_timeout: Page crashed`（或 `Locator.count: Target crashed`）
   —— chromium **渲染进程死亡**，随后卡在崩溃页上；
2. **静默卡住**：连报错都没有（脚本里所有等待都有 5~15s 上限，所以只能是 C 层调用不返回）。

**已排除的原因**（都有实测证据，不是推测）：

| 怀疑 | 证据 | 结论 |
|---|---|---|
| 服务端把 `run_batch` 跑挂了 | 进程内直调同一步：**首次 1.8s、其后 0.1s**，`{total:2, success:2, failed:0}` | ❌ 不是服务端 |
| 内存压力 | 跑该脚本期间每 6s 采样 python+chrome 工作集：**全程 ~750MB 平稳** | ❌ 不是内存 |
| GPU / swiftshader | 给该脚本单独加 `--disable-gpu` 连跑 3 次：**2 次仍崩** | ❌ 不是 GPU（已回退该实验改动） |
| 我本轮改的影子库 | ① 同一现象在**上一轮会话**就有（记为「12 分钟挂住」，当时影子库还没动）；② 业务动作已完成（toast 已出、落表在崩溃点之前）；③ 同一步在**其他 18 个 view 脚本**里没有 | ❌ 不是影子库引入 |
| 断言失败被当成崩溃 | 崩溃点之前/之后的断言都正常 | ❌ 不是断言 |

**当前处置（都已落地）**：
- `run_gates` 超时**按层给**（view 300s）⇒ 从「半小时无输出」变成「5 分钟一条 FAIL」；
- 对 `Page crashed` / `Target crashed`（**两种拼写**）**重试一次**，且全程响亮打点
  （策略与边界见《验证门禁.md》§五之二：**只认这一种特征**，断言失败/超时一律不重试）；
- 跑手给 chain/view 加 `-u`（无缓冲）—— 此前脚本挂住被强杀时，**缓冲区里最后一屏（往往正是死因）会一起丢掉**，
  这也是"第一次失败没触发重试"的真实原因；
- 断言报错信息带上看到的内容（`sales_forecast` 那处）。

**判定实验结果（2026-09-18，用户批准的方案 A）**：**不成立，不能指控 ECharts**。

| 组 | 条件 | 结果 |
|---|---|---|
| 实验组 | 临时跳过 §3 VT-MODAL-03（唯一会 `echarts.init(#fitChart)` 的步骤） | **3/3 PASS** |
| 对照组 | 恢复该步（原样） | **3/3 PASS** |

连续 6 次全过 ⇒ 曲线渲染**未被证明**是根因。顺着这条线继续查，找到**三个真问题**（比原猜测更能解释"时好时坏"）：

1. **`config=True` 每次白复制 102.6 MB**：`config/` 合计 103.2 MB，其中 `agent_service.db`（Agent 会话库，
   view e2e 完全不碰）就占 **102.6 MB**，而业务库总共才 **1.4 MB** ⇒ 每个 view 脚本白拷 ~103 MB，
   22 个脚本一轮 ≈ **2.3 GB** 无效 I/O。而且——**只有 `users.py` 认 `FDE_CONFIG_ROOT`**，
   复制其余 config 库**没有任何隔离收益**（它们压根不看那个变量）。
2. **被强杀时影子目录不清理** ⇒ temp 里实测堆了 **16 个目录 / 1.3 GB**（`fde_shadow_*`）。
3. **孤儿进程累积**：脚本自己 `Popen` 起平台、playwright 再起 chromium；跑手强杀时**只杀直接子进程**，
   孙子全留下 —— 实测一轮下来攒了 **5 个孤儿 python**（占内存/句柄/端口）。
   而"间歇失败"的几次**恰好都扎堆出现在残留累积之后**，单跑（机器干净时）几乎都过。

**处置（已落地）**：
- `platform_dbs()` **收窄为只含 `auth.db`** ⇒ 每轮少 2.3 GB 复制，残留从 103 MB/次降到 ~2 MB/次；隔离效果不变；
- `run_gates` 超时时 **按进程树杀**（Windows `taskkill /T /F`）⇒ 孤儿不再累积；
- 清理现存残留（1.3 GB 影子目录 + 830 KB chromium profile）与 5 个孤儿进程；
- 保留按层超时（300s）、只认 `Page crashed`/`Target crashed` 的响亮重试、跑手 `-u`。

**验收**：修完 PSC 全套**连跑 2 轮** + 该脚本**单跑 5 次**（结果见下）。

> **留下的教训**：这次的"间歇失败"第一反应是怀疑被测页面（ECharts），**实际是测试基础设施在攒垃圾** ——
> 三个问题都不是"哪一行写错了"，而是**"没人清理"**：临时目录、进程、以及一个每次都不必要地拷 103 MB 的复制范围。
> 所以**先做判定实验再动手**是对的：跳过曲线的对照组如果照旧崩，我就会去改一个没毛病的页面。

### 7. `FDE_CONFIG_ROOT` 只覆盖 auth.db ⇒ 测试起的平台会**真发定时任务**（2026-09-18 发现，**待决策**）

### 9. 卡住诊断落地 + 三次实测：**不是 JS 死循环**（2026-09-18）

**先落地诊断能力**（用户批准）：新增 `fde_platform/view_watchdog.py`（与 `shadowdb.py` 同类的测试支撑模块，
平台运行时不加载），**22 个 view 脚本全部接入**（`install_watchdog(errors, step_getter=lambda: STEP)`）：

- 守护线程每 5s 看一次"脚本走到哪一步"（步骤变化 = 有进展）；
- 连续 `stall_s`（默认 120s，可用 `VIEW_WATCHDOG_STALL_S` 调小）没进展 ⇒ 打一段现场：
  **最后完成的步骤 + 已收集的 console/pageerror/HTTP 错误 + chromium 内存与累计 CPU 采样**；
- **只打印、不终止进程**（诊断不许改变被测脚本行为）；线程里不碰 playwright（非线程安全），
  内存/CPU 用 `tasklist` / PowerShell 从 **OS 侧**采。

**实测（抓到一次卡住，两次连过）**：

```
⚠ [watchdog] 疑似卡住：已 45s 没有进展   ← 最后完成的步骤：'§4 VT-FORM-03 批量拟合…'
  · 已收集的错误 0 条： （空 —— 没有 console/pageerror/HTTP 错误）
  · chromium 内存采样：['482MB/5进程'] → ['481MB/5进程']        ← **平稳，不涨**
  · chromium 累计 CPU 秒：['25.4'] → ['30.2']                   ← 31s 墙钟只涨 4.8s ≈ 15% 核
```

**结论（三条都有判据支撑）**：

| 观察 | 排除了什么 |
|---|---|
| console/pageerror/HTTP 错误 **0 条** | 不是 JS 抛异常（那会有报错） |
| 内存**平稳**（482→481MB） | 不是"边循环边分配" ⇒ **不是 OOM 型崩溃** |
| CPU 只涨 ~15% 核（自旋会是 ~100%） | **不是 JS 死循环**（`while(true)` 会吃满一个核） |
| 步骤停在 §4 且该步的 toast 断言已通过（`assert_toast` 在前、崩溃点在 `wait_for_timeout`） | 后端已返回；**卡住发生在页面收到响应之后** |

⇒ 形态是「**渲染/网络层面挂起**」：页面不再推进、也没报错、也没在算。环境里有同源线索：
浏览器日志多次出现 `Network service crashed or was terminated, restarting service.`
与 `WSALookupServiceBegin failed with: 10108`（本机网络位置感知/服务发现在这个环境里被挡了）。
**页面的下一次 `fetch` 若落在网络服务重启窗口里，就会永远不 settle** —— 这与
"无报错、无 CPU、无进展"完全吻合。

**这条与"前台还是后台"的关系**：进一步支持 §8 的结论 —— **后台数据正常**（这次连后端都没再被问；
卡的是浏览器侧），**不是业务缺陷**。

**留给下一步的三个选项**（都属测试基础设施，不动产品代码）：
① 换浏览器运行时（playwright 自带 headless shell → `channel="chrome"` 或 `headless="new"`），
看是否绕开这个环境的网络服务问题；② 只记账收工（现有兜底：按层超时 300s + 只认崩溃字样的响亮重试）；
③ 继续查网络服务线索（如给平台加请求侧日志、或在卡住时从 OS 侧数 TCP 连接）。

**收尾决定（2026-09-18，用户选 ②）**：**只记账，不改浏览器运行时**。理由：

- 根因已定位到**环境层**（浏览器网络服务在这台机器上不稳 ⇒ 页面的下一次 `fetch` 不 settle），
  不是我们的代码；换 `channel="chrome"` / `headless="new"` 属于"碰运气绕开"，
  为消一个环境抖动去改 22 个脚本不划算；
- **现场诊断已经落地**（`view_watchdog.py` + 22 个脚本接入）⇒ 下次再犯，输出里直接有
  「最后完成的步骤 + 错误 + 内存/CPU 采样」，不用再靠残留副本倒推；
- **兜底仍在**：按层超时（view 300s）+ 只认 `Page crashed`/`Target crashed` 的**响亮重试一次**。

**顺手补的一条防"红灯脱敏"**：`run_gates` 遇到失败时，若输出里出现过 `[watchdog]`，
会**单独打一行**提示「本次失败伴随 watchdog 卡住现场（页面冻住，非断言失败）—— 后端数据正常」。
理由是这类失败**看起来像断言红**，但性质完全不同：不标出来，人要么去修没毛病的产品代码，
要么干脆对红灯脱敏（本仓最忌的那件事）。
