# PSC 缺陷台账 · 2026-09-20

> 发现方式以「哪条判据报出来的」为准 —— 本轮两条应用缺陷都是**判据第一次拿到非空分母**时才暴露的，
> 而它们此前**一直是绿的**。这本身就是记录价值：常绿不等于对，可能只是分母为空。

---

## B-13 空客户行的行级动作全被「客户编号非空」挡住 ⇒ 兜底闸够不到它要保护的行

**现象**：`scripts/verify_psc_oracles.py` 的 **C7「非异常行必须有最终预测」** 报红：

```
实际：BYD-HAN-FB27//N+1 非异常但无最终预测 | …N+2 | …N+3
```

（客户段为空 —— 这三行是**空客户行**。）

**为什么此时才发现**：C7 此前**长期处在「分母为空」的状态**（台账 2026-09-19 已记：C7 与 C6 从没被触发过）。
本次录屏重录造出 202611 的预测数据后，C7 第一次拿到非空分母，一触发就报出这三行。

**根因**：`open_version` 对「没有任何历史采购记录」的物料**只初始化一行、客户留空**
（否则 N 个客户 × 3 个月会把表铺满）—— 这类空客户行是合法数据。但
`decide` / `set_final` / `get` / `calc_baseline` / `adjust_event` 的第一句都是

```python
customer_no = self._require(customer_no, "客户编号")     # 空串 ⇒ FdeError
```

而 `decide_batch` 对单行失败是**「跳过」**。于是这类行**瘫在表里**：算不出、标不了异常、
连详情都打不开，最终仍在 `summarize` 里按 `COALESCE(final_qty,0)` 变成 0。

**这是 B-11 的同族补刀**：B-11 补的是「两源皆空必须标异常」（兜底闸），
但兜底闸在 `decide` 里，而 `decide` 对这类行**根本进不去** —— **闸门在它上游**。

**修法**：行级动作的客户键改用 `_clean_customer_key`（**允许为空**）。
理由是行身份本就是「版本 + 物料 + 客户 + 滚动月度」四元组，客户可以为空；
真正的校验在 `_get_line`（行不存在即抛「处理表行不存在」），所以只清洗、不设非空。
`fill_customer` **仍要求非空** —— 给一个没有客户的行「填报客户预测」没有意义。

**修复前后实测**（202611，`decide_batch`）：

| | `failed` | `abnormal` | 三行 `abnormal_flag` |
|---|---|---|---|
| 修复前 | 有跳过 | — | 0 / 0 / 0 |
| 修复后 | **0** | 12 | **1 / 1 / 1** |

`final_qty` 仍为空 —— 这正是设计意图（异常行不自动填值，交人工）。

**回归**：`TC-ERR-45`（`verify_chain_psc_part2.py`）。**突变取证**：把
`_clean_customer_key` 改回 `_require` ⇒ 该用例当场红，报的正是 `客户编号不能为空`；还原 ⇒ 绿。
⚠ 与 `TC-ERR-44` 的分工：那条用的是 `C002`（**有客户**），所以它在缺陷期间**照样通过** —— 两条缺一不可。

## B-14 A15 与 C7 口径打架：判据停在兜底闸之前的语义

**现象**：修完 B-13 后 C7 转绿，**A15「BR-12 偏离率与异常标记」当场转红**，且指向同一批行：

```
BYD-HAN-FB27//N+1：重算 应正常，实际 abnormal_flag=1（客户值=None 基线=None MAPE=None）
```

**根因**：A15 里有一句

```python
if adj_sum is None or base is None:
    expect = False          # 无从算偏离率 ⇒ 按 BR-14 不标记
```

那句注释写的是**BR-14 兜底闸加入之前**的语义。A15 没跟着更新，于是它与 C7 对同一批空客户行
给出**相反期望**：C7 判它必须标异常，A15 判它必须正常 —— **两条判据谁也没错，是口径没对齐**。

**修法**：按 BR-14 现文把 A15 改成**并集**：

```
expect = (MAPE 存在 ∧ 偏离率 > 5%)        # BR-12
       ∨ (final_qty 为空)                 # BR-14 兜底闸
```

并同步更新该判据的说明文字与 docstring（含这次口径打架的来龙去脉，免得下次又只改一边）。

**教训**：**加了兜底闸，就要把所有「重算同一件事」的判据一起过一遍**。
两条判据对同一批数据给出相反期望时，红的不是数据，是判据之间的不一致 ——
而只要分母一直是空的，这种不一致可以**长期不被发现**。

## D-1 部署侧：平台代码烤进镜像，`git pull` 不重建 ⇒ schema 漂移把一整个应用打死

> 不在 PSC 应用内，记在这里是因为它是**同日同一条链上**查出来的，且后果最重。

**现象**（测试服务器 `8.130.64.94`，线上接口实测）：

```
POST /api/apps/psc/md_material/call/list
→ {"kind":"system","message":"系统错误：UndefinedColumn","status":"error"}      ← 读也坏
POST /api/apps/psc/md_material/call/create
→ 同样 UndefinedColumn                                                           ← 写也坏
```

19 个应用逐个打 `call/list`，**只有 `psc/md_material` 失败**；而 **12 个应用依赖 md_material**
（销售预测、库存策略、库存推移、主计划、需求池、出库计划、历史台账、策略拟合、项目零件映射、
替换关系、断点、以及它自己）。

**根因**：`docker-compose.yml` 只挂载 `./app` 与 `./config`，**`fde_platform/` 是烤进镜像的**。
宿主机 `git pull` 只更新 `app/`，**平台代码不 `docker-compose build` 就不会更新** ——
于是出现「应用代码是新的、平台代码是旧的」的错配：

- `app/psc/md_material/schema.sql` 已声明 `predecessor_material_no` / `model_blob` / `sigma_l` 等列；
- 容器里那份 `fde_platform/ddl.py`（60 行）**只有建表、没有「对账补列」**；
- ⇒ 新声明的列永远补不上，任何读写它的语句全炸。

**完整漂移**（拿本地新 `ddl.py` 逐表比对声明与现状）：

```
psc_md_material.md_material              -> 缺 ['model_blob', 'sigma_l']     （另 predecessor_material_no 先前已补）
psc_md_material.md_material_param_version -> 缺 ['model_blob']
psc_strategy_fitting.strategy_fitting     -> 缺 ['mase','pred_qty','pred_lo','pred_hi','sigma_l','detail_json']
```

**修复**：把本地那份带 `reconcile_columns` 的 `ddl.py` 送进容器，对全部应用跑一遍
`execute_schema(..., reconcile=True)` ⇒ **3 张表 9 列一次补齐**，19/19 应用恢复，
**无需重启、无需重建、无需推送**。这同时证明「部署新代码就能自动修好」这条路是通的。

**清理**：验证期间造的临时物料已删，物料表回到原有 1 条、断点表仍 0 行、临时文件已删。

**要记住的两件事**：
1. **部署这套平台时，`git pull` 不等于更新** —— `fde_platform/` 必须重建镜像才生效。
   `scripts/deploy.sh` 是齐全的（pull + `build --no-cache` + up），手工 `git pull` 不是。
2. **核实这类问题的取法**：`docker exec … python -c "from fde_platform import db; print(db.db_mode())"`
   会报「连接失败→回退 SQLite」—— 那是**新进程里连接池懒加载**，不代表线上在跑 SQLite。
   要看正在跑的进程，用**容器启动横幅**或查 PG 里有没有那些 schema；
   验证线上行为最硬的方式是**直接打 HTTP 接口**，那测的才是真正在跑的那个进程。
