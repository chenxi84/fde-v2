## B-11 两个来源都没有的行：既不标异常、也不给最终值 ⇒ 汇总时静默按 0

**判据**：`C7 预测 · 非异常行必须有最终预测`
**实际**：3 行 —— `202611 / BYD-HAN-FB27 / N+1、N+2、N+3`，`abnormal_flag=0` 而 `final_qty IS NULL`

### 为什么会这样

`BYD-HAN-FB27` 是从 ERP 同步进来的**改款新料**，两个来源**都空**：

| 来源 | 为什么空 |
|---|---|
| 统计基线 | 物料**没有历史**（既无前序物料链，也无断点链）⇒ `calc_baseline` 给不出 `base_qty` |
| 客户预测 | 客户本期**没有报数** ⇒ `orig_qty` / `adj_qty` 均为空 |

再看 `decide` 的分支：

```python
if adj_sum is None:  final_qty = base_pick or adj_qty   # base_pick 也空 ⇒ 结果仍是空
elif base_qty is None:  final_qty = adj_qty             # 走这一档，不标异常
elif mape 存在 and deviation > 0.05:  abnormal_flag = 1  # ← 标异常的闸门
```

**标异常的条件是「有 MAPE 且两源偏离超阈值」**；这里连基线都没有，算不出偏离，
于是这一档**只把 final_qty 留空，且不设任何标记**。

### 后果

`summarize` 用 `SUM(COALESCE(final_qty, 0))` 做合计 ⇒ 这条物料的预测**静默变成 0**，
毛需求那一层拿不到任何量，而**页面上没有任何提示**：既不是异常行，也没有「数据不足」标记。

### 与 B-01 的关系（同族，不同路径）

| | B-01（2026-09-15 已修） | B-11（本条） |
|---|---|---|
| 路径 | **基线算好了**，客户没报数 ⇒ 基线被丢弃 | **两个源都没有** ⇒ 系统无话可说 |
| 表现 | `final_qty` 空、`abnormal_flag=0` | 同样 |
| 合计后果 | 6025.88 件静默归零 | 该物料整条静默归零 |

一句共同的话：**系统在不能替人决定的时候，没有说自己不能决定。**

### 与设计意图的出入

`宣传/演示业务方案.md` §2.5 把 FB27 设计成**反例**，写明期望行为是：

> 历史为 0，无前序无断点 → **如实标记「数据不足」，预测留空待人工**

**「预测留空」做到了，「标记数据不足」没做。**

### 处置：**已修（2026-09-19，业务确认后）**

**改法**：没有逐条去补分支（每条分支都可能落到空值），而是在**出口加一道兜底闸** ——
决策走完后若 `final_qty is None and not abnormal_flag`，一律置 `abnormal_flag = True`：

```python
if final_qty is None and not abnormal_flag:
    abnormal_flag = True
```

一道闸盖住全部路径，且语义单一：**系统不能替人决定的时候，必须说出来。**

## B-12 已下达的补库单可以没有承诺入库日 —— 判据要求有，界面上是选填

**判据**：`C6 状态机 · 已完成补库单须有承诺入库日`
**实际**：`RP202609170002`（BYD-HAN-FB25）状态=已下达，`promised_inbound` 为空

### 矛盾点

判据的 SQL 查的是：

```sql
WHERE status IN ('已下达','生产中','已完成') AND (promised_inbound IS NULL OR promised_inbound = '')
```

即**判据认为「下达及之后就必须有承诺入库日」**。而界面上：

```html
<!-- demand_pool/view.html 下达确认框 -->
<div>承诺入库时间（可选回填）</div>
```

`release(..., promised_inbound=None)` 是**合法调用** —— 服务侧不拦。

### 两边必有一边要改（也是口径问题）

| 选项 | 适用前提 |
|---|---|
| **判据收窄**为只查 `生产中 / 已完成` | 「承诺入库时间是**产能平衡后**才给得出的」，下达瞬间给不出是正常的；ERP 回传开工后才谈得上承诺 |
| **界面改成必填** | 下达就必须有人承诺日期（否则推移表判断"能否赶上要求日"缺依据） |

**我的倾向：判据收窄。** 理由：承诺入库日按设计是**产能平衡的结果**，它天然晚于「下达」这个动作；
在当前实现里，推移表对「无承诺日」也有兜底（`promised_inbound` 为空则退回用 `required_inbound`），
所以缺它不会让推演失真。**但这条得业务点头**，因为「下达」的语义由业务定。

### 处置：**已按「判据收窄」办（2026-09-19，业务确认后）**

**关键一点：这不是"把判据调松"，而是让 SQL 回到判据自己声明的口径** ——
它的**名字**写的是「已完成补库单须有承诺入库日」，SQL 却自己扩到了「已下达」。

| 改动 | 内容 |
|---|---|
| `scripts/verify_psc_oracles.py` | C6 的 SQL 收窄到 `生产中 / 已完成`；名称与期望话术同步；注释写明三条依据 |
| 同文件 | **新增 C6b 参考项（WARN）**：`已下达` 且 `updated_at` 早于 7 天前仍无承诺日 → 报出来但**不卡闸** |
| `demand_pool/应用详设.md` | 字段表 `promised_inbound` 行 + 「承诺入库时间的口径」新节 + 状态机那两处 |

**依据全部在仓库里**（不是"我觉得"）：服务签名 `promised_inbound: Optional[str] = None`；
字段表标「否」；详设原文「产能平衡后承诺（具体回填时点待确认）」——
本次一并把那个**悬了很久的"待确认"关闭**了。

**为什么 C6b 做成 WARN 而不是 FAIL**：「下达后多久必须补上承诺日」业务上确实还没定论，
一条**永远红**的检查会训练人无视红灯，比没有检查更坏（本项目已写进纪律）。

**验证（判据能失败吗 —— 两边都验，而不是只跑一遍门禁）**：在演示库里造两条对照行、跑完删掉：

| 对照 | 造的行 | 期望 | 实测 |
|---|---|---|---|
| 正 | `生产中` + 无承诺日 | C6 **必须报** | ✗ FAIL，且**只**点名这条 ✅ |
| 负 | `已下达` + 无承诺日（`updated_at` 回拨 10 天） | C6 **不报**；C6b 报 | C6 未点名；`! WARN C6b … RP-TEST-C6-ISSUED@2026-09-09` ✅ |

清理后：门禁 **6/6 PASS**；对账体检 **通过 144 · 失败 0 · 参考 6**。

## G8 参数版本快照与主数据脱节（**演示数据陈旧，非代码缺陷** —— 已对齐）

**判据**：`G8 版本记录 == 主数据当前参数`（只在 `--scenario` 层跑）
**实际**：`BYD-HAN-BRK`、`BYD-HAN-WIR`、`BYD-HAN-SPARM` 三条快照的
`batch_window` / `service_level` 与主数据不一致

### 诊断

主数据**全部正确** —— 与 `宣传/演示业务方案.md` §2.3 的计划员设定值逐条吻合：

| 物料 | 主数据（正确） | 快照（陈旧） |
|---|---|---|
| BYD-HAN-BRK | 14 / 0.98 | **28 / 0.95** |
| BYD-HAN-SPARM | 56 / 0.90 | **28 / 0.95** |
| BYD-HAN-WIR | 28 / 0.90 | **28 / 0.95** |

三条陈旧快照的 `28 / 0.95` 正是**退役前那对写死的常量**（B-08 修的就是"人工维护的组参被拟合常量静默冲掉"），
写入时间均为 `2026-09-15 14:50:4x`（演示造数那一刻），**从未反映过计划员的实际设定**。

**当前代码路径是自洽的**：今天录 f16 时经 `approve → set_fit_params` 写下的
`BYD-HAN-FB26 / v202609` 快照，与主数据**逐字段一致**（28/0.95 vs 28/0.95）。
也就是说：**陈旧的是数据，不是逻辑** —— 这批快照是 B-08 修复前留下的。

### 处理：对齐（数据修复，非代码修复）

按快照的定义（"记**当时生效的两个值**，回滚时才能原样还原"），它本就应该等于当时的实际参数。
已把 3 条快照对齐到主数据当前值：

```sql
UPDATE md_material_param_version SET batch_window=?, service_level=?
 WHERE material_no=? AND fit_version=?
```

备份：`宣传/_backup_20260919_125203_snapshot_fix/`。对齐后门禁 **6/6 PASS**。

> ⚠️ **这条不是"把判据改绿"**：检查的是"快照 == 主数据"，改的是**快照那一侧的错误数据**，
> 判据本身、主数据、代码都没动。之所以敢认定是数据陈旧而非判据过严，证据是上表——
> 主数据与业务方案吻合，快照与**已废弃的常量**吻合，且当前代码写出的快照是自洽的。

### 顺带记一条运维事实

排查中发现 `app/psc/md_material/md_material.db` 的 mtime 变成了**当天 11:26** ——
那是为拍定时任务截图手动触发 `psc/md_material.sync_external_material` 的时刻。
即**ERP 物料同步会整体重写 `md_material` 行**（`mock_erp` 回的值与造数一致，故值没变，但写入发生了）。
