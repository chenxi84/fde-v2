| 别名 | 类型 | 造数服务 | 关键参数 |
|---|---|---|---|
| VER1 | 月度版本（跨应用前置） | md_monthly_version.create | version_no="202608", anchor_period="2026-08", opening_date="2026-08-01"（lock_status 默认「草稿」） |

## §3 模态全字段

- **VT-MODAL-01 详情模态全字段 + base_params tryParse + abnormal_flag**
  - 页面: `psc:sales_forecast`
  - 前置造数: §0 全链 + 对 M1/C001/N+1 行先 calc_baseline（见 §4 VT-FORM-03，填充 base_method/base_params）后开模态
  - 操作: 点 M1/C001/N+1 行的主键列 `.b-link` → `wait_modal()`（轮询 `.modal-mask:visible .loadbox` 消失再断言，pitfalls #16）
  - 断言: `.modal-bd.first` 含全部业务字段标签/值：
    - 头带复合键 `version_no · material_no · customer_no · rolling_month` + abnormal_flag 徽章
    - 定位信息: version_no / material_no / customer_no / rolling_month
    - 客户预测: orig_qty / mape / bias / adj_qty（mape/bias 注「attainment 派生」）
    - 基线: base_method / base_params / base_qty / bp_material_no / switch_time
    - 事件调整: event_analysis / event_adj / base_event_qty
    - 决策结果: abnormal_flag / final_qty
    - 时间信息: created_at / updated_at
    - 底部「原始数据」折叠可展开（get 返回全量 JSON）
  - **base_params JSON tryParse**: base_method="移动平均"、base_params=`{"window": 6}` 经 tryParse 结构化展示 window=6（非原文 JSON；解析失败回退原文）
  - **abnormal_flag 徽章**: 当前为 0 → 灰「正常」徽章（`hue()` 映射）
  - 页脚 `.modal-ft` 草稿版本按钮可见: 【填预测】【算基线】【事件调整】【决策】；abnormal_flag=0 时**无**【填最终】
  - 选择器注意: 多 `.modal-bd` 用 `.first`（pitfalls #15）；wait_modal 防加载态抢跑（#16）

## §4 操作落库回显（手工参考创建：开启版本 + 行级加工）

- **VT-FORM-01 开启版本（open_version，唯一"创建"入口）**
  - 前置造数: VER1 + C001 + M1 + AT1（不含 SF1，本用例自行 open_version）
  - 操作: 点【开启版本】→ 模态版本下拉选 202608（仅 lock_status=草稿 项）→ 提交
  - 断言: toast 带「清单 1 行 · 处理表 3 行」；关闭模态；列表回显 3 行（M1×C001×N+1/N+2/N+3）
  - 选择器注意: 版本下拉仅「草稿」项（发布（锁定）/冻结版本不显示）
- **VT-FORM-02 填预测（fill_customer）→ 回显 adj_qty**
  - 前置造数: §0 全链（已 open_version）
  - 操作: 点 M1/C001/N+1 行【填预测】→ 模态 orig_qty=1000 → 提交
  - 断言: 回显 adj_qty == 950（= orig_qty × (1 − bias) = 1000 × (1 − 0.05)，bias 来自 attainment 自动算）；列表行 orig_qty=1000、adj_qty=950；成功 toast（非错误）
- **VT-FORM-03 算基线（calc_baseline）→ 回显 base_method/base_params**
  - 前置造数: §0 全链 + 已 fill_customer（M1/C001/N+1）
  - 操作: 点 M1/C001/N+1 行【算基线】→ 确认（按钮直发，无表单）
  - 断言: 回显 base_method="移动平均"、base_params=`{"window": 6}`；无断点时 bp_material_no/switch_time 不显示（历史 stub 空 → base_qty 为 dash，属预期）
- **VT-FORM-04 事件调整（adjust_event）→ 回显 event_analysis/event_adj**
  - 前置造数: §0 全链 + 已 fill_customer（M1/C001/N+1）
  - 操作: 点行【事件调整】→ event_analysis="促销"、event_adj=20 → 提交
  - 断言: 回显 event_analysis="促销"、event_adj=20（`event_adj` 带符号 fmt 显示）
- **VT-FORM-05 决策（decide）→ 回显 final_qty/abnormal_flag**
  - 前置造数: §0 全链 + 已 fill_customer + calc_baseline（M1/C001/N+1）
  - 操作: 点 M1/C001/N+1 行【决策】→ 确认（按钮直发）
  - 断言: 回显 final_qty == 950（基线和事件合计未算 → 取客户调整后值 adj_qty）、abnormal_flag == 0（正常）；成功 toast
- **VT-FORM-06 汇总（summarize + get_summary）**
  - 前置造数: §0 全链 + 已 fill_customer + decide（M1/C001/N+1 有 final_qty=950）
  - 操作: 点【汇总】→ 选版本 202608（草稿）→ 执行 summarize；点【查看汇总】→ 选版本 202608 → 表格展示
  - 断言: summarize toast「已汇总 N 行」（**N == 3**：summarize 按 `GROUP BY material_no, rolling_month` 合计，6 行处理表 → M1×N+1/N+2/N+3 三个分组）；汇总查询表 `.tbl.tight` 表头 == 版本/物料/滚动月度/最终预测合计（契约列 version_no/material_no/rolling_month/final_qty_sum），共 3 行，M1×N+1 行四个单元格 == `["202608","M1","N+1","950"]`（`fmt()` 加粗；空客户行 final_qty 为 NULL 计 0，不影响合计）
  > 2026-09-17 补充（非订正）：原句只写「toast 已汇总 N 行」，未点明 N；脚本把它钉成 3 行，并把「列」落到实际表头文案上（页面表头是中文标签，不是字段名）。

- **VT-FORM-07 新建组合（create · 客户可空）**（2026-09-17 回写）
  - 前置造数: §0 全链已跑（M1×C001 三行已在册）
  - 操作: 点【新建组合】→ 弹窗内确认版本下拉默认当前草稿版本 `202608` → 物料 autocomplete 填 `M1`
    选中「物料A」→ **客户留空** → 点【创建组合】
  - 断言: toast「已新建组合」；关闭后列表变 **6 行**（M1×C001 三行 + M1×空客户三行）
  - 选择器注意: 物料用 autocomplete（`.auto-drop div:has-text("物料A")`），不是普通 input
  - 为什么回写: 本条**脚本里测了、用例文档里漏了**（三方对账 `scripts/view_coverage.py` 的 V2 判据抓出）——
    与 `md_customer` 用例文档里的「平台列排序」（升→降→默认序三击）同属「测了但没记」，是同一类漂移的反方向。
    （2026-09-17 订正：原文此处连编号一起引用了 **md_customer** 的列排序用例，被 `view_coverage.py`
    的 V3 判据当成**本页**用例（「文档写了、脚本里找不到断言」）——属跨应用引用造成的误报，故改写为不带编号的引用。）
