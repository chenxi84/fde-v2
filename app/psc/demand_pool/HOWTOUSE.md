# demand_pool 使用要点

**管什么**：补库单（需求池）——库存推移表击穿水位线时自动产生的补库需求，及其下达与作废流转。

## 标准工作流（按此顺序）

1. `list` — 筛 `status="待下达"` 定位待下达补库单
2. `get` — 核对当前状态与字段
3. `release` — 下达生产：`待下达 → 已下达`，下发生产计划给 ERP，可回填 `promised_inbound`

补库单**由 `inventory_projection.scan_alert` 击穿时跨应用自动创建**（初始 `待下达`）——不要试图手工造单。

需求消失作废：`list`/`get` 定位 → `cancel`（`待下达`/`已下达` → `已取消`）。

## 前置条件与禁忌

- **状态机**：`待下达 → 已下达 → 生产中 → 已完成`；`已完成` / `已取消` 为终态，不可再流转。
- **`on_workorder_started` / `on_inbound` 不在你的工具表里**。它们是 ERP 回调入口（工单开工回传、入库回传），不是你发起的动作——**你的职责到 `release` 为止**。用户问「工单开工了吗 / 入库了吗」，用 `list`/`get` 查状态答复，不要试图推进这两步。
- `cancel` 只在 `待下达`/`已下达` 可用；`生产中`/`已完成` 不可取消。
- `replenish_no` 由系统生成（`RP` + 日期 + 流水），**不能指定**；后续操作必须用已存在的单号。
- `replenish_type` 仅 `缺货补库` / `最低库存补库` / `安全库存补库`，多条件命中取最高优先级。
- `create` 会校验 `material_no` 存在于 `md_material`，不存在则不建单。
- 本应用**无修改补库数量/物料/类型的服务，也无删除服务**（作废走 `cancel`）。
