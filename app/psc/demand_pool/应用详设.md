## 1. 需求概览

### 1.1 基本信息
- **需求名称**: 需求池（补库单）管理
- **需求编号**: REQ-PSC-DP-001
- **所属模块**: 产销协同-需求池管理
- **需求来源**: 业务方（计划）
- **创建日期**: 2026-08-14
- **优先级**: P0

### 1.2 需求背景
#### 1.2.1 为什么需要这个需求？
主计划（净需求经产能平衡后的月度总量）无法覆盖期间内的时点缺货。库存推移表逐日推演库存水位，在击穿水位线（<0 / <A / <A+C）时触发补库需求，把主计划在时点上的缺口重新转为执行项。需求池承载这批「时点补库单」，并走「下达 → 生产 → 入库」的 ERP 闭环，是对主计划（进而生产计划）准确性不足的补充。

#### 1.2.2 期望达到什么目标？
建立三类补库单（缺货 / 最低库存 / 安全库存）的生成与状态机管理能力：击穿触发自动生成补库单，按产能松紧分档补货量，经 ERP 下达/回传闭环流转，最终补充生产计划（生产需求 = 主计划 + 需求池补充需求）。

### 1.3 需求范围
#### 1.3.1 包含哪些功能？
补库单自动生成（库存推移表击穿触发）、下达生产、工单开工回传、入库回传、取消补库单、补库单详情查看、补库单列表查询。

#### 1.3.2 不包含哪些功能？
- 不做手工新建补库单（数据来源类型为自动参考创建，前端不提供"新建"按钮）
- 不做产能平衡（在线下完成，产能松紧标记由线下产能平衡人工维护，见 BRD §6.2/§5.5）
- 不做库存推移推演（属 `inventory_projection` 聚合，本应用只接收其击穿触发）
- 不做生产排程 / 工单执行（属 ERP，本应用只下发生产计划并接收回传）

> **数据来源类型**: 自动参考创建 —— 补库单由上游库存推移表（`inventory_projection`）击穿水位线时自动生成，用户无需手工触发；前端禁止提供"新建"入口。US/FUNC 中的 `create` 以"系统在击穿时自动生成补库单"表述，而非"用户新建"。

### 1.4 涉及角色
**谁会使用这个功能？**

- **总部计划**: 产能平衡后下达生产补库单、取消需求消失的补库单、查看补库单列表与详情
- **系统（库存推移表 / ERP）**: 非登录用户——库存推移表击穿触发自动生成补库单；ERP 回传工单开工/入库驱动状态流转

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 系统击穿自动生成补库单（优先级：P1）

- **故事描述**: 作为系统（库存推移表击穿触发），当某物料库存余额击穿水位线时，自动生成对应类型的补库单，以便于把时点缺货缺口转为可执行的生产补充需求
- **为何赋予此优先级**：补库单是需求池全部后续流转（下达/生产/入库）的起点，无补库单则需求池无数据可流转
- **独立测试**：可通过构造库存余额击穿水位线（<0 / <A / <A+C）的场景，验证系统自动生成对应类型的补库单来独立测试
- **前置条件**: 库存推移表已完成当日逐日推演并识别击穿水位线；物料已存在于物料主数据 `md_material`
- **后置条件**: 系统生成一条待下达状态的补库单，补库类型/数量/要求入库时间按 BR 规则确定

**验收场景**：

1. `US-01-AC1` **场景**: 缺货击穿自动生成缺货补库单
   - **Given** 某物料库存余额 <0（击穿缺货线），**When** 库存推移表触发扫描，**Then** 系统生成一条 replenish_type=缺货补库、status=待下达 的补库单，补库数量按产能松紧分档确定

2. `US-01-AC2` **场景**: 击穿最低水位自动生成最低库存补库单
   - **Given** 某物料库存余额 <A 且 ≥0（击穿最低水位），**When** 库存推移表触发扫描，**Then** 系统生成一条 replenish_type=最低库存补库 的补库单

3. `US-01-AC3` **场景**: 击穿安全水位自动生成安全库存补库单
   - **Given** 某物料库存余额 <A+C 且 ≥A（击穿安全水位），**When** 库存推移表触发扫描，**Then** 系统生成一条 replenish_type=安全库存补库 的补库单

4. `US-01-AC4` **场景**: 物料不存在被拒绝
   - **Given** 触发补库的 material_no 不存在于 md_material，**When** 系统尝试生成补库单，**Then** 系统拒绝生成并记录错误（主数据引用铁律）

---

#### 2.1.2 `US-02` 用户故事 — 下达生产补库单（优先级：P1）

- **故事描述**: 作为总部计划，我想要在产能允许时把待下达的补库单下达生产给 ERP，以便于启动补库执行
- **为何赋予此优先级**：下达是把需求池补库需求转为实际生产/在途的关键动作，是补库单状态机的核心推进步骤
- **独立测试**：可通过选择一条待下达补库单执行下达，验证其状态转为已下达且已通过适配器下发 ERP 来独立测试
- **前置条件**: 补库单处于待下达状态；产能允许（线下产能平衡确认，产能松紧已人工标记）
- **后置条件**: 补库单状态转为已下达；系统通过 `_dispatch_to_erp` 适配器下发生产计划给 ERP

**验收场景**：

1. `US-02-AC1` **场景**: 待下达补库单下达成功
   - **Given** 存在一条 status=待下达 的补库单，**When** 执行 release 下达，**Then** 状态转为已下达，并调用 `_dispatch_to_erp` 下发生产计划

2. `US-02-AC2` **场景**: 非待下达状态下达被拒绝
   - **Given** 补库单 status=已下达 或 已完成，**When** 再次执行 release，**Then** 系统拒绝并提示"当前状态不可下达"（状态机非法跳转拦截）

---

#### 2.1.3 `US-03` 用户故事 — 回传工单开工（优先级：P1）

- **故事描述**: 作为系统（ERP 回传），接收 ERP 工单开工回传，把已下达补库单转为生产中/在途，以便于跟踪补库执行进度
- **为何赋予此优先级**：开工回传是状态机「已下达 → 生产中/在途」的必经环节，缺失则补库单状态停滞
- **独立测试**：可通过模拟 ERP 回传开工回执，验证补库单状态从已下达转为生产中/在途来独立测试
- **前置条件**: 补库单处于已下达状态
- **后置条件**: 补库单状态转为生产中/在途

**验收场景**：

1. `US-03-AC1` **场景**: 已下达补库单开工回传成功
   - **Given** 存在一条 status=已下达 的补库单，**When** 收到 ERP 开工回执 on_workorder_started，**Then** 状态转为生产中/在途

2. `US-03-AC2` **场景**: 非已下达状态开工回传被拒绝
   - **Given** 补库单 status=待下达 或 已完成，**When** 收到开工回执，**Then** 系统拒绝并记录错误（状态机非法跳转拦截）

#### 2.1.4 `US-04` 用户故事 — 回传入库（优先级：P1）

- **故事描述**: 作为系统（ERP 回传），接收 ERP 入库回传，把生产中/在途补库单转为已完成，以便于关闭补库闭环
- **为何赋予此优先级**：入库回传是状态机「生产中/在途 → 已完成」的终态推进，标志着补库需求已满足
- **独立测试**：可通过模拟 ERP 回传入库回执，验证补库单状态从生产中/在途转为已完成来独立测试
- **前置条件**: 补库单处于生产中/在途状态
- **后置条件**: 补库单状态转为已完成（终态）

**验收场景**：

1. `US-04-AC1` **场景**: 生产中/在途补库单入库回传成功
   - **Given** 存在一条 status=生产中/在途 的补库单，**When** 收到 ERP 入库回执 on_inbound，**Then** 状态转为已完成

2. `US-04-AC2` **场景**: 非生产中/在途状态入库回传被拒绝
   - **Given** 补库单 status=待下达 或 已下达，**When** 收到入库回执，**Then** 系统拒绝并记录错误（状态机非法跳转拦截）

#### 2.1.5 `US-05` 用户故事 — 取消补库单（优先级：P2）

- **故事描述**: 作为总部计划，我想要在需求消失（库存已补 / 客户取消）时取消补库单，以便于作废不再需要执行的补库需求
- **为何赋予此优先级**：取消是需求变化时的兜底操作，避免对已消失的需求继续下达生产
- **独立测试**：可通过选择一条待下达或已下达补库单执行取消，验证其状态转为已取消来独立测试
- **前置条件**: 补库单处于待下达或已下达状态；需求已消失（库存已补 / 客户取消）
- **后置条件**: 补库单状态转为已取消（终态）

**验收场景**：

1. `US-05-AC1` **场景**: 待下达补库单取消成功
   - **Given** 存在一条 status=待下达 的补库单，**When** 执行 cancel，**Then** 状态转为已取消

2. `US-05-AC2` **场景**: 已下达补库单取消成功
   - **Given** 存在一条 status=已下达 的补库单，**When** 执行 cancel，**Then** 状态转为已取消

3. `US-05-AC3` **场景**: 生产中/已完成补库单取消被拒绝
   - **Given** 补库单 status=生产中/在途 或 已完成，**When** 执行 cancel，**Then** 系统拒绝并提示"当前状态不可取消"（状态机非法跳转拦截）

#### 2.1.6 `US-06` 用户故事 — 查看补库单详情（优先级：P2）

- **故事描述**: 作为总部计划，我想要按补库单号查看单条补库单详情，以便于核对补库类型、数量与状态流转情况
- **为何赋予此优先级**：详情查看是下达、取消操作的前置核对步骤
- **独立测试**：可通过输入已知 replenish_no 调起详情并验证字段回显完整来独立测试
- **前置条件**: 系统中已存在目标补库单
- **后置条件**: 返回该补库单的完整字段记录

**验收场景**：

1. `US-06-AC1` **场景**: 按补库单号查询成功
   - **Given** 存在 replenish_no=R202608140001 的补库单，**When** 通过 get 查询，**Then** 返回完整字段（单号/物料/类型/数量/要求与承诺入库时间/状态）

2. `US-06-AC2` **场景**: 查询不存在的补库单被拒绝
   - **Given** 系统中不存在 replenish_no=NOTEXIST，**When** 通过 get 查询，**Then** 系统返回"补库单不存在"错误

**验收场景**：

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 补库单自动生成（击穿触发）
1. 库存推移表（`inventory_projection`）每日 0 点以 ERP 库存为锚点，逐日推演未来 3 个月库存余额
2. 库存推移表逐日对照水位线（最低 A / 安全 C / 组批 B），识别击穿信号
3. 击穿触发时，调用 `demand_pool.create(...)` 自动生成补库单
4. 系统按触发条件确定补库类型（缺货 / 最低库存 / 安全库存）
5. 系统按产能松紧分档确定补库数量
6. 系统记录要求入库时间（推演出的击穿时点），补库单状态 = 待下达

#### 3.1.2 场景2: 下达生产闭环（含 ERP 回传）
1. 总部计划进入补库单列表，筛选待下达补库单
2. 计划确认产能允许（线下产能平衡已标记产能松紧）
3. 计划执行下达，系统校验状态（须为待下达）
4. 系统调用 `_dispatch_to_erp` 适配器下发生产计划给 ERP，状态转为已下达
5. ERP 执行生产，回传工单开工 → 系统将补库单状态转为生产中/在途
6. ERP 回传入库 → 系统将补库单状态转为已完成（闭环结束）

#### 3.1.3 场景3: 需求消失取消
1. 总部计划发现补库需求已消失（库存已补 / 客户取消）
2. 计划在补库单详情/列表执行取消
3. 系统校验状态（须为待下达或已下达）
4. 校验通过，状态转为已取消（作废）

### 3.2 业务规则

#### 3.2.1 `BR-01` 补库单号全局唯一
- **规则描述**: replenish_no 为补库单唯一标识，全局唯一，系统自动生成（具体生成格式待确认）
- **适用场景**: 创建
- **示例**: replenish_no=R202608140001 已存在，则不可再生成相同单号

#### 3.2.2 `BR-02` 补库类型枚举约束
- **规则描述**: replenish_type 仅限"缺货补库 / 最低库存补库 / 安全库存补库"三类
- **适用场景**: 创建
- **示例**: 传入"组批补库"等非法值 → 拒绝，提示"补库类型仅支持缺货/最低库存/安全库存补库"

#### 3.2.3 `BR-03` 状态枚举约束
- **规则描述**: status 仅限"待下达 / 已下达 / 生产中（在途）/ 已完成 / 已取消"五种
- **适用场景**: 创建、状态流转
- **示例**: 创建时 status 默认"待下达"

#### 3.2.4 `BR-04` 三类补库触发条件
- **规则描述**: 库存推移表逐日对照水位线，击穿即触发对应类型补库：

| 补库类型 | 触发条件 |
|---|---|
| 缺货补库 | 库存余额 < 0 |
| 最低库存补库 | 库存余额 < 最低水位 A |
| 安全库存补库 | 库存余额 < 最低 A + 安全 C |

- **适用场景**: 击穿触发创建
- **示例**: 某物料库存余额 = -10 → 触发缺货补库；库存余额 = 5（A=20）→ 触发最低库存补库

#### 3.2.5 `BR-05` 三类补库优先级
- **规则描述**: 三类补库优先级为 缺货补库 > 最低库存补库 > 安全库存补库；同一物料同时满足多个触发条件时，按最高优先级处理（缺货最高）
- **适用场景**: 击穿触发创建
- **示例**: 库存余额 = -5（同时 <0、<A、<A+C）→ 按缺货补库处理

#### 3.2.6 `BR-06` 补货量分档（产能松紧）
- **规则描述**: 补货量按产能松紧分两档：

| 补库类型 | 产能紧张时补货量 | 产能富余时补货量 |
|---|---|---|
| 缺货补库 | 缺货量（补回 0） | 缺货量 + 组批 B（补到组批水位） |
| 最低库存补库 | 补到最低 A | 补到组批水位 B |
| 安全库存补库 | 补到最低 A + 安全 C | 补到组批水位 B |

核心逻辑：任何补库触发，产能富余就一次按组批量切线上足（补到组批水位 B），减少未来切线；产能紧张时只补到触发的那条水位线。
- **适用场景**: 击穿触发创建（确定 replenish_qty）
- **计算方式**: 产能富余 → 补库量 = 目标水位 B − 当前库存余额；产能紧张 → 补库量 = 触发水位线 − 当前库存余额（缺货补回 0）
- **示例**: 物料当前库存余额 = 10，A=20、C=15、B=80，触发最低库存补库：产能富余 → 补到 B=80（补 70）；产能紧张 → 补到 A=20（补 10）

#### 3.2.7 `BR-07` 产能松紧判定来源
- **规则描述**: 「产能富余 / 产能紧张」由线下产能平衡时人工标记（与产能平衡在线下完成一致），作为补货量分档的依据
- **适用场景**: 击穿触发创建（分档依据）
- **示例**: 计划在线下产能平衡时标记某期间为产能紧张，则该期间补库按"只补到触发水位线"分档

#### 3.2.8 `BR-08` 物料主数据引用铁律
- **规则描述**: material_no 必须引用物料主数据 `md_material`，创建时校验物料存在，禁止手工录入
- **适用场景**: 创建
- **示例**: material_no 不存在于 md_material → 拒绝生成补库单；前端字段来源：`md_material.list` 下拉选择

#### 3.2.9 `BR-09` 补库数量校验
- **规则描述**: replenish_qty 必须为正数（>0）
- **适用场景**: 创建
- **示例**: 分档计算出的补库量 ≤0（如库存余额已 ≥ 目标水位）→ 不生成补库单

#### 3.2.10 `BR-10` 要求入库时间由击穿时点确定
- **规则描述**: required_inbound 由库存推移表推演出的缺货/击穿时点确定，补库须在此之前入库
- **适用场景**: 创建
- **示例**: 推演出某物料第 7 天库存余额击穿 <0，则 required_inbound 应不晚于该击穿日

#### 3.2.11 `BR-11` 状态机合法流转
- **规则描述**: 补库单状态流转须遵循状态机（见 §3.4），非法跳转拒绝
- **适用场景**: release / on_workorder_started / on_inbound / cancel
- **示例**: 已完成补库单再执行 cancel 或 release → 拒绝

#### 3.2.12 `BR-12` 状态流转前置条件
- **规则描述**: 待下达 → 已下达由系统下达生产给 ERP 触发；已下达 → 生产中（在途）、生产中（在途）→ 已完成依赖 ERP 回传工单状态与入库
- **适用场景**: release / on_workorder_started / on_inbound
- **示例**: 未收到 ERP 开工回传时，已下达补库单不会自动转为生产中/在途

#### 3.2.13 `BR-13` 已取消条件
- **规则描述**: 已取消仅用于需求消失（库存已补 / 客户取消）时作废；已完成（终态）不可取消
- **适用场景**: cancel
- **示例**: 补库单 status=已完成 → 执行 cancel 被拒绝

### 3.3 业务数据

#### 3.3.1 数据1: 补库单号 replenish_no
- **数据描述**: 补库单的唯一标识，全局主键
- **数据类型**: 文本
- **数据来源**: 系统自动生成（生成格式待确认）
- **示例值**: R202608140001

#### 3.3.2 数据2: 物料号 material_no
- **数据描述**: 被补库的物料号，引用物料主数据
- **数据类型**: 文本
- **数据来源**: 引用 `md_material`（主数据），非手工录入
- **示例值**: 8210001

#### 3.3.3 数据3: 补库类型 replenish_type
- **数据描述**: 触发补库的类型
- **数据类型**: 枚举值
- **数据来源**: 系统按触发条件判定（BR-04/BR-05）
- **示例值**: 缺货补库 / 最低库存补库 / 安全库存补库

#### 3.3.4 数据4: 补库数量 replenish_qty
- **数据描述**: 本次补库的数量，按产能松紧分档确定
- **数据类型**: 数字
- **数据来源**: 系统按分档规则计算（BR-06）
- **示例值**: 70

- **数据描述**: 库存推移表推演出的缺货/击穿时点，须在此之前入库
- **数据类型**: 日期
- **数据来源**: 库存推移表推演结果
- **示例值**: 2026-08-21

#### 3.3.6 数据6: 承诺入库时间 promised_inbound
- **数据描述**: 产能平衡后承诺的入库时间
- **数据类型**: 日期
- **数据来源**: 产能平衡后承诺（release 环节回填，具体填写时点待确认）
- **示例值**: 2026-08-25

#### 3.3.7 数据7: 状态 status
- **数据描述**: 补库单生命周期状态
- **数据类型**: 枚举值
- **数据来源**: 系统按状态机维护
- **示例值**: 待下达 / 已下达 / 生产中（在途）/ 已完成 / 已取消

### 3.4 状态机

补库单状态流转（存在状态流转，必须绘制状态图 + 转换规则矩阵）：

```
待下达 ── release（系统下达生产给 ERP）──▶ 已下达 ── on_workorder_started（ERP 回传开工）──▶ 生产中/在途 ── on_inbound（ERP 回传入库）──▶ 已完成
   │                                          │
   └────── cancel（需求消失/库存已补）───────▶ 已取消 ◀────── cancel（需求消失/库存已补）──────┘
```

**状态转换规则矩阵：**

| 当前状态 | 目标状态 | 触发动作 | 前置条件 |
|----------|----------|----------|----------|
| (新建) | 待下达 | create | 库存推移表击穿对应水位线（<0 / <A / <A+C），由 inventory_projection.scan_alert 触发 |
| 待下达 | 已下达 | release | 产能允许（线下产能平衡确认），系统通过 `_dispatch_to_erp` 下发生产计划给 ERP |
| 待下达 | 已取消 | cancel | 需求消失（库存已补 / 客户取消） |
| 已下达 | 生产中/在途 | on_workorder_started | ERP 回传工单开工 |
| 已下达 | 已取消 | cancel | 需求消失（库存已补 / 客户取消） |
| 生产中/在途 | 已完成 | on_inbound | ERP 回传入库完成 |

> 已完成、已取消为终态，不可再流转。

#### 4.3.1 F01-01 补库单

##### 4.3.1.1 FUNC-01 自动生成补库单

**功能描述**:
库存推移表（`inventory_projection.scan_alert`）击穿水位线时，跨应用调用本应用 `create(...)` 自动生成补库单。此功能为自动参考创建——前端不提供"新建"入口，无用户手工新建故事。

**系统处理流程**:
1. `inventory_projection` 逐日推演库存余额，识别击穿水位线（<0 / <A / <A+C）
2. 击穿时调用 `demand_pool.create(material_no, replenish_type, replenish_qty, required_inbound)`
3. 系统校验 material_no 存在于 `md_material`（BR-08）
4. 系统按触发条件确定补库类型（BR-04）、按优先级判定（BR-05）
5. 系统按产能松紧分档计算补库数量（BR-06 / BR-07）
6. 系统生成 replenish_no，记录 required_inbound（击穿时点，BR-10）
7. 补库单入库，status=待下达

**输入数据**:
- material_no: 物料号 - 必填，引用 md_material - 示例：8210001
- replenish_type: 补库类型 - 必填，枚举（缺货/最低库存/安全库存补库） - 示例：缺货补库
- replenish_qty: 补库数量 - 必填，正数，按分档计算 - 示例：70
- required_inbound: 要求入库时间 - 必填，击穿时点 - 示例：2026-08-21

**输出数据**:
- 补库单: replenish_no, material_no, replenish_type, replenish_qty, required_inbound, status=待下达
- 错误消息: "物料记录不存在" / "补库类型非法" / "补库数量必须大于0"

**业务规则**:
- BR-01: replenish_no 全局唯一
- BR-02: replenish_type 枚举约束
- BR-04: 三类补库触发条件
- BR-05: 三类补库优先级
- BR-06: 补货量分档（产能松紧）
- BR-07: 产能松紧判定来源
- BR-08: material_no 主数据引用铁律
- BR-09: replenish_qty > 0
- BR-10: required_inbound 由击穿时点确定

**特殊处理**:
- 本功能由 `inventory_projection.scan_alert` 跨应用调用触发（非用户手工操作）
- material_no 引用主数据，创建时校验 `md_material.get(material_no)` 存在

**业务实体**:
- **DemandPool**: 补库单，标识为 replenish_no；由库存推移表击穿触发，状态机流转

**DemandPool 字段**

| 字段名称 | 字段类型 | 是否必填 | 默认值 | 业务逻辑 |
|---|---|---|---|---|
| replenish_no | 文本 | 是（系统生成） | 自动生成 | 补库单号，PK，全局唯一，系统自动生成 |
| material_no | 文本 | 是 | - | 物料号；来源：md_material.list 下拉选择/引用，禁止手工录入 |
| replenish_type | 枚举值 | 是 | - | 缺货补库/最低库存补库/安全库存补库，由触发条件判定 |
| replenish_qty | 数字 | 是 | - | 补库数量，按产能松紧分档计算，>0 |
| required_inbound | 日期 | 是 | - | 要求入库时间，推移表推演的缺货/击穿时点 |
| promised_inbound | 日期 | 否 | - | 承诺入库时间，产能平衡后承诺（release 环节回填，时点待确认） |
| status | 枚举值 | 是 | 待下达 | 待下达/已下达/生产中(在途)/已完成/已取消 |

##### 4.3.1.2 FUNC-02 下达生产

**功能描述**:
对处于待下达状态的补库单执行下达，系统通过 `_dispatch_to_erp` 适配器下发生产计划给 ERP，状态转为已下达。

**用户操作流程**:
1. 总部计划进入补库单列表，筛选待下达补库单
2. 计划确认产能允许（线下产能平衡已标记产能松紧）
3. 计划执行下达（release）
4. 系统校验状态（须为待下达，BR-11）
5. 系统调用 `_dispatch_to_erp` 适配器下发生产计划
6. 状态转为已下达，promised_inbound 记录承诺入库时间

**输入数据**:
- replenish_no: 补库单号 - 必填，作为定位键 - 示例：R202608140001

**输出数据**:
- 补库单状态: 已下达
- 下发结果: `_dispatch_to_erp` 下发回执
- 错误消息: "当前状态不可下达" / "补库单不存在"

**业务规则**:
- BR-11: 状态机合法流转（仅待下达 → 已下达）
- BR-12: 待下达 → 已下达由系统下达生产给 ERP 触发

**特殊处理**:
- 调用 `_dispatch_to_erp` 适配器（下发生产计划给 ERP，出向），非跨应用调用
- 承诺入库时间 promised_inbound 在产能平衡后承诺（具体回填时点待确认）

**业务实体**:
- **DemandPool**: 同上 FUNC-01

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 击穿触发自动生成补库单
- **关联用户故事**: US-01
- **关联业务规则**: BR-02, BR-04, BR-05, BR-06, BR-07, BR-08
- **验证方式**: 构造库存余额击穿 <0 / <A / <A+C 三种场景，触发 inventory_projection.scan_alert
- **测试数据**: 物料 8210001（A=20, C=15, B=80），库存余额分别取 -10、5、30
- **预期结果**: 分别生成缺货补库/最低库存补库/安全库存补库单，补库数量按产能松紧分档正确，status=待下达

#### 6.1.2 标准2: 补库单状态机闭环
- **关联用户故事**: US-02, US-03, US-04
- **关联业务规则**: BR-11, BR-12
- **验证方式**: 依次执行 release → on_workorder_started → on_inbound
- **测试数据**: 一条待下达补库单
- **预期结果**: 状态依次转为 待下达→已下达→生产中/在途→已完成，release 时调用 _dispatch_to_erp

#### 6.1.3 标准3: 状态机非法跳转拦截
- **关联用户故事**: US-02, US-03, US-04, US-05
- **关联业务规则**: BR-11, BR-13
- **验证方式**: 对已完成补库单执行 cancel/release；对待下达补库单执行 on_inbound
- **测试数据**: status=已完成 与 status=待下达 的补库单各一条
- **预期结果**: 非法跳转均被拒绝并提示"当前状态不可XX"

#### 6.1.4 标准4: 补库类型与补货量分档正确性
- **关联用户故事**: US-01
- **关联业务规则**: BR-04, BR-05, BR-06
- **验证方式**: 对同一击穿场景分别在产能富余/紧张下验证补货量
- **测试数据**: 物料 8210001（A=20, C=15, B=80），库存余额=10 触发最低库存补库
- **预期结果**: 产能富余 → 补到 80（补 70）；产能紧张 → 补到 20（补 10）

#### 6.1.5 标准5: 需求消失取消
- **关联用户故事**: US-05
- **关联业务规则**: BR-11, BR-13
- **验证方式**: 对待下达/已下达补库单执行取消，对生产中补库单执行取消
- **测试数据**: status=待下达、已下达、生产中 各一条
- **预期结果**: 待下达/已下达转为已取消；生产中取消被拒绝

#### 6.1.6 标准6: 补库单查询
- **关联用户故事**: US-06, US-07
- **关联业务规则**: —
- **验证方式**: 按补库单号查详情；按物料/类型/状态筛选列表
- **测试数据**: 多条不同物料/类型/状态的补库单
- **预期结果**: 详情回显完整；列表筛选结果正确，支持分页

### 6.2 非功能验收标准
**性能要求**: 列表查询（5000条以内）页面加载时间<2秒；击穿触发创建补库单单条响应<1秒
**安全性要求**: 无敏感加密需求（业务单据）；状态流转经状态机校验防非法跳转
**兼容性要求**: 支持 Chrome、Edge 浏览器

### 6.3 已知问题或限制
- replenish_no 自动生成的具体格式（前缀/流水号）BRD 未明确，待确认
- promised_inbound 承诺入库时间的具体回填时点（release 时由系统/产能平衡回填）待确认
- 产能松紧标记在系统内的落点（是否显式维护"产能松紧"字段/标记）待确认——BRD §6.2 称"线下产能平衡时人工标记"
- 同一物料连续多日击穿时是否重复生成补库单（去重策略）待确认
- ERP 下发/回传接口（_dispatch_to_erp、on_*_result）的具体报文与节奏待实施设计确认（参考 BRD §8.5.1 日度/周度）

### 7.4 备注
- 本应用数据来源类型为"自动参考创建"，前端不提供"新建"按钮；create 是"推移表击穿触发"自动生成，而非用户手工新建
- 补库单是需求池的核心执行项，状态机经 ERP 下达/回传闭环（待下达→已下达→生产中/在途→已完成/已取消）
- 生产需求 = 主计划 + 需求池补充需求（BRD §6.4），本应用是对主计划时点缺口的动态修正
- material_no 标注主数据来源 md_material，禁止手工录入（主数据引用铁律）
