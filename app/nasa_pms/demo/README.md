# `nasa_pms` 演示环境

一条命令回到「能开演的状态」：

```bash
python app/nasa_pms/demo/demo_build.py          # 清空 → 造数 → 体检
python main.py                                  # 起平台 → http://127.0.0.1:4000（admin/admin）
```

| 脚本 | 作用 |
|---|---|
| `demo_build.py` | 编排：① 清空本组 **13** 个库的表 ② 造数 ③ 体检（`--keep` 只追加；`--start` 顺便起服） |
| `demo_seed.py` | 故事线造数（**经真实服务**，所以造出来的是天生的合法状态） |
| `verify_demo.py` | 体检：**按身份**校验关键对象在不在 —— `rc=0` 是演示环境、`rc=2` 是「环境没造好」 |

## 演示场景：近地轨道遥感卫星 EO-3 —— 从需求走到**发射**

一条从「用户方提观测需求」，经「研制与总装试验」，走到**「公司要发射这颗卫星」**
（发射段 + 在轨段）的完整系统工程故事。
**13 个聚合根每个状态档位都有样本**（看板的状态分布、列表筛选、状态机动作都能点得动）：

| 应用 | 演示里有什么 |

| 利益相关者 | 8 条（用户方 / 承包商 / 内部机构），6 条期望（含 1 条 MOE 带度量口径、2 条 committed 约束）；新增**运载火箭研究院 / 发射场测发大队 / 测控站网** |
| 需求 | 19 条（系统 / 技术 / 接口 / 派生），**8 条已基线（B1 研制期 4 + B2 发射段 4）**、2 条派生挂上游、1 条作废留痕 |
| 技术计划 | 6 份：SEMP 已批准 / V&V 审批中 / 集成草稿 / 技术评估**已修订**（版本台账两条）+ **发射实施计划（批准 · D 阶段）** / **在轨测试计划（审批中 · E 阶段）** |

| 风险 | 10 条覆盖 识别 / 分析中 / 缓解中 / 已关闭 / **已接受**；含 1 条严重（5×5）在缓解中 + **4 条发射段与在轨段风险**（窗口 / 星箭耦合 / 场区排期 / 单粒子） |

| 评审 | 5 场：SRR 已关闭 / PDR **跟踪中** / CDR 计划中 / **TRR 已通过并关闭** / **PRR 行动项跟踪中**；**FRR（飞行就绪）刻意不预置**——留给数字员工现场建 |
| 决策 | 3 条：按最高分定的（已实施）/ 按依据选非最高分的 / 权衡中 |
| 接口 | 7 条：已发布 / **已冻结** / 定义中 + **整星—运载分离接口（ICP）** / **发射场地面保障（IDD）** / **测控站—卫星测控（IRD）** |
| WBS | 10 个元素：产品树 + 使能性工作 + 已收口，另有**发射支持系统 → 发射场保障**（流程编排现场挂活动的叶子） |
| 进度活动 | 6 条（星务软件链 + 一条开口端样本）；**发射活动链刻意不预置**——由「发射链排程 → 体检 → 基线 → 回填实绩」这条 flow 现场造 |

> **为什么"发射"不用新开聚合**：13 个聚合根是按**过程产出的东西**选的，而「发射」在模型里
> 不是对象而是**各台账在不同阶段的行** —— 素材本来就在字典里：`review.review_type` 有 trr/prr/**frr**/orr，
> `verification.phase` 有 **on_orbit**，`tech_plan.phase` 有 **d/e**，`configuration_item.baseline`
> 有 **as_deployed**，`interface.if_type` 有 **icp**（运载火箭作为接口另一方）。
> 所以发射任务靠**已有 13 个聚合装得下**，一条 DDL 都不用改。

## 三个"为什么这么设计"

- **为什么经服务造数、不直连 SQL**：状态机、BR 校验、跨应用弱引用都走真实路径，
  造出来的数据**天生合法**；顺带等于跑了一遍端到端演练（写错了服务会立刻给人话报错）。
- **为什么需要 `verify_demo.py` 这个哨兵**：环境没造好时最坏的失败模式是
  「agent 说没有要处理的、ground truth 也是没有 —— **两边一致地错，测试照样绿**」
  （这条是从 `scripts/verify_agent_quality.py` 学来的）。所以体检**按身份**校验、不按数量，
  不过就明确报「不是演示环境，请先跑 demo_build.py」，而不是让调用方把环境问题读成"业务上确实没有"。
  `rc=2` 的口径与 PSC 的 eval 一致。
- **为什么不用停 dev server**（与 PSC 的 `宣传/demo_build.py` 的差别）：PSC 那个走 dbguard **移库**
  所以必须先停服；本脚本是**普通写业务库**，SQLite/WAL 支持并发写。只是演示期间别在浏览器里
  同时改同一批数据（会撞 BR 校验，报错倒是会明确指出来）。

## 已做 / 未做

### ⑩⑪ 已落地（2026-09-25 起，本节 2026-09-27 订正 —— 此前这里写着"未声明"，是过期的）

- **角色声明**：`_roles.py` 4 个角色（需求与验证工程师 / 风险与度量分析师 / 配置与变更管理员 /
  技术计划与评审主管），覆盖 13 个应用；每个角色绑定的应用都有 `HOWTOUSE.md`（没有就会**静默不注入**）。

  实施 → 发版 / **发射链排程 → 体检 → 基线 → 回填实绩** / 度量超阈值 → 告警 → 纠正 → 复测 → 关闭 /
  WBS 分解 → 覆盖对账 → 基线 → 变更）。入口在「流程总览」页每行的「让 AI 管家跑」。
- **技能库 / 定时任务 / 集成接口**仍**没有**对应产物（这三样是平台资产，不属于本组的业务故事线）。
- **智能体质量 eval**（`scripts/verify_agent_quality.py`）目前**不覆盖本组**：它的场景与写服务清单
  是 PSC 专属（写死 `psc__…` 工具名 + 按身份校验 7 个物料），组名虽可配
  （`FDE_AGENT_QUALITY_GROUP`）但**没有 nasa_pms 的场景**。要给本组配质量门禁，得先有数据（本目录
  已具备）再写场景 —— 这是一件独立工作。
- **知识库**：本组的 LightRAG 索引已建（`app/nasa_pms/kg_config.json` + `config/kg_storage/nasa_pms/`），
  用前需起嵌入服务：`python -m fde_platform.embed_service`。
