## 3. 交互规则（逐条对应后端约束）

| # | 规则 | 依据 |
|---|---|---|
| F-1 | 新建表单里**名称 / 计划类型 / 覆盖阶段三项必填**，未齐时提交按钮禁用；**类型与阶段都不给默认值** —— 它们就是 I-1「计划与阶段绑定」的那两个键，不该被默认值悄悄替人做主 | `BR-02` + 非空校验 |
| F-2 | **「草稿」与「已修订」内容可写**（名称 / 类型 / 阶段 / 成熟度 / 范围 / 责任人）；**「审批中」与「已批准」只读** —— 且**报错文案点名各自的解锁入口** | `BR-05` —— **本页与同组其它页的语义差**，见 §7 第 1 条 |
| F-3 | 两条锁定路径**互不混淆**：`frozenText()` 分两套文案（审批中 → 「先撤回」；已批准 → 「修订出下一版」）；页脚按状态只给**那一条**路径的动作 | `BR-05` 的两半（`withdraw` vs `revise`） |
| F-4 | 「提交审批」二次确认（**提交后内容即锁定**，审批对着的必须是定下来的那一版）；行内与页脚都可发起 | `US-02` / §4.3.2 |
| F-5 | 「撤回」是**审批中唯一可退回**的动作，且回到**提交前那一态**（`V1` → 草稿、`V2+` → 已修订）—— 撤回后 `V2` 的新版没有被丢掉 | `US-04` / §3.4 的撤回口径 |
| F-6 | 「批准」是**独立模态**：批准人**必填**（未填时按钮禁用），并提示"批准后这一版进版本台账" | `BR-08` |
| F-7 | 批准被 I-1 拦下时**模态不关闭、状态不变**（错误经 `api.js` 的 toast 呈现）—— 页面**不预判**哪一格已被占（判定权威在后端） | `BR-03`（I-1） |
| F-8 | 「修订」是**独立模态**：修订说明必填；可携带「推进到阶段」与「成熟度」（不选＝沿用当前）；模态里给出「当前 V1 → 修订后成为 V2」的提示 | `BR-06` + `BR-04`（I-2 的版本递增） |
| F-9 | 版本台账随详情**一次取回**（`get` 带 `versions`，不做二次请求）；提交 / 批准 / 撤回 / 修订后若详情开着，**重取一次详情** | `get` 返回 `versions`；台账变了详情不刷新会前后不一致 |
| F-10 | 覆盖卡片按**阶段**用 `fchip` 收敛（默认「全部阶段」= 48 格）；每格给「已覆盖 / 缺口」徽标 + 覆盖来源（**此刻生效** / **历史版本** + 计划编号与版本）与计划数；该卡片是**只读查询视图**，无行内写动作 | `coverage` 是查询视图；缺口是**事实**不是错误（`应用详设.md` §6.3） |
| F-11 | 行内动作**按状态显隐**：草稿 / 已修订 → [编辑][提交审批]；审批中 → [批准]；已批准 → [修订]；详情页脚另有 [撤回] | 状态机（§3.4 到达服务表） |
| F-12 | 四个筛选控件变化即刷新（下拉 `@change`、输入 `@keydown.enter`；重置到第 1 页）；列表默认按编号升序 | `US-07` |

## 7. 已知限制

- **⚠ 本页没有硬终态，两条锁定路径各有解锁入口**（本页与同组其它页最容易照抄错的地方）：
  - 同组 `review` / `configuration_item` / `technical_measure` 都有 `locked()`（`status === 'closed'`
    之类）——"到达即锁死、无解锁入口"；
  - 本页的状态机是**环**：`已修订 → 审批中 → 已批准 → 已修订 → …`。锁的是两个**过程态**，
    且各有入口：「审批中」→ **撤回**（退回提交前那一态）、「已批准」→ **修订**（**版本递增**）。
  - 照抄 `locked()` 会同时错两处：**已批准改不了**（其实该走修订）与**"永远锁死"**（其实能出下一版）。
  模板里所有读 `modal.d` 的地方都走 `isStatus / inStatus / stName / stCls / editable /
  canSubmit / canApprove / canWithdraw / canRevise / frozenText / headText` 这层空安全 helper，
  **不写裸取值**（理由见 `view.js` 的空安全注释与 `前端测试用例.md` §15 的坑 1）。
- **模态里所有枚举下拉都用静态 `<option>`** —— 本页的「计划类型」「覆盖阶段」「成熟度」三条都要
  **由数据回填**（`openDetail` 后写 `modal.d.plan_type` / `phase` / `maturity`）。
  用 `x-for` 生成选项时这个回填会**静默停在第一项**（Alpine 的 effect 跑在选项插入之前、
  此后不再重跑）—— 页面不报错、只是修订/编辑改错值。**筛选区的三个下拉也一并写成静态的**，口径统一。
- **筛选控件与模态字段一律带 `data-role`**（`f-type` / `f-phase` / `f-status` / `m-type` …）而不是
  靠 `select:visible` 的 `nth` 下标定位 —— 平台壳的 Agent 右栏自带一个会话选择器，
  数总数会被壳的实现变更搞红、按下标会**静默筛错维度**（同组 `technical_measure` 的坑 1）。
- **「批准」没有"否决"分支** —— 后端状态机没有「已拒绝」态，不认可就走「撤回」
  （退回编制方修改）或干脆不批。这符合材料的口径：§6.1.1.2.5 的 buy-in 是"拿到承诺"，
  没拿到时计划**停在那里**（在覆盖矩阵里就是一个缺口），不需要一个"被否决"的记录。
- **页面不预判 I-1** —— 点「批准」前不检查同阶段同类型是否已有生效版本（那要么多发一次
  `coverage` 查询、要么把判定逻辑复制到前端）；被拒时把后端的话原样弹出（`BR-03` 的判定权威在后端）。
- **撤回只在详情页脚**（行内没放）—— 行内按钮已经 4~5 个，撤回是低频且"改主意"性质的动作，
  放在详情里更不容易误点。
- **覆盖卡片是只读的** —— 缺口是**事实**不是错误（`应用详设.md` §6.3：「至少一份」不可被同事务强制），
  所以这张卡片没有行内动作，只有阶段筛选。
- **新建表单不给「计划类型」「覆盖阶段」默认值** —— 有意为之：默认值会让人在无意间把计划
  挂到错阶段上，而这两个键恰恰是 I-1 的全部（"计划与阶段绑定"）。
- **组级 `_contracts.md` 尚未冻结本应用** —— 本页的服务名 / 入参**逐字取自 `tech_plan.py`
  的公共方法签名**（`create` / `submit` / `approve` / `withdraw` / `revise` / `update` /
  `get` / `list` / `coverage`）；契约冻结应由第⑤步出口的统一 dump 完成
  （本任务范围不含改 `_contracts.md`）。
