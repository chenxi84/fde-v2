# tech_plan 使用要点

**管什么**：技术计划台账 —— 计划类文档（SEMP、验证与确认计划、集成计划、技术开发计划、HSI Plan、风险管理计划、评审计划、配置管理计划）的统一登记与审批，以「计划类型 + 覆盖阶段」区分。回答「这个阶段有哪些计划、生效的是第几版、谁批的、还缺哪类计划」用它。

## 标准工作流（按此顺序）

1. `create` — 建计划，落「草稿」、版本 `V1`，编号自动生成（`PLAN-001` 起）；名称 / 计划类型 / 覆盖阶段必填，成熟度缺省「方法」
2. `update` — 定稿前改内容（名称 / 类型 / 阶段 / 成熟度 / 范围 / 责任人 / 所属项目）
3. `submit` — 提交审批：草稿 / 已修订 → **审批中**，内容自此锁定
4. `approve` — 批准：审批中 → **已批准**。必传批准人；**同一次调用**往版本台账落一行快照（版本 / 阶段 / 成熟度 / 批准人 / 意见），并拒绝"同阶段同类型已有另一份已批准"
5. `revise` — 修订：已批准 → **已修订**、**版本递增**，必给修订说明；可顺带推进覆盖阶段 / 成熟度
6. `coverage` — 看「阶段 × 计划类型」覆盖矩阵，KDP 前找缺口

核对用：`list`（按类型 / 阶段 / 状态 / 责任人筛）→ `get`（含台账明细）。

## 前置条件与禁忌

- **状态闸**：`update` 只认草稿 / 已修订；`approve` 只认审批中；`revise` **只认已批准**（报「只有已批准的计划才能修订」）；`withdraw` 只认审批中。
- **两个锁定态各有唯一解锁入口**：审批中要改先 `withdraw`；已批准要改走 `revise`（**不是** `update`）。
- **守卫顺序**：`approve` 先查批准人非空（批准要记名），再查同阶段同类型唯一 —— 看报错哪条就知道先缺哪个。
- **台账是快照**：台账行记的是"批准当刻"的版本 / 阶段 / 成熟度，**只增不改**，`revise` 不动旧行。`version_total` / `latest_approved_ver` / `latest_approver` 由台账推导，不可填。
- **撤回回到哪一态是推断的**：`V1` 回「草稿」、`V2` 及以后回「已修订」；撤回**不改版本号、不落台账行**。
- 字典：计划类型 `semp/verification/integration/technology_dev/hsi/risk_mgmt/review/cm`（**项目计划不在内** —— 它是技术计划的上位）；阶段 `pre_a/a/b/c/d/e`；成熟度 `approach/preliminary/baseline/update`，其中「更新」**以已有获批版本为前提**，否则直接报错。
- 编号 / 版本 / 状态 / 修订说明**不在 `update` 的字段白名单里**（流转产物，没有参数可传）。
- **本页没有硬终态**：已修订 → 审批中 → 已批准 是一条**环**，可无限循环，别当一次性流程。
- 「至少一份」只落在 `coverage` 视图上：`approve` 拦得住"第二份已批准"，拦不住"这个阶段还缺 SEMP"（缺计划的格子没有记录可拦）。
- `get` 未命中返回 `None`，不抛异常。

## 出错时

不确定某条服务怎么调、或报错看不懂时，先 `platform_read_app_doc(app="nasa_pms/tech_plan", doc="应用详设")`
读本应用详设（`doc` 取值见 `fde_platform/agent_common.py::_APP_DOC_FILENAMES`）；
**不要凭猜重试**——本应用的报错话术里都写着"缺哪一步"。
