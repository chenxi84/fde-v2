# 新增术语（应用级回填）：技术计划 tech_plan

> **为什么单独一个文件**：组级 `app/nasa_pms/术语表.md` 是本组**业务名唯一来源**，
> 但本轮多个应用并行产出，直接改那份会互相覆盖。故本应用第②步新增的业务名先落在这里，
> **格式与组级表一致（三列）**，由组级统一任务合并回 `术语表.md`（合并时按原词去重即可）。
> 列义同组级表：`原词` = 材料里的写法（可直接检索回原文）；`语境 / 所属类型` = 消歧用；
> `业务名` = 全链路使用的正式名（中英并列）。

## 6. 就地细化的说明（诚实记录）

材料给了**计划类型清单**（§6.1.1.2.4 + 附录 K TABLE K-1）、**成熟度图例**（A/P/B/U）、
**更新节奏**（"updated throughout the project life cycle"、"at every KDP"），以及
§6.1.1.2.7 的"计划置于配置控制之下"。以下六处是第②步的**工程口径**，无原文可逐字引：

1. **「成熟度」是一个可写字段** —— 附录 K TABLE K-1 是一张"**期望**成熟度"的表（"a typical
   **expectation** of maturity"），本应用只记"**实际**标的是什么"，**不做**"到 PDR 就该是 B"的
   自动推导（那需要把整张期望矩阵入库）。本字段把那张表的行内信息变成可查询的数据。
2. **覆盖矩阵的字段口径**（`covered` / `covered_by` / `plan_count` / `approved_no` /
   `approved_ver` / `approved_maturity`）—— 材料只有那张**表格**，没有查询口径。
   本版按"**先看此刻已批准、再看台账曾获批**"两支来判定一格是否被覆盖：
   后者正是 I-2「历史版本保留」的用处 —— 计划推进到 B 阶段后，A 阶段那一格靠台账里的 `V1` 仍算覆盖。
3. **「同一阶段同一类型只允许一份已批准」（`BR-03`）是 I-1 的推论，不是原文** ——
   I-1 写的是"**至少**一份"，本版把它补成"**恰好**一份"：两份都生效时，
   "该阶段该类的计划是哪一份、成熟度按哪份算"就没有答案（附录 K 每格只有一个字母）。
   可强制的那一半（唯一）放在 `approve` 的同事务守卫里；不可强制的那一半（至少）放在
   `coverage` 视图上 —— **见 `应用详设.md` §3.2.3 与 §6.3 的分工说明**。
4. **「撤回审批」（`withdraw`）是补的状态迁移** —— 卡片 10 的状态机只写了
   `草稿 → 审批中 → 已批准 → 已修订`。没有撤回，「审批中」就是一个**死结**（不批就永远出不来），
   所以本版补上，并让"回到哪一态"由 `version` 推断（`V1` → 草稿、`V2+` → 已修订），
   使撤回**不丢信息**（不额外存"提交前的状态"）。
5. **「更新」（`U`）成熟度以已有基线版本为前提（`BR-07`）** —— 从图例语义推出：
   `U = Update` 指"对**已存在**的计划做更新"，一份从未获批的计划没有"旧"可更。
6. **计划类型不含「项目计划」** —— §6.1.1.2.4："The SEMP is a **subordinate document to the
   project plan**"：项目计划是上位文档，不是技术计划之一（术语表也把它列在「单据」而非「计划类」）。
   同理，附录 K 里的 `Integrated Logistics Support Plan` / `Mission Operations Plan` /
   `Decommissioning Plan` 等**未收入本版字典**（它们分属后勤 / 运行 / 退役等专业管理，
   不是 §6.1.1.3 Outputs 意义上的"支持技术努力实施"的技术计划）。

> 与同组其它应用的处理方式一致：材料没给字段口径的，就地细化并**在此登记**，
> 不假装它是原文（参见 `technical_measure/新增术语.md` §5 对优化方向与告警字段的同类说明）。
