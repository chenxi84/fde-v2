## 1. 技术计划概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `tech_plan` |
| 类名 | `TechPlan` |
| 聚合根 | 技术计划 |
| 标识 | `plan_no`（`PLAN-<三位序号>`） |
| 数据来源类型 | **独立创建**（计划由技术团队编制，无上游单据自动生成） |
| 聚合内子表 | `plan_version`（版本台账）—— **无独立标识**，随本聚合同事务维护 |
| 跨应用调用 | **无**（卡片 10 的「跨应用调用：无」；阶段以枚举属性承载，不独立成聚合） |

> **「技术计划」是一类文档的统一管理，不是一个文档。** 卡片 10 的原话是「计划类文档
> （SEMP、验证计划、集成计划…）的统一管理」，以**计划类型**属性区分 —— 所以本聚合的
> 实例是「一份计划文档」，它的 `plan_type` 决定它是 SEMP 还是集成计划。

### 1.2 技术计划背景

#### 1.2.1 为什么需要这个聚合根？

材料把「技术规划」放在**共性技术管理的最前面**（第 06 章 §6.1），因为它是其余过程的**上游**：

> "the Systems Engineering Management Plan (SEMP) and other technical plans are developed and
> baselined. Once the SEMP and technical plans have been established, they should be **synchronized
> with the project master plans and schedule**."

而 §6.1.1.3 Outputs 明确这批计划是**发给所有其它过程**的：

> "**SEMP and other technical plans**: Technical planning strategy, WBS, SEMP, HSI Plan, V&V Plan,
> and other technical plans that **support implementation of the technical effort (to all processes;
> applicable plans to technical processes)**."

计划的「类」由 §6.1.1.2.4 与附录 K 给出：SEMP 是**顶层**那一份（"The SEMP is the primary,
top-level technical management document for the project"），其余计划与它**并列且从属**：

> "Other plans, such as system safety, probabilistic risk assessment, and an HSI Plan also need to be
> planned for and coordinated with the SEMP. … The project SEMP is the senior technical management
> document for the project; **all other technical plans should comply with it**."

「一份计划会随生命周期**一版一版往上走**」这件事写在 §6.1.1.2.4 与附录 K：

> §6.1.1.2.4: "developed early in the Formulation Phase and **updated throughout the project life
> cycle**."
> §6.1 开篇: "As the system matures and progresses through the life cycle, these plans should be
> **updated as necessary** to reflect the current environment and resources … At a minimum, these
> updates will occur **at every Key Decision Point (KDP)**."
> 附录 K TABLE K-1 的图例："A = Approach / B = Baseline / P = Preliminary / U = Update" ——
> 同一份 SEMP 在 Pre-Phase A 标 `P`、Phase A（SRR）标 `B`、其后各阶段一律 `U`。

现状是计划散在共享盘与邮件里：**哪个阶段该有哪些计划**没人说得清，**现在生效的是第几版**要靠翻
文件名（`SEMP_v3_final_改.docx`），**谁批的**只在会议纪要里提一句。本聚合把这三件事收进一个事务
边界：**计划（类型 × 阶段 × 成熟度）+ 版本台账 + 审批留痕**。

#### 1.2.2 期望达到什么目标？

- 每份计划**有唯一编号**（`plan_no`）、**绑定一个覆盖阶段**与一个**计划类型** ——
  「计划与阶段绑定」是卡片 I-1 的前半（§1.3 的落点说明）
- **同一阶段同一类型只允许一份「已批准」的计划**（I-1 的「生效唯一」面，`approve` 同事务拦截）——
  否则"该阶段该类的计划是哪一份"没有答案
- **一屏看到哪个阶段还缺哪类计划**（I-1 的「至少一份」面）—— 覆盖矩阵是查询视图，
  正对应附录 K TABLE K-1 那张「计划 × 阶段 × 成熟度」的表
- **版本随阶段推进递增，历史版本保留**（卡片 I-2）：`revise` 是唯一的版本递增入口，
  每批准一版在台账里留一行**快照**（版本 / 阶段 / 成熟度 / 批准人 / 审批意见），不回溯改写
- **批准要记名**（谁批的、批的是第几版），且**审批中与已批准的内容都锁定** ——
  锁定的两个状态**各有解锁入口**（撤回 / 修订），不把"锁定"变成"锁死"

### 1.3 技术计划范围

#### 1.3.1 包含哪些功能？

- 计划的建立、修改、查询、列表（`create` / `update` / `get` / `list`）
- **状态机流转**：`submit`（提交审批）/ `approve`（批准，记名 + 落版本台账）/
  `withdraw`（撤回，退回提交前状态）/ `revise`（修订，版本递增 + 可推进阶段）
- **版本台账**（聚合内子表）：每批准一版落一行快照，供追溯"当初承诺的是哪一版"
- **阶段覆盖矩阵**（查询视图 `coverage`）：阶段 × 计划类型的覆盖与缺口（卡片 I-1 的可见面）
- 与**评审**（`review`，评审依据的计划）、**变更请求**、**配置项**的关系：本应用是**被引用方**
  （`review.plan_no` 弱引用本应用的编号），本应用**不发跨应用调用**（卡片 10）

#### 1.3.2 不包含哪些功能？

- **不展开每份计划的章节内容** —— 附录 H（集成计划提纲）、附录 I（V&V 计划提纲）、
  附录 J（SEMP 提纲）、附录 M（CM 计划提纲）、附录 R（HSI 计划提纲）给的是**目录与写作要点**，
  本应用管的是"**这份计划本身**"（类型 / 阶段 / 成熟度 / 版本 / 审批 / 覆盖），
  不把提纲的章节落成字段。正文属**技术数据管理**（§6.6）与**配置管理**（§6.5）的范畴：
  §6.1.1.2.7 说得很清楚 —— "Some of the more important products of technical planning (i.e., the
  WBS, the SEMP, and the schedule, etc.) are **kept under configuration control** and captured
  using the CM process."
- **不做计划正文的版本控制**（配置项那条路）—— 本应用的"版本"是**计划的版本**（V1/V2…与它的
  获批快照），不是配置项的版本；两者同族但事务边界不同（聚合根卡 3 vs 卡 10）。
- **不做 WBS / 进度 / 成本**（§6.1.1.2.2 Define the Technical Work、§6.1.1.2.3 Schedule, Organize,
  and Budget、§6.1.1.2.6 Issue Technical Work Directives）—— 那是项目管理与 EVM 的范畴，
  `architecture.md` §⑤ 待确认表第 1 条也把 WBS 列在待确认里。
- **不做「阶段」本身的实体** —— 阶段是计划的**枚举属性**（卡片 10「引用的聚合：无」+
  关键设计决策 3"阶段不独立成聚合"）。
- **不做跨阶段的计划推进编排**（"到了 PDR 就自动推进全部计划"）—— 那要一个流程引擎，
  且**没有可拒绝的写入动作**；本版把推进留在人手上（`revise` 携带新阶段）。
- **不做变更请求联动** —— 卡片 10 写明「跨应用调用：无」，故 `revise` **不**要求携带变更请求号。
  §6.1 说的是"if there is a significant change in the project … all plans should be analyzed for the
  impact"，那是**影响分析**这一动作，不是"改计划必须挂 CR"（§6.5.1.2.3 的变更控制在配置项一侧）。
  见 §6.3 的已知限制。

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 系统工程师 | 编制计划（`create` / `update`）、提交审批、修订出下一版 | 材料 §6.1.1.2.4（SEMP 与技术计划由系统工程师主导编制） |
| 项目 / 技术管理层 | 批准计划（`approve`，记名）；关注覆盖矩阵 | 材料 §6.1.1.2.5「Review of these plans … constitutes **buy-in** from the stakeholders to the technical content」 |

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 建一份技术计划（优先级：P1）

**作为**一名系统工程师
**我希望**登记一份计划（名称、计划类型、覆盖阶段、成熟度、范围、责任人）
**以便**它进台账被跟踪，而不是散在共享盘里

**验收条件**：
- 给定名称 / 类型 / 阶段齐备，当提交时，则新计划以「草稿」状态落库、版本 `V1`，编号自动生成（`PLAN-001` 起）
- 给定类型或阶段填了字典外的值，当提交时，则**拒绝**（`BR-02`）
- 给定名称或类型或阶段为空（含全空白），当提交时，则**拒绝**并提示「…不能为空」
- 给定成熟度填了字典外的值，当提交时，则**拒绝**（`BR-07`）
- 给定**从未获批过任何版本**的计划却标成熟度「更新」，当提交时，则**拒绝**（附录 K 图例 U = Update）

#### 2.1.2 `US-02` 用户故事 — 提交审批（优先级：P1）

**作为**一名系统工程师
**我希望**把定稿的那一版提交给管理层批
**以便**审批对着的是一份**定下来的**计划，而不是随时会变的草稿

**验收条件**：
- 给定草稿 / 已修订的计划，当提交时，则状态变「审批中」，**内容自此锁定**
- 给定审批中改内容，当提交时，则**拒绝**并指向 `withdraw`（`BR-05`）
- 给定已批准的计划，当再提交时，则**拒绝**并指向 `revise`（要改就出下一版）
- 给定审批中的计划，当重复提交时，则**拒绝**

#### 2.1.3 `US-03` 用户故事 — 批准（优先级：P1）

**作为**一名项目 / 技术管理层
**我希望**批准这一版并留下"谁批的"
**以便**"当前生效的是哪一版、谁批的"有确定答案

**验收条件**：
- 给定审批中的计划 + 批准人，当批准时，则状态变「已批准」，且**同一次调用**在版本台账落一行快照（`I-2` / `BR-04`）
- 给定批准人为空（或全空白），当批准时，则**拒绝**（`BR-08`）
- 给定**同一阶段同一类型已有另一份已批准**，当批准时，则**拒绝**并点名那一份（`I-1` / `BR-03`）
- 给定草稿 / 已修订 / 已批准的计划，当批准时，则**拒绝**（须先提交 / 不能重复批准）
- 被拒的批准**不留任何痕迹**（状态与版本台账都不变）

#### 2.1.4 `US-04` 用户故事 — 撤回审批（优先级：P1）

**作为**一名系统工程师
**我希望**审批没通过时能把计划退回来改
**以便**不必"要么批要么僵着"

**验收条件**：
- 给定审批中的计划，当撤回时，则回到**提交前的状态**（`V1` 回「草稿」、`V2` 及以后回「已修订」）
- 给定草稿 / 已修订的计划，当撤回时，则**拒绝**（「不在审批中，无需撤回」）
- 给定已批准的计划，当撤回时，则**拒绝**（要改走 `revise`）
- 撤回**不改版本号**、**不产生台账行**（没有产生任何被批准的版本）

#### 2.1.5 `US-05` 用户故事 — 修订出下一版（优先级：P1）

**作为**一名系统工程师
**我希望**在阶段推进或内容确需更新时，出一版**新的**（而不是原地改已批准的那一版）
**以便**"当初承诺的是哪一版"永远可追溯

**验收条件**：
- 给定已批准的计划 + 修订说明，当修订时，则状态变「已修订」、**版本递增**（`V1 → V2`），
  可选把覆盖阶段 / 成熟度一起推进（`I-2` / `BR-04`）
- 给定修订说明为空，当修订时，则**拒绝**（版本因何而升要留痕）
- 给定草稿 / 审批中的计划，当修订时，则**拒绝**（改内容走 `update`，不动版本号）
- 给定已修订的计划，当再修订时，则**拒绝**（不能连续修订 —— 先提交或直接 `update`）
- 修订后**旧的台账行不变**（`V1` 仍是"当时批的 V1@A 阶段·初步"）

#### 2.1.6 `US-06` 用户故事 — 修改计划内容（优先级：P2）

**作为**一名系统工程师
**我希望**在计划还没定下来的时候（草稿 / 已修订）修名称、类型、阶段、成熟度、范围、责任人
**以便**纠正登记错漏

**验收条件**：
- 给定草稿 / 已修订的计划，当修改时，则成功（成熟度仍受 `BR-07` 约束）
- 给定审批中 / 已批准的计划，当修改时，则**拒绝**，且报错文案**点名各自的解锁入口**（`BR-05`）
- 给定一次不带任何字段的 `update`，则**拒绝**（「没有要修改的内容」）
- 版本号 / 状态 / 修订说明**不在字段白名单里**（传进去由契约层拦下）—— 它们是流转产物

#### 2.1.7 `US-07` 用户故事 — 查询计划列表、详情与版本台账（优先级：P2）

**作为**一名技术人员 / 评审主持人
**我希望**按类型 / 阶段 / 状态 / 责任人筛选，并看到某份计划的**版本台账**
**以便**回答"这个阶段有哪些计划""现在生效的是第几版""谁批的"

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序），**分页返回 `{items, total}`**；
`get` 返回主档 + 版本台账（子表随聚合一起返回），未命中返回 `None` 不抛异常；
`list` 与 `get` 的主档字段与三个派生计数（`version_total` / `latest_approved_ver` /
`latest_approver`）**同口径**。

#### 2.1.8 `US-08` 用户故事 — 看阶段覆盖矩阵（优先级：P2）

**作为**一名项目经理 / 系统工程师
**我希望**一屏看到"每个阶段 × 每个计划类型"里**有没有已批准的计划**
**以便**在 KDP 之前知道**还缺哪些计划**（而不是等评审会上被问住）

**验收条件**：`coverage` 按 `phase` / `plan_type` 过滤、分页返回 `{items, total}`；每格给出
`covered`（0/1）、`covered_by`（`current` 此刻生效 / `history` 历史版本 / 空 = 缺口）、
`plan_count`（此刻声明覆盖该阶段的该类计划数）、`approved_no` / `approved_ver` / `approved_maturity`。

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 一份计划的一生（对齐状态机）

1. 系统工程师按阶段需要建计划（材料 §6.1.1.2.4：SEMP "developed early in the Formulation Phase"）
   —— `create` → 草稿（`draft`）、`V1`
2. 编制过程中反复改（`update`）—— 草稿态内容自由
3. 定稿提交 —— `submit` → 审批中（`in_review`），**内容自此锁定**（审的就是这一版）
4. 管理层不认可 → `withdraw` → 回草稿（改完再来）；认可 → `approve`（记名）
   → 已批准（`approved`），**同一次调用**落一行版本台账（`V1@A 阶段·初步`）
5. 阶段推进到 B（材料 §6.1.1.2.4："updated throughout the project life cycle"；附录 K 的 P → B）
   —— `revise`（说明 + 新阶段 + 新成熟度）→ 已修订（`revised`）、`V2`；旧的 `V1` 行**留在台账里**
6. 再提交、再批准 —— `V2@B 阶段·基线` 进台账（**历史版本保留**：两版都在）
7. 需要时继续下一轮修订（`V3`…）—— 这条链**没有终点**（本页没有硬终态）

#### 3.1.2 场景2: KDP 前的覆盖盘点（材料附录 K TABLE K-1 的用法）

1. 项目经理打开「阶段覆盖」，选 `B 阶段` → 8 格里 3 格"已覆盖"、5 格"缺口"
2. 其中「集成计划」那格 `plan_count=1` 但 `covered=0` —— **有计划但还没批**（停在审批中）
3. 找集成计划的负责人提交 / 批准，缺口补上（`covered_by=current`）
4. **阶段推进过的计划**由台账覆盖：`SEMP` 在 A 阶段的格子 `covered_by=history`、
   指向 `PLAN-001 V1` —— 这正是附录 K TABLE K-1 里"同一份计划在多个阶段各占一格"的读法

### 3.2 业务规则

#### 3.2.1 `BR-01` 计划编号唯一且不可变

- **规则描述**: `plan_no` 系统生成（`PLAN-` + 三位序号）、落库后不得修改
- **适用场景**: 创建、修改
- **计算方式**: 唯一性校验（取当前最大序号 +1）
- **依赖输入**: `[plan_no(实体字段)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `tech_plan.create`（生成）/ `update`（**字段白名单里没有编号**，无从改起）
- **示例**: `update(plan_no="PLAN-001", plan_no="PLAN-900")` → 该参数不存在（`TypeError`），服务不接受
- **依据**: 材料 §6.1.1.2.7 "Capture Technical Planning Work Products"（计划要可追溯，前提是有唯一标识）；
  与同组其余页的编号规则同源口径

#### 3.2.2 `BR-02` 计划与阶段（类型）绑定、受字典约束

- **规则描述**: `plan_type ∈ {semp, verification, integration, technology_dev, hsi, risk_mgmt,
  review, cm}` 且**必填**；`phase ∈ {pre_a, a, b, c, d, e}` 且**必填**；两者都不给默认值
- **适用场景**: 创建、修改、修订（推进阶段）
- **计算方式**: 非空校验 + 字典校验（**先 `_clean` 再判空再查字典**）
- **依赖输入**: `[plan_type / phase(实体字段与服务实参)]`
- **输出**: `tech_plan.plan_type` / `phase`
- **生效点**: `tech_plan.create` / `update` / `revise` → 校验
- **示例**: `create(..., plan_type="其它")` → 拒绝「计划类型只能是 semp/verification/…之一（BR-02）」；
  `create(..., phase="  ")` → 拒绝「覆盖阶段不能为空 —— 计划与阶段绑定（I-1 / BR-02）」
- **依据**: 卡片 10 的 I-1「计划与阶段绑定」；计划类型清单取自 §6.1.1.2.4 + 附录 K TABLE K-1
  （"Examples of technical plans in addition to the SEMP are listed in Appendix K"）；
  阶段清单与同组 `review` 同口径（术语表的 Pre-Phase A..Phase E）
- **⚠ 计划类型为什么不含「项目计划」**：§6.1.1.2.4 明确 "The SEMP is a **subordinate document to the
  project plan**" —— 项目计划是技术计划的**上位**，不是技术计划之一（术语表把「项目计划（Project Plan）」
  列在「单据」而不是「计划类」）。

#### 3.2.3 `BR-03` 同一阶段同一类型只允许一份已批准的计划（卡片 I-1 的「生效唯一」面）

- **规则描述**: `approve` 时，若 `(plan_type, phase)` 下已有**另一份**状态为「已批准」的计划，则拒绝
- **适用场景**: 批准
- **计算方式**: 同表查询 + 拒绝（**同事务**：与状态变更、台账写入在同一次调用内）
- **依赖输入**: `[plan_type / phase / status(实体字段)]`
- **输出**: `tech_plan.status`（被拒时不落库）
- **生效点**: `tech_plan.approve → _check_phase_unique`
- **示例**: `PLAN-002`（verification@A）已批准时批准 `PLAN-007`（同为 verification@A）→ 拒绝
  「同一阶段同一类型只允许一份生效（I-1 / BR-03），要换计划请修订那一份（版本递增）」
- **依据**: 卡片 10 的 I-1；附录 K TABLE K-1 每格只有一个成熟度字母 —— 若某格有两份都生效，
  "该阶段该类的计划是哪一份、成熟度按哪份算"就没有答案
- **⚠ 与 I-1 的「至少一份」面的分工**（本页最关键的设计取舍）：
  「至少一份」是**集合层面的事实**，它**没有可拒绝的写入动作** —— 缺计划的阶段没有任何一条记录
  可以被拿来拦截，所以它只能落在**查询视图**（`coverage`）上把缺口**显出来**。
  这与同组 `technical_measure` 把卡片 I-1 拆成「同事务写告警」+ `list_alerts` 视图**同构**。

#### 3.2.4 `BR-04` 版本只增不减、历史版本保留（卡片 I-2）

- **规则描述**:
  - `revise` 是版本递增的**唯一**入口（`V1 → V2 → …`），且**只能从「已批准」发起**；
  - 每次 `approve` 在**同一次调用**里往 `plan_version` 落一行快照
    （`version` / `phase` / `maturity` / `approver` / `note`）；
  - 台账行**不回溯改写**：计划推进到新阶段后，旧阶段那一行仍是当时的快照
- **适用场景**: 修订、批准
- **计算方式**: 写入型（版本 = 当前 + 1）+ 追加型（台账只 INSERT，无 UPDATE 路径）
- **依赖输入**: `[version / phase / maturity / status(实体字段), approver / note(服务实参)]`
- **输出**: `tech_plan.version` / `status`；`plan_version`（新增一行）
- **生效点**: `tech_plan.revise` / `approve`
- **示例**: `PLAN-001` 在 A 阶段批 `V1`（初步）→ `revise(phase="b", maturity="baseline")` →
  `V2`；台账仍是 `[V1@a/preliminary, V2@b/baseline]` 两行
- **依据**: 卡片 10 的 I-2；§6.1.1.2.4 "developed early in the Formulation Phase and **updated
  throughout the project life cycle**"；§6.1.1.2.7 计划"**kept under configuration control**"
  （配置控制的题中之义就是版本与历史）；附录 K TABLE K-1 的 P → B → U 逐阶段演进

#### 3.2.5 `BR-05` 状态守卫：审批中与已批准内容锁定，各有解锁入口

- **规则描述**:
  - 「审批中」：`update` / `revise` **拒绝**，`submit` **拒绝**；解锁入口是 **`withdraw`（撤回）**
  - 「已批准」：`update` / `submit` / `withdraw` / 重复 `approve` **拒绝**；解锁入口是 **`revise`（修订）**
  - 「草稿」/「已修订」：`update` **允许**；`approve` **拒绝**（须先提交）；`withdraw` **拒绝**
- **适用场景**: 修改、提交、批准、撤回、修订
- **计算方式**: 校验型（按状态拦截；守卫顺序：**最"往前走不回去"的状态排最前**）
- **依赖输入**: `[status(实体字段)]`
- **输出**: `tech_plan.status`
- **生效点**: `tech_plan.submit` / `approve` / `withdraw` / `revise` / `update`
- **示例**: 对已批准的 `PLAN-002` 调 `update(name=…)` → 拒绝「内容不可直接修改 —— 要改请「修订」
  （revise）出下一版（BR-04 / BR-05）」；对审批中的 `PLAN-003` 调 `update` → 拒绝「要改请先 withdraw 撤回」
- **依据**: 步骤 4 的口径（审批对着的必须是定下来的那一版）+ 规则 2.3.4 的版本语义；
  §6.1.1.2.5 "Review of these plans and the agreements from the stakeholders to the content of these
  plans constitutes **buy-in**" —— 批的是**那一版的内容**，内容变了批的就不是同一个东西
- **⚠ 与同组其它页的语义差（照抄样板会漏）**：本页**没有硬终态**。`review` / `configuration_item` /
  `technical_measure` 都有一个"到达后一律拒"的状态（已关闭 / 已发布…），本页的状态机是**环**：
  `已修订 → 审批中 → 已批准 → 已修订 → …` 可以无限循环。照抄 `locked()`（`status === 'closed'`）
  会同时错两处：**已批准改不了**（其实该走 `revise`）与**"永远锁死"**（其实能出下一版）。

#### 3.2.6 `BR-06` 修订只能从「已批准」发起，且必须给修订说明

- **规则描述**:
  - `revise` 只接受 `status = approved`；草稿 / 审批中 → 拒绝（改内容走 `update`，不动版本号）；
    已修订 → 拒绝（不能连续修订）
  - `summary`（修订说明）**必填**（空白即拒）
- **适用场景**: 修订
- **计算方式**: 状态守卫 + 非空校验（顺序：状态 → 说明 → 阶段字典）
- **依赖输入**: `[status(实体字段), summary / phase / maturity(服务实参)]`
- **输出**: `tech_plan.version` / `status` / `revise_note` / `phase` / `maturity`
- **生效点**: `tech_plan.revise`
- **示例**: `revise(PLAN-004 草稿, …)` → 拒绝「只有已批准的计划才能修订（先 submit → approve，BR-06）」；
  `revise(PLAN-002, summary="  ")` → 拒绝「修订说明不能为空 —— 版本因何而升要留痕（BR-06）」
- **依据**: 卡片 I-2「计划**随阶段推进**更新版本」—— 没生效的计划谈不上"推进"；
  附录 K TABLE K-1 的行是"计划在该阶段**应达到**的成熟度"，推进必须能被说明（否则两版的差别无从追溯）

#### 3.2.7 `BR-07` 成熟度受字典约束，「更新」以已有基线版本为前提

- **规则描述**:
  - `maturity ∈ {approach, preliminary, baseline, update}`；不传则取缺省 `approach`（方法）
  - `maturity = update`（更新）时，该计划**必须已有获批过的版本**（`version_total > 0`），否则拒绝
- **适用场景**: 创建、修改（`revise` 不需再查 —— 能从「已批准」发起就已经满足前提）
- **计算方式**: 字典校验 + 存在性校验（台账条数）
- **依赖输入**: `[maturity(服务实参), plan_version(聚合内子表)]`
- **输出**: `tech_plan.maturity`
- **生效点**: `tech_plan.create` / `update` → `_check_update_maturity`
- **示例**: `create(..., maturity="update")` → 拒绝「成熟度「更新」以已有基线版本为前提 ——
  本计划还没有获批过任何版本，谈不上更新（附录 K 图例：U = Update，BR-07）」
- **依据**: 附录 K TABLE K-1 的图例 "A = Approach / B = Baseline / P = Preliminary / U = Update"：
  `U` 只出现在同一份计划**已经 P/B 之后**的各阶段（SEMP 在 SDR/MDR 标 P、PDR 标 B、其后一律 U）——
  一份从未获批的计划没有"旧"可更

#### 3.2.8 `BR-08` 批准必须记名

- **规则描述**: `approve` 的 `approver`（批准人）**必填**（空白即拒），并写入版本台账
- **适用场景**: 批准
- **计算方式**: 非空校验（在状态守卫之后、I-1 唯一性校验之前）
- **依赖输入**: `[approver(服务实参)]`
- **输出**: `plan_version.approver`
- **生效点**: `tech_plan.approve → 校验`
- **示例**: `approve(PLAN-007, approver="   ")` → 拒绝「批准人不能为空 —— 批准要记名留痕（BR-08）」
- **依据**: §6.1.1.2.5 的 buy-in 与 §6.7.1.2.2 的评审留痕口径 —— "谁批的"是审批这件事的一半；
  同组 `change_request` 的 `approver`、`review` 的 `owner` 同族

### 3.3 业务数据

> 主档 11 项（`tech_plan` 表）+ 台账 7 项（`plan_version` 表）。列名见 `schema.sql`，此处给业务口径。

#### 3.3.1 数据1: 计划编号（plan_no）

- **数据描述**: 计划的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`PLAN-` + 三位序号）
- **示例值**: "PLAN-001"

#### 3.3.2 数据2: 计划名称（name）

- **数据描述**: 这份计划叫什么（列表与详情的第一识别项）
- **数据类型**: 文本（≤120 字）
- **数据来源**: 人工录入
- **示例值**: "系统工程管理计划"

#### 3.3.3 数据3: 计划类型（plan_type）

- **数据描述**: 这份计划是**哪一类**计划 —— 卡片 10「以「计划类型」属性区分」的那一半
- **数据类型**: 字典：semp / verification / integration / technology_dev / hsi / risk_mgmt / review / cm
- **数据来源**: 人工选择
- **字典对应业务名**: 系统工程管理计划（SEMP）/ 验证与确认计划（V&V Plan）/ 集成计划（Integration Plan）/
  技术开发计划 / 人因集成计划（HSI Plan）/ 风险管理计划（Risk Management Plan）/
  评审计划（Review Plan）/ 配置管理计划（Configuration Management Plan）
- **示例值**: "semp"

#### 3.3.4 数据4: 覆盖阶段（phase）

- **数据描述**: 这份计划为**哪个阶段**而制定（计划与阶段绑定 —— 卡片 I-1 前半）
- **数据类型**: 字典：pre_a / a / b / c / d / e
- **数据来源**: 人工选择
- **字典对应业务名**: 预 A 阶段（Pre-Phase A）/ A 阶段（Phase A）/ B 阶段（Phase B）/
  C 阶段（Phase C）/ D 阶段（Phase D）/ E 阶段（Phase E）
- **示例值**: "a"
- **说明**: 阶段在本聚合里是**枚举属性**，不独立成聚合（卡片 10 + 关键设计决策 3）

#### 3.3.5 数据5: 成熟度（maturity）

- **数据描述**: 这份计划在该阶段**成熟到什么程度**（附录 K TABLE K-1 每格的那个字母）
- **数据类型**: 字典：approach / preliminary / baseline / update
- **数据来源**: 人工选择（缺省 `approach`）
- **字典对应业务名**: 方法（Approach）/ 初步（Preliminary）/ 基线（Baseline）/ 更新（Update）
- **示例值**: "preliminary"
- **说明**: 图例逐字取自附录 K TABLE K-1；`update` 以已有基线版本为前提（`BR-07`）

#### 3.3.6 数据6: 版本号（version）

- **数据描述**: 当前是第几版（`V1` 起，`revise` 递增）
- **数据类型**: 整数（≥1）
- **数据来源**: 系统按流转规则生成（`create` 落 1，`revise` +1）
- **示例值**: 2
- **说明**: **不在 `update` 的字段白名单里** —— 只能经 `revise` 递增

#### 3.3.7 数据7: 计划状态（status）

- **数据描述**: 计划在状态机上的位置
- **数据类型**: 字典：draft / in_review / approved / revised
- **数据来源**: 系统按流转规则变更
- **示例值**: "approved"
- **说明**: **没有硬终态**（状态机是环）—— 见 `BR-05` 的语义差说明

#### 3.3.8 数据8: 计划范围说明（scope）

- **数据描述**: 这份计划管什么（一句话边界，选填）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "系统工程过程与 17 项共性技术过程"

#### 3.3.9 数据9: 修订说明（revise_note）

- **数据描述**: 最近一次修订**为什么**（由哪一版走到这一版的来由）
- **数据类型**: 文本（可空 —— 从未修订时为空）
- **数据来源**: 人工录入（`revise` 必填）
- **示例值**: "阶段推进到 B 阶段，过程裁剪口径更新"
- **说明**: 与版本台账的分工 —— 台账记"每版批了什么"（快照），修订说明记"**最新这一版为何而升**"

#### 3.3.10 数据10: 计划责任人（owner）

- **数据描述**: 谁负责编制与维护这份计划
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "张三"

#### 3.3.11 数据11: 所属项目（project_no）

- **数据描述**: 这份计划隶属的项目
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "P-2026-01"

#### 3.3.12 数据12: 版本台账（plan_version，聚合内子表）

- **数据描述**: **曾获批的版本**留痕 —— 卡片 I-2「历史版本保留」的落点
- **字段**: `seq`（本计划内台账序号）/ `version`（版本号，与该次批准时的主档一致）/
  `phase`（**该版本批准时**覆盖的阶段）/ `maturity`（**该版本批准时**的成熟度）/
  `approver`（批准人，必填 —— `BR-08`）/ `note`（审批意见，选填）
- **数据来源**: 随 `approve` **同事务**产生（追加型，无 UPDATE 路径）
- **示例值**: `seq=1, version=1, phase="a", maturity="preliminary", approver="李四", note="SRR 前批准"`
- **说明**: `phase` / `maturity` 是**快照** —— 计划推进到 B 阶段后，这一行仍是 `a`/`preliminary`；
  覆盖矩阵的「历史版本」那一支正是读它

#### 3.3.13 数据13: 派生计数（version_total / latest_approved_ver / latest_approver）

- **数据描述**: 由台账推导的三个字段，`get` 与 `list` **同口径**
- **口径**: `version_total` = 台账行数（= 已获批版本数）；`latest_approved_ver` / `latest_approver`
  = **版本号最高**那一行的版本号与批准人（版本号只增不减，故它就是最近批准的那一版）
- **数据来源**: 系统推导（无填写入口）
- **示例值**: `version_total=2, latest_approved_ver=2, latest_approver="李四"`

#### 3.3.14 数据14: 覆盖格子（coverage 视图）

- **数据描述**: 阶段 × 计划类型的一格（**查询视图**，不落库）
- **字段**: `phase` / `plan_type` / `covered`（0/1）/ `covered_by`（`current` / `history` / 空）/
  `plan_count` / `approved_no` / `approved_ver` / `approved_maturity`
- **数据来源**: 系统推导（主档 + 台账）
- **示例值**: `phase="a", plan_type="semp", covered=1, covered_by="history", plan_count=0,
  approved_no="PLAN-001", approved_ver=1, approved_maturity="preliminary"`

### 3.4 状态机

```
draft（草稿：内容未定）
   │ submit（提交审批 → 内容锁定）
   ▼
in_review（审批中）── withdraw（撤回）──► 回提交前的状态
   │ approve（记名批准 + 同事务落版本台账）        │ V1 → draft
   ▼                                              │ V2+ → revised
approved（已批准：这一版生效、内容锁定）
   │ revise（修订说明 + 可选推进阶段/成熟度）→ **版本递增**
   ▼
revised（已修订：新版待提交）── submit ──► in_review（回到上面，**可以无限循环**）
```

**每个状态的到达服务**（详设 §4.1 的 FUNC 与服务一一对应）：

| 状态 | 到达服务 |
|---|---|
| `draft` | `create`（首次）／ `withdraw`（`V1` 的撤回） |
| `in_review` | `submit` |
| `approved` | `approve` |
| `revised` | `revise`（版本递增）／ `withdraw`（`V2+` 的撤回） |

> **合法迁移**：`draft|revised→in_review`（`submit`）、`in_review→approved`（`approve`）、
> `approved→revised`（`revise`）、`in_review→draft|revised`（`withdraw`，按 `version` 回到提交前那一态）。
> **拦截迁移**：`in_review→` 改内容（须先 `withdraw`）、`approved→` 改内容 / 提交 / 撤回
> （须走 `revise`）、`draft|in_review|revised→` 修订（须先 `approve`）。
> **没有"有状态无服务"的空洞** —— 四个状态各自都有能到达它的服务。
> ⚠ **本页没有硬终态**：`revised → in_review → approved → revised …` 是一条**环**，
> 与同组 `review` / `configuration_item` / `technical_measure` 的"终态一律拒"不同（见 `BR-05` 的语义差）。
> ⚠ **撤回回到哪一态是推断的**：`version > 1` ⇒ 回 `revised`（能走到 `V2` 只可能是因为 `V1` 曾获批
> 并被 `revise`），否则回 `draft` —— 这样撤回**不丢信息**（不额外存"提交前的状态"）。

### 4.3 功能详细说明

#### 4.3.1 建立计划（FUNC-01）

- **输入**: 名称、计划类型、覆盖阶段、成熟度（选填，缺省「方法」）、范围说明、责任人、所属项目
- **校验**: 名称非空 → `BR-02`（类型、阶段字典）→ `BR-07`（成熟度字典 + 「更新」须已有基线）
- **处理**: 生成 `plan_no`（`PLAN-<序号>`）→ 落库 `status='draft'`、`version=1`
- **输出**: 新计划记录（含空 `versions` 与三个派生计数为 0 / `None`）

#### 4.3.2 提交审批（FUNC-02）

- **输入**: `plan_no`
- **校验**: `BR-05`（已批准 → 拒并指向 `revise`；审批中 → 拒并指向 `withdraw`）
- **处理**: 状态置 `in_review`
- **输出**: 更新后的计划
- **说明**: 提交是"内容锁定"的那一刻 —— 审批对着的必须是定下来的那一版

#### 4.3.3 批准（FUNC-03）

- **输入**: `plan_no` + 批准人（**必填**）+ 审批意见（选填）
- **校验**: 状态须为 `in_review`（否则拒）→ `BR-08` 批准人非空 → `BR-03` 同阶段同类型唯一
- **处理**: 往 `plan_version` 插入一行快照（**同事务**）→ 状态置 `approved`
- **输出**: 更新后的计划（台账多一行）
- **说明**: 三件事收在同一次调用里；被拒时**整次调用不落库**（状态与台账都不变）

#### 4.3.4 撤回审批（FUNC-04）

- **输入**: `plan_no` + 撤回原因（选填，本版仅接口保留）
- **校验**: 已批准 → 拒（走 `revise`）；不在审批中 → 拒（「无需撤回」）
- **处理**: 状态回到提交前那一态（`version > 1` → `revised`，否则 → `draft`）
- **输出**: 更新后的计划
- **说明**: 不改版本号、不产生台账行 —— 撤回**没有产生任何被批准的版本**

#### 4.3.5 修订出下一版（FUNC-05）

- **输入**: `plan_no` + 修订说明（**必填**）+ 推进到的阶段（选填）+ 成熟度（选填）
- **校验**: 状态须为 `approved`（已修订 → 拒「不能连续修订」；草稿 / 审批中 → 拒"先 submit → approve"）
  → 修订说明非空 → 阶段 / 成熟度字典（`BR-02` / `BR-07`）
- **处理**: `version` +1 → 状态置 `revised` → 写 `revise_note`，可一并推进 `phase` / `maturity`
- **输出**: 更新后的计划
- **说明**: **历史台账行不改**（`V1` 仍是"当时批的 V1@A 阶段·初步"）—— I-2 的"历史版本保留"

#### 4.3.6 修改计划内容（FUNC-06）

- **输入**: `plan_no` + 名称 / 类型 / 覆盖阶段 / 成熟度 / 范围 / 责任人 / 所属项目（皆选填）
- **校验**: 状态须为草稿 / 已修订（`BR-05`，报错点名解锁入口）→ 各字段字典与非空校验
- **处理**: 字段白名单 UPDATE
- **输出**: 更新后的计划
- **说明**: 版本号 / 状态 / 修订说明**不在白名单里**（`BR-04`）；一次不带任何字段 → 拒「没有要修改的内容」

#### 4.3.7 阶段覆盖矩阵（FUNC-09）

- **输入**: 覆盖阶段 / 计划类型（皆可选）+ 分页
- **处理**: 遍历 `PHASES × PLAN_TYPES` 的交叉格（按筛选收敛），逐格判定覆盖来源
  （先"此刻已批准"，再"台账曾获批"），带出计划数与覆盖计划
- **输出**: `{items, total}`，每格 8 个字段
- **说明**: 这是**查询视图**，不是聚合 —— 它不拥有任何状态；且**它不可被写入**（缺口是事实，不是错误）

> 材料 §6.1.1.2.5 的 buy-in 是"stakeholders 对技术途径的认可"，不是自编自批。
> 本版由 `approver` 必填（`BR-08`）承担"谁批的"这一半；**角色分工在前端体现**，

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 计划与阶段绑定，同阶段同类型只允许一份已批准

**Given** `PLAN-002`（verification@A 阶段）已批准
**When** 建一份 `PLAN-007`（同类型同阶段）并批准
**Then** 拒绝并点名 `PLAN-002`（`BR-03` / I-1）
**And given** 同类型的 `PLAN-007` 换到 B 阶段 **when** 批准 **then** 成功（阶段不同不冲突）

#### 6.1.2 标准2: 版本随阶段推进递增、历史版本保留

**Given** `PLAN-001` 在 A 阶段批准（`V1`、成熟度「初步」）
**When** `revise(summary=…, phase="b", maturity="baseline")`
**Then** 状态「已修订」、版本 `V2`、阶段 B、成熟度「基线」
**And given** 修订后 **when** `get` **then** 台账仍是 `[V1@a/preliminary, V2@b/baseline]`
（`V1` 那一行**未被改写**）

#### 6.1.3 标准3: 两条锁定路径各有解锁入口

**Given** `PLAN-002` 已批准
**When** `update(name=…)` / `submit` / `withdraw` / 重复 `approve`
**Then** 四者全拒，且 `update` 的文案指向 `revise`
**And given** `PLAN-003` 审批中 **when** `update` **then** 拒绝且文案指向 `withdraw`
**And given** 撤回后 **when** `update` **then** 成功（解锁真的解开了）

#### 6.1.4 标准4: 批准记名且同事务落台账

**Given** `PLAN-003` 审批中
**When** `approve(approver="  ")`
**Then** 拒绝「批准人不能为空」
**And given** `approve(approver="李四", note=…)` **when** 提交 **then** 状态「已批准」且
**同一次调用**后台账 `version_total=1`、`latest_approver="李四"`、首行快照期次 / 成熟度齐备

#### 6.1.5 标准5: 覆盖矩阵把缺口显出来

**Given** 造出「A 阶段 SEMP 已批准并推进到 B」「B 阶段集成计划停在审批中」两份计划
**When** `coverage(phase="a")` / `coverage(phase="b")`
**Then** A 阶段 `semp` 格 `covered=1, covered_by="history"`（由台账 `V1` 覆盖）；
B 阶段 `integration` 格 `covered=0, plan_count=1`（有计划但未批 —— **缺口**）

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms；`coverage` 固定 48 格（6 阶段 × 8 类型），同量级
- 计划编号生成在并发登记下不重复（`BR-01`）
- `get` 未命中**不抛异常**，返回 `None`（供跨应用探测式调用 —— 如 `review` 侧选依据计划）
- 批准的两处写入**同事务**：台账插入与状态变更任一步失败，整次调用不落库（链测试 TC-04 / TC-32 验证）

### 6.3 已知问题或限制

- **「至少一份」不可被同事务强制** —— 卡片 I-1 的「每个阶段至少有一份已批准的该类计划」里，
  "至少一份"是**集合层面的事实**：缺计划的阶段**没有任何一条记录**可以被拿来拦截
  （没有写入动作就没有拒绝的落点）。本版把它落在 `coverage` 视图上把缺口显出来，
  与同组 `technical_measure` 把 I-1 拆成「同事务写告警」+ `list_alerts` 视图同构。
  若将来要**硬卡**（"该阶段缺 SEMP 就不许推进评审"），那是一条**跨应用的读校验**
  （`review.create` 里查 `tech_plan.coverage`），属评审侧的改动，不在本应用。
- **`revise` 不要求携带变更请求号** —— 卡片 10 写明「跨应用调用：无」，故本版不引入
  `change_request` 这条边（同组 `configuration_item.bump_version` / `technical_measure.rebaseline`
  都留了"只校验非空、不校验已批准"的缺口，本页干脆不设该字段）。若将来要接，
  是"加一个可选 `change_no` 形参 + 一行字面量 `self.fde.call("change_request","get",…)`"。
- **卡片 10 的对外操作只写了 `create / update / approve / list`，本版另加了
  `submit / withdraw / revise / get / coverage`** —— 前三个是状态机里「审批中」「已修订」两个状态的
  **唯一到达路径**（没有它们那两个状态是死的），`get` 是同组各页一致的服务面，
  `coverage` 是 I-1「至少一份」面的落点。`withdraw` 是本版**新增**的（卡片状态机没写）：
  没有它，「审批中」是个死结（不批就永远出不来），故补上并在此登记。
- **不做"阶段推进"的自动编排** —— 到了 KDP 不会自动推进计划（那要流程引擎，且没有可拒绝的
  写入动作）；推进由人经 `revise` 做，一次一份。
- **成熟度不自动推导** —— 附录 K 的 `A/B/P/U` 是"该阶段**应达到**的成熟度"，本应用只记
  "**实际**标的是什么"，不做"到 PDR 就该是 B"的校验（那需要 TABLE K-1 的期望矩阵入库）。
  `BR-07` 只拦了最明显的一处不自洽：「更新」而从未获批。
- **不做计划正文与附件**（`resource/` 导入导出不在服务面）—— 见 §1.3.2。
- **`withdraw` 的 `reason` 不落库** —— 本版只作接口保留（撤回没有产生版本，故没有可挂靠的记录）；
  若将来要给撤回留痕，加一张聚合内子表或写进 `revise_note` 均可，**不需要改状态机**。
- **`list` 与 `get` 的字段口径**：主档 11 字段 + 三个派生计数**两边一致**；版本台账**明细只在 `get`**
  （列表不做 N+1 取子表）。这不是"口径差"，是刻意的分层。
