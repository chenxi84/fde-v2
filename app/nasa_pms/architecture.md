# nasa_pms 架构设计

> 产出技能：`fde-aggregate-identification`（第①步，规格 `design-plus/架构设计.md`）
> 输入：`brd/`（SE 手册 27 章 + WBS 手册 9 章）+ `本体对象.md`（实体提及清单）+ `术语表.md`

## ② 聚合根卡

### 1. 需求 `requirement` / `Requirement`

- **标识**：`req_no`（需求编号）
- **核心属性**：标题、正文、类型（技术/系统/接口/派生）、来源（利益相关者期望 / 上游需求）、验证方法、状态
- **对外操作**：`create` / `update` / `baseline`（纳入基线）/ `derive`（派生） / `list` / `get`
- **关键不变量（界定一致性边界）**：
  - **I-1 每条需求必须有验证方法** —— 无验证方法的需求不允许进入基线
  - **I-2 派生需求必须保留上游来源** —— 需求与其派生链同事务维护（改上游要能看到下游）
  - **I-3 需求编号全局唯一且不可变**（`REQ-` + 三位序号，取全局最大号递增；不按 `project_no` 分段）
- **引用的聚合**：`stakeholder`（弱引用，需求的来源方）
- **跨应用调用**：`stakeholder.list`
- **状态机**：`草稿 →（submit_review）待评审 →（baseline）已基线 → 已废弃`（「变更中」已收敛：变更全流程在 `change_request`）

### 2. 风险 `risk` / `Risk`

- **标识**：`risk_no`
- **核心属性**：描述、类别、可能性、后果、风险等级、缓解措施、责任人、状态
- **对外操作**：`create` / `update` / `assess`（重评等级）/ `mitigate` / `close` / `list`
- **关键不变量**：
  - **I-1 关闭风险必须有处置结论**（接受 / 缓解完成 / 转移）
  - **I-2 风险等级由可能性 × 后果推导**，不允许直接写等级
- **引用的聚合**：`requirement`（弱引用，风险指向受影响的需求）
- **跨应用调用**：`requirement.list`
- **状态机**：`识别 → 分析中 → 缓解中 → 已关闭 / 已接受`

### 3. 配置项 `configuration_item` / `ConfigurationItem`

- **标识**：`ci_no`
- **核心属性**：名称、类型、当前版本、所属基线、责任人、状态
- **对外操作**：`create` / `update` / `release`（发版）/ `assign_baseline` / `list`
- **关键不变量**：
  - **I-1 配置项版本只能递增**，已发布版本不可改写
  - **I-2 配置项的版本变更必须经由已批准的变更请求**（与 `change_request` 跨应用协作，非同一事务）
- **引用的聚合**：`change_request`（弱引用）
- **跨应用调用**：`change_request.get`
- **状态机**：`草稿 → 受控 → 已发布 → 已归档`

### 4. 变更请求 `change_request` / `ChangeRequest`

- **标识**：`cr_no`
- **核心属性**：标题、申请方、影响的配置项 / 需求、影响分析、审批意见、状态
- **对外操作**：`create` / `analyze` / `approve` / `reject` / `implement` / `list`
- **关键不变量**：
  - **I-1 变更必须指明影响范围**（至少一个配置项或需求）
  - **I-2 审批与影响分析同事务落库**（不允许"先批后分析"）
- **引用的聚合**：`configuration_item`、`requirement`
- **跨应用调用**：`configuration_item.list`、`requirement.list`
- **状态机**：`提交 → 影响分析 → 审批中 → 已批准 / 已拒绝 → 已实施`

### 5. 评审 `review` / `Review`

- **标识**：`review_no`
- **核心属性**：类型（PDR/SRR/CDR/…）、阶段、评审对象、评审项清单、结论、行动项
- **对外操作**：`create` / `add_item` / `conclude` / `list` / `get`
- **关键不变量**：
  - **I-1 结论为"通过（有条件）"时必须有行动项**（评审结论与行动项同事务）
  - **I-2 行动项必须指定责任人与期限**
- **引用的聚合**：`tech_plan`（评审依据的计划）
- **跨应用调用**：`tech_plan.list`
- **状态机**：`计划 → 进行中 → 已结论 → 行动项跟踪中 → 已关闭`
- **并入说明**：**行动项并入本聚合**（随评审结论同事务产生，无独立标识）——
  跨评审的"行动项汇总"是**查询视图**，不是独立聚合

### 6. 验证项 `verification` / `Verification`

- **标识**：`ver_no`
- **核心属性**：对应需求、验证方法（检验/分析/演示/测试）、验证阶段、结果、证据
- **对外操作**：`create` / `record_result` / `list`
- **关键不变量**：
  - **I-1 每条进入基线的需求至少有一条验证项**（与 `requirement` I-1 呼应，跨应用校验）
  - **I-2 判定为"不通过"必须记录证据与后续处置**
- **引用的聚合**：`requirement`（强关联：验证项必须挂在一条需求上）
- **跨应用调用**：`requirement.get`
- **状态机**：`规划 → 执行中 → 通过 / 不通过 → 关闭`

### 7. 技术度量 `technical_measure` / `TechnicalMeasure`

- **标识**：`tpm_no`
- **核心属性**：名称、类别（TPM/MOP/KPP）、目标值、阈值、实测值、度量期次
- **对外操作**：`create` / `record`（记实测值）/ `list`
- **关键不变量**：
  - **I-1 实测值超出阈值必须触发告警记录**（度量与告警同事务）
  - **I-2 目标值与阈值一经基线不可直接改写**，须经变更请求
- **引用的聚合**：`requirement`（弱引用，度量服务于哪条需求）
- **跨应用调用**：`requirement.list`
- **状态机**：`定义 → 度量中 → 超阈值 → 已纠正 → 关闭`

### 8. 决策 `decision` / `Decision`

- **标识**：`dec_no`
- **核心属性**：议题、备选方案、评价准则、权衡结果、结论、依据
- **对外操作**：`create` / `add_option` / `conclude` / `list`
- **关键不变量**：
  - **I-1 结论必须指向一个备选方案**，且该方案须有评价得分
  - **I-2 备选方案少于两个时不允许结论**（决策必须有权衡）
- **引用的聚合**：`technical_measure`（准则可能取自度量）
- **跨应用调用**：`technical_measure.list`
- **状态机**：`提出 → 权衡中 → 已决策 → 已实施`

### 9. 接口 `interface` / `Interface`

- **标识**：`if_no`
- **核心属性**：接口名称、两端（提供方/使用方）、接口类型、约定内容（ICD）、版本
- **对外操作**：`create` / `update` / `release` / `list`
- **关键不变量**：
  - **I-1 接口必须明确两端**（提供方与使用方都不能为空）
  - **I-2 接口版本变更必须通知两端**（变更记录同事务）
- **引用的聚合**：`configuration_item`（弱引用，接口文档本身是配置项）
- **跨应用调用**：`configuration_item.list`
- **状态机**：`定义中 → 已发布 → 变更中 → 冻结`

### 10. 技术计划 `tech_plan` / `TechPlan`

- **标识**：`plan_no`
- **核心属性**：计划类型（SEMP/验证计划/集成计划/…）、版本、覆盖阶段、责任人、审批状态
- **对外操作**：`create` / `update` / `approve` / `list`
- **关键不变量**：
  - **I-1 每个阶段至少有一份已批准的该类计划**（计划与阶段绑定）
  - **I-2 计划随阶段推进更新版本**，历史版本保留
- **引用的聚合**：无（**阶段以枚举属性承载**，不独立成聚合 —— 见处置表）
- **跨应用调用**：无
- **状态机**：`草稿 → 审批中 → 已批准 → 已修订`

### 11. 利益相关者 `stakeholder` / `Stakeholder`（主数据）

- **标识**：`sh_no`
- **核心属性**：名称、类型（客户/承包商/内部组织）、职责、期望清单
- **对外操作**：`upsert` / `get` / `list`
- **关键不变量**：
  - **I-1 期望必须挂在本聚合内**（期望随相关方维护，无独立标识）
- **引用的聚合**：无
- **跨应用调用**：无
- **状态机**：无（主数据，只读引用为主）
- **来源**：外部同步（机构与人员），本系统**只读引用、不维护源数据**

### 12. 工作分解结构元素 `wbs` / `Wbs`

- **标识**：`wbs_no` —— 点分**十进制层级码**（`123456.02.07`）；**最多 7 层、含句点不超过 24 字符**
- **核心属性**：元素名称、父元素编号、元素类型（产品 / 使能 / 控制账户 / 工作包 / 规划包）、内容描述、
  范围定义出处、关联规范（号 + 名）、预算与报告号、责任方、版次与修订授权、状态
- **对外操作**：`create` / `add_child` / `update` / `baseline` / `change` / `close` /
  `get` / `list` / `tree` / `coverage`
- **关键不变量**：
  - **I-1 编号与层级自洽** —— 编号是点分十进制；非顶层元素的 `parent_no` 必须是其编号**去掉最后一段**；
    ≤ 7 层且 ≤ 24 字符（3.4.2 的编码规则）
  - **I-2 父先于子** —— 父元素不存在不得建子元素；**父未基线，子不得基线**（自上而下，3.1 / 3.5.4）
  - **I-3 不得含未授权范围** —— 没有**范围定义出处**（`scope_ref`）的元素不得基线
    （3.3.3「与需求/规范文档相对应」、3.3.5「WBS 绝不能包含未授权的工作范围」）
  - **I-4 产品导向** —— 元素名不得是**职能 / 组织 / 阶段 / 工种**词（3.5.2 的例子：设计、工程、制造、
    A 阶段、装配工、直接人工、返工、复测、翻修…）
  - **I-5 基线后修订必须带已批准的变更号** —— 与 `change_request` 跨应用协作（3.3.6「基线 WBS 的
    任何修订都要按配置管理过程留文档，含变更理由与项目经理批准」），**非同一事务**
- **引用的聚合**：`change_request`（弱引用）、`requirement`（覆盖对账）
- **跨应用调用**：`change_request.get`、`requirement.list`
- **状态机**：`草稿 → 已基线 → 变更中 → 已关闭`
- **来源**：`NASA/SP-20250006071`《NASA WBS Handbook》(2025-06) —— SE 手册 6.1 把 WBS 的细则
  **外链**给这本书（当时是 SP-2010-3404），故它是本聚合的依据

## ④ 关键设计决策

1. **聚合根来自"过程管理的东西"，不是材料里的名词** —— 材料讲的是过程（需求管理/风险管理/配置管理…），
   所以聚合根取这些过程**产出与跟踪的对象**；材料里 2786 个提及对象绝大多数是方法论步骤，不入聚合。
2. **行动项并入评审** —— 它随评审结论同事务产生、无独立标识；跨评审汇总属查询视图。
3. **阶段不独立成聚合** —— 它是计划/评审/度量的**枚举属性**，没有独立生命周期。
4. **利益相关者是唯一主数据** —— 其余都是过程产物；相关方来自机构与人员，本系统只读引用。
5. **变更请求与配置项分属两个聚合** —— 二者**事务边界不同**：变更要审批流程、配置项要版本控制，
   合成一个聚合会让"审批中"与"已发布"互相锁死。
6. **验证项与需求分属两个聚合（但有强关联）** —— 需求基线与验证执行是**不同节奏**（前者一次、后者多轮），
   合并会让验证结果反复改动需求基线。
7. **WBS 独立成聚合，而非并入 `tech_plan`**（2026-09-26 补）—— SE 手册 6.1 把 **WBS / SEMP / 进度表
   并列**，三者都受配置控制；细化到 WBS 手册后可见：WBS 有自己的**层级标识体系**（7 层十进制码）、
   **元素级的变更控制**、**全包含性与需求覆盖对账**。`tech_plan` 管的是"文档及其批准"，
   事务边界是版本与批准；WBS 的事务边界是**元素树 + 元素级修订**。二者合并会让"改一个元素"
   与"改一份计划的批准状态"互相锁死 —— 与决策 5 同一条理由。
