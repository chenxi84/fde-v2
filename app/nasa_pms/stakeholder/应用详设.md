## 1. 利益相关者概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `stakeholder` |
| 类名 | `Stakeholder` |
| 聚合根 | 利益相关者 |
| 标识 | `sh_no`（**由外部来源系统给定**，本系统不生成） |
| 数据来源类型 | **外部同步（机构与人员）** —— 本系统**只读引用、不维护源数据** |
| 聚合内子表 | `stakeholder_expectation`（利益相关者期望）—— **无独立标识**，随本聚合同事务维护 |
| 状态机 | **无**（卡片 11：「状态机：无（主数据，只读引用为主）」） |
| 对外服务 | `upsert` / `add_expectation` / `update_expectation` / `get` / `list` |

> ⚠ **本应用与同组其它九个应用不是一类东西**：其余九个都是**过程产物**（需求、风险、配置项、
> 变更、评审、验证、度量、决策、接口），有编号生成、有状态流转、有（可选的）删除语义；
> 本应用是本组**唯一的主数据**，上述三样**一样都没有**。
> 照抄别的页的骨架会同时错三处（没有 `create` / 没有状态机 / 没有删除入口）——
> 见 §1.3.1 与 §3.4。

### 1.2 利益相关者概览背景

#### 1.2.1 为什么需要这个聚合根？

材料把「识别相关方并搞清他们要什么」放在 **SE 引擎的起点**：

> "The Stakeholder Expectations Definition Process is the **initial process within the SE engine**
>  that establishes the foundation from which the system is designed and the product is realized.
>  The main purpose of this process is to **identify who the stakeholders are and how they intend
>  to use the product**."（§4.1）

> "A '**stakeholder**' is a group or individual that is affected by or has a stake in the product
>  or project."（§4.1.1.2.1）

材料同时给出了这个聚合最要紧的一条**边界**：相关方**不是**本系统"建"出来的 ——
他们是既有的机构与人员，本系统只是**引用**他们并记录"他们要什么"：

> "Other interested parties are those who affect the project by providing broad, overarching
>  constraints within which the customers' needs should be achieved."（§4.1.1.2.1）

现状是相关方散落在会议纪要、通讯录与邮件里：**没有唯一编号**（于是需求文档里的"客户"到底指谁
说不清）、**期望没有落点**（"当时谈过哪些期望"答不上来）、**谈成没谈成没有标记**
（§4.1.1.2.8 要求取得承诺，§4.1.1.2.9 要求基线化）。本应用给这三件事各一个落点。

#### 1.2.2 期望达到什么目标？

- 每个相关方**有唯一编号**（`sh_no`，取自外部主数据），可被需求、评审**按号引用**
- 期望**逐条登记在相关方名下**（`add_expectation`）—— 卡片 **I-1**：期望随相关方维护、
  **无独立标识**，不存在"跨相关方的期望大表"
- 每条期望**记得下来源**（`source`，§4.1.1.2.7："The NGOs or other stakeholder expectation
  documentation **should also capture the source of the expectation**"）
- 标为**度量有效性（MOE）**的期望**必须给出度量口径**（§4.1.1.2.6）—— 否则 MOE 与"目标"没有区别
- 期望可标记**已获相关方承诺**（§4.1.1.2.8），且**承诺过的不许单方面改**
  （"signatures or other forms of commitment are obtained"）
- 相关方本体**只读引用**：同步进来的不删（§4.1.1.2.10 Capture Work Products —— 记录是留痕），
  本系统维护的只有**期望**

### 1.3 利益相关者范围

#### 1.3.1 包含哪些功能？

- 相关方的**同步落库**：`upsert`（存在即更新、幂等；编号由外部来源给定）
- **期望清单**：逐条登记期望（`add_expectation`，本聚合子表，序号本相关方内递增）
- **期望维护**：改陈述 / 类别 / 来源 / 度量口径 / 承诺 / 备注（`update_expectation`）
- 相关方的查询与列表（`get` / `list`，`list` 支持类型精确 / 关键字跨字段模糊 / 所属项目）

#### 1.3.2 不包含哪些功能？

- **没有 `create`** —— 相关方本体来自外部同步（卡片「来源」一栏），本系统**不生成编号**。
  这是本页与同组其它九页最直观的差别：入口叫「**同步相关方**」，不叫「新建」。
  代价与收益写在这里：**同步方必须先给出编号**（增量/全量推送都能对上号），
  收益是 upsert **幂等**（重跑同步不会造出重复相关方，也不会把引用它的需求指丢）。
- **没有 `delete`** —— 主数据只读引用，且期望是"当时谈过什么"的留痕。
  同步源把某相关方移除时，本系统**保留**这条记录（需求/评审可能还引用着它）；
  真要"停用"应由外部主数据给状态，本系统不替它做决定（卡片也未要求）。
- **没有状态机** —— 卡片 11 明确「状态机：无」。本聚合只有两条写轴：
  **主档 = 幂等同步**、**期望 = 随相关方维护 + 承诺后冻结**。§3.4 详细交代这一点的落法。
- **没有跨相关方的期望汇总视图** —— 与 `review.list_actions`（跨评审行动项汇总）刻意不同：
  卡片 11 **没有**「并入说明」那类要求，期望的语义边界就是"属于某个相关方"。
  §4.1.1.2.7 要求的"可追溯"是**逐条**属性（`source` 字段），不是把期望拉平成一张独立台账的理由。
- **不做期望的基线化（§4.1.1.2.9）** —— 材料确实要求"agreed upon 的期望与 ConOps 一起基线化"，
  但那条基线的载体是**需求基线**（`requirement.baseline`：期望 → 需求 → 基线是 §4.1 的流向）；
  本应用是主数据，自建一套"期望基线 + 冻结状态"就是 §3.4 里说的"为一致硬造状态"。
- **不做 ConOps / MOE 文档本身** —— 材料 §4.1.1.2.4 的 ConOps 与 §4.1.1.3 的 MOE 文档属
  `tech_plan`（计划类文档）与配置项的范畴；本应用只**记一条期望的度量口径**（`moe` 字段）。
- **不做 NGO 的层级化**（Need → Goal → Objective 的追溯树）—— 本版把"层级"落在**期望类别**
  （`kind`）上逐条标注，不建父子关系：材料的追溯要求（§4.1.1.2.7）是
  "期望 ↔ 需求"的**双向**追溯，那是 `requirement` 侧的事（`source_req_no` / `source` 口径）。
- **不做相关方的合并 / 去重 / 改名换号** —— 编号是外部主数据的键，本系统不替它合并。

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 系统工程师 | 识别相关方、elicit 期望、逐条登记并维护期望、记下来源与度量口径 | 材料 §4.1.1.2.1（"Identify Stakeholders"）与 §4.1.1.2.2（"Through interviews/discussions, surveys, marketing groups, e-mails, a SOW…"） |
| 项目经理 | 推动取得相关方**承诺**（§4.1.1.2.8）与期望基线化（§4.1.1.2.9）；只读消费"哪些相关方、谈成没有" | 材料 §4.1.1.2.8 / §4.1.1.2.9 |
| 客户 / 承包商（相关方本人或代表） | 提出期望、给出（或拒绝给出）承诺 | 材料 TABLE 4.1-1 的 stakeholder 举例与术语表「客户」「承包商」 |
| 外部主数据（机构与人员） | **写入相关方本体**（同步 = `upsert`）—— 本系统只读引用 | 聚合根卡 11「来源」一栏 |

> 术语表未收「系统工程师」以外的本应用特有角色，按材料语境取用（见 `新增术语.md` §5）。

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 从外部主数据同步一条相关方（优先级：P1）

**作为**一名系统工程师（或接入外部主数据的同步任务）
**我希望**把机构与人员主数据里的一条相关方同步进来（编号 / 名称 / 类型 / 职责 / 所属机构 / 联系方式 / 所属项目）
**以便**后续能在它名下登记期望，并被需求、评审按号引用

**验收条件**：
- 给定编号 / 名称 / 类型齐备，当同步时，则相关方落库（编号**原样取外部来源的**，本系统不生成）
- 给定同一编号**再次**同步，当提交时，则**更新**该条（幂等，**不产生第二条**）
- 给定编号为空，当提交时，则**拒绝**并提示「利益相关者编号不能为空（编号由外部来源系统给定…）」
- 给定名称为空，当提交时，则**拒绝**并提示「利益相关者名称不能为空」
- 给定类型填了字典外的值（或为空），当提交时，则**拒绝**（`BR-03`）

#### 2.1.2 `US-02` 用户故事 — 增量同步不抹掉已有内容（优先级：P1）

**作为**一名接入方
**我希望**同步载荷里**没给的**字段保持原值，只有**显式给空串**的才被清空
**以便**做增量同步时不会因为"这次只推了名称"而静默抹掉本系统里的职责 / 联系方式

**验收条件**：
- 给定一条已存在的相关方，当只传编号 / 名称 / 类型时，则职责 / 所属机构 / 联系方式 / 所属项目**全部保持原值**
- 给定 `contact=""`，当提交时，则联系方式被**清空**，其余未传字段不动（`BR-08`）

#### 2.1.3 `US-03` 用户故事 — 在相关方名下登记一条期望（优先级：P1）

**作为**一名系统工程师
**我希望**把访谈 / SOW / 上级需求里谈到的期望**逐条**写在该相关方名下，
带上类别（需要 / 目标 / 指标 / MOE / 约束）与**来源**
**以便**"这个要求是谁提的、从哪来的"有据可查（§4.1.1.2.5 / §4.1.1.2.7）

**验收条件**：
- 给定相关方存在，当登记期望时，则清单多一条（`seq` 本相关方内递增），承诺缺省为「未承诺」
- 给定相关方**不存在**，当登记时，则**拒绝**并提示「期望必须挂在本聚合内（卡片 I-1）」（`BR-04`）
- 给定陈述 / 类别 / 来源任一项为空，当提交时，则**拒绝**（`BR-05`）
- 给定类别为字典外的值，当提交时，则**拒绝**（`BR-05`）

#### 2.1.4 `US-04` 用户故事 — 给期望补度量口径（优先级：P1）

**作为**一名系统工程师
**我希望**对"可度量的成功判据"这类期望（MOE）写出**度量口径**
**以便**它真的能被度量，而不是一句口号（§4.1.1.2.6 "Analyze Expectations Statements for
Measures of Effectiveness"）

**验收条件**：
- 给定类别选了 `moe` 且填了口径，当提交时，则**接受**
- 给定类别选了 `moe` 但口径为空，当新增 / 修改时，则**拒绝**并提示「必须填写度量口径」（`BR-06`）
- 给定类别不是 `moe`，当不给口径时，则**接受**（口径非必填）
- 给定已存在的期望只把类别改成 `moe`，当提交时，则**拒绝**（库里没有口径，`BR-06` 判的是**合并后**的口径）

#### 2.1.5 `US-05` 用户故事 — 标记期望已获相关方承诺（优先级：P1）

**作为**一名项目经理
**我希望**在双方就某条期望达成一致后把它标为「已获相关方承诺」，并让它**定稿**
**以便**承诺是真的（§4.1.1.2.8），而不是"系统里还留着上个月那版说法"

**验收条件**：
- 给定一条未承诺的期望，当标记承诺时，则 `committed=1`
- 给定一条**已承诺**的期望，当改陈述 / 类别 / 来源 / 度量口径时，则**拒绝**并提示
  「已获相关方承诺…要改请先撤回承诺」（`BR-07`）
- 给定一条**已承诺**的期望，当只改**备注**时，则**接受**（备注不受冻结影响）
- 给定撤回承诺（`committed=0`），当再次改写时，则**接受**；**撤回与改写可在同一次调用完成**

#### 2.1.6 `US-06` 用户故事 — 查询相关方列表与详情（优先级：P2）

**作为**一名项目经理 / 系统工程师
**我希望**按类型 / 关键字 / 所属项目筛选相关方，并看到某相关方的**全部期望**
**以便**回答"这类相关方有哪些、谁还没谈过期望、哪些期望还没获承诺"

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序），**分页返回 `{items, total}`**；
`get` 返回主档 + 期望清单（子表随聚合一起返回）与 `expectation_total` / `committed_total`
两个派生计数，未命中返回 `None` 不抛异常。

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 一条期望的一生（对齐卡片 I-1 与 §4.1.1.2.5..§4.1.1.2.9）

1. 外部主数据把相关方带进来 —— `upsert`（**编号来自外部**，本系统不生成）
2. 系统工程师通过访谈 / 讨论 / 调查 / 邮件 / SOW 弄清楚相关方要什么
   （§4.1.1.2.2 "Through interviews/discussions, surveys, marketing groups, e-mails,
   a Statement of Work (SOW)…"）
3. 把期望写成**可接受的陈述**逐条登记 —— `add_expectation`（陈述 / 类别 / 来源；MOE 带口径）
4. 对 MOE 类期望**写出度量口径**（§4.1.1.2.6 的活动）—— `update_expectation`
5. 双方达成一致后**取得承诺**（§4.1.1.2.8 "signatures or other forms of commitment are
   obtained"）—— `update_expectation(committed=1)` ⇒ 该条**定稿**（`BR-07`）
6. 日后要修订：先**撤回承诺**再改（可一次调用完成）—— 冻结**可解锁**
7. 期望经 `requirement` 转成需求（§4.1 的流向：期望 → 需求 → 基线），本系统不再改它的"内容"

#### 3.1.2 场景2: 为什么「已获承诺」要冻结，又为什么要留一个解锁口

材料的原话把承诺当成**签字**：

> "Once the stakeholder and the technical team are in agreement with the expressed stakeholder
>  expectations and the concept of operations, **signatures or other forms of commitment are
>  obtained**."（§4.1.1.2.8）

签过字的那句话被单方面改掉，承诺就不成立了 —— 所以**陈述 / 类别 / 来源 / 度量口径**四项冻结。
但材料紧接着又说要把它**基线化**并**走正式或非正式的审批流程**再改：

> "The set of stakeholder expectations … that are agreed upon are now baselined. **Any further
>  changes will be required to go through a formal or informal (depending on the nature of the
>  product) approval process** involving both the stakeholder and the technical team."（§4.1.1.2.9）

也就是说"改"是被允许的，**前提是重新经过相关方**。于是本应用把"重新经过相关方"落成
**撤回承诺**（`committed=0`：这一版不再代表已达成的一致）：
撤回之前改不了，撤回之后随便改 —— **冻结可解锁**。
这与同组 `technical_measure` 的「基线冻结 + `rebaseline` 携带变更请求号解锁」是**同一形状**，
差别在解锁的凭据：那里是变更请求号，这里是**相关方的承诺本身**（期望还没有"变更请求"这一层，
它比需求更早，材料 §4.1 的流程里它先于需求存在）。

**备注（`note`）刻意不冻结** —— "已列入验证计划 V-007"这类跟踪留痕本来就该在承诺之后还能写。

#### 3.1.3 场景3: 「这条相关方的状态是什么」——答案是**没有状态**

同组九页都有 `status` 列与状态机；本页没有，且这是**规格**而不是遗漏：

- 卡片 11 写明「状态机：无（主数据，只读引用为主）」
- 相关方的"状态"属于**外部主数据**（机构在编不在编、人员在职离职），本系统不掌握、也不该猜 ——
  卡片也说了本系统「只读引用、不维护源数据」
- 本系统真正会变的只有**期望**：它从"刚谈下来"走到"已获承诺"。但那不是**相关方**的状态 ——
  同一个相关方可以有一条已承诺、两条还在谈（材料 §4.1.1.2.8 的承诺对象是
  "the **validated set of expectations**"，是**一批期望**，不是一个相关方）。
  把"承诺"上提成整条相关方的状态，就会出现"这个相关方已承诺，但它第 3 条期望还在改"的自相矛盾。

所以本页的"状态感"落在**期望行的「已承诺 / 未承诺」**上（`committed` 0/1 标记），
列表的派生列是「期望 已承诺/总」（如 `1/3`）—— 一行就能读出"这个相关方谈成了几分之一"。

### 3.2 业务规则

#### 3.2.1 `BR-01` 相关方编号由外部来源给定、必填、落库不可变

- **规则描述**: `sh_no` 必填；`upsert` 以它为业务键（**命中即更新**、未命中才新增）；
  没有任何服务能改它（`update` 不存在，`upsert` 回写的编号就是入参本身）
- **适用场景**: 同步（新增与更新）
- **计算方式**: 校验型（非空 + 存在性）
- **依赖输入**: `[sh_no(服务实参)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `stakeholder.upsert → 校验`
- **示例**: `upsert(sh_no="SH-001", name="航天科技集团", sh_type="customer")` 两次 →
  库里仍只有一条 `SH-001`（第二次是更新）；`upsert(sh_no="  ", …)` → 拒绝
- **依据**: 聚合根卡 11「来源：外部同步（机构与人员），本系统只读引用、不维护源数据」+
  卡片的标识就是 `sh_no`；与 `psc/md_customer` 的 `customer_no`（外部客户编码，必填、不可改）同口径

#### 3.2.2 `BR-02` 相关方名称必填

- **规则描述**: `name` 清洗（去首尾空白）后必须非空
- **适用场景**: 同步
- **计算方式**: 校验型（非空）
- **依赖输入**: `[name(服务实参)]`
- **输出**: `stakeholder.name`
- **生效点**: `stakeholder.upsert → 校验`
- **示例**: `upsert(sh_no="SH-900", name="   ", sh_type="customer")` → 拒绝
  「利益相关者名称不能为空」（**先 `_clean` 再判空**，否则 `"   "` 是真值会漏过去）
- **依据**: 材料 §4.1.1.2.1 的定义以"group or individual"为主体，名称就是它的识别信息；
  与同组各页"名称必填"一致

#### 3.2.3 `BR-03` 相关方类型必填且受字典约束

- **规则描述**: `sh_type ∈ {customer, contractor, internal_org}`，必填
- **适用场景**: 同步
- **计算方式**: 字典校验（+ 非空校验）
- **依赖输入**: `[sh_type(服务实参)]`
- **输出**: `stakeholder.sh_type`
- **生效点**: `stakeholder.upsert → 校验`
- **示例**: `upsert(…, sh_type="partner")` → 拒绝「相关方类型只能是 customer/contractor/internal_org 之一」；
  `sh_type="  "` → 拒绝「相关方类型不能为空」（两条**不是**同一条分支：先清洗判空，再查字典）
- **依据**: 聚合根卡 11 核心属性「类型（**客户 / 承包商 / 内部组织**）」；
  业务名逐字取自术语表「客户」「承包商」两行；"内部组织"取材料 TABLE 4.1-1 里的
  NASA Headquarters / NASA Centers / Mission Directorate 这类**项目内部单位**

#### 3.2.4 `BR-04` 期望必须挂在本聚合内（卡片 I-1）

- **规则描述**: 期望的读 / 写一律带 `sh_no`，且**先校验该相关方存在**；期望无独立业务编号
  （`(sh_no, seq)` 复合主键）；`get` 一次带回期望清单；**不提供**跨相关方的期望汇总视图
- **适用场景**: 加期望、改期望
- **计算方式**: 校验型（存在性）
- **依赖输入**: `[sh_no(服务实参)]`
- **输出**: 无（派生量：期望随相关方维护、无独立实体与编号）
- **生效点**: `stakeholder.add_expectation` / `update_expectation → 校验`
- **示例**: `add_expectation(sh_no="SH-999", …)` → 拒绝
  「利益相关者 SH-999 不存在 —— 期望必须挂在本聚合内（卡片 I-1）」；
  `update_expectation(sh_no="SH-001", seq=9, …)` → 拒绝「没有序号为 9 的期望」
- **依据**: **聚合根卡 11 的 I-1** 原话：「期望必须挂在本聚合内（期望随相关方维护，无独立标识）」

#### 3.2.5 `BR-05` 期望的陈述 / 类别 / 来源必填，类别受字典约束

- **规则描述**: `statement` 清洗后非空；`kind ∈ {need, goal, objective, moe, constraint}` 必填；
  `source` 清洗后非空
- **适用场景**: 加期望、改期望
- **计算方式**: 校验型（非空 + 字典）
- **依赖输入**: `[statement / kind / source(服务实参)]`
- **输出**: `stakeholder_expectation.statement` / `.kind` / `.source`
- **生效点**: `stakeholder.add_expectation` / `update_expectation`
- **示例**: `add_expectation(…, kind="wish")` → 拒绝「期望类别只能是 need/goal/objective/moe/constraint 之一」；
  `source="  "` → 拒绝「期望来源不能为空」
- **依据**: §4.1.1.2.5「Define Stakeholder Expectations in **Acceptable Statements**」（陈述）；
  §4.1.1.2.3「Identify **Needs, Goals, and Objectives**」（类别字典的前三项）+
  §4.1.1.2.6（MOE）+ §4.1.1.2.2 的 "operational constraints"（约束）；
  §4.1.1.2.7「**should also capture the source** of the expectation」（来源）

#### 3.2.6 `BR-06` 类别为「度量有效性（MOE）」的期望必须有度量口径

- **规则描述**: `kind = moe` 时 `moe`（度量口径）必填；`kind ≠ moe` 时选填；
  `update` 时判的是**合并后**的类别与口径（只改类别也要过这一关）
- **适用场景**: 加期望、改期望
- **计算方式**: 校验型（条件必填）
- **依赖输入**: `[kind / moe(服务实参 + 实体字段)]`
- **输出**: `stakeholder_expectation.moe`
- **生效点**: `stakeholder.add_expectation` / `update_expectation`
- **示例**: `add_expectation(…, kind="moe")` → 拒绝「必须填写度量口径」；
  `update_expectation(…, kind="moe")`（库里该条原有口径为空）→ 同样拒绝；
  `update_expectation(…, kind="moe", moe=">= 5K")` → 接受（同一次调用补齐）
- **依据**: §4.1.1.2.6 的活动名就是 "Analyze Expectations Statements for **Measures of
  Effectiveness**"；§4.1.1.3 Outputs 定义 "**Measures of Effectiveness**: A set of MOEs is developed
  based on the stakeholder expectations. These are measures that represent expectations that are
  **critical to the success of the system**" —— 标成 MOE 却不写口径，它和 goal 就没有区别了

#### 3.2.7 `BR-07` 已获相关方承诺的期望冻结（可撤回解锁）

- **规则描述**: `committed = 1` 时，**陈述 / 类别 / 来源 / 度量口径**不可改写（`note` 不受限）；
  把 `committed` 传 `0`（撤回承诺）即可解锁，**撤回与改写允许在同一次调用完成**
- **适用场景**: 改期望
- **计算方式**: 校验型（按当前承诺标记 + 本次是否仍为承诺态拦截）
- **依赖输入**: `[committed(实体字段与服务实参)]`
- **输出**: `stakeholder_expectation.committed` 与其余四个字段
- **生效点**: `stakeholder.update_expectation → 校验`（**守卫排最前**）
- **示例**: 对已承诺的 `(SH-001, 3)` 调 `update_expectation(statement=…)` → 拒绝
  「已获相关方承诺（材料 §4.1.1.2.8），陈述 / 类别 / 来源 / 度量口径不可改写 —— 要改请先撤回承诺」；
  `update_expectation(seq=3, note="已列入验证计划 V-007")` → 接受；
  `update_expectation(seq=3, committed=0, statement="…（修订）")` → 接受（一次调用完成撤回 + 改写）
- **依据**: 材料 §4.1.1.2.8（取得承诺）+ §4.1.1.2.9（"Any further changes will be required to go
  through a formal or informal approval process **involving both the stakeholder and the technical
  team**"）—— 见 §3.1.2 的完整推导

#### 3.2.8 `BR-08` `upsert` 的部分更新语义与承诺标记的归一

- **规则描述**:
  - 四个描述性字段（`duty` / `org` / `contact` / `project_no`）：**传 `None`（不传）= 不改**，
    **传空串 = 清空**（外部同步是**增量**推送，全量覆盖会把同步方没给的字段静默抹掉）
  - 承诺标记（`committed`）：`true` / `"1"` / `"yes"` / `"是"` → 1；`false` / `"0"` / `"no"` / `""` → 0；
    其余**拒绝**（不猜）
  - 期望序号（`seq`）：必须是正整数
- **适用场景**: 同步、改期望
- **计算方式**: 校验型（归一 + 拒绝非法）
- **依赖输入**: `[duty / org / contact / project_no / committed / seq(服务实参)]`
- **输出**: `stakeholder.duty` / `stakeholder.org` / `stakeholder.contact` / `stakeholder.project_no` / `stakeholder.committed` / `seq`
- **生效点**: `stakeholder.upsert` / `update_expectation`
- **示例**: 已有 `duty="用户方"`，`upsert(sh_no="SH-001", name="X", sh_type="customer")` →
  `duty` 仍是"用户方"；`upsert(…, duty="")` → 清空；
  `update_expectation(…, committed="也许")` → 拒绝「只能是 true / false」；
  `update_expectation(…, seq=0)` → 拒绝「期望序号必须是正整数」
- **依据**: 材料未规定同步协议的更新粒度，这是第②步的**工程口径**（登记在 `新增术语.md` §6）；
  「不猜」的理由同 `_flag` 的注释：静默把 `"no"` 当 1 是最糟的错法

### 3.3 业务数据

> 主档 7 项（`stakeholder` 表）+ 期望子表 8 项 + 2 个派生计数。列名见 `schema.sql`，此处给业务口径。

#### 3.3.1 数据1: 相关方编号（sh_no）

- **数据描述**: 相关方的唯一标识 —— **来自外部主数据**（机构与人员），本系统不生成、落库不可变
- **数据类型**: 文本（必填，主键）
- **数据来源**: 外部同步（`upsert` 的入参）
- **示例值**: "SH-001"

#### 3.3.2 数据2: 名称（name）

- **数据描述**: 机构名或人员名（列表与详情的第一识别项）
- **数据类型**: 文本（必填）
- **数据来源**: 外部同步
- **示例值**: "航天科技集团"

#### 3.3.3 数据3: 类型（sh_type）

- **数据描述**: 该相关方属于哪一类（材料 TABLE 4.1-1 按阶段给的相关方举例就是按类别点的）
- **数据类型**: 字典：customer / contractor / internal_org
- **数据来源**: 外部同步
- **字典对应业务名**: 客户 / 承包商 / 内部组织
- **示例值**: "customer"

#### 3.3.4 数据4: 职责（duty）

- **数据描述**: 该相关方在项目里承担什么（"他关心什么、他负责什么"）
- **数据类型**: 文本（选填）
- **数据来源**: 外部同步
- **示例值**: "用户方"

#### 3.3.5 数据5: 所属机构（org）

- **数据描述**: 机构名 —— 相关方来源是「**机构与人员**」两处，一条**人员**相关方靠它归口到机构
- **数据类型**: 文本（选填）
- **数据来源**: 外部同步
- **示例值**: "航天科技集团"
- **口径说明**: 本版**不区分**"这条是机构还是人员"（卡片核心属性里没有这一维）——
  机构本身也是一条相关方（`name` = 机构名），人员相关方用 `org` 指向其机构。
  ⚠ 若后续要做"只选人"的下拉（如 `requirement.owner` 的 autocomplete），需要给 `list` 加参数
  （属服务契约变更，见 §7.3）

#### 3.3.6 数据6: 联系方式（contact）

- **数据描述**: 怎么找到这个人 / 这个单位
- **数据类型**: 文本（选填）
- **数据来源**: 外部同步
- **示例值**: "张工 138****"
- **依据**: 材料 §4.1.1.2.2 列举的 elicit 手段（interviews/discussions、surveys、e-mails）都以
  "知道找谁、怎么找"为前提

#### 3.3.7 数据7: 所属项目（project_no）

- **数据描述**: 该相关方参与的项目
- **数据类型**: 文本（选填）
- **数据来源**: 外部同步
- **示例值**: "P-2026-01"

#### 3.3.8 数据8: 期望序号（seq，聚合内子表）

- **数据描述**: 该条期望在本相关方内的序号（**不是**业务编号 —— 期望无独立标识，卡片 I-1）
- **数据类型**: 整数（本相关方内唯一，与 `sh_no` 组成复合主键）
- **数据来源**: 系统生成（`add_expectation` 时取"本相关方内最大 seq + 1"）
- **示例值**: `3`

#### 3.3.9 数据9: 期望陈述（statement，聚合内子表）

- **数据描述**: 期望的正文 —— 材料要求写成**可接受的陈述**（§4.1.1.2.5）
- **数据类型**: 文本（必填）
- **数据来源**: 人工录入
- **示例值**: "全任务周期内可靠运行"

#### 3.3.10 数据10: 期望类别（kind，聚合内子表）

- **数据描述**: 这条期望是哪一类（材料把它们分成 Need / Goal / Objective，另有 MOE 与约束）
- **数据类型**: 字典：need / goal / objective / moe / constraint（必填）
- **数据来源**: 人工选择
- **字典对应业务名**: 需要（Need）/ 目标（Goal）/ 指标（Objective）/ 度量有效性（MOE）/ 约束（Constraint）
- **示例值**: "moe"
- **依据**: §4.1.1.2.3 "Identify **Needs, Goals, and Objectives**"、§4.1.1.2.6 "Measures of
  Effectiveness"、§4.1.1.2.2 "operational **constraints**"

#### 3.3.11 数据11: 期望来源（source，聚合内子表）

- **数据描述**: 这条期望从哪来（访谈 / 调查 / SOW / 上级需求 / 战略规划…）
- **数据类型**: 文本（必填）
- **数据来源**: 人工录入
- **示例值**: "访谈"
- **依据**: §4.1.1.2.7 "The NGOs or other stakeholder expectation documentation **should also
  capture the source of the expectation**. Depending on the location within the product layer, the
  expectation may be traced to an NGO or a requirement of a higher layer product, to organizational
  strategic plans, or **other sources**." —— 材料给的是**开放式**清单，故本字段是自由文本而非字典

#### 3.3.12 数据12: 度量口径（moe，聚合内子表）

- **数据描述**: 这条期望**怎么算达成**（可度量的成功判据）
- **数据类型**: 文本（**条件必填**：`kind = moe` 时必填，见 `BR-06`）
- **数据来源**: 人工录入
- **示例值**: ">= 99.9%"

#### 3.3.13 数据13: 已获相关方承诺（committed，聚合内子表）

- **数据描述**: 相关方是否已就这条期望**给出承诺**（§4.1.1.2.8 的"签字"）
- **数据类型**: 整数 0 / 1（缺省 0）
- **数据来源**: 人工标记
- **示例值**: `1`
- **口径说明**: 这是**期望行**的属性，不是整条相关方的状态（见 §3.1.3）

#### 3.3.14 数据14: 备注（note，聚合内子表）

- **数据描述**: 跟踪留痕（"已列入验证计划 V-007"这类）
- **数据类型**: 文本（选填）
- **数据来源**: 人工录入
- **示例值**: "已列入验证计划 V-007"
- **口径说明**: **不受 `BR-07` 冻结影响**（承诺之后仍可写）

#### 3.3.15 派生字段（`get` 与 `list` 同口径，不落库）

| 字段 | 口径 |
|---|---|
| `expectation_total` | 本相关方的期望条数 |
| `committed_total` | 已获承诺（`committed = 1`）的期望条数 |

### 3.4 状态机

```
（无）

卡片 11：「状态机：无（主数据，只读引用为主）」。
```

**本聚合为什么没有状态机**，以及"没有"落到哪三个可观测事实上（本步必须交代清楚，
否则"少了一个状态机"会被读成"漏做了一节"）：

| # | 事实 | 在哪看 |
|---|---|---|
| 1 | 表里**没有** `status` 列 | `schema.sql` 的 `stakeholder` 与 `stakeholder_expectation`；链测试 TC-29 用 `PRAGMA table_info` 断言 |
| 2 | 服务里**没有**任何流转服务 | 服务只有 `upsert` / `add_expectation` / `update_expectation` / `get` / `list`；链测试 TC-29 逐名断言 `create` / `delete` / `obsolete` / `archive` / `close` / `update_status` 均「无此服务」 |
| 3 | **没有 `create`** | 主档唯一的写入口是 `upsert`（外部同步），编号由外部来源给定（`BR-01`） |

**那么"每个状态都要有服务能到达"这条门禁怎么落？** —— 它对本聚合**不适用**，理由见 §3.1.3。
替代它的是**两条写轴各自的可达性**，这两条同样是可测的：

| 写轴 | 到达方式 | 守卫 |
|---|---|---|
| **主档**：不存在 ⇄ 存在 | `upsert`（同一入口既新增也更新 —— 幂等） | `BR-01` / `BR-02` / `BR-03` |
| **期望**：未承诺 ⇄ 已承诺 | `update_expectation(committed=0/1)`（**双向可达**） | `BR-07`（已承诺时口径字段冻结） |

> ⚠ **没有终态**：本聚合不像同组各页那样有"到达即不可逆"的硬终态 ——
> 承诺**可撤回**（`committed` 双向）、同步**可反复**（`upsert` 幂等）。
> 这是主数据的形状，也是"不留解锁口就没人敢用"的现实：机构会改名、人会换岗、期望会重谈。

## 4. 功能描述

### 4.1 功能清单

| 编号 | 功能 | 对应 US | 服务 | 说明 |
|---|---|---|---|---|
| `FUNC-01` | 同步相关方 | US-01 | `upsert` | 唯一写主档的入口；编号由外部来源给定；存在即更新（幂等） |
| `FUNC-02` | 登记期望 | US-03 / US-04 | `add_expectation` | 聚合内子表，`seq` 本相关方内递增；MOE 必须带口径（`BR-06`） |
| `FUNC-03` | 维护期望 | US-04 / US-05 | `update_expectation` | 改陈述 / 类别 / 来源 / 口径 / 承诺 / 备注；已承诺则口径字段冻结（`BR-07`） |
| `FUNC-04` | 相关方列表 | US-06 | `list` | 分页 `{items, total}`，与 `get` 同字段口径；类型精确 / 关键字模糊 / 所属项目 |
| `FUNC-05` | 相关方详情 | US-06 | `get` | 主档 + 期望清单 + 两个派生计数；未命中返回 `None` |

> **功能数只有 5 个**，是同组最少的一页 —— 因为主数据只做三件事：**同步进来、把期望挂上去、查**。
> 没有状态流转功能，也就没有"按状态显隐的按钮组"这一整块（见 `前端详设.md` §3）。

### 4.2 功能模块结构图

```
利益相关者 stakeholder
├── 主档（外部同步：机构与人员）
│   └── FUNC-01 同步相关方（upsert：新增 / 更新，幂等）
├── 期望清单（聚合内子表，卡片 I-1：无独立标识）
│   ├── FUNC-02 登记期望（陈述 + 类别 + 来源 [+ MOE 口径]）
│   └── FUNC-03 维护期望（含承诺冻结与撤回解锁）
└── 查询
    ├── FUNC-04 相关方列表（类型 / 关键字 / 所属项目）
    └── FUNC-05 相关方详情（含期望清单与派生计数）
```

### 4.3 功能详细说明

#### 4.3.1 同步相关方（FUNC-01）

- **输入**: 编号、名称、类型、职责、所属机构、联系方式、所属项目
- **校验**: `BR-01`（编号非空）、`BR-02`（名称非空）、`BR-03`（类型字典）；选填字段按 `BR-08` 归一
- **处理**: 编号命中 ⇒ `UPDATE`（只写"传了的"字段）；未命中 ⇒ `INSERT`
- **输出**: 更新后的相关方（含空/既有期望清单与两个派生计数）

#### 4.3.2 登记期望（FUNC-02）

- **输入**: `sh_no` + 陈述 + 类别 + 来源 [+ 度量口径] [+ 承诺] [+ 备注]
- **校验**: `BR-04`（相关方存在）、`BR-05`（陈述 / 类别 / 来源非空 + 类别字典）、
  `BR-06`（MOE 必须有口径）、`BR-08`（承诺标记归一）
- **处理**: `seq = 本相关方内最大 seq + 1` → 插入子表
- **输出**: 更新后的相关方（含刷新后的期望清单与派生计数）

#### 4.3.3 维护期望（FUNC-03）

- **输入**: `sh_no` + `seq` [+ 陈述 / 类别 / 来源 / 度量口径 / 承诺 / 备注]
- **校验**: **守卫顺序（= 安全边界）**：`BR-04` 相关方存在 → 序号正整数 → 序号命中 →
  **`BR-07` 承诺冻结（排在校验之前）** → 逐字段非空与字典 → `BR-06`（**合并后**的类别与口径）
  → 无字段可改则拒绝
- **处理**: 按传入字段拼 `UPDATE`（`None` = 不改）
- **输出**: 更新后的相关方

#### 4.3.4 相关方列表（FUNC-04）

- **输入**: 类型（精确）/ 关键字（跨字段模糊：编号 / 名称 / 所属机构 / 职责）/ 所属项目（精确）+
  分页 `page` / `size`
- **校验**: 筛选值先 `_clean`（空白 = 不过滤）
- **处理**: 单条 SQL 取主档全字段 → 每行一次子表计数（**非 N+1 取明细**）→ 服务端切片
- **输出**: `{"items": [...], "total": 切片前全量行数}`

#### 4.3.5 相关方详情（FUNC-05）

- **输入**: `sh_no`
- **校验**: 编号空白 → 直接返回 `None`（不抛异常，供探测式调用）
- **处理**: 主档 + 期望清单（按 `seq` 升序）+ 派生计数
- **输出**: 相关方字典 / `None`（未命中）

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 同一编号再次同步不产生第二条（`BR-01`）

**Given** `SH-001` 已在库中
**When** 再以相同编号 `upsert`（哪怕只给名称与类型）
**Then** 库里仍只有一条 `SH-001`，名称 / 类型被更新，其余字段保持原值

#### 6.1.2 标准2: 期望必须挂在本聚合内（卡片 I-1）

**Given** 相关方 `SH-999` 不存在
**When** `add_expectation(sh_no="SH-999", …)`
**Then** 拒绝，提示「期望必须挂在本聚合内（卡片 I-1）」
**And given** `SH-001` 只有 3 条期望，**when** `update_expectation(seq=9)`，
**then** 拒绝，提示「没有序号为 9 的期望」

#### 6.1.3 标准3: MOE 类期望必须有度量口径（`BR-06`）

**Given** 相关方 `SH-003` 处于"无期望"状态
**When** `add_expectation(kind="moe")` 且不给口径
**Then** 拒绝，提示「必须填写度量口径（BR-06）」
**And given** 一条已有 `goal` 期望（无口径），**when** 只把类别改成 `moe`，
**then** 同样拒绝（判的是**合并后**的口径）

#### 6.1.4 标准4: 已获承诺的期望冻结，且冻结可解锁（`BR-07`）

**Given** `(SH-001, 3)` 已标记承诺
**When** 改陈述 / 类别 / 来源 / 度量口径
**Then** 全部拒绝（提示指向"先撤回承诺"）
**And given** 只改备注，**then** 接受
**And given** `committed=0` + 新陈述（**同一次调用**），**then** 接受，且该条变回"未承诺"

#### 6.1.5 标准5: 主数据形态 —— 没有 `create` / 没有 `delete` / 没有状态

**Given** 本应用已加载
**When** 调用 `create` / `delete` / `obsolete` / `close` / `update_status` 等
**Then** 全部返回「无此服务」
**And given** `get(SH-001)`，**then** 返回里**没有** `status` 字段；
**and given** `PRAGMA table_info(stakeholder)`，**then** 表里**没有** `status` 列

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms（含派生计数：每行一次子表计数，非 N+1 取明细）
- `upsert` 幂等：同一编号重复同步不产生重复行、不改动未传字段
- `get` 未命中**不抛异常**，返回 `None`（供 `requirement` / `review` 探测式调用）
- `get` 返回的 `expectation_total` / `committed_total` 与 `list` 行**同口径**（共用 `_counts` 算法）
- 「撤回承诺 + 改写陈述」与状态**同一次调用落库**（链测试 TC-16 验证）
- 被拒的写入**零副作用**：整次调用不落库（链测试 TC-22 / TC-24 前后计数不变）

### 6.3 已知问题或限制

- **`requirement` / `review` 尚未接入本应用**（**本次交付的连带影响，留给后续迭代**）——
  那两页的 `owner`（需求责任人）与相关方目前是**纯文本**字段，各自详设 §6.3 记了
  "待 `stakeholder` 建成后改为 autocomplete"。**本应用已就绪**，
  接口形状见 §7.3；接线时需要改的是那两个应用（本任务范围不含改别人的文件）。
- **不区分"机构相关方"与"人员相关方"** —— 卡片核心属性里没有这一维，本版用
  `name`（机构名或人名）+ `org`（人员的所属机构）表达。
  ⚠ 后果：`requirement.owner` 的 autocomplete 会**同时列出一个机构**（因为 `sh_type` 是
  客户/承包商/内部组织的**机构维度**，不是"人 / 单位"维度）。要"只选人"，需给 `list` 加参数
  （如 `party_kind`）或加一列 —— 那是**服务契约变更**，须重跑 `contract_dump` 重新冻结
  `_contracts.md`，故本版不做（详见 §7.3 的"两条路"）。
- **期望的基线化（§4.1.1.2.9）不在本应用** —— 理由见 §1.3.2：期望基线的载体是需求基线
  （`requirement.baseline`）。本应用只标记"已获承诺"（§4.1.1.2.8），不引入冻结终态。
- **没有跨相关方的期望汇总视图** —— 理由见 §1.3.2 与 `BR-04`（卡片 11 无「并入说明」类要求）。
  若将来确实要"一屏看全部未承诺期望"，那是一个**查询视图服务**（形如 `list_expectations`），
  属新增服务而非新增聚合 —— 但本版刻意不加，避免把期望的语义边界拉开。
- **没有同步状态 / 同步批次记录** —— 本版 `upsert` 逐条同步，不留"这批同步了几条、谁触发的"；
  平台审计列（`created_by` / `updated_at`）能回答"最后谁改的、什么时候"。
  若接入真实外部系统，按 CONVENTION §12.2 把 HTTP 调用封在 `_` 前缀适配器里（`_EXTERNAL_ADAPTERS`），
  **不改**公共方法签名。
- **期望不可删除** —— 只有"加"与"改"。登记错了改掉即可；认为整条不该存在的，
  正确做法是**改写成最终结论**（如"经复核，该项不构成期望"）而不是抹掉痕迹
  （§4.1.1.2.10 的 Capture Work Products 口径）。
- **`seq` 在本相关方内唯一，不是全局编号** —— 期望没有业务编号（卡片 I-1 的"无独立标识"），
  跨应用引用期望时必须同时给出 `sh_no` 与 `seq`。

#### 7.3.1 供 `requirement` / `review` 接入的接口形状（**本节的用意：那两页的后续迭代照此接线**）

> 背景：`requirement.owner`（需求责任人）与 `review` 的相关方当前是**纯文本**，
> 各自详设 §6.3 记了"待 `stakeholder` 建成后改为 autocomplete"。本应用已建成，
> 形状如下（**逐字取自 `stakeholder.py` 的公共方法签名**；`_contracts.md` 的冻结由组级统一 dump 完成）：

```
list(sh_type=None, keyword=None, project_no=None, page=None, size=None)
    返回 {"items": [...], "total": n}
    items[i] = {sh_no, name, sh_type, duty, org, contact, project_no,
                expectation_total, committed_total}
    · sh_type  ：精确匹配，取值 customer / contractor / internal_org（空白 = 不过滤）
    · keyword  ：**跨字段模糊**（编号 / 名称 / 所属机构 / 职责 四列 LIKE %kw%）—— autocomplete 用这个
    · project_no：精确匹配（空白 = 不过滤）
    · page/size：分页；size 给了才切片（total 恒为切片前全量）

get(sh_no=None) → {...} | None      # 未命中返回 None，不抛异常（探测式调用安全）
```

**两条接线路（按需要的强度选一条）**：

| 路 | 做法 | 代价 |
|---|---|---|
| **A. 最小改动（推荐先做）** | 把 `owner` / 相关方输入框换成 **autocomplete**：输入片段 → `svc("stakeholder","list",{keyword: 片段, size: 20})` → 候选显示 `name`（右侧灰字带 `typeName(sh_type)` 与 `org`），选中后**写入 `name`**。**不改库、不改契约、不改 `_contracts.md`**（`owner` 保持文本） | 无强引用：写进去的名字不校验存在性（与现状同） |
| **B. 强引用（需要校验时）** | 在 `requirement` / `review` 里**新增** `owner_no` 字段，`create`/`update` 里加 `self.fde.call("stakeholder", "get", sh_no=…)` 的存在性校验（**必须字面量**，否则扫描器标"动态目标"）；校验是**弱引用**（跨应用非同一事务，可悬空留空） | 服务签名变了 ⇒ **重跑 `contract_dump` 重新冻结 `_contracts.md`**；两页的表单/列表/测试都要跟着改 |

**给 autocomplete 的两条注意事项**（本应用侧已就绪，接线方需知道）：

1. **不区分机构与人员**：`sh_type` 是"客户 / 承包商 / 内部组织"的**机构维度**，
   一个机构与一个人都可能出现在候选里（人员相关方用 `org` 指向其机构）。
   若要"只列人"，须给 `list` 加参数（如 `party_kind`）或加一列 —— **属服务契约变更**，
   要重跑 `contract_dump`，故本版不做（已记入 §6.3）。
2. **前端调用用短名**：页面里写 `svc("stakeholder", "list", …)`（壳自动补组前缀）；
   **测试脚本走 REST 时用组限定名** `nasa_pms/stakeholder`（短名 404「应用不存在」）。
