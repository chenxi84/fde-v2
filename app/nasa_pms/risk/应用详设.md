## 1. 风险概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `risk` |
| 类名 | `Risk` |
| 聚合根 | 风险 |
| 标识 | `risk_no` |
| 数据来源类型 | **独立创建**（风险由项目内人员识别录入，无上游自动生成） |

### 1.2 需求背景

#### 1.2.1 为什么需要这个需求？

材料（NASA SE Handbook Rev 2 §6.4）把风险管理定义为贯穿全生命周期的横切过程，并明确风险的
**三元组**表述：**情景（scenario）→ 可能性（likelihood）→ 后果（consequence）**。
§6.4.1.2.2 要求技术团队持续识别风险并"准备清晰的**风险陈述**（clear risk statements）录入
项目风险管理体系"；§6.4.1.2.3 要求对风险做评估；§6.4.1.2.4 要求按**风险等级/阈值**决定
哪些风险进入缓解；§6.4.1.3 的输出是"缓解/应急动作"与"技术风险报告"。

现状是风险躺在会议纪要里：**没有编号、没有等级依据、没有关闭口径** ——
"这条风险怎么来的、等级怎么定的、什么时候算关掉了"都答不上来。

#### 1.2.2 期望达到什么目标？

- 每条风险**可编号、可跟踪**（识别 → 评估 → 缓解 → 关闭）
- 风险等级**由可能性 × 后果推导**，不允许"拍脑袋填一个高"
- 关闭风险**必须给出处置结论**（接受 / 缓解完成 / 转移），不留"挂了但没说怎么挂的"的悬案
- 风险可**弱引用**它影响的（技术）需求，形成"风险 ↔ 需求"的可追溯链

### 1.3 需求范围

#### 1.3.1 包含哪些功能？

- 风险的识别、修改、查询、列表
- **评估等级**：写入可能性 / 后果，等级与风险值由二者推导
- **登记缓解措施**：进入「缓解中」
- **关闭**：给出处置结论（接受 / 缓解完成 / 转移）并进入终态
- 风险与 `requirement` 通过**弱引用**关联（跨应用只读校验）

#### 1.3.2 不包含哪些功能？

- **不做风险报告 / 状态报告生成** —— §6.4.1.2.5「周期性监控与报告」是**查询视图**，不是本聚合的状态
- **不做风险汇总台账页** —— 跨应用聚合属组级看板（`app/nasa_pms/dashboard.*`）
- **不维护需求本体** —— 属 `requirement` 聚合，本应用只读引用其编号
- **不做告警** —— 等级跃升后的通知属平台能力（`fde_platform/alerts.py`），本应用只负责把等级算出来

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 系统工程师 | 识别风险、评估等级、登记缓解措施 | 材料 §6.4.1.2.2 / §6.4.1.2.3 |
| 风险责任人 | 对单条风险的缓解与关闭负责（`owner` 字段） | 材料 §6.4.1.2.4「明确哪些相关方需要被告知」 |
| 项目经理 | 决定以「接受」收尾（低于阈值的风险） | 材料 §6.4.1.2.6 阈值触发口径 |

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 识别一条技术风险（优先级：P1）

**作为一名**系统工程师
**我希望**录入一条技术风险（含标题、风险情景、类别，可附可能性/后果与受影响需求）
**以便**它能进入风险台账被持续跟踪

**验收条件**：
- 给定标题、风险情景、类别齐备，当提交时，则新风险以「识别」状态落库，编号自动生成
- 给定风险情景为空，当提交时，则**拒绝**并提示「风险情景不能为空」
- 给定只填了可能性没填后果，当提交时，则**拒绝**（等级必须成对推导，`BR-01`）
- 给定填了受影响需求 `REQ-999` 而它不存在，当提交时，则**拒绝**（`BR-07`，跨应用校验）

#### 2.1.2 `US-02` 用户故事 — 评估风险等级（优先级：P1）

**作为一名**系统工程师
**我希望**填上可能性与后果，由系统推导等级
**以便**缓解与否有客观依据，而不是主观判断

**验收条件**：
- 给定可能性 3、后果 4，当评估时，则风险值 = 12、等级 = 「高」，状态变「分析中」
- 给定可能性 5、后果 5，当评估时，则等级 = 「严重」（≥16）
- 给定在任何写服务里试图直接写等级，则**不可能**（`create` / `update` 都没有等级入参，`BR-01`）

#### 2.1.3 `US-03` 用户故事 — 缓解与关闭风险（优先级：P1）

**作为一名**风险责任人
**我希望**登记缓解措施并在时机成熟时以明确的口径关闭风险
**以便**风险不会"悬着"，关闭有据可查

**验收条件**：
- 给定一条未评估等级的风险，当登记缓解措施时，则**拒绝**（缓解须在分析之后）
- 给定风险已登记缓解措施，当以「缓解完成」关闭时，则状态变「已关闭」，`disposition = mitigated`
- 给定一条等级为「严重」的风险，当试图以「接受」关闭时，则**拒绝**（`BR-03`），须缓解或转移
- 给定不带处置结论直接关闭，则**拒绝**并提示必须给出处置结论（`BR-02`）
- 给定风险已处于终态，当再改 / 再评 / 再缓解 / 再关闭时，则**一律拒绝**（`BR-06`）

#### 2.1.4 `US-04` 用户故事 — 查询风险台账（优先级：P2）

**作为一名**项目经理
**我希望**按类别 / 状态 / 等级 / 受影响需求筛选风险
**以便**在评审前看到"高等级未关闭"的风险清单

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序，分页返回 `{items, total}`）

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 风险从识别到关闭（本应用主链）

1. 系统工程师识别风险，录入**标题 + 风险情景 + 类别**（材料 §6.4.1.2.2 的"clear risk statements"）
2. 对该风险做**评估**：给出可能性与后果，系统推导**风险值**与**风险等级**（§6.4.1.2.3）
3. 等级达到阈值 → 按 §6.4.1.2.4 选择进入缓解，**登记缓解措施**
4. 缓解完成 / 转移给外部承担 / 决定接受 → **关闭**并给出处置结论（§6.4.1.2.6 / §6.4.1.3）
5. 关闭后记录**保留**（终态不可改），供周期性报告与评审取数

#### 3.1.2 场景2: 风险指向受影响的需求（跨应用）

1. 识别风险时，从**需求台账**（`requirement.list`）里选择受影响的需求编号
2. 写入时本应用经 `requirement.get` **校验该需求存在**（BR-07，跨应用只读，非同一事务）
3. 需求后续被作废时，风险**不受影响、不级联** —— 弱引用允许悬空（与 `requirement` 的
   `source_req_no` 同一口径）

### 3.2 业务规则

#### 3.2.1 `BR-01` 风险等级由可能性 × 后果推导，不允许直接写入

- **规则描述**: `risk_score = likelihood × consequence`；`risk_level` 按分档规则由 `risk_score` 推导。
  `create` / `update` / `close` **都没有**等级入参；唯一能改那对取值的是 `assess`
- **适用场景**: 创建、评估、修改
- **计算方式**: 计算型 —— `score = likelihood × consequence`（1..25）；
  分档 `≤4 → low（低）` · `5..9 → medium（中）` · `10..15 → high（高）` · `≥16 → critical（严重）`
- **依赖输入**: `[likelihood(实体字段), consequence(实体字段)]`
- **输出**: `risk.risk_score`、`risk.risk_level`
- **生效点**: `risk.create → 校验+推导` / `risk.assess → 推导`
- **示例**: 可能性 3 × 后果 4 = 12 → 「高」；可能性 5 × 后果 5 = 25 → 「严重」
- **依据**: 材料 §6.4「Key Concepts in Risk Management」把风险定义为三元组，
  可能性与后果是**输入**、等级是**结论**；§6.4.1.2.4 又要求按"风险等级或阈值"触发缓解动作 ——
  等级若可随手写，阈值就失去意义。分档阈值材料未逐格给出，本应用按 5×5 均匀四档实现（见 §6.3）

#### 3.2.2 `BR-02` 关闭风险必须给出处置结论

- **规则描述**: `close` **只接受「缓解中」的风险**（§3.4 状态机：`mitigating → close`，这是入口闸）；
  其 `disposition` 必填且受字典约束（`mitigated` 缓解完成 / `transferred` 转移 / `accepted` 接受）；
  结论为 `mitigated` 时**必须已登记缓解措施**（状态闸之后这条已成**防御性不变量**，见下）
- **适用场景**: 关闭
- **计算方式**: 校验型
- **依赖输入**: `[status(实体字段), disposition(入参), mitigation(实体字段)]`
- **输出**: `risk.status`（`accepted` → 已接受；其余 → 已关闭）、`risk.disposition`、`risk.close_note`
- **生效点**: `risk.close → 校验`（守卫顺序：存在性 → 终态 BR-06 → **状态闸** → 结论非空 → 字典 → BR-02 → BR-03）
- **示例**: 「分析中」的风险直接关闭 → 拒绝（须先 `assess` 再 `mitigate`）；给出「转移」+ 说明 → 落库为已关闭
- **⚠ 2026-09-25 补闸**：此前 `close` **没有状态闸**（实现与 §3.4 状态机不一致）—— 实测后果是
  「识别」态且**从未评估**的风险给个「转移」就能直接关闭，而 `BR-03` 因为 `risk_level` 为空**完全拦不住**
  「高风险径直接受」。补闸后 BR-03 的适用前提（等级已推导）才成立。
- **依据**: 材料 §6.4.1.3 把"缓解/应急动作"与"残余风险"列为**风险输出** ——
  没有处置结论的关闭等于没有输出。与聚合根卡 2 的不变量 I-1 逐字对应

#### 3.2.3 `BR-03` 等级为「高」及以上不得以「接受」关闭

- **规则描述**: `risk_level ∈ {high, critical}` 时，`disposition` 不可为 `accepted`
- **适用场景**: 关闭
- **计算方式**: 校验型（按等级拦截）
- **依赖输入**: `[risk_level(实体字段), disposition(入参)]`
- **输出**: 拒绝流转（`risk.status` 不变）
- **生效点**: `risk.close → 校验`
- **示例**: 「严重」风险以「接受」关闭 → 拒绝，提示须缓解或转移
- **依据**: 材料 §6.4.1.2.4「identifying the risk level or threshold that will trigger a risk mitigation
  action plan」—— 达到阈值就**必须**进入缓解/转移，不能原地接受。这是本应用对"阈值"的可执行化
  （**属解读，非材料原话**，见 §6.3）

#### 3.2.4 `BR-04` 风险编号唯一且不可变

- **规则描述**: `risk_no` 落库后不得修改；全局唯一
- **适用场景**: 创建、修改
- **计算方式**: 唯一性校验
- **依赖输入**: `[risk_no(实体字段)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `risk.create` / `risk.update`（update 不提供编号参数）
- **示例**: 试图把 `RSK-001` 改成别的编号 → 无入口

#### 3.2.5 `BR-05` 类别 / 可能性 / 后果受字典约束

- **规则描述**: `category ∈ {technical, cost, schedule, programmatic, safety}`；
  `likelihood`、`consequence ∈ {1,2,3,4,5}`
- **适用场景**: 创建、评估、修改
- **计算方式**: 字典校验
- **依赖输入**: `[category, likelihood, consequence(实体字段)]`
- **输出**: `risk.category` / `risk.likelihood` / `risk.consequence`
- **生效点**: `risk.create` / `risk.update` / `risk.assess`
- **示例**: 类别填「其它」→ 拒绝；可能性填 6 → 拒绝
- **依据**: 材料 §6.4 的 Key Concepts 逐条列出 Technical / Cost / Schedule / Programmatic Risk
  与 safety 域

#### 3.2.6 `BR-06` 终态（已关闭 / 已接受）不得再修改

- **规则描述**: `status ∈ {closed, accepted}` 时，`update` / `assess` / `mitigate` / `close` **一律拒绝**
- **适用场景**: 修改、评估、缓解、关闭
- **计算方式**: 校验型（按状态拦截）
- **依赖输入**: `[status(实体字段)]`
- **输出**: 无（拒绝：终态记录一律不可流转 —— 四个写服务共用一个守卫）
- **生效点**: 四个写服务共用一个 `_check_mutable` 守卫
- **示例**: 对已关闭风险登记缓解措施 → 拒绝
- **依据**: 材料 §6.4.1.3 的"技术风险报告"要求状态与残余风险可复现 ——
  终态记录被改写会让历史报告失去依据

#### 3.2.7 `BR-07` 受影响需求必须真实存在

- **规则描述**: `req_no` 可留空（弱引用）；填了则必须能在 `requirement` 中查到
- **适用场景**: 创建、修改
- **计算方式**: 跨应用校验（`self.fde.call("requirement", "get", ...)`，**只读、非同一事务**）
- **依赖输入**: `[req_no(实体字段), requirement(上游服务实参)]`
- **输出**: `risk.req_no`
- **生效点**: `risk.create → 校验` / `risk.update → 校验`
- **示例**: 填 `REQ-999`（不存在）→ 拒绝，提示先录入需求
- **依据**: 聚合根卡 2「引用的聚合：requirement（弱引用，风险指向受影响的需求）」

### 3.3 业务数据

#### 3.3.1 数据1: 风险编号（risk_no）

- **数据描述**: 风险的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`RSK-` + 序号）
- **示例值**: "RSK-001"

#### 3.3.2 数据2: 风险标题（title）

- **数据描述**: 一句话概括，用于列表展示
- **数据类型**: 文本（≤120 字）
- **数据来源**: 人工录入
- **示例值**: "ICD 未按期冻结"

#### 3.3.3 数据3: 风险情景（statement）

- **数据描述**: 触发事件 → 不良后果的链条（材料 §6.4 风险三元组的第 1 项 scenario）
- **数据类型**: 长文本
- **数据来源**: 人工录入
- **示例值**: "若分系统接口控制文档未在 PDR 前冻结，集成阶段将出现接口不匹配，导致返工与进度滑移"

#### 3.3.4 数据4: 风险类别（category）

- **数据描述**: 风险所属领域
- **数据类型**: 字典：technical / cost / schedule / programmatic / safety
- **数据来源**: 人工选择
- **字典对应业务名**: 技术风险 / 成本风险 / 进度风险 / 程序性风险 / 安全风险（术语表）
- **示例值**: "technical"

#### 3.3.5 数据5: 可能性（likelihood）

- **数据描述**: 该情景发生的可能性（材料三元组第 2 项）
- **数据类型**: 整数 1..5（未评估为空）
- **数据来源**: 人工选择（评估时）
- **示例值**: 4

#### 3.3.6 数据6: 后果（consequence）

- **数据描述**: 情景发生时性能退化的严重程度（材料三元组第 3 项）
- **数据类型**: 整数 1..5（未评估为空）
- **数据来源**: 人工选择（评估时）
- **示例值**: 4

#### 3.3.7 数据7: 风险值（risk_score）

- **数据描述**: `可能性 × 后果`，1..25
- **数据类型**: 整数（**推导值**）
- **数据来源**: 系统按 `BR-01` 推导
- **示例值**: 16

#### 3.3.8 数据8: 风险等级（risk_level）

- **数据描述**: 由风险值分档得到，是"要不要缓解"的判据
- **数据类型**: 字典：low / medium / high / critical（**推导值**）
- **数据来源**: 系统按 `BR-01` 推导
- **字典对应业务名**: 低 / 中 / 高 / 严重（术语表）
- **示例值**: "critical"

#### 3.3.9 数据9: 缓解措施（mitigation）

- **数据描述**: 降低该风险的动作（材料 §6.4.1.2.4 / §6.4.1.3 的 mitigation action）
- **数据类型**: 长文本
- **数据来源**: 人工录入（`mitigate` 服务）
- **示例值**: "提前开展接口冻结评审，并准备接口适配回退方案"

#### 3.3.10 数据10: 受影响需求（req_no）

- **数据描述**: 这条风险会影响哪条（技术）需求（弱引用，可留空、可悬空）
- **数据类型**: 文本
- **数据来源**: 人工选择（跨应用下拉：`requirement.list`）
- **示例值**: "REQ-001"

#### 3.3.11 数据11: 责任人（owner）

- **数据描述**: 对这条风险的缓解与关闭负责的人
- **数据类型**: 文本
- **数据来源**: 人工录入（`stakeholder` 应用未建成，暂按文本，见 §6.3）
- **示例值**: "张三"

#### 3.3.12 数据12: 状态（status）

- **数据描述**: 风险在生命周期中的位置
- **数据类型**: 字典：identified / analyzing / mitigating / closed / accepted
- **数据来源**: 系统按流转规则变更
- **字典对应业务名**: 识别 / 分析中 / 缓解中 / 已关闭 / 已接受
- **示例值**: "analyzing"

#### 3.3.13 数据13: 处置结论（disposition）

- **数据描述**: 关闭时给出的收尾口径
- **数据类型**: 字典：mitigated / transferred / accepted（关闭才写）
- **数据来源**: 人工选择（`close` 服务）
- **字典对应业务名**: 缓解完成 / 转移 / 接受
- **示例值**: "transferred"

#### 3.3.14 数据14: 处置说明（close_note）

- **数据描述**: 处置结论的补充说明（如转移给谁）
- **数据类型**: 文本
- **数据来源**: 人工录入（选填）
- **示例值**: "转移给分系统承包商承担"

### 3.4 状态机

```
identified（识别）
   │ create 完成（可能性 / 后果可暂缺，缺则等级为空）
   │
   │ assess（写入 可能性 × 后果 → 推导风险值与等级）
   ▼
analyzing（分析中）
   │ mitigate（登记缓解措施）
   ▼
mitigating（缓解中）
   │
   ├── close（处置结论 = 缓解完成 / 转移）────────► closed（已关闭）
   │
   └── close（处置结论 = 接受，且等级 ≤ 中）──────► accepted（已接受）

   · **`close` 只认「缓解中」**（2026-09-25 起由服务端强制，前端也只在该态显示「关闭」按钮）
   · 终态（closed / accepted）**无出边** —— update / assess / mitigate / close 一律拒绝（BR-06）
   · BR-03：等级为「高」/「严重」时，`accepted` 这条边**不可用**
   · 状态机里的每个状态都有服务能到达：create→identified / assess→analyzing /
     mitigate→mitigating / close→closed / close→accepted
```

## 4. 功能描述

### 4.1 功能清单

| 编号 | 功能 | 对应 US | 说明 |
|---|---|---|---|
| `FUNC-01` | 识别风险 | US-01 | create（可能性/后果可暂缺；等级不可入参） |
| `FUNC-02` | 评估等级 | US-02 | assess（唯一能改等级的入口，BR-01） |
| `FUNC-03` | 登记缓解措施 | US-03 | mitigate（要求等级已评估） |
| `FUNC-04` | 关闭风险 | US-03 | close（须有处置结论，BR-02 / BR-03） |
| `FUNC-05` | 修改风险 | US-01 | update（改描述性字段；**不含等级**，BR-01/BR-06） |
| `FUNC-06` | 风险列表 | US-04 | list（类别 / 状态 / 等级 / 受影响需求 + 分页） |
| `FUNC-07` | 风险详情 | US-04 | get（未命中返回 None，不抛异常） |

### 4.2 功能模块结构图

```
风险 risk
├── 识别与维护
│   ├── FUNC-01 识别风险
│   ├── FUNC-05 修改风险
│   └── FUNC-07 风险详情
├── 等级与缓解
│   ├── FUNC-02 评估等级
│   └── FUNC-03 登记缓解措施
├── 关闭
│   └── FUNC-04 关闭风险
└── 查询
    └── FUNC-06 风险列表
```

### 4.3 功能详细说明

#### 4.3.1 识别风险（FUNC-01）

- **输入**: 标题、风险情景、类别、（选填）可能性、后果、受影响需求、责任人
- **校验**: `BR-05`（类别字典）、`BR-07`（受影响需求须存在）、`BR-01`（可能性与后果成对）
- **处理**: 生成 `risk_no` → 推导风险值/等级（两端都给才推导）→ 落库 → 状态置 `identified`
- **输出**: 新风险记录

#### 4.3.2 评估等级（FUNC-02）

- **输入**: `risk_no` + 可能性 + 后果
- **校验**: `BR-05`（1..5）、`BR-06`（非终态）
- **处理**: 写入那对取值 → 推导 `risk_score` / `risk_level` → 状态置 `analyzing`
- **输出**: 更新后的风险（含推导出的等级）

#### 4.3.3 登记缓解措施（FUNC-03）

- **输入**: `risk_no` + 缓解措施
- **校验**: 缓解措施非空；**等级须已评估**（材料 §6.4.1.2.4：缓解由等级/阈值触发）；`BR-06`
- **处理**: 写入 `mitigation` → 状态置 `mitigating`
- **输出**: 更新后的风险

#### 4.3.4 关闭风险（FUNC-04）

- **输入**: `risk_no` + 处置结论 + （选填）处置说明
- **校验**: `BR-02`（结论必填且字典内；`mitigated` 须已登记缓解措施）、`BR-03`（高等级不得接受）、`BR-06`
- **处理**: 状态置 `closed`（结论=接受时置 `accepted`），落 `disposition` / `close_note`
- **输出**: 终态风险记录

#### 4.3.5 修改风险（FUNC-05）

- **输入**: `risk_no` + 待改字段（标题 / 情景 / 类别 / 受影响需求 / 责任人）
- **校验**: `BR-06`（终态拦截）、`BR-05`、`BR-07`
- **输出**: 更新后的风险 —— **等级与风险值必与修改前一致**（字段白名单里没有它们）

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 等级不可直接写

**Given** 一条任意状态的风险
**When** 调 `update` 改标题、调 `create` 建新风险
**Then** 入参里**没有**等级字段；等级只在 `assess` 时由 可能性 × 后果 推导（`BR-01`）

#### 6.1.2 标准2: 关闭必须有处置结论

**Given** 一条已登记缓解措施的高等级风险
**When** 以「缓解完成」关闭
**Then** 落 `disposition = mitigated` 且状态为「已关闭」；若未登记缓解措施则**拒绝**（`BR-02`）

#### 6.1.3 标准3: 高等级不得以「接受」收尾

**Given** 一条等级为「严重」的风险
**When** 试图以「接受」关闭
**Then** 拒绝，提示须缓解或转移（`BR-03`）

#### 6.1.4 标准4: 终态不可改

**Given** 一条状态为「已关闭」的风险
**When** 调 `update` / `assess` / `mitigate` / `close` 中任意一个
**Then** 全部拒绝并提示已处于终态（`BR-06`）

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms
- 风险编号生成在并发录入下不重复（`BR-04`）

### 6.3 已知问题或限制

- **等级分档阈值（4 / 9 / 15）写在代码里**：材料 §6.4 未给出逐格的 5×5 矩阵分档表，
  本应用按均匀四档实现（`≤4 低 · ≤9 中 · ≤15 高 · ≥16 严重`）。若要按项目风险计划调整阈值，
  需改 `risk.py` 的 `_BANDS`（非配置项）。
- **`BR-03` 属解读**：材料只说要"识别触发缓解动作的风险等级或阈值"，没有逐字禁止"接受高风险"。
  本应用把它落成硬约束，是让阈值可执行的一种做法；若业务方要求允许高风险接受（需留痕），
  这里要放开。
- **「转移」与「缓解完成」共用终态「已关闭」**：二者靠 `disposition` 区分，状态机里没有独立的
  「已转移」。这是**有意的合并**（关闭口径是查询维度，不是生命周期阶段），不是为了省服务的缺口。
- **终态不可逆**：没有「重开」服务。误关闭只能重新识别一条（新编号），历史记录保留。
- **责任人为「文本输入 + 候选建议」**（2026-09-25 改）：同 `requirement` —— `owner` 挂 `datalist`、
  候选来自 `stakeholder.list`，**值仍是文本姓名**（不落 `sh_no`；全组一致口径，单页上外键会造成
  "同一件事两种口径"）。
- **受影响需求不级联**：需求被作废后风险仍指向它（弱引用允许悬空），本应用不做悬空检测。
