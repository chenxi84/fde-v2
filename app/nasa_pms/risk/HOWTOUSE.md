# risk 使用要点

**管什么**：一条技术风险——**不确定事件**：风险情景 + 可能性 × 后果 → 推导等级 → 缓解措施 → 处置结论。
等级**不由人填**。查「指标实测值超没超阈值」用『技术度量』，不是这里。

## 标准工作流（按此顺序）

1. `create` — 识别：`title` + `statement`（风险情景）+ `category` 必填，落「识别」态；`likelihood` / `consequence` 可暂缺，**给出就必须成对**（成对才推导等级）；`req_no` 填了就经 `requirement.get` 校验存在
2. `assess` — **唯一**能改等级的入口：写可能性 × 后果，风险值 / 等级由二者推导，状态推进「分析中」
3. `mitigate` — 登记缓解措施 → 「缓解中」
4. `close` — 关闭：处置结论（缓解完成 / 转移 / 接受）与终态**同事务**落库

核对用：`list`（按类别 / 状态 / 等级 / 受影响需求筛）→ `get`（未命中返回 `None`，不抛异常）。

## 前置条件与禁忌

- **等级不可直接写**：`create` / `update` 都没有等级入参，改等级只能走 `assess`。
- **守卫顺序**（`close`，报错话术取决于它）：结论非空 → 结论在字典内 → 结论为「缓解完成」时须**已登记缓解措施** → 等级「高」/「严重」**不得**以「接受」关闭（须缓解或转移）——「没给结论」与「高风险想接受」是两句不同的错。
- **状态闸**：`mitigate` 要求等级已评估（报「尚未评估等级」= 缺 `assess`）；终态「已关闭」/「已接受」下 `update` / `assess` / `mitigate` / `close` **一律拒绝**；**终态不可逆**（没有重开服务，误关闭只能重新 `create` 一条）。
- 字典：`category` ∈ `technical` / `cost` / `schedule` / `programmatic` / `safety`（技术 / 成本 / 进度 / 程序性 / 安全风险）；可能性、后果 ∈ **1..5 整数**；等级按风险值分档 ≤4 低 · ≤9 中 · ≤15 高 · ≥16 严重；`disposition` ∈ `mitigated` / `transferred` / `accepted`。
- 编号形如 `RSK-001`，系统生成、不可变；受影响需求是**弱引用**（可留空、可悬空，不级联）。
- 本应用只把等级算出来，**不做通知 / 风险报告**。
