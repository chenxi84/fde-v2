## 1. 变更请求概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `change_request` |
| 类名 | `ChangeRequest` |
| 聚合根 | 变更请求 |
| 标识 | `cr_no` |
| 数据来源类型 | **独立创建**（变更由提出人登记，无上游自动生成） |

### 1.2 变更请求背景

#### 1.2.1 为什么需要这个应用？

材料把配置管理称为企业结构的 **"backbone"**，而其五要素中的第三步就是
**Configuration Change Control**（§6.5.1.2.3）："Configuration change management is a process to
manage approved designs and **the implementation of approved changes**"，且必须经
"a **systematic proposal, justification, and evaluation** of proposed changes followed by
incorporation of approved changes and verification of implementation"。

现状问题（同组 `configuration_item` 侧的对照）：配置项能发版、能递版本，但**版本变更的"授权"没有载体**——
`configuration_item.bump_version(ci_no, n, change_no)` 的 `change_no` 只能填一个字符串，
"这个变更号是谁提的、评估了什么影响、CCB 批没批"在系统里**答不出来**。
材料 FIGURE 6.5-4 的八步链条（提出 → 登记 → 评审收集 → 决策包 → CCB 排期 → 处置 → 记录 →
执行与验证）也完全没有承载物。

#### 1.2.2 期望达到什么目标？

- 每次变更**有唯一编号**（`cr_no`），可被配置项、需求、接口**按号引用**（`configuration_item`
  的 `change_no` 就是引用它）
- 变更**必须指明影响范围**（至少一个配置项或一条需求）—— 材料要求"评估"，没有范围就没有评估对象
- 影响分析与审批**成链且不可倒置**：没有影响分析到不了审批（不允许"先批后分析"）
- 审批结论与意见**留痕**，且**已拒绝 / 已实施是硬终态**（不能复活、不能误实施）

### 1.3 变更请求范围

#### 1.3.1 包含哪些功能？

- 变更请求的提出（create）、修改（update）、查询列表 / 详情
- **提交影响分析**（analyze）：登记影响分析内容
- **提交审批**（submit_review）：把分析完毕的变更送上 CCB
- **批准 / 拒绝**（approve / reject）：记录审批结论与审批意见
- **实施**（implement）：登记"已批准的变更已落地"
- 影响范围与 **配置项 / 需求**通过弱引用关联（`ci_nos` / `req_nos`），列表支持按它们筛选

#### 1.3.2 不包含哪些功能？

- **不改配置项的版本** —— 材料 FIGURE 6.5-4 第 9 步「Execute approved changes」的执行面在配置项侧
  （`configuration_item.bump_version(ci_no, n, cr_no)`）；本应用只发号 + 记录实施
  （跨应用无分布式事务，CONVENTION §8）
- **不做需求的改写** —— 需求变更由 `requirement` 侧执行（其 `update(change_no=…)` 引用本应用的号）
- **不做 CCB 会议管理 / 会议纪要**（FIGURE 6.5-4 第 5、8b 步的排期与 minutes）—— 审批结论落在本聚合，
  会议过程本身不在数据面
- **不做配置审计** —— §6.5.1.2.5 的 functional / physical configuration audit 由后续评审/验证类应用承载

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 变更提出方（Originator） | 提出变更请求、填写变更说明与影响范围 | 材料 FIGURE 6.5-4 第 1 列 |
| 配置管理员（CM） | 接收并登记变更、组织评审、提交 CCB 审批 | 材料 FIGURE 6.5-4 第 2、5 列 |
| CCB（配置控制委员会） | 处置变更请求（批准 / 拒绝）并给出意见 | 材料 §6.5.1.2.3 与 FIGURE 6.5-4 第 7 列 |
| 实施方（Actionee） | 执行已批准的变更 | 材料 FIGURE 6.5-4 第 8a 列 |

> 术语表已收「变更提出方」「配置管理员（CM）」（`configuration_item` 第②步回填）；
> 「CCB」与「Actionee」按材料语境就地取名为**配置控制委员会（CCB）**、**实施方（Actionee）**并回填（§7.4）。

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 提出变更请求（优先级：P1）

**作为**一名变更提出方
**我希望**登记一条变更请求，写清要改什么、影响哪些配置项或需求
**以便**后续能对它做影响分析与审批

**验收条件**：
- 给定标题、申请方齐备且影响范围至少一个，当提交时，则新变更请求以「已提交」落库，编号自动生成（`CR-001` 起）
- 给定影响范围为空，当提交时，则**拒绝**并提示「变更必须指明影响范围」（`BR-01`）
- 给定标题或申请方为空，当提交时，则**拒绝**（`BR` 非空校验）
- 给定影响范围里填了不存在的配置项 / 需求，当提交时，则**拒绝**（`BR-05`）
- 给定影响范围里填了**已归档的配置项**或**已废弃的需求**，当提交时，则**拒绝**（`BR-07`）

#### 2.1.2 `US-02` 用户故事 — 修改未分析的变更请求（优先级：P2）

**作为**一名变更提出方
**我希望**在影响分析开始前修正标题、申请方、说明或影响范围
**以便**提交错漏能被纠正

**验收条件**：
- 给定一条 `submitted` 的变更请求，当修改标题时，则成功
- 给定一条 `analyzing` / `reviewing` / `approved` 的变更请求，当修改任何内容时，则**拒绝**（`BR-06`）
- 给定把影响范围改成**空**，当提交时，则**拒绝**（`BR-01`，按改完之后的整体范围校验）
- 给定一次不带任何字段的 `update`，则**拒绝**（「没有要修改的内容」）

#### 2.1.3 `US-03` 用户故事 — 提交影响分析（优先级：P1）

**作为**一名配置管理员
**我希望**把影响分析登记到变更请求上
**以便**审批时有一份被评估过的依据

**验收条件**：
- 给定一条 `submitted` 的变更请求，当填写影响分析时，则内容落库、状态变为 `analyzing`
- 给定影响分析为空，当提交时，则**拒绝**（`BR-02`）
- 给定已处于 `analyzing` 及之后的变更请求，再次登记影响分析则**拒绝**（状态机单向）

#### 2.1.4 `US-04` 用户故事 — 提交审批（优先级：P1）

**作为**一名配置管理员
**我希望**把分析完毕的变更请求送上 CCB
**以便**它进入待处置队列

**验收条件**：
- 给定一条 `analyzing` 的变更请求，当提交审批时，则状态变为 `reviewing`
- 给定一条 `submitted` 的变更请求，当直接提交审批时，则**拒绝**（`BR-02`：先分析后审批）

#### 2.1.5 `US-05` 用户故事 — 批准 / 拒绝（优先级：P1）

**作为**一名 CCB 成员
**我希望**对审批中的变更请求给出批准或拒绝，并写下意见
**以便**决策可追溯

**验收条件**：
- 给定一条 `reviewing` 的变更请求，当批准并写意见时，则状态变为 `approved`，审批意见与审批人落库
- 给定审批意见为空，当批准 / 拒绝时，则**拒绝**（`BR-02`）
- 给定一条**未做影响分析**的变更请求，当尝试批准时，则**拒绝**（`BR-02`：先批后分析不可达）
- 给定拒绝，则状态变为 `rejected`（**终态**）

#### 2.1.6 `US-06` 用户故事 — 实施（优先级：P2）

**作为**一名实施方
**我希望**在执行完已批准的变更后登记"已实施"
**以便**变更链条闭环

**验收条件**：
- 给定一条 `approved` 的变更请求，当实施时，则状态变为 `implemented`（**终态**）
- 给定一条**未批准**（已提交 / 影响分析 / 审批中）或**已拒绝**的变更请求，当实施时，则**拒绝**（`BR-04`）
- 给定已实施 / 已拒绝的变更请求，当再次任何动作（修改 / 分析 / 审批 / 实施）时，则**全部拒绝**（`BR-04`）

#### 2.1.7 `US-07` 用户故事 — 查询变更请求（优先级：P2）

**作为**一名配置管理员 / 提出方
**我希望**按状态、申请方、影响的配置项、影响的需求筛选变更请求
**以便**回答"这条基线相关的变更都有哪些""谁的变更还卡在审批中"

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序），**分页返回 `{items, total}`**，
返回项与 `get` **同口径（全字段）**

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 一条变更请求的一生（对齐状态机与 FIGURE 6.5-4）

1. 提出方登记变更（`create`）→ 已提交（`submitted`）—— 写明影响哪些配置项 / 需求
2. CM 接收并登记，组织评审（材料 FIGURE 6.5-4 第 2~4 步）
3. `analyze` 登记影响分析 → 影响分析（`analyzing`）
4. `submit_review` 送 CCB（第 5 步）→ 审批中（`reviewing`）
5. CCB 处置（第 7 步）：`approve` → 已批准（`approved`）/ `reject` → 已拒绝（`rejected`，终态）
6. 实施方执行（第 9 步）并在本应用 `implement` 登记 → 已实施（`implemented`，终态）；
   **真正的改动落在配置项侧**：`configuration_item.bump_version(ci_no, n, cr_no)`

#### 3.1.2 场景2: 与配置项的双向协作（跨应用，两条边）

1. **本应用 → 配置项**（读）：提交变更时校验影响范围里的配置项**真实存在**且**未归档**
   （`configuration_item.list`，BR-05 / BR-07）
2. **本应用 → 需求**（读）：同上，校验需求存在且未废弃（`requirement.list`，BR-05 / BR-07）
3. **配置项 → 本应用**（读，反向）：`configuration_item.bump_version` 只校验"带了变更号"，
   而"该变更号是否已批准"由本应用的数据保证 —— 该应用建成后改为跨应用校验是其详设 §6.3 的已知待办，
   **本应用已是可被校验的一方**（`get(cr_no).status == "approved"`）

### 3.2 业务规则

#### 3.2.1 `BR-01` 变更必须指明影响范围

- **规则描述**: 配置项（`ci_nos`）与需求（`req_nos`）**至少有一个**非空；修改影响范围时按**改完之后**的整体范围校验
- **适用场景**: 提出、修改
- **计算方式**: 校验型（两侧合并后判空）
- **依赖输入**: `[ci_nos(实体字段), req_nos(实体字段)]`
- **输出**: `change_request.ci_nos` / `req_nos`
- **生效点**: `change_request.create → 校验` / `update → 校验`
- **示例**: `create(标题, 申请方, ci_nos=[], req_nos=[])` → 拒绝
- **依据**: 聚合根卡 4 的 **I-1**；材料 §6.5.1.2.3 要求变更经 "systematic proposal, **justification**,
  and **evaluation**" —— 影响范围是被评估的对象，缺了它评估无从谈起

#### 3.2.2 `BR-02` 审批与影响分析同事务落库（不许"先批后分析"）

- **规则描述**: 审批（`approve` / `reject`）只接受 `reviewing`；而 `reviewing` 只能由 `submit_review`
  到达、`submit_review` 又只接受 `analyzing`（即影响分析已落库）。审批**必须给出审批意见**，
  意见、审批人与状态在**同一条 UPDATE** 里写入
- **适用场景**: 影响分析、提交审批、批准、拒绝
- **计算方式**: 校验型（状态门 + 非空校验）
- **依赖输入**: `[status(实体字段), impact_analysis(实体字段), comment(服务实参)]`
- **输出**: `change_request.impact_analysis` / `decision_note` / `approver` / `status`
- **生效点**: `analyze → 校验` / `submit_review → 校验` / `approve → 校验` / `reject → 校验`
- **示例**: 对 `submitted` 的变更直接 `approve` → 拒绝「只有审批中的变更请求才能审批」
- **依据**: 聚合根卡 4 的 **I-2**；材料 FIGURE 6.5-4 第 3~4 步（评审人提交意见、CM 收集与裁决）
  在 CCB 排期（第 5 步）之前 —— 顺序不可倒

#### 3.2.3 `BR-03` 变更请求编号唯一且不可变

- **规则描述**: `cr_no` 系统生成（`CR-` + 三位序号）、落库后不得修改
- **适用场景**: 提出、修改
- **计算方式**: 唯一性校验
- **依赖输入**: `[cr_no(实体字段)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `change_request.create`（生成）/ `update`（**字段白名单里没有编号**，无从改起）
- **示例**: `update(cr_no="CR-001", cr_no="CR-100")` → 该参数不存在，服务不接受
- **依据**: 材料 §6.5.1.2.2 "Identification requires unique identifiers"；聚合根卡 4

#### 3.2.4 `BR-04` 状态机单向，已拒绝 / 已实施为硬终态

- **规则描述**: 合法迁移只有 `submitted→analyzing→reviewing→{approved|rejected}`、`approved→implemented`；
  到达 `rejected` / `implemented` 后，**任何**动作（修改 / 影响分析 / 提交审批 / 审批 / 实施）一律拒绝
- **适用场景**: 全部动作服务
- **计算方式**: 校验型（终态守卫 + 状态门）
- **依赖输入**: `[status(实体字段)]`
- **输出**: `change_request.status`
- **生效点**: `analyze` / `submit_review` / `approve` / `reject` / `implement` / `update` 的**最前置守卫**
- **示例**: 对 `rejected` 的变更调 `implement` → 拒绝「已处于终态「已拒绝」，不能再操作」
- **依据**: 材料 FIGURE 6.5-4 —— 处置过的变更请求留痕但不得复活；已执行的变更不得重复执行
  （第 8b 步 "Release CCB minutes / Track actions" 要求记录被跟踪到底）
- ⚠ **守卫顺序即安全边界**：终态判断**排在状态门与参数校验之前** —— 否则终态对象会被参数错误
  的提示"绕过"掉终态语义（断言顺序见《测试用例.md》TC-25 / TC-27）

#### 3.2.5 `BR-05` 影响范围的对象必须真实存在

- **规则描述**: `ci_nos` 里每个编号必须在配置项台账中存在；`req_nos` 里每个编号必须在需求台账中存在
- **适用场景**: 提出、修改
- **计算方式**: 跨应用只读校验（`configuration_item.list` / `requirement.list`）
- **依赖输入**: `[ci_nos, req_nos(服务实参), 被调应用的 items]`
- **输出**: 无（拦截性校验）
- **生效点**: `change_request.create → 校验` / `update → 校验`
- **示例**: `create(…, ci_nos=["CI-999"])` → 拒绝「影响的配置项 CI-999 不存在」
- **依据**: 聚合根卡 4「引用的聚合：configuration_item、requirement；跨应用调用：`configuration_item.list`、
  `requirement.list`」；弱引用不悬空（同组 `risk` 的 BR-07 同例）

#### 3.2.6 `BR-06` 内容只在「已提交」可改

- **规则描述**: `update` 只接受 `submitted`；进入 `analyzing` 之后（含 `reviewing` / `approved`）内容定型
- **适用场景**: 修改
- **计算方式**: 校验型（状态门）
- **依赖输入**: `[status(实体字段)]`
- **输出**: `change_request.title` / `requester` / `ci_nos` / `req_nos` / `description`
- **生效点**: `change_request.update → 校验`
- **示例**: 对 `analyzing` 的变更改标题 → 拒绝「只有已提交的变更请求才能修改」
- **依据**: 影响分析一旦登记，分析结论针对的就是当时那份影响范围；审批前还能改范围 ⇒
  "被分析的对象"与"分析结论"对不上（`BR-02` 的成链性依赖它）

#### 3.2.7 `BR-07` 已归档配置项 / 已废弃需求不得再作为影响范围

- **规则描述**: 影响范围里的配置项状态不得为 `archived`、需求状态不得为 `obsolete`
- **适用场景**: 提出、修改
- **计算方式**: 跨应用只读校验（读 `configuration_item.list` / `requirement.list` 的 `status` 列）
- **依赖输入**: `[ci_nos, req_nos(服务实参), 被调应用行的 status]`
- **输出**: 无（拦截性校验）
- **生效点**: `change_request.create → 校验` / `update → 校验`
- **示例**: 对已归档的 `CI-003` 提变更 → 拒绝「配置项 CI-003 已归档（终态），不能再作为变更的影响范围」
- **依据**: 两个被引用聚合的终态语义 —— `configuration_item` 的 BR-02（归档为终态，不可再变更版本）、
  `requirement` 的 BR-04（已废弃不得再改）；归档 / 废弃的对象不可能再被变更驱动，
  让它进影响范围只会产出**永远无法实施**的变更请求
- ⚠ 这条规则是**跨应用 `list` 调用真正的消费者**：只判存在性用 `get` 就够，
  判状态必须拿列表里的 `status`（也是"为什么卡片写的跨应用调用是 `list` 而非 `get`"的答案）

### 3.3 业务数据

#### 3.3.1 数据1: 变更请求编号（cr_no）

- **数据描述**: 变更请求的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`CR-` + 三位序号）
- **示例值**: "CR-001"

#### 3.3.2 数据2: 变更请求标题（title）

- **数据描述**: 这次要改什么（一句话）
- **数据类型**: 文本（≤120 字）
- **数据来源**: 人工录入
- **示例值**: "飞控软件并发指标上调"

#### 3.3.3 数据3: 申请方（requester）

- **数据描述**: 变更的提出人 / 提出组织（材料 FIGURE 6.5-4 的 Originator 列）
- **数据类型**: 文本
- **数据来源**: 人工录入
- **示例值**: "张三"

#### 3.3.4 数据4: 影响的配置项（ci_nos）

- **数据描述**: 本次变更波及的配置项编号集合（弱引用 `configuration_item`，可与"影响的需求"二选一，见 BR-01）
- **数据类型**: 文本列表（库内逗号分隔，服务口径为**列表**）
- **数据来源**: 人工选择（下拉来自 `configuration_item.list`）
- **示例值**: `["CI-001", "CI-002"]`

#### 3.3.5 数据5: 影响的需求（req_nos）

- **数据描述**: 本次变更波及的需求编号集合（弱引用 `requirement`）
- **数据类型**: 文本列表（同 `ci_nos`）
- **数据来源**: 人工选择（下拉来自 `requirement.list`）
- **示例值**: `["REQ-001"]`

#### 3.3.6 数据6: 变更说明（description）

- **数据描述**: 为什么改、改成什么（材料 §6.5.1.2.3 的 "justification"）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "并发指标 1000 → 1200"

#### 3.3.7 数据7: 影响分析（impact_analysis）

- **数据描述**: 改动波及哪些配置项 / 需求、代价与风险（材料 FIGURE 6.5-4 第 3~4 步的评审与裁决结论）
- **数据类型**: 文本（`analyze` 时必填）
- **数据来源**: 人工录入（`analyze`）
- **示例值**: "影响 CI-001 的并发指标与 REQ-001 的验证用例"

#### 3.3.8 数据8: 审批意见（decision_note）

- **数据描述**: CCB 批准或拒绝的理由（BR-02：审批时必填，与状态同事务落库）
- **数据类型**: 文本
- **数据来源**: 人工录入（`approve` / `reject`）
- **示例值**: "CCB 2026-09 第 3 次会议通过"

#### 3.3.9 数据9: 审批人（approver）

- **数据描述**: 做出审批结论的 CCB 成员 / 代表
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（`approve` / `reject`）
- **示例值**: "CCB-主席"

#### 3.3.10 数据10: 实施说明（implement_note）

- **数据描述**: 变更如何落地的记录（如"CI-001 已版本变更到 v2"）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（`implement`）
- **示例值**: "CI-001 已在配置项侧版本变更到 v2"

#### 3.3.11 数据11: 状态（status）

- **数据描述**: 变更请求在变更控制链条中的位置
- **数据类型**: 字典：submitted / analyzing / reviewing / approved / rejected / implemented
- **数据来源**: 系统按流转规则变更
- **示例值**: "reviewing"

#### 3.3.12 数据12: 所属项目（project_no）

- **数据描述**: 变更请求归属的项目
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（仅 `create`）
- **示例值**: "P-2026-01"

### 3.4 状态机

```
submitted（已提交）
   │ analyze（提交影响分析，BR-02）
   ▼
analyzing（影响分析）
   │ submit_review（提交审批 —— 审批中的唯一入口）
   ▼
reviewing（审批中）
   ├── approve（批准，须填审批意见，BR-02）──► approved（已批准）
   └── reject（拒绝，须填审批意见）─────────► rejected（已拒绝，硬终态）
                                                  ▲
approved（已批准）                                 │
   │ implement（执行已批准的变更）                  │ 任何动作都被拒（BR-04）
   ▼                                               │
implemented（已实施，硬终态）───────────────────────┘
```

**每个状态的到达服务**（详设 §4.1 的 FUNC 与服务一一对应 —— 每个状态都可达）：

| 状态 | 到达服务 |
|---|---|
| `submitted` | `create` |
| `analyzing` | `analyze` |
| `reviewing` | `submit_review` |
| `approved` | `approve` |
| `rejected` | `reject` |
| `implemented` | `implement` |

> **合法迁移**：`submitted→analyzing`、`analyzing→reviewing`、`reviewing→approved|rejected`、
> `approved→implemented`。
> **拦截迁移**：`submitted→reviewing`（须先分析，BR-02）、`submitted|analyzing|reviewing→implemented`
> （须先批准）、`rejected|implemented→*`（硬终态，BR-04）、`analyzing|reviewing|approved` 的 `update`（BR-06）。

## 4. 功能描述

### 4.1 功能清单

| 编号 | 功能 | 对应 US | 说明 |
|---|---|---|---|
| `FUNC-01` | 提出变更请求 | US-01 | create（编号自动生成；BR-01 / BR-05 / BR-07） |
| `FUNC-02` | 修改变更请求 | US-02 | update（BR-06：只接受已提交；字段白名单不含编号，BR-03） |
| `FUNC-03` | 提交影响分析 | US-03 | analyze（已提交 → 影响分析；仅「已提交」可登记） |
| `FUNC-04` | 提交审批 | US-04 | submit_review（影响分析 → 审批中；须已完成影响分析） |
| `FUNC-05` | 批准 | US-05 | approve（审批中 → 已批准；审批意见必填，BR-02） |
| `FUNC-06` | 拒绝 | US-05 | reject（审批中 → 已拒绝，终态） |
| `FUNC-07` | 实施 | US-06 | implement（已批准 → 已实施，终态；BR-04） |
| `FUNC-08` | 变更请求列表 | US-07 | list（分页 `{items, total}`；筛选 status/requester/ci_no/req_no） |
| `FUNC-09` | 变更请求详情 | US-07 | get（未命中返回 None，不抛异常） |

### 4.2 功能模块结构图

```
变更请求 change_request
├── 提出与维护
│   ├── FUNC-01 提出变更请求
│   └── FUNC-02 修改变更请求
├── 变更控制链
│   ├── FUNC-03 提交影响分析
│   ├── FUNC-04 提交审批
│   ├── FUNC-05 批准
│   ├── FUNC-06 拒绝
│   └── FUNC-07 实施
└── 查询
    ├── FUNC-08 变更请求列表
    └── FUNC-09 变更请求详情
```

### 4.3 功能详细说明

#### 4.3.1 提出变更请求（FUNC-01）

- **输入**: 标题、申请方、影响的配置项、影响的需求、变更说明、所属项目
- **校验**: 标题 / 申请方非空；`BR-01`（影响范围两侧至少一个）；`BR-05` / `BR-07`（跨应用存在且非终态）
- **处理**: 生成 `cr_no`（`CR-<序号>`）→ 落库 → 状态置 `submitted`
- **输出**: 新变更请求记录（`ci_nos` / `req_nos` 为列表）

#### 4.3.2 提交影响分析（FUNC-03）

- **输入**: `cr_no` + 影响分析
- **校验**: `BR-04`（终态最先拦）、状态须为 `submitted`、影响分析非空（`BR-02`）
- **处理**: 写 `impact_analysis`，状态置 `analyzing`
- **输出**: 更新后的变更请求

#### 4.3.3 提交审批（FUNC-04）

- **输入**: `cr_no`
- **校验**: `BR-04`、状态须为 `analyzing`、影响分析须已存在（`BR-02` 的兜底断言）
- **处理**: 状态置 `reviewing`
- **输出**: 更新后的变更请求
- **说明**: 这是"审批中"的**唯一入口** —— `BR-02` 的"先批后分析不可达"由它保证

#### 4.3.4 批准 / 拒绝（FUNC-05 / FUNC-06）

- **输入**: `cr_no` + 审批意见 + 审批人
- **校验**: `BR-04`（终态最先拦）、状态须为 `reviewing`、影响分析须已存在、审批意见非空
- **处理**: **同一条 UPDATE** 写入状态、审批意见、审批人
- **输出**: 更新后的变更请求

#### 4.3.5 实施（FUNC-07）

- **输入**: `cr_no` + 实施说明
- **校验**: `BR-04`（终态最先拦）、状态须为 `approved`
- **处理**: 状态置 `implemented`（终态）
- **输出**: 更新后的变更请求

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 影响范围是硬门槛

**Given** 一条只有标题与申请方的变更请求草稿
**When** 提交
**Then** 拒绝，提示「变更必须指明影响范围：至少选择一个配置项或一条需求」（`BR-01`）
**And given** 影响范围里含已归档配置项 / 已废弃需求，**when** 提交，**then** 拒绝（`BR-07`）

#### 6.1.2 标准2: 不许先批后分析

**Given** 一条 `submitted` 的变更请求（无影响分析）
**When** 直接批准
**Then** 拒绝，提示「只有审批中的变更请求才能审批」（`BR-02`）

#### 6.1.3 标准3: 终态不可复活

**Given** 一条 `rejected` 的变更请求
**When** 再次 `update` / `analyze` / `approve` / `implement`
**Then** 全部拒绝，且提示**终态**（`BR-04`，错误信息不得落在参数或状态门上）

#### 6.1.4 标准4: 未批准不得实施

**Given** 一条 `submitted` / `analyzing` / `reviewing` 的变更请求
**When** 实施
**Then** 拒绝，提示「只有已批准的变更请求才能实施」（`BR-04`）

#### 6.1.5 标准5: 影响范围的对象必须可用

**Given** 影响范围里写了不存在的 `CI-999`
**When** 提交
**Then** 拒绝，提示「影响的配置项 CI-999 不存在」（`BR-05`）

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms
- 变更请求编号生成在并发登记下不重复（`BR-03`）
- `get` 未命中**不抛异常**，返回 `None`（供跨应用探测式调用）
- 跨应用校验失败时**不得**把被调应用的口径直接透出（如"应用不存在"），须转成本应用的影响范围校验失败

### 6.3 已知问题或限制

- **跨应用校验是"读一次全表"** —— `_assert_scope` 每次调 `configuration_item.list` / `requirement.list`
  **不带筛选拉全量**再在内存里比编号。卡片规定的跨应用调用就是这两个 `list`（判状态必须拿 `status` 列），
  配置项 / 需求规模上千时应改为"按编号批量查询"的服务（本应用无需改动，只换调用）。
- **实施不写配置项**：跨应用无分布式事务（CONVENTION §8），"执行已批准的变更"由调用方**分两步**
  完成（先 `change_request.implement`，再 `configuration_item.bump_version(ci_no, n, cr_no)`）。
  两步之间的一致性靠人工/Agent 顺序保证；**不做补偿式自动回滚**（同组同约定）。
- **审批不做会签 / 多级**：`approve` 一次单人结论即终；材料 FIGURE 6.5-4 的"决策包"（第 6 步）
  与投票过程不在数据面。
- **`ci_nos` / `req_nos` 以逗号分隔文本落库**：`list` 的成员筛选在 Python 侧做（LIKE 判边界会把
  `CI-001` 误命中 `CI-0011`）。若将来影响范围需要"逐条影响描述"，应改为子表
  （属聚合内部结构变更，不影响对外服务签名）。
- **配置项侧尚未反向校验本应用**：`configuration_item.bump_version` 目前只校验"带了变更号"，
  未校验"该变更号是否已批准"（其详设 §6.3 已登记为待办）—— 本应用已具备被校验的能力
  （`get(cr_no).status`），建成该跨应用校验后 `BR-02` 才真正端到端闭合。
