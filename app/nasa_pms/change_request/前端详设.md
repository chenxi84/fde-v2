# 前端详设：变更请求（change_request）

> 产出技能：第⑥步 前端设计（规格 `design-plus/前端设计.md`，规范正本 `VIEW_CONVENTION.md`）
> 输入：`应用详设.md`（US/FUNC/PERM/状态机）+ `architecture.md`（聚合根卡 4）
> 后端契约**以 `change_request.py` 源码为准**（组级 `_contracts.md` 由第⑤步出口的统一 dump 冻结）

---

## 1. 页面定位

| 项 | 内容 |
|---|---|
| key / name | `change_request` / 变更请求 |
| 一句话 | 变更请求台账：提出、提交影响分析、提交审批、审批（批准/拒绝）、实施，按状态/申请方/影响范围筛选 |
| 数据来源类型 | **独立创建** —— 因此**保留「提出变更」入口**（与服务契约 `create` 对应） |
| `PAGE_META.order` | `640` —— **组内序不在此复抄**：真值 = 各页 `PAGE_META.order`，组级 view 测试的「菜单序」断言从 `PAGE_META` + `shell.js` 的 `PLATFORM_PAGES` **现算**。本行此前逐页复抄了一遍 —— 复抄必漂：2026-09-25 因 `order` 并列、平台按 key 字母序兜底，「配置项」被渲染到「风险」之前，而复抄的清单还把旧值当成了正确值（见 pitfalls #43）。 |

## 3. svc 字面量清单（授权派生依据 —— 必须字面量 `svc("应用","服务")`）

| 调用 | 用途 |
|---|---|
| `svc("change_request", "list", …)` | 列表（含四个筛选参数 + page/size） |
| `svc("change_request", "get", …)` | 详情（打开模态时按号取全字段） |
| `svc("change_request", "create", …)` | 提出变更 |
| `svc("change_request", "update", …)` | 保存编辑（仅已提交） |
| `svc("change_request", "analyze", …)` | 提交影响分析 |
| `svc("change_request", "submit_review", …)` | 提交审批 |
| `svc("change_request", "approve", …)` | 确认批准 |
| `svc("change_request", "reject", …)` | 确认拒绝 |
| `svc("change_request", "implement", …)` | 确认实施 |
| `svc("configuration_item", "list", {}, {quiet:true})` | **跨应用**：影响范围 / 筛选下拉的配置项选项 |
| `svc("requirement", "list", {}, {quiet:true})` | **跨应用**：影响范围 / 筛选下拉的需求选项 |

> `approve` 与 `reject` **必须写成两个字面量分支**（不能变量拼服务名）——
> 平台靠源码里的 `svc("app","svc")` 字面量派生"页→服务"隐式放行边（VIEW_CONVENTION 硬性规则 10）。

## 4. 数据来源与下拉

| 依赖 | 用途 | 调用 |
|---|---|---|
| `configuration_item`（配置项） | 影响范围多选 + 「影响配置项」筛选的选项源（`ci_no · name`） | `svc("configuration_item", "list", {}, {quiet:true})` |
| `requirement`（需求） | 影响范围多选 + 「影响需求」筛选的选项源（`req_no · title`） | `svc("requirement", "list", {}, {quiet:true})` |
| 无 | 申请方 `requester` 为文本字段（**当前不经 autocomplete**，见 §8） | — |

> 两个跨应用调用**失败静默兜底为空列表**（`quiet: true` + `catch`）——
> 变更请求本身仍可查看与流转，只是"选不了新范围"；不喷 toast 干扰主流程。

## 5. 交互规则（逐条对应后端约束）

| # | 规则 | 依据 |
|---|---|---|
| F-1 | 提出表单里**标题 / 申请方必填**，且**影响范围至少选一个配置项或一条需求**，否则提交按钮禁用 | `BR-01` + 非空 |
| F-2 | 影响范围是**多选下拉**（`select[multiple]`），选项来自跨应用；列表里以 `、` 连接展示 | `BR-05` |
| F-3 | 详情里**变更请求编号为纯文本**（不可编辑，也没有输入框承载它） | `BR-03` |
| F-4 | 内容（标题 / 申请方 / 变更说明 / 影响范围）**只在「已提交」的编辑态可改**；其余状态一律置灰只读 | `BR-06` |
| F-5 | 状态为**徽标**（`.st` + `.st-<色>`），六态：已提交 / 影响分析 / 审批中 / 已批准 / 已拒绝 / 已实施 | 状态机 §3.4 |
| F-6 | **动作按钮按状态显隐**：已提交→[编辑][提交影响分析]；影响分析→[提交审批]；审批中→[审批]；已批准→[实施]；已拒绝/已实施→无 | 状态机 §3.4 |
| F-7 | 「提交影响分析」是**独立模态**：影响分析非空才可提交 | `BR-02` |
| F-8 | 「审批」模态里**批准与拒绝共用一份「审批意见」**：未填时两个按钮都禁用；两者都只对审批中开放 | `BR-02` |
| F-9 | 终态（已拒绝 / 已实施）行**不再出现任何动作按钮**（只剩「详情」） | `BR-04` |
| F-10 | 列表默认按编号升序；四个筛选（状态 / 影响配置项 / 影响需求 / 申请方）**与后端 `list` 的参数一一对应**，变化即刷新并重置到第 1 页 | `US-07` |
| F-11 | 「提交审批」是单键动作，故用**二次确认**，文案强调"提交后内容即定型" | `BR-06` |

## 6. 字段展示（业务名取自术语表，列名见后端）

| 列 / 字段 | 后端字段 | 展示 |
|---|---|---|
| 变更请求编号 | `cr_no` | `mono` 等宽，点击开详情 |
| 变更请求标题 | `title` | 截断 40 字 |
| 申请方 | `requester` | 空显示 `—` |
| 影响的配置项 | `ci_nos` | 列表（`、` 连接）；空显示 `—` |
| 影响的需求 | `req_nos` | 列表（`、` 连接）；空显示 `—` |
| 状态 | `status` | 徽标（六态） |
| 变更说明 | `description` | 详情里 textarea（只读态展示全文） |
| 影响分析 | `impact_analysis` | 详情只读文本；「提交影响分析」态可写 |
| 审批意见 | `decision_note` | 详情只读文本（有则显示） |
| 审批人 | `approver` | 与审批意见同组回显 |
| 实施说明 | `implement_note` | 详情只读文本（有则显示） |
| 所属项目 | `project_no` | 详情只读（`create` 专属，`update` 不接受 → 快照字段） |

`col_default_hidden`：**无**（本页字段数适中，全部默认显示）

> **状态徽标用平台设计系统的 `.st` + `.st-<色>`**（`design-plus/view-convention/design-system.md`：
> blue=流程中态 / amber=进行中待办 / green=完成 / red=失败退回）。
> ⚠ **不要写 `var(--ok)` / `var(--red)` 之类内联色** —— 设计令牌（`fde_platform/static/fde.css`）
> 里**没有**这两个变量，浏览器会静默回落成继承色：**页面不报错、颜色全不对**
> （同组 `configuration_item` / `requirement` 样板即此写法，属可对照的既有瑕疵）。
> 本页 `已批准` 与 `已实施` 同为绿色（都是"完成"态），靠文本区分。

## 8. 已知限制

- **申请方尚未接候选**：`requester` 仍是文本字段（材料 FIGURE 6.5-4 的 Originator 是"人/组织"）。
  `stakeholder` 应用**已建成**（本节此前写"尚未建成"作废），要接只是给该输入框挂一个
  `datalist` + `svc("stakeholder", "list", {}, {quiet:true})`（照 `requirement` 页 `FE-51` 的范式，
  值仍存文本姓名、不动契约）。
- **影响范围下拉不做搜索过滤**：配置项 / 需求数量大时应改为可搜索的 autocomplete；
  当前是"一次拉全量 + 原生多选"，中小规模够用（与 `risk` 的「受影响需求」下拉同例）。
- **列表不展示变更说明 / 影响分析 / 审批意见**：长文本不进列表列（列表列是详情字段集的子集）。
- **审批不做会签**：一次结论即终（后端 `approve` / `reject` 单人结论），多级审批需后端先扩状态机。
- **实施需两步**：本页 `implement` 只登记"已实施"；真正的配置项版本变更在配置项页
  （`bump_version`）——跨应用无分布式事务（CONVENTION §8），页面上以实施说明留痕。
- **组级 `_contracts.md` 尚未收录本应用** —— 本页服务名 / 入参**逐字取自 `change_request.py` 的公共方法签名**；
  契约冻结应由第⑤步出口的统一 dump 完成（本任务范围不含改 `_contracts.md`）。

## 9. 验收关注点（供第⑧步）

1. 四态同屏（已提交 / 审批中 / 已批准 / 已拒绝）时动作按钮**各自不同**（F-6 / F-9）
2. 提出表单三个门：全空禁用 → 标题+申请方齐备仍禁用（范围空，F-1）→ 选了范围才可提交
3. 只读态 vs 编辑态：审批中行标题置灰、影响范围是纯文本而非 select（F-4）
4. 审批模态两个按钮同生共死（未填意见都禁用，F-8）
5. 终态行零动作按钮（F-9）
6. 四个筛选各收敛一次（F-10）
