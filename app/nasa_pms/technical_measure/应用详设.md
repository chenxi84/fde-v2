## 1. 技术度量概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `technical_measure` |
| 类名 | `TechnicalMeasure` |
| 聚合根 | 技术度量 |
| 标识 | `tpm_no`（`TPM-<三位序号>`） |
| 数据来源类型 | **独立创建**（度量的名称与目标/阈值由项目技术团队按技术计划定义，无上游单据自动生成） |
| 聚合内子表 | `tpm_reading`（实测值序列）、`tpm_alert`（告警记录）—— 二者**无独立标识**，随本聚合同事务维护 |
| 跨应用调用 | `requirement.get`（弱引用校验，只读） |

### 1.2 技术度量背景

#### 1.2.1 为什么需要这个聚合根？

材料把「技术度量」放在 **Technical Assessment** 过程的**入口位置**。§6.7.1.2.1 的第一句就是它的出处：

> "the technical plans provide the initial inputs into the Technical Assessment Process. These
> documents outline the technical reviews/assessment approach as well as **identify the technical
> measures that will be tracked and assessed to determine technical progress**."

而 FIGURE 6.7-1 把这一过程的输入直接写成 "Technical Measures … which will be **assessed or tracked
to determine technical progress**. These measures are also referred to as **MOEs, MOPs, KPPs, and TPMs**."
度量是这条反馈环上唯一的**量化读数**（FIGURE 6.7-2：Status Reporting → Assessing → Decision-making
→ (Re-)Planning）。

判定"超阈值"的口径写在附录 B 的两条定义里：

> **Technical Performance Measures**: "A set of performance measures that are **monitored by comparing
> the current actual achievement of the parameters with that anticipated at the current time and on
> future dates** … **Assessed parameter values that fall outside an expected range around the
> anticipated values indicate a need for evaluation and corrective action.**"
>
> **Threshold Requirements**: "A **minimum acceptable** set of technical and project requirements;
> the set could represent the **descope position** of the project."

告警这件事则写在 §6.7.1.2.1 与 §6.7.1.2.2：

> "Summarize the condition of the project by using **color-coded (red, yellow, and green) alert zones
> for all technical measures**."
>
> "Should there be indications that existing trends, if allowed to continue, will yield an unfavorable
> outcome, **corrective action should begin as soon as practical**."

现状是度量散在月报、状态报告的表格里：目标值与阈值一旦被随手改过就再没人知道"当初承诺的是多少"，
超阈值的那个月只是在会上被口头提一句，**没有留痕、没有处置记录、也没有"这条度量闭没闭"的答案**。
本聚合把这三件事收进一个事务边界：**口径（目标/阈值/方向）+ 实测值序列 + 告警与纠正**。

#### 1.2.2 期望达到什么目标？

- 每条度量**有唯一编号**（`tpm_no`），可被状态报告、告警、决策按号引用
- **目标值 / 阈值 / 优化方向**构成"判定口径"，在基线化时**冻结** —— 改它必须携带变更请求号（卡片 I-2）
- 实测值**按期成序列**落库（不是只留最新值）—— 度量的价值是趋势，不是快照
- **实测值超出阈值时，告警与这条实测值同事务落库**（卡片 I-1），告警**只有一个产生点**
- 告警有**纠正措施**可了结，未了结的告警**不许把度量关掉** —— 「早期预警 → 纠正」这条链不许断
- 一屏看到**跨度量的告警汇总**（材料原文就是一句汇总视图的需求，见 §1.2.1 的 alert zones 引文）

### 1.3 技术度量范围

#### 1.3.1 包含哪些功能？

- 度量的定义、修改、查询、列表（`create` / `update` / `get` / `list`）
- **基线化**：冻结判定口径并开始度量（`baseline`）
- **记实测值**：按期落库，超阈值时**同事务**产生告警（`record`）
- **纠正**：登记纠正措施并了结未了结的告警（`correct`）
- **重设基线**：改写判定口径的**唯一**入口，必填变更请求号（`rebaseline`）
- **关闭度量**：无未了结告警时收尾为终态（`close`）
- **跨度量告警汇总查询视图**（`list_alerts`）
- 与技术度量所服务的**需求**（`requirement`）通过弱引用（`req_no`）关联

#### 1.3.2 不包含哪些功能？

- **告警不独立成聚合**（卡片 I-1 的「同事务」）—— 它随实测值同一次调用产生、无独立标识；
  **跨度量的"告警汇总"是查询视图**（`list_alerts`），不是第二个聚合。
  这样切分的代价与收益：跨度量改一条告警的状态必然落在**它所属那条度量**的事务里，
  不能"批量销一批告警"；收益是**超阈值与告警永远一致**（不会出现"记了 8.2 却没有告警"）。
- **不做实测值的采集 / 接入**（测量数据怎么来）—— 材料 §6.7.1.2.2 说的是 "Regular, periodic
  (e.g., monthly) **tracking** of the technical measures"，采集管道属外部系统；本应用只承接
  「谁在什么时候把哪一期的读数报进来」，人经页面 / Agent 录入。
- **不做告警的通知 / 推送** —— 平台侧的通知能力（`fde_platform/alerts.py`）不属本聚合；
  本应用只负责把告警**留痕在案**。前端用「告警汇总卡片」承担"看得见"。
- **不做变更请求本身** —— 「判定口径的变更」是 `change_request`（聚合根卡 4）的范畴，
  本应用只**引用**变更请求号（`change_no`，弱引用文本），与同组 `configuration_item.bump_version`
  的处置一致（见 §6.3）。
- **不做 MOE** —— 卡片 7 的「类别（TPM/MOP/KPP）」只收三种；效能度量（MOE）是**定性**的
  （附录 B："A MOE is typically qualitative in nature or not able to be used directly as a
  design-to requirement"），它没有"实测值 vs 阈值"这种量化判定，不落进本聚合的模型。
- **不做成本 / 进度类度量** —— 附录 J §7.4 在同一节里列了 EVM、cost trends、schedule trends，
  但那些是**项目管理**范畴（挣值 / 关键路径），本聚合只承载**技术**度量（卡片 7 与术语表
  「技术度量（Technical Measure）」的口径）。

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 系统工程师 | 定义度量、基线化口径、记实测值、纠正、关闭 | 材料 §6.7.1.1 Inputs（technical plans 与 SEMP §7.4 由系统工程师编制） |
| 技术团队 | 只读消费度量与告警（作为状态评审 / 决策的输入） | 材料 §6.7.1.2.2「Key reviews … technical measures and their trends should be carefully scrutinized」 |
| 项目经理 | 只读消费告警汇总（红黄绿 alert zones 的读者） | 材料 §6.7.1.2.1「Project managers need visibility into the progress of those plans」 |

> 术语表未收「度量责任人」，按材料语境就地取名为**度量责任人**并回填（见 `新增术语.md`）。

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 定义一条技术度量（优先级：P1）

**作为**一名系统工程师
**我希望**登记一条度量（名称、类别、优化方向、目标值、阈值、单位、关联需求）
**以便**后续基线化并开始按期跟踪

**验收条件**：
- 给定名称 / 类别 / 方向 / 目标值 / 阈值齐备，当提交时，则新度量以「定义」状态落库，编号自动生成（`TPM-001` 起）
- 给定名称或目标值为空，当提交时，则**拒绝**并提示「度量名称不能为空」/「目标值不能为空」
- 给定类别或方向填了字典外的值，当提交时，则**拒绝**（`BR-04`）
- 给定「越大越好」却把目标值填得比阈值低，当提交时，则**拒绝**（`BR-05`）
- 给定 `req_no` 指向一条不存在的需求，当提交时，则**拒绝**并提示先去需求台账录入（跨应用弱引用）

#### 2.1.2 `US-02` 用户故事 — 基线化度量（优先级：P1）

**作为**一名系统工程师
**我希望**把目标值 / 阈值 / 优化方向冻结成一个基线版本并进入度量
**以便**判定"超没超阈值"时的口径是当初承诺的那一份，不会被事后改动

**验收条件**：
- 给定一个 `defined` 的度量，当基线化时，则状态变为 `measuring`、`baseline_ver` 落 `B1`
- 给定**已基线**的度量，当再次基线化时，则**拒绝**（每个度量只能基线一次）
- 给定基线化后的度量，当尝试 `update` 改目标值 / 阈值 / 方向时，则**拒绝**并指向 `rebaseline`（`BR-02`）
- 给定**未基线**的度量，当改目标值 / 阈值 / 方向时，则**允许**（冻结的是「基线之后」）

#### 2.1.3 `US-03` 用户故事 — 记一期实测值（优先级：P1）

**作为**一名系统工程师
**我希望**把这一期的实测值报进来
**以便**趋势可见，且**一旦超阈值立刻有告警在案**

**验收条件**：
- 给定一个 `measuring` 的度量，当记一期在阈内的实测值，则状态保持 `measuring`、`readings` 多一行
- 给定同一个度量，当记一期**超阈值**的实测值，则状态变 `exceeded`，且**同一次调用**产生一条 `open` 告警（`BR-01`）
- 给定已记过的**期次**，当再记一次时，则**拒绝**（`BR-07`：期次在本度量内唯一）
- 给定**尚未基线**的度量，当记实测值时，则**拒绝**（`BR-06`：口径未冻结，超没超阈值无从判定）
- 给定**已超阈值且未纠正**的度量，当继续记实测值时，则**拒绝**（`BR-06`：先纠正）
- 给定实测值不是数字（或为空），当提交时，则**拒绝**（`BR-08`）

#### 2.1.4 `US-04` 用户故事 — 纠正超阈值（优先级：P1）

**作为**一名系统工程师
**我希望**登记纠正措施并了结这条告警
**以便**"发现偏差 → 处置"这条链完整，且度量能继续往下度量

**验收条件**：
- 给定处于 `exceeded` 的度量，当提交纠正措施时，则状态变 `corrected`、告警变 `handled` 并带上措施文本
- 给定纠正措施为空，当提交时，则**拒绝**（「纠正措施不能为空」）
- 给定**不在** `exceeded`（定义 / 度量中 / 已纠正 / 已关闭）的度量，当纠正时，则**拒绝**
- 纠正后再记实测值：在阈内回到 `measuring`，再次出阈则重新置 `exceeded` 并生成**新**告警（旧告警留在台账）

#### 2.1.5 `US-05` 用户故事 — 重设基线（优先级：P1）

**作为**一名系统工程师
**我希望**在口径确实要变时，带着已批准的变更请求号改写目标值 / 阈值
**以便**承诺的改变走变更，而不是被"顺手改一下"抹掉

**验收条件**：
- 给定已基线的度量 + 变更请求号，当重设基线时，则目标值 / 阈值 / 方向被改写、`baseline_ver` 递增为 `B2`
- 给定**不带**变更请求号，当重设基线时，则**拒绝**（`BR-02`）
- 给定**尚未基线**的度量，当重设基线时，则**拒绝**（此时直接 `update` 即可，不需要变更请求号）
- 给定**已关闭**的度量，当重设基线时，则**拒绝**（硬终态）
- 给定重设后目标值与阈值违反了方向一致性，当提交时，则**拒绝**（`BR-05` 依旧生效）

#### 2.1.6 `US-06` 用户故事 — 关闭度量（优先级：P1）

**作为**一名系统工程师
**我希望**在告警都了结之后把度量关掉
**以便**"这条度量闭没闭"有确定答案，且关闭后记录不可再改

**验收条件**：
- 给定处于 `measuring` / `corrected` 的度量，当关闭时，则状态变 `closed`
- 给定**还有未了结告警**（`exceeded`）的度量，当关闭时，则**拒绝**并提示还剩几条（`BR-06`）
- 给定**定义态**（从未基线）的度量，当关闭时，则**拒绝**（没有度量过，无"关闭"可言）
- 给定已关闭的度量，当再关闭 / 记录 / 纠正 / 修改 / 重设基线时，则**全部拒绝**（硬终态）
- 关闭后**记录仍在**（不删除，含实测值序列与告警台账）

#### 2.1.7 `US-07` 用户故事 — 修改度量内容（优先级：P2）

**作为**一名系统工程师
**我希望**修改度量的名称 / 类别 / 计量单位 / 关联需求 / 责任人，并在未基线时修正判定口径
**以便**纠正定义时的登记错漏

**验收条件**：
- 给定未基线的度量，当改目标值时，则成功（但仍受 `BR-05` 约束）
- 给定已基线的度量，当改名称 / 单位 / 责任人时，则成功；当改目标值 / 阈值 / 方向时，则**拒绝**（`BR-02`）
- 给定一次不带任何字段的 `update`，则**拒绝**（「没有要修改的内容」）
- 给定已关闭的度量，当修改时，则**拒绝**（硬终态）

#### 2.1.8 `US-08` 用户故事 — 查询度量列表、详情与告警汇总（优先级：P2）

**作为**一名项目经理 / 技术团队成员
**我希望**按类别 / 状态 / 方向 / 关联需求筛选度量，看到某条度量的实测值序列与告警全貌，
并一屏看到**跨度量的告警汇总**
**以便**判断"哪些度量在告警、差多少、有没有人管"

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序），**分页返回 `{items, total}`**；
`get` 返回主档 + 实测值序列 + 告警台账（子表随聚合一起返回），未命中返回 `None` 不抛异常；
`list_alerts` 同样按 `{items, total}` 分页并带出所属度量的名称 / 类别 / 单位 / 目标值 / 阈值。

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 一条度量的一生（对齐状态机）

1. 系统工程师按技术计划定义度量（材料 §6.7.1.2.1：technical plans "identify the technical
   measures that will be tracked and assessed"）—— `create` → 定义（`defined`）
2. 口径定了就冻结并开测（附录 B 的 goal/threshold 口径、§6.7.1.2.1 的 "(Re-)Planning"）
   —— `baseline` → 度量中（`measuring`），`baseline_ver` = `B1`
3. 按期报读数（§6.7.1.2.2："Regular, periodic (e.g., monthly) tracking"）—— `record` ×N
   - 在阈内 → 仍是「度量中」
   - **超阈值** → 「超阈值」（`exceeded`），并**同一次调用**写出告警（卡片 I-1）
4. 看到告警就纠正（§6.7.1.2.2："corrective action should begin as soon as practical"）
   —— `correct` → 已纠正（`corrected`），告警了结
5. 纠正后再测 —— `record`：在阈内回到「度量中」，又出阈则重新置「超阈值」并行新告警
6. 口径确需变更 —— `rebaseline`（带变更请求号）→ `B2`（卡片 I-2）
7. 告警都了结后收尾 —— `close` → 已关闭（`closed`，硬终态，记录保留）

#### 3.1.2 场景2: 跨度量的告警汇总（材料原文的 alert zones）

1. 「功耗」超阈值 → 一条 `open` 告警
2. 「质量余量」超阈值 → 另一条 `open` 告警
3. 项目经理打开「告警汇总」（`list_alerts`，带所属度量的名称 / 类别 / 单位 / 目标值 / 阈值）→ 一屏看全
4. 逐条回各自度量做 `correct` 了结；两条度量随后各自才允许 `close`（`BR-06`）
   —— 汇总只是**查询视图**，改了状态仍然落在各自度量的事务里（§1.3.2 的取舍说明）

### 3.2 业务规则

#### 3.2.1 `BR-01` 实测值超出阈值必须触发告警记录（同事务）

- **规则描述**: `record` 判定为超阈值时，**同一次调用**插入一条 `tpm_alert`（`status='open'`）并把状态置 `exceeded`；在阈内则**不**产生告警
- **适用场景**: 记实测值
- **计算方式**: 校验 + 写入型（按方向判定：`higher` 时 `实测值 < 阈值`，`lower` 时 `实测值 > 阈值`）
- **依赖输入**: `[direction / threshold_value(实体字段), measured_value(服务实参)]`
- **输出**: `tpm_alert`（新增一行）、`technical_measure.status`
- **生效点**: `technical_measure.record → 判定后写入`
- **示例**: `record(TPM-001, "2026-Q2", 8.2)`（阈值 10、越大越好）→ `exceeded` + 告警
  「推进剂余量 第「2026-Q2」期实测值 8.2% 低于阈值 10%（超出 1.8%）」
- **依据**: 聚合根卡 7 的 **I-1**；材料 §6.7.1.2.1「Summarize the condition of the project by using
  color-coded (red, yellow, and green) **alert zones** for all technical measures」；
  附录 B「Assessed parameter values that fall outside an expected range around the anticipated values
  **indicate a need for evaluation and corrective action**」—— 告警就是"需要评估与纠正"这条判定的落点，
  与产生它的实测值分两次写就会出现"有读数没告警"的窗口

#### 3.2.2 `BR-02` 目标值与阈值一经基线不可直接改写，须经变更请求

- **规则描述**:
  - 状态为 `defined`（未基线）时，`update` **可**改 `direction` / `target_value` / `threshold_value`
  - 状态**离开** `defined` 后，`update` 传这三个字段**一律拒绝**；改写唯一入口是 `rebaseline`
  - `rebaseline` 必填 `change_no`（变更请求号），并把 `baseline_ver` 递增（`B1 → B2`）
- **适用场景**: 修改、重设基线
- **计算方式**: 字段白名单 + 必填校验（守卫顺序：**硬终态排最前**，其次"未基线不必走变更"）
- **依赖输入**: `[status / baseline_ver(实体字段), change_no(服务实参)]`
- **输出**: `technical_measure.target_value` / `threshold_value` / `direction` / `baseline_ver` / `change_no`
- **生效点**: `technical_measure.update → 校验` / `rebaseline → 校验并写入`
- **示例**: 对已基线的 `TPM-002` 调 `update(target_value=1100)` → 拒绝
  「已基线（B1），目标值 / 阈值 / 优化方向不可直接改写，须经变更请求（rebaseline + 变更请求号）」
- **依据**: 聚合根卡 7 的 **I-2**；附录 B「**Threshold Requirements**: A minimum acceptable set …
  the set could represent the **descope position** of the project」—— 阈值是"退到什么程度还算数"的承诺，
  承诺不能靠改一行数据来兑现
- **⚠ 与同组其它页的语义差**：这里**不是**"字段一律只读"（`review` / `configuration_item` 的已结论态
  是"无解锁入口"），而是**「基线前自由改、基线后须走变更」** —— 前端的字段锁定条件因此不同（见 §7.4）

#### 3.2.3 `BR-03` 度量编号唯一且不可变

- **规则描述**: `tpm_no` 系统生成（`TPM-` + 三位序号）、落库后不得修改
- **适用场景**: 创建、修改
- **计算方式**: 唯一性校验
- **依赖输入**: `[tpm_no(实体字段)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `technical_measure.create`（生成）/ `update`（**字段白名单里没有编号**，无从改起）
- **示例**: `update(tpm_no="TPM-001", tpm_no="TPM-100")` → 该参数不存在，服务不接受
- **依据**: 材料 §6.7.1.2.3 "Capture Work Products"（度量产出要**可追溯**，前提是有唯一标识）；
  与同组其余页的编号规则同源口径

#### 3.2.4 `BR-04` 类别 / 优化方向受字典约束

- **规则描述**: `category ∈ {tpm, mop, kpp}`；`direction ∈ {higher, lower}`；两者皆**必填**
- **适用场景**: 创建、修改、重设基线
- **计算方式**: 字典校验（+ 非空校验）
- **依赖输入**: `[category / direction(实体字段与服务实参)]`
- **输出**: `technical_measure.category` / `direction`
- **生效点**: `technical_measure.create` / `update` / `rebaseline`
- **示例**: `create(..., category="其它", ...)` → 拒绝「度量类别只能是 tpm/mop/kpp 之一」
- **依据**: 卡片 7 的「类别（TPM/MOP/KPP）」；业务名逐字取自术语表（技术绩效指标（TPM））
  与材料附录 A 缩略语表（MOP = Measure of Performance / KPP = Key Performance Parameter）；
  优化方向见 §7.4 的就地细化说明

#### 3.2.5 `BR-05` 目标值与阈值必须与优化方向一致

- **规则描述**: `higher`（越大越好）⇒ `目标值 ≥ 阈值`；`lower`（越小越好）⇒ `目标值 ≤ 阈值`
- **适用场景**: 创建、修改（含未基线时）、重设基线
- **计算方式**: 校验型（三者联合）
- **依赖输入**: `[direction / target_value / threshold_value(实体字段与服务实参)]`
- **输出**: `technical_measure.target_value` / `threshold_value`
- **生效点**: `technical_measure.create` / `update` / `rebaseline` → 校验
- **示例**: `create(..., direction="higher", target_value=8, threshold_value=10)` → 拒绝
  「优化方向为「越大越好」时，目标值 8 不能低于阈值 10」
- **依据**: 附录 B 的两条定义必须能同时成立 —— 目标值（"that anticipated"）与阈值
  （"a **minimum acceptable** set … the descope position"）在同一个方向上必须一前一后，
  否则阈值不构成底线、告警永远不响（或永远响）

#### 3.2.6 `BR-06` 状态守卫：未基线不得度量、超阈值未纠正不得继续、已关闭为硬终态

- **规则描述**:
  - 状态为 `defined` 时：`record` / `correct` / `close` / `rebaseline` **一律拒绝**
  - 状态为 `exceeded` 时：`record` / `close` **拒绝**（须先 `correct`）
  - 状态为 `closed` 时：`record` / `correct` / `update` / `baseline` / `rebaseline` / 再 `close` **全部拒绝**
- **适用场景**: 记实测值、纠正、关闭、基线化、重设基线、修改
- **计算方式**: 校验型（按状态拦截，守卫顺序：**硬终态排最前**）
- **依赖输入**: `[status / alert_open(实体字段与聚合内子表)]`
- **输出**: `technical_measure.status`
- **生效点**: `technical_measure.record` / `correct` / `close` / `baseline` / `rebaseline` / `update`
- **示例**: 对 `exceeded` 的 `TPM-004` 调 `close()` → 拒绝「还有 1 条告警未了结（超阈值未纠正）」
- **依据**: 材料 §6.7.1.2.2「corrective action should **begin as soon as practical**」——
  有未了结的告警时不允许靠继续测量把告警冲淡，也不允许"关了就当没事"；
  卡片 7 的状态机把「已关闭」放在末位（无后继），即硬终态

#### 3.2.7 `BR-07` 度量期次在本度量内唯一

- **规则描述**: 同一 `tpm_no` 下不允许出现两个相同的 `period`；跨度量同名期次互不影响
- **适用场景**: 记实测值
- **计算方式**: 唯一性校验（聚合内子表）
- **依赖输入**: `[tpm_reading.period(聚合内子表)]`
- **输出**: `tpm_reading` 新增一行（`period` / `measured_value`）
- **生效点**: `technical_measure.record → 校验`
- **示例**: 对 `TPM-002` 再记一次 `2026-Q1` → 拒绝「第「2026-Q1」期已经记过实测值」
- **依据**: 附录 B 的 TPM 定义是"把当前实际达成值与**预期值按期比较**"—— 同一期有两条读数，
  趋势就没有确定含义（也要重测就换一个新期次标签，如 `2026-Q1-R2`）

#### 3.2.8 `BR-08` 数值字段必须是数字

- **规则描述**: `target_value` / `threshold_value` / `measured_value` 三者必须可解析为数字（空值即拒）
- **适用场景**: 创建、修改、重设基线、记实测值
- **计算方式**: 类型校验（四舍五入前先拦下非数字）
- **依赖输入**: `[target_value / threshold_value / measured_value(服务实参)]`
- **输出**: `technical_measure.target_value` / `threshold_value`、`tpm_reading.measured_value`
- **生效点**: `technical_measure.create` / `update` / `rebaseline` / `record` → 校验
- **示例**: `create(..., target_value="十五", ...)` → 拒绝「目标值必须是数字，当前为「十五」」
- **依据**: 附录 B 的 TPM 定义通篇是**量化**比较（"quantitative measure" / "the current actual
  achievement of the parameters"）—— 非数字的目标值不可能构成可判定的阈值

### 3.3 业务数据

> 主档 16 项（`technical_measure` 表）+ 两张子表共 13 项。列名见 `schema.sql`，此处给业务口径。

#### 3.3.1 数据1: 度量编号（tpm_no）

- **数据描述**: 度量的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`TPM-` + 三位序号）
- **示例值**: "TPM-001"

#### 3.3.2 数据2: 度量名称（name）

- **数据描述**: 这条度量叫什么（列表与详情的第一识别项；附录 J §7.4 的 TPM 清单逐条即一个名称）
- **数据类型**: 文本（≤120 字）
- **数据来源**: 人工录入
- **示例值**: "推进剂余量"

#### 3.3.3 数据3: 度量类别（category）

- **数据描述**: 这条度量属于哪一类（材料 §6.7.1.2.1："Also referred to as MOEs, MOPs, KPPs, and TPMs"）
- **数据类型**: 字典：tpm / mop / kpp
- **数据来源**: 人工选择
- **字典对应业务名**: 技术绩效指标（TPM）/ 性能度量（MOP）/ 关键性能参数（KPP）
- **示例值**: "tpm"

#### 3.3.4 数据4: 优化方向（direction）

- **数据描述**: 这个量"往哪边算好" —— 判定口径的一半（另一半是阈值）
- **数据类型**: 字典：higher（越大越好）/ lower（越小越好）
- **数据来源**: 人工选择
- **示例值**: "higher"
- **说明**: 材料未给这个词，属第②步**工程口径**（见 §7.4 与 `新增术语.md` §5）

#### 3.3.5 数据5: 计量单位（unit）

- **数据描述**: 目标值 / 阈值 / 实测值的单位（只用于展示与告警文案，不参与判定）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "%"

#### 3.3.6 数据6: 目标值（target_value）

- **数据描述**: 这条度量的目标水平（附录 B："that **anticipated** at the current time and on future dates"）
- **数据类型**: 数值
- **数据来源**: 人工录入（基线后须经 `rebaseline`）
- **示例值**: 15.0

#### 3.3.7 数据7: 阈值（threshold_value）

- **数据描述**: 最低可接受水平（附录 B："**Threshold Requirements**: A minimum acceptable set …
  the set could represent the **descope position** of the project"）—— 越过它就是告警线
- **数据类型**: 数值
- **数据来源**: 人工录入（基线后须经 `rebaseline`）
- **示例值**: 10.0

#### 3.3.8 数据8: 基线版本标记（baseline_ver）

- **数据描述**: 当前生效的判定口径是第几版基线（`baseline` 落 `B1`，`rebaseline` 递增）
- **数据类型**: 文本（可空 —— 未基线时为空）
- **数据来源**: 系统按流转规则生成
- **示例值**: "B1"

#### 3.3.9 数据9: 变更请求号（change_no）

- **数据描述**: 最近一次改写判定口径所依据的变更请求（**弱引用** `change_request`，见 §6.3）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（`rebaseline` 必填）
- **示例值**: "CR-007"

#### 3.3.10 数据10: 当前实测值（current_value）

- **数据描述**: 最近一期的实测值（由 `record` 同步；未测过为空）—— 列表上的"读数"列
- **数据类型**: 数值（可空）
- **数据来源**: 系统（`record` 时写入）
- **示例值**: 12.5

#### 3.3.11 数据11: 当前度量期次（current_period）

- **数据描述**: 最近一期实测值对应的期次
- **数据类型**: 文本（可空）
- **数据来源**: 系统（`record` 时写入）
- **示例值**: "2026-Q3"

#### 3.3.12 数据12: 关联需求（req_no）

- **数据描述**: 这条度量服务于哪条需求（**弱引用** `requirement`，可悬空、可留空）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（填了即跨应用校验存在性）
- **示例值**: "REQ-001"

#### 3.3.13 数据13: 度量责任人（owner）

- **数据描述**: 谁负责这条度量的口径与读数（组织并上报读数的人）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "张三"

#### 3.3.14 数据14: 状态（status）

- **数据描述**: 度量在生命周期中的位置
- **数据类型**: 字典：defined / measuring / exceeded / corrected / closed
- **数据来源**: 系统按流转规则变更
- **示例值**: "measuring"

#### 3.3.15 数据15: 关闭说明（close_note）

- **数据描述**: 关闭度量时的收尾说明（谁因何收的尾）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（随 `close` 一起写入）
- **示例值**: "口径已达标"

#### 3.3.16 数据16: 所属项目（project_no）

- **数据描述**: 这条度量隶属的项目
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "P-2026-01"

#### 3.3.17 数据17: 实测值（tpm_reading，聚合内子表）

- **数据描述**: 按期落库的实测值序列 —— TPM 的本质是趋势，只留最新值就看不出趋势
- **字段**: `seq`（本度量内序号）/ `period`（度量期次，必填、**本度量内唯一**，`BR-07`）/
  `measured_value`（实测值，数值，必填，`BR-08`）/ `passed`（1 在阈内 / 0 超阈值，**判定推导值**）/
  `note`（备注：数据来源 / 测量工况，选填）
- **数据来源**: 人工录入（`record`）；`passed` 由服务判定后写入，无填写入口
- **示例值**: `seq=1, period="2026-Q1", measured_value=12.5, passed=1`

#### 3.3.18 数据18: 告警记录（tpm_alert，聚合内子表）

- **数据描述**: 超阈值这件事的记录（卡片 I-1："实测值超出阈值必须触发告警记录"）
- **字段**: `seq`（本度量内序号）/ `period`（触发期次，与实测值记录一致）/ `measured_value`（触发时实测值，快照）/
  `deviation`（超出量，恒为正）/ `message`（告警信息，人话）/ `status`（open / handled）/
  `handle_note`（纠正措施，`correct` 时写入）
- **数据来源**: 随 `record` **同事务**产生；`status` / `handle_note` 由 `correct` 变更
- **示例值**: `seq=1, period="2026-Q2", measured_value=8.2, deviation=1.8, status="open"`

### 3.4 状态机

```
defined（定义：口径已定义，未基线）
   │ baseline（基线化：冻结判定口径 → 开始度量）
   ▼
measuring（度量中） ──── record 超阈值 ────►  exceeded（超阈值，同事务生成告警）
   ▲                                              │ correct（登记纠正措施 + 了结告警）
   │ record 在阈内                                 ▼
   └──────────────────────────────────── corrected（已纠正）

measuring / corrected ──────── close ────────► closed（已关闭，终态：
                                               不可再记录 / 纠正 / 修改 / 重设基线）
```

**每个状态的到达服务**（详设 §4.1 的 FUNC 与服务一一对应）：

| 状态 | 到达服务 |
|---|---|
| `defined` | `create` |
| `measuring` | `baseline`（首次）／ `record`（在阈内，从 `corrected` 回来） |
| `exceeded` | `record`（实测值超阈值，同事务出告警） |
| `corrected` | `correct` |
| `closed` | `close`（`measuring` / `corrected` 皆可，须无未了结告警） |

> **合法迁移**：`defined→measuring`、`measuring↔exceeded`（经 `record` / `correct`）、
> `corrected→measuring|exceeded`（经 `record`）、`measuring|corrected→closed`。
> **拦截迁移**：`defined→*`（除 `measuring`，即未基线一律不许记录 / 纠正 / 关闭）、
> `exceeded→measuring|closed`（必须先 `correct`）、`closed→*`（终态，全部拒绝）。
> **没有"有状态无服务"的空洞** —— 五个状态各自都有能到达它的服务。
> ⚠ `defined` 态**允许** `update` 改判定口径（`BR-02` 的语义差），这是它有别于"纯只读初始态"的地方。

### 4.3 功能详细说明

#### 4.3.1 定义度量（FUNC-01）

- **输入**: 名称、类别、优化方向、目标值、阈值、计量单位、关联需求、责任人、所属项目
- **校验**: 名称非空 → `BR-04`（类别、方向字典）→ `BR-08`（目标值、阈值是数字）→ `BR-05`（与方向一致）→ 关联需求存在性（跨应用只读）
- **处理**: 生成 `tpm_no`（`TPM-<序号>`）→ 落库 → 状态置 `defined`
- **输出**: 新度量记录（含空 `readings` / `alerts` 与三计数为 0）

#### 4.3.2 基线化（FUNC-02）

- **输入**: `tpm_no` + 基线版本标记（选填，缺省 `B1`）
- **校验**: `BR-06`（终态拒绝；非 `defined` 拒绝 —— 已基线者要走 `rebaseline`）
- **处理**: 状态置 `measuring`、写 `baseline_ver`
- **输出**: 更新后的度量
- **说明**: 这是判定口径"从可改到冻结"的那一刻，也是"能不能记实测值"的闸门（一并构成 `BR-02` 的前半）

#### 4.3.3 记实测值（FUNC-03）

- **输入**: `tpm_no` + 度量期次 + 实测值 + 备注（选填）
- **校验**: 状态守卫（终态 → 未基线 → 超阈值未纠正，`BR-06`）→ 期次非空与唯一（`BR-07`）→ 实测值是数字（`BR-08`）
- **处理**: 判定（`_judge`，唯一实现）→ 插入 `tpm_reading` → **超阈值则插入 `tpm_alert`（同一事务）** →
  更新 `status` / `current_value` / `current_period`
- **输出**: 更新后的度量（含新读数与可能的告警）
- **说明**: 判定与告警在**同一应用、同一连接、同一次服务调用**内完成，平台保证一个事务（CONVENTION §8）

#### 4.3.4 纠正（FUNC-04）

- **输入**: `tpm_no` + 纠正措施
- **校验**: 终态拒绝 → 未基线拒绝 → 非 `exceeded` 拒绝；措施非空
- **处理**: 把该度量**所有 `open` 告警**置 `handled` 并写 `handle_note` → 状态置 `corrected`（同事务）
- **输出**: 更新后的度量
- **说明**: 由 `BR-06` 的"未基线不得记录"推论可知，同一时刻**最多一条** `open` 告警；
  实现仍按"了结所有 open"写，语义是"当前未了结的告警"，不依赖那条推论

#### 4.3.5 重设基线（FUNC-05）

- **输入**: `tpm_no` + 目标值 + 阈值 + 变更请求号 + 优化方向（选填，缺省沿用当前）
- **校验**: 终态拒绝 → 未基线拒绝（此时直接 `update` 即可）→ 变更请求号非空 → 数值合法（`BR-08`）
  → 方向字典（`BR-04`）→ `BR-05`
- **处理**: 改写三个口径字段、`baseline_ver` 递增、写 `change_no`
- **输出**: 更新后的度量
- **说明**: 历史读数**不改**（每行 `passed` 是当时的判定快照）—— 口径改了不等于过去没发生过

#### 4.3.6 关闭度量（FUNC-06）

- **输入**: `tpm_no` + 关闭说明（选填）
- **校验**: 已关闭拒绝 → 未基线拒绝（从未度量）→ 有未了结告警拒绝（`BR-06`）
- **处理**: 状态置 `closed`、写 `close_note`
- **输出**: 更新后的度量（记录保留）

#### 4.3.7 告警汇总（FUNC-10）

- **输入**: 度量编号 / 告警状态 / 度量类别（皆可选）+ 分页
- **处理**: `tpm_alert JOIN technical_measure` 取出行项与所属度量的名称 / 类别 / 单位 / 方向 / 目标值 / 阈值
- **输出**: `{items, total}`
- **说明**: 这是**查询视图**，不是聚合 —— 它不拥有任何状态（§1.3.2）

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 超阈值必须同事务出告警

**Given** `TPM-001`（阈值 10、越大越好）处于度量中
**When** 记一期实测值 `8.2`
**Then** 状态变「超阈值」，且**同一次调用**后 `alert_open = 1`、告警带期次与超出量（`BR-01`）
**And given** 被拒绝的一次 `record`（如期次重复）**when** 提交 **then** 实测值与告警**都不落库**（同事务的另一面）

#### 6.1.2 标准2: 判定口径基线后冻结

**Given** `TPM-002` 已基线（`B1`）
**When** `update(target_value=1100)` / `update(threshold_value=1300)` / `update(direction="higher")`
**Then** 三者全部拒绝，提示"须经变更请求"（`BR-02`）
**And given** 未基线的 `TPM-003` **when** 改目标值 **then** 成功（冻结的是"基线之后"）

#### 6.1.3 标准3: 重设基线必须带变更请求号

**Given** 已基线的 `TPM-002`
**When** `rebaseline(target, threshold, change_no="  ")`
**Then** 拒绝「请提供变更请求号」
**And given** `change_no="CR-007"` **when** 重设 **then** 成功且 `baseline_ver` 变 `B2`

#### 6.1.4 标准4: 超阈值未纠正不得继续记录 / 不得关闭

**Given** `TPM-004` 处于 `exceeded`（1 条 `open` 告警）
**When** `record(...)` / `close()`
**Then** 两者都拒绝（`record` 提示先纠正；`close` 提示还有 1 条告警未了结）
**And given** 先 `correct` **when** 再 `record` **then** 成功

#### 6.1.5 标准5: 已关闭为硬终态、记录保留

**Given** `TPM-001` 已关闭
**When** `record` / `correct` / `update` / `rebaseline` / `close` 任一
**Then** 全部拒绝（`BR-06`）
**And given** 关闭后 **when** `get` **then** 主档 + 3 期实测值 + 1 条告警**都还在**

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms；`list_alerts` 同
- 度量编号生成在并发登记下不重复（`BR-03`）
- `get` 未命中**不抛异常**，返回 `None`（供跨应用探测式调用）
- 实测值与告警**同事务**：`record` 在写告警之前的任何一步失败，整次调用不落库（链测试 TC-30/TC-31 验证）

### 6.3 已知问题或限制

- **变更请求只校验"带了变更请求号"，不校验"该变更已批准"** ——
  `rebaseline(change_no=...)` 只保证非空。真正校验需要 `self.fde.call("change_request", "get",
  change_no=...)`，与同组 `configuration_item.bump_version` 的处置一致（那页也留了同一个缺口）。
  卡片 7 的跨应用调用只写了 `requirement`，本版不额外引入该边；`change_request` 应用已建成，
  将来补这一处是"加一个私有校验方法 + 一行字面量调用"。
- **卡片 7 的跨应用调用写作 `requirement.list`，落实现为 `requirement.get`** ——
  `architecture.md` ③ 的跨应用调用表把这类调用统称 `.list`（用途列写的是"选受影响需求"），
  而核对**单条**弱引用必须按号取，故落成 `requirement.get`（同组 `risk` / `verification`
  两页同口径）。`requirement.list` 的签名里没有任何能定位单条需求的参数（只有
  `req_type` / `status` / `source_req_no`），用它做不了存在性校验。
- **不做 `pending` 的跨应用联动** —— 度量超阈值"may trigger changes to requirements"
  （材料 §6.2.1.1 的 Inputs），但那是**跨应用写操作**（要在 `requirement` 侧改状态），
  需两应用同时改动 + 补偿设计（CONVENTION §8），本版不做；告警里带上 `req_no` 即为线索。
- **`passed` 与阈值是"当时判定"的快照** —— 重设基线后**不回溯**改历史读数的 `passed`。
  这是刻意的（"口径改了不等于过去没发生过"），但也意味着：拿旧读数与**当前**阈值对比会得到
  与 `passed` 不同的结论。前端因此把"阈值"列展示为**当前生效口径**，并在详情里并列展示历史读数。
- **没有删改实测值的服务** —— 实测值是**留痕**，记错了只能再记一期（换期次标签）并在备注里说明。
  这与同组 `review` 的"评审项不可删"同口径。若将来要允许更正，加一个字段白名单只含 `note` 的服务即可。
- **没有批量纠正** —— `correct` 作用于**一条**度量（它最多只有一条未了结告警，批量没有对象）。
- **`list` 与 `get` 的字段口径**：主档 16 字段 + `reading_total` / `alert_total` / `alert_open`
  三计数**两边一致**；实测值序列与告警台账**明细只在 `get`**（列表不做 N+1 取子表）。
  这不是"口径差"，是刻意的分层。
