> 产出技能：第②步 逐聚合根应用设计（规格 `design-plus/应用设计.md`）
> 输入：`app/nasa_pms/architecture.md`（聚合根卡 9，含不变量 I-1 / I-2）+ `brd/`
> （第 06 章 §6.3 Interface Management、第 18 章 附录 L Interface Requirements、
> 第 07 章 附录 A 缩略语表）
> + `app/nasa_pms/术语表.md`
> 业务名取自术语表（已收「接口控制文档（ICD）」）；表里没有的（接口编号 / 接口名称 / 接口类型 /

## 1. 接口概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `interface` |
| 类名 | `Interface` |
| 聚合根 | 接口（系统/分系统之间的接口约定） |
| 标识 | `if_no`（`IF-<三位序号>`） |
| 数据来源类型 | **独立创建**（接口由项目内人员在系统设计活动中识别并约定，无上游自动生成） |
| 聚合内子表 | `interface_change`（版本变更通知记录）—— 无独立标识，随本聚合同事务维护 |
| 跨应用调用 | `configuration_item.list`（弱引用校验：接口文档本身是配置项） |

### 1.2 接口背景

#### 1.2.1 为什么需要这个聚合根？

材料把接口管理列为横切技术管理过程之一（§6.3）："The definition, management, and control of
interfaces are crucial to successful programs or projects."，并说明它存在的**前提是分工**——
"to assist in controlling product development when efforts are divided among parties (e.g.,
Government, contractors, geographically diverse technical teams, etc.) **and/or** to define and
maintain compliance among the products that should interoperate."

分工一旦发生，"这个口的定义是什么、谁提供、谁使用、现在是第几版"就成了必须先答的问题：

- §6.3.1.1 Inputs 的第一项就是 **Interface Requirements**（"the internal and external functional,
  physical, and performance interface requirements developed as part of the Technical Requirements
  Definition Process for the product(s)"）；
- §6.3.1.2.2 明确接口管理在系统设计期要**建立接口的四要素** ——
  "This analysis will establish the **origin, destination, stimuli, and special characteristics**
  of the interfaces that need to be documented and maintained."（origin / destination 就是**两端**）；
- §6.3.1.3 Outputs 给出接口文档的四种形态：IRD / ICD / IDD / ICP，并说明它们
  "will then be maintained and approved using the Configuration Management Process and become a
  part of the overall technical data package for the project."；
- §6.3.1.3 同时给出**变更的硬约束**："**For interfaces that require approval from all sides,
  unanimous approval is required.**" —— 两端都必须在链条里，一端不知情的"接口变更"不成立。

现状是接口靠接口控制文件的 Word/PDF 散落传递：没有统一编号可引用、两端是谁靠正文叙述、
"现在是第几版、上一版改了什么都通知了谁"无人能答；而材料给出的代价口径很硬 ——
接口文档是**产品验证与确认的输入**（"interface control documentation and approved interface
requirement changes are used as inputs to the Product Verification Process and the Product
Validation Process"），改接口晚在研制后期，"more likely to have a significant impact on the cost,
schedule, or technical design/operations"。

#### 1.2.2 期望达到什么目标？

- 每条接口**有唯一编号**（`if_no`），可被 ICD、验证项、评审材料按号引用
- 每条接口**明确两端**（提供方 / 使用方）—— 卡片 **I-1** 的落点：两端都不能为空，
  且**不能是同一个系统**（一条接口的两端必须是两个东西，否则不构成接口）
- 接口类型受字典约束（ICD / IRD / IDD / ICP，逐字取自材料 §6.3.1.3）
- **版本只能递增**（字母修订版 A→B→C），首次发布定版 `A`
- **版本变更必须通知两端**（卡片 **I-2**）—— 通知记录与版本变更**同事务**落库，
  且每次变更**恰好两条**（提供方一条、使用方一条）；没有"只通知一端"的入口
- 接口的收尾是**冻结**（硬终态），冻结后记录留存、不可再改（配置状态记账要求留痕）

### 1.3 接口范围

#### 1.3.1 包含哪些功能？

- 接口的定义、修改、查询、列表（`create` / `update` / `get` / `list`）
- **发布**：定义中 → 已发布（`release`）—— 首次发布**定版 A 并通知两端**；
  若接口处于「变更中」，同一服务承担**变更落实**（回到已发布，不重复通知）
- **版本变更**：已发布 → 变更中（`revise`）—— 改版本号、登记变更原因（与可选的 ICD 新内容），
  并**通知两端**（与版本号同事务）
- **冻结**：已发布 → 已冻结（`freeze`，硬终态）
- **变更通知台账**：跨接口的变更通知汇总查询视图（`list_changes`）
- 接口文档与**配置项**的弱引用关联（`ci_no`，跨应用 `configuration_item.list` 校验存在且未归档）

#### 1.3.2 不包含哪些功能？

- **不做接口需求的条目化**（IR 本身是**需求**）—— 材料附录 L 的接口需求（"the interface
  requirement on each side of the interface plane"）在需求管理过程里管，本应用管的是
  **接口约定（接口文档）**；接口类型的字典里有 `ird`（接口需求文档），指的是"这条接口以 IRD
  形态受控"，不是"本应用维护需求条目"。
- **不做接口要求的逐条技术参数**（附录 L §3.2 的 mass properties / structural / fluid /
  electrical / EMI / vibroacoustics …）—— 那是**接口文档正文**的内容，本应用只用
  `icd_content` 存正文摘要与关键条款，不把这些参数建成字段树（否则本应用会变成一份文档模板引擎）。
- **不做配置项本身**（版本、基线、归档）—— 属 `configuration_item`；本应用只弱引用编号，
  跨应用只读校验（§6.3）。
- **不做接口的验证执行** —— 属 `verification`（每条进入基线的需求至少一条验证项，
  接口需求亦在其列）；本应用不落验证结果。
- **不做 IWG（接口工作组）的组织管理** —— §6.3.1.2.4 的 IWG 是**组织与职责**
  （"technical team with appropriate technical membership from the interfacing parties"），
  属组织主数据；本应用只在 `owner` 上落一个接口责任人，在变更记录里落**通知对象**。
- **不做跨接口的批量变更** —— 每次变更都落在**它自己那条接口**的事务里（§1.3.2 的取舍），
  没有"一次改一批接口"的服务。

> **为什么把「版本变更通知记录」并入本聚合**（而不是独立成一个"通知/待办"聚合）：
> 卡片 I-2 要求"变更记录同事务"，而跨应用/跨聚合的写没有分布式事务（CONVENTION §8）——
> 一旦通知独立成聚合，就会出现"版本已改、通知还没写"的窗口。并入本聚合的代价是：
> **跨接口的批量通知做不到**（每次变更必须逐条接口发起）；收益是
> **版本号与两端通知永远一致**（不会出现"改到 B 版了但使用方还拿着 A 版"）。

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 接口责任人 | 定义接口、发布、发起版本变更、冻结（`owner`） | 材料 §6.3.1.2.1（接口管理职责的指派） |
| 接口两端（提供方 / 使用方） | 被通知的对象：每次版本变更各收到一条记录；跨方变更须一致同意 | 材料 §6.3.1.2.4（IWG 的沟通链路）、§6.3.1.3（unanimous approval） |
| 配置管理员（CM） | 把接口文档作为受控项纳入配置管理（跨应用） | 材料 §6.3.1.3（"maintained and approved using the Configuration Management Process"） |
| 系统工程师 / 技术团队 | 只读消费接口约定（作为设计、集成与验证的输入） | 材料 §6.3.1.2.2 / §6.3.1.2.3 |

> 术语表已收「系统工程师」「技术团队」「配置管理员（CM）」；**接口责任人**按材料语境
> （接口管理职责的承担者）就地取名并回填。

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 定义一条接口（优先级：P1）

**作为**一名接口责任人
**我希望**登记一条系统/分系统之间的接口约定（名称、类型、提供方、使用方、约定内容）
**以便**后续能发布定版、按版本变更，并让两端有据可依

**验收条件**：
- 给定名称 / 类型 / 提供方 / 使用方齐备，当提交时，则新接口以「定义中」落库，编号自动生成（`IF-001` 起），**此时尚无版本**
- 给定提供方（或使用方）为空，当提交时，则**拒绝**并提示「接口的提供方不能为空」/「接口的使用方不能为空」（`BR-01`，卡片 I-1）
- 给定两端填成同一个系统，当提交时，则**拒绝**并提示「接口的两端不能是同一个系统」（`BR-01`）
- 给定类型填了字典外的值（或为空），当提交时，则**拒绝**（`BR-02`）
- 给定关联的配置项不存在（或已归档），当提交时，则**拒绝**（`BR-08`）

#### 2.1.2 `US-02` 用户故事 — 发布接口（首次定版 + 通知两端）（优先级：P1）

**作为**一名接口责任人
**我希望**把定义好的接口发布出去、定版为 A，并把这一版**通知到两端**
**以便**两端知道自己要按哪一版做设计

**验收条件**：
- 给定一个「定义中」的接口，当发布时，则版本置 `A`、状态变 `released`，
  并**同时落两条通知记录**（提供方一条、使用方一条，`BR-04`）
- 给定一个「变更中」的接口，当发布时（＝完成变更），则状态回到 `released`，
  **不新增通知记录**（变更通知已在 `revise` 时发出）
- 给定已发布 / 已冻结的接口，当再次发布时，则**拒绝**（`BR-07` / 重复发布）

#### 2.1.3 `US-03` 用户故事 — 发起版本变更（改版 + 通知两端）（优先级：P1）

**作为**一名接口责任人
**我希望**把接口从 A 版改到 B 版，并说明为什么改
**以便**版本号与两端收到的那份约定始终一致

**验收条件**：
- 给定一个已发布的接口，当以新版本 `B` 与变更原因发起变更时，则版本变 `B`、状态变 `changing`，
  并**同时落两条通知记录**（两端各一条，`BR-04`，卡片 I-2）
- 给定新版本号不是单个大写字母（如 `b` / `AB` / 空），当提交时，则**拒绝**（`BR-03`）
- 给定新版本号**不大于**当前版本（如当前 A 却提交 A），当提交时，则**拒绝**（`BR-03`：版本只能递增）
- 给定未填变更原因，当提交时，则**拒绝**（`BR-04`：原因要记入通知台账）
- 给定接口仍是「定义中」（尚未定版），当发起变更时，则**拒绝**（先发布）
- 给定接口已在「变更中」，当再次发起变更时，则**拒绝**（先完成本次变更）
- 给定可选的 ICD 新内容，当提交时，则约定内容**随版本一起更新**（同事务）

#### 2.1.4 `US-04` 用户故事 — 完成版本变更（优先级：P1）

**作为**一名接口责任人
**我希望**在变更落到实处后把接口回到「已发布」
**以便**区分"正在改"与"改完了、这就是当前有效版本"

**验收条件**：
- 给定一个「变更中」的接口，当执行发布（＝完成变更）时，则状态变 `released`，版本不变
- 该动作**不产生新的通知记录**（同一次变更不会在台账里出现两轮）

#### 2.1.5 `US-05` 用户故事 — 冻结接口（优先级：P1）

**作为**一名接口责任人
**我希望**在接口定稿后冻结它
**以便**"这条接口到底定没定"有确定答案，且冻结后记录不可再改

**验收条件**：
- 给定一个「已发布」的接口，当冻结时，则状态变 `frozen`（硬终态），可附冻结说明
- 给定「定义中」或「变更中」的接口，当冻结时，则**拒绝**（`BR-09`：未定版 / 变更未落实）
- 给定已冻结的接口，当再冻结 / 修改 / 发布 / 变更版本时，则**全部拒绝**（`BR-07`）
- 冻结后**记录仍在**（不删除，含全部历史通知记录）

#### 2.1.6 `US-06` 用户故事 — 修改接口内容（优先级：P2）

**作为**一名接口责任人
**我希望**修改接口的名称 / 类型 / 责任人 / 所属项目 / 关联配置项
**以便**纠正登记错漏

**验收条件**：
- 给定一个「定义中」的接口，当改名称 / 两端 / 约定内容时，则成功（还没定版，怎么改都是定义过程）
- 给定一个**已定版**（已发布 / 变更中）的接口，当改**两端**或**约定内容**时，则**拒绝**并提示走版本变更（`BR-05`）
- 给定一个已定版的接口，当改名称 / 类型 / 责任人 / 项目 / 关联配置项时，则成功（描述性字段）
- 给定把两端改成同一个系统（只改一端也可能撞上），当提交时，则**拒绝**（`BR-01`，**改后整体校验**）
- 给定一次不带任何字段的 `update`，则**拒绝**（「没有要修改的内容」）
- 给定已冻结的接口，当修改时，则**拒绝**（`BR-07`）

#### 2.1.7 `US-07` 用户故事 — 查询接口列表与详情（优先级：P2）

**作为**一名系统工程师 / 技术团队成员
**我希望**按类型 / 状态 / 两端筛选接口，并看到某条接口的版本变更通知全貌
**以便**判断"哪些接口还没定版""这条口改过几版、都通知了谁"

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序），**分页返回 `{items, total}`**；
`get` 返回主档 + 变更通知记录（子表随聚合一起返回），未命中返回 `None` 不抛异常。

#### 2.1.8 `US-08` 用户故事 — 变更通知台账（跨接口视图）（优先级：P2）

**作为**一名接口责任人 / 配置管理员
**我希望**在一个台账里看到所有接口的版本变更通知（按端筛选）
**以便**核验"每次变更确实通知到了两端"（卡片 I-2 的可核查面）

**验收条件**：给定端（提供方 / 使用方）或接口编号或起因，当查询时，则返回匹配的通知行
（含所属接口的名称 / 类型 / 当前状态），**分页返回 `{items, total}`**。

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 一条接口的一生（对齐状态机）

1. 在系统设计活动里识别出一个接口，登记它的两端与约定内容（材料 §6.3.1.2.2：establish the
   **origin, destination**, stimuli, and special characteristics）—— `create` → 定义中（`defined`）
2. 还没定版前反复推敲：改名称、改两端、改约定内容（`update`，仅定义中可改端与内容）
3. 定版发布：把这一版交给两端 —— `release` → 已发布（`released`），版本 `A`，
   **两条通知记录同事务落库**（提供方 / 使用方各一条）
4. 需要改：发起版本变更并说明原因 —— `revise` → 变更中（`changing`），版本 `B`，
   **再通知两端**（§6.3.1.3："For interfaces that require approval from all sides,
   unanimous approval is required." —— 两端都必须在链条里）
5. 变更落实（设计/接口文件同步到位）—— `release` → 回到已发布（`released`），版本 `B`
6. 接口定稿、进入配置管理 —— `freeze` → 已冻结（`frozen`，硬终态，记录保留）

#### 3.1.2 场景2: 一次版本变更产生的两条通知（I-2 的落法）

1. 接口责任人对 `IF-001` 发起 `revise(new_version="B", reason="舵机控制器换代，周期改 10ms")`
2. 同一事务里：版本号改为 `B`、状态转「变更中」，并写入**两条**通知记录 ——
   `(seq=3, party=provider, party_name=飞控计算机（FCC）, old=A, new=B)` 与
   `(seq=4, party=consumer, party_name=舵机控制器（SACU）, old=A, new=B)`
3. 台账（`list_changes`）里按端筛选，两端各看到他该收到的那一条
4. 若只写了一条就提交 —— **不可能**：写两条这件事由私有方法 `_notify` **一次完成**，
   没有任何"只通知一端"的公开入口（不变量不靠调用方自觉）

### 3.2 业务规则

#### 3.2.1 `BR-01` 接口必须明确两端（提供方与使用方都不能为空且相异）

- **规则描述**: `create` / `update` 后，`provider` 与 `consumer` 都必须非空，且**不相等**
- **适用场景**: 定义、修改
- **计算方式**: 校验型（非空 + 相异；`update` 校验的是**改完之后**的两端）
- **依赖输入**: `[provider / consumer(实体字段与服务实参)]`
- **输出**: `interface.provider` / `interface.consumer`（NOT NULL）
- **生效点**: `interface.create` / `update → 校验`
- **示例**: `create(..., consumer="  ", ...)` → 拒绝「接口的使用方不能为空」；
  `create(..., provider="系统甲", consumer="系统甲")` → 拒绝「接口的两端不能是同一个系统」
- **依据**: 聚合根卡 9 的 **I-1**（"提供方与使用方都不能为空"）；材料 §6.3.1.2.2 把
  "origin, destination" 列为要建立的四要素之首 —— 两端是接口的身份，缺一端就不是接口；
  两端相同则"互操作"的对象不存在（§6.3 开篇 "products that should interoperate"）
- **说明**: "相异"是 I-1 的**就地细化**（材料没有这一句），已登记在 §7.4 —— 与
  `configuration_item` 处理"类型字典 / 基线名称"的方式一致

#### 3.2.2 `BR-02` 接口类型受字典约束

- **规则描述**: `if_type ∈ {icd, ird, idd, icp}`，且**必填**
- **适用场景**: 定义、修改
- **计算方式**: 字典校验（+ 非空校验）
- **依赖输入**: `[if_type(实体字段与服务实参)]`
- **输出**: `interface.if_type`
- **生效点**: `interface.create` / `update → 校验`
- **示例**: `create(..., if_type="其它", ...)` → 拒绝「接口类型只能是 icd/ird/idd/icp 之一」
- **依据**: 材料 §6.3.1.3 原文 —— "Types of interface documentation include the Interface
  Requirements Document (IRD), Interface Control Document/Drawing (ICD), Interface Definition
  Document (IDD), and Interface Control Plan (ICP)."（四类逐字成字典；业务名回填见 `新增术语.md`）

#### 3.2.3 `BR-03` 版本只能递增（首次发布定版 A）

- **规则描述**: 版本是**单个大写字母**（`A` 起）；`release`（首次）把版本置 `A`；
  `revise` 的新版本必须**严格大于**当前版本；「定义中」不得发起变更
- **适用场景**: 发布、版本变更
- **计算方式**: 字典 + 单调性校验
- **依赖输入**: `[version(实体字段), new_version(服务实参)]`
- **输出**: `interface.version`
- **生效点**: `interface.release` / `revise → 校验`
- **示例**: 当前 `A`，`revise(new_version="A")` → 拒绝「接口版本只能递增：新版本 A 不大于当前版本 A」；
  `revise(new_version="b")` → 拒绝「新版本号必须是单个大写字母」
- **依据**: 材料 §6.3.1.3 —— 接口需求一经基线，变更须经需求管理过程评估影响并**更新文档**；
  接口版本回退会让两端的既有设计失去依据。**字母修订版**与
  「首次发布定 A」都是第②步**工程口径**（材料只给了 ICD/IRD/IDD/ICP 这些**文档**名，
  没有版本号格式），与同组 `configuration_item`（整型 `v1/v2`）取**不同**口径是刻意的：
  接口文档的行业惯例是 Rev A/B/C，而配置项版本是发布次数

#### 3.2.4 `BR-04` 接口版本变更必须通知两端（变更记录同事务）

- **规则描述**: 每一次**版本号发生变化**（`release` 首次定版、`revise` 改版）都要在
  **同一事务**里写入**恰好两条**通知记录：`party=provider` 一条、`party=consumer` 一条；
  变更原因必填（`revise`）；「变更中 → 已发布」（变更落实）**不重复通知**
- **适用场景**: 发布、版本变更
- **计算方式**: 校验型（原因非空）+ 结构化保证（`_notify` 一次写两条，无"只通知一端"的入口）
- **依赖输入**: `[status / version(实体字段), reason(服务实参)]`
- **输出**: `interface_change`（`(if_no, seq)` 复合主键，本接口内递增）+ `interface.version`
- **生效点**: `interface.release` / `revise → _notify`
- **示例**: `revise(IF-001, "B", "舵机控制器换代")` → `change_total` 从 2 变 4，
  且新增的两条 `(revise, provider, A→B)` / `(revise, consumer, A→B)`
- **依据**: 聚合根卡 9 的 **I-2**（"接口版本变更必须通知两端（变更记录同事务）"）；
  材料 §6.3.1.2.4（IWG 的职责是 "establish communication links between those responsible for
  interfacing systems"）、§6.3.1.3（"For interfaces that require approval from all sides,
  unanimous approval is required"）、§6.3.1.2.5（"actions taken to correct identified interface
  anomalies" 要可追溯 —— 记录里带**端名快照** `party_name`）

#### 3.2.5 `BR-05` 已定版后「两端」与「约定内容（ICD）」不可直接改

- **规则描述**: 状态不是 `defined` 时，`update` 传 `provider` / `consumer` 或 `icd_content` **一律拒绝**
- **适用场景**: 修改
- **计算方式**: 校验型（按状态拦截）
- **依赖输入**: `[status(实体字段)]`
- **输出**: `interface.provider` / `consumer` / `icd_content`
- **生效点**: `interface.update → 校验`
- **示例**: 对 `released` 的 `IF-005` 调 `update(consumer="其它分系统")` → 拒绝
  「接口 IF-005 已定版（已发布），两端不能再改（改端等于换一条接口，BR-05）」
- **依据**: 材料 §6.3.1.2.2 把两端当作接口的 origin / destination（身份）；
  §6.3.1.3 要求接口需求基线化之后的变更走变更过程 —— **改端 = 换一条接口**
  （应新建），**改约定内容 = 接口变更**（应走 `revise`，带新版本与原因并通知两端）。
  ⚠ 与同组两个页面的锁定条件**都不同**（逐条重判，不照抄）：`configuration_item` 是
  "带变更号即可解锁"，`review` 是"结论后一律冻结"，本页是
  **"定义中随便改、定版后两端与内容锁死但描述性字段仍可改"**

#### 3.2.6 `BR-06` 接口编号唯一且不可变

- **规则描述**: `if_no` 系统生成（`IF-` + 三位序号），落库后不得修改
- **适用场景**: 定义、修改
- **计算方式**: 唯一性校验
- **依赖输入**: `[if_no(实体字段)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `interface.create`（生成）/ `update`（**字段白名单里没有编号**，无从改起）
- **示例**: `update(if_no="IF-001", if_no="IF-100")` → 该参数不存在，服务不接受
- **依据**: 材料 §6.3.1.3（接口文档是 "overall technical data package" 的一部分，
  可追溯的前提是有唯一标识）；与同组 `configuration_item` 的 BR-04 同源口径

#### 3.2.7 `BR-07` 已冻结为硬终态

- **规则描述**: 状态为 `frozen` 时，`update` / `release` / `revise` / `freeze` **全部拒绝**
- **适用场景**: 修改、发布、版本变更、冻结
- **计算方式**: 校验型（守卫顺序：**硬终态排最前**）
- **依赖输入**: `[status(实体字段)]`
- **输出**: `interface.status`
- **生效点**: 四个服务的状态守卫第一步
- **示例**: 对 `frozen` 的 `IF-001` 调 `update(if_name="偷改")` → 拒绝「已冻结（终态），不能再修改」
- **依据**: 卡片 9 的状态机把「冻结」放在末位（无后继）；材料 §6.3.1.3 —— 接口文档进入
  配置管理过程之后由 CM 维护与批准，本应用不再改它

#### 3.2.8 `BR-08` 关联配置项必须真实存在且未归档

- **规则描述**: `ci_no` 非空时，跨应用校验该配置项**存在**且**不是 `archived`**
- **适用场景**: 定义、修改
- **计算方式**: 跨应用只读校验（`configuration_item.list` → 建索引）
- **依赖输入**: `[ci_no(服务实参), configuration_item(跨应用)]`
- **输出**: `interface.ci_no`（弱引用，可空）
- **生效点**: `interface.create` / `update → _check_ci`
- **示例**: `create(..., ci_no="CI-999")` → 拒绝「关联的配置项 CI-999 不存在…」；
  `create(..., ci_no="CI-003")`（已归档）→ 拒绝「已归档（终态），不能作为新的关联」
- **依据**: 聚合根卡 9 的"引用的聚合：`configuration_item`（弱引用，接口文档本身是配置项）"；
  材料 §6.3.1.3 —— 接口文档 "maintained and approved using the Configuration Management Process
  and become a part of the overall technical data package"，即它**必须是**一个受控配置项。
  ⚠ 跨应用调用**只读、非同一事务**（CONVENTION §8）：台账不可用时按业务失败报错，不静默放行

#### 3.2.9 `BR-09` 只有已发布的接口才能冻结

- **规则描述**: `freeze` 要求状态为 `released`
- **适用场景**: 冻结
- **计算方式**: 校验型（按状态拦截）
- **依赖输入**: `[status(实体字段)]`
- **输出**: `interface.status`（`frozen`）
- **生效点**: `interface.freeze → 校验`
- **示例**: 对「定义中」的 `IF-003` 调 `freeze` → 拒绝「当前为「定义中」，只有已发布的接口才能冻结」；
  对「变更中」的 `IF-004` 同样拒绝
- **依据**: 冻结是对**已定版接口**的收口（§6.3.1.3 的接口文档是"已被批准的那一版"）——
  定义中的接口还没有版本可冻，变更中的接口应先 `release` 落实变更再冻结，
  否则历史里会出现"版本刚改、变更未落实就已冻结"的空洞（与 `configuration_item`
  的「只有已发布才能归档」同源思路、但约束对象不同）

### 3.3 业务数据

> 主档 12 项（`interface` 表）+ 子表 8 项。列名见 `schema.sql`，此处给业务口径。

#### 3.3.1 数据1: 接口编号（if_no）

- **数据描述**: 接口的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`IF-` + 三位序号）
- **示例值**: "IF-001"

#### 3.3.2 数据2: 接口名称（if_name）

- **数据描述**: 这条接口叫什么（一般写成"提供方—使用方 接口名"）
- **数据类型**: 文本
- **数据来源**: 人工录入
- **示例值**: "飞控计算机—舵机控制器 总线接口"

#### 3.3.3 数据3: 接口类型（if_type）

- **数据描述**: 这条接口以哪一类接口文档受控（材料 §6.3.1.3 的四类）
- **数据类型**: 字典：icd / ird / idd / icp
- **数据来源**: 人工选择
- **字典对应业务名**: 接口控制文档（ICD）/ 接口需求文档（IRD）/ 接口定义文档（IDD）/ 接口控制计划（ICP）
- **示例值**: "icd"

#### 3.3.4 数据4: 提供方（provider）

- **数据描述**: 接口的一端 —— 提供数据/服务/机械/电气连接的那一侧（材料 §6.3.1.2.2 的 origin）
- **数据类型**: 文本（**必填**，BR-01）
- **数据来源**: 人工录入（弱引用组织/分系统主数据，本版按文本）
- **示例值**: "飞控计算机（FCC）"

#### 3.3.5 数据5: 使用方（consumer）

- **数据描述**: 接口的另一端 —— 使用上述提供的那一侧（§6.3.1.2.2 的 destination）
- **数据类型**: 文本（**必填**，且与提供方相异）
- **数据来源**: 人工录入
- **示例值**: "舵机控制器（SACU）"

#### 3.3.6 数据6: 约定内容（icd_content）

- **数据描述**: 接口约定的正文摘要 / 关键条款（总线类型、周期、消息格式、连接器、
  供电与接地等 —— 材料附录 L §3.2 列举的各类接口要求的技术口径）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（`create` / 定义中的 `update` / `revise` 随版本一起更新）
- **示例值**: "1553B 总线，周期 20ms，消息格式见 ICD-001 §3.2"

#### 3.3.7 数据7: 版本（version）

- **数据描述**: 当前有效版本（字母修订版）；**定义中为空**（未定版）
- **数据类型**: 字典 / 格式：单个大写字母 `A`..`Z`
- **数据来源**: 系统（`release` 首次定版 `A`；`revise` 递增）
- **示例值**: "B"

#### 3.3.8 数据8: 状态（status）

- **数据描述**: 接口在生命周期中的位置
- **数据类型**: 字典：defined / released / changing / frozen
- **数据来源**: 系统按流转规则变更
- **示例值**: "changing"

#### 3.3.9 数据9: 关联配置项（ci_no）

- **数据描述**: 本接口文档对应的配置项编号（卡片 9：接口文档本身是配置项）
- **数据类型**: 文本（可空，**弱引用** `configuration_item`，BR-08 校验存在且未归档）
- **数据来源**: 人工选择 / 录入
- **示例值**: "CI-001"

#### 3.3.10 数据10: 冻结说明（freeze_note）

- **数据描述**: 冻结时的收尾说明（谁因何冻结/纳入哪次基线）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（随 `freeze` 一起写入）
- **示例值**: "接口随 CDR 定稿，纳入配置管理"

#### 3.3.11 数据11: 接口责任人（owner）

- **数据描述**: 对这条接口负责的人（接口管理职责的承担者）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "张三"

#### 3.3.12 数据12: 所属项目（project_no）

- **数据描述**: 该接口隶属的项目
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "P-2026-01"

#### 3.3.13 数据13: 版本变更通知记录（interface_change，聚合内子表）

- **数据描述**: 卡片 I-2 的落点 —— 每次**版本号发生变化**产生**两条**（提供方 / 使用方各一条）
- **字段**:
  - `seq`（本接口内序号，聚合内自增）
  - `action`（起因：`release` 首次发布 / `revise` 版本变更）
  - `old_version`（变更前版本，首次发布时为空）
  - `new_version`（变更后版本，必填）
  - `party`（通知到的哪一端：`provider` / `consumer`）
  - `party_name`（该端名称**快照** —— 两端日后不可改，快照保证台账永远能回答"当时通知的是谁"）
  - `reason`（变更原因；`revise` 必填，`release` 为空）
  - `created_at`（通知落库时间，平台审计列）
- **数据来源**: 随 `release` / `revise` **同事务**产生（`_notify` 一次写两条）
- **示例值**: `seq=3, action=revise, old=A, new=B, party=provider, party_name=飞控计算机（FCC）`

### 3.4 状态机

```
defined（定义中：尚未定版）
   │ release（首次发布：定版 A + 通知两端）
   ▼
released（已发布）─── revise（版本变更：A→B + 通知两端）───► changing（变更中）
   ▲                                                            │
   └──────── release（变更落实完成，回到已发布，不再重复通知）────┘
released ──┐
            ├── freeze（冻结，须处于已发布）──► frozen（已冻结，终态：
changing ──┘                                     不可再修改 / 发布 / 变更版本）
```

**每个状态的到达服务**（详设 §4.1 的 FUNC 与服务一一对应）：

| 状态 | 到达服务 |
|---|---|
| `defined` | `create` |
| `released` | `release`（从「定义中」首次发布定版 A；从「变更中」完成变更） |
| `changing` | `revise`（版本变更：改版本号 + 通知两端） |
| `frozen` | `freeze`（仅「已发布」可冻结，BR-09） |

> **合法迁移**：`defined→released`、`released→changing`、`changing→released`、`released→frozen`。
> **拦截迁移**：`defined→changing`（尚未定版，BR-03）、`changing→changing`（已在变更中）、
> `defined|changing→frozen`（BR-09）、`released→released`（重复发布）、`frozen→*`（终态，全部拒绝）。
> **没有"有状态无服务"的空洞** —— 四个状态各自都有能到达它的服务。

### 4.3 功能详细说明

#### 4.3.1 定义接口（FUNC-01）

- **输入**: 接口名称、接口类型、提供方、使用方、约定内容（选填）、关联配置项（选填）、
  责任人（选填）、所属项目（选填）
- **校验**: 名称非空 → `BR-02` 类型字典 → `BR-01` 两端非空且相异 → `BR-08` 配置项存在且未归档
- **处理**: 生成 `if_no`（`IF-<序号>`）→ 落库 → 状态置 `defined`，**`version` 为空**
- **输出**: 新接口记录（含空 `changes` 与 `change_total=0`）

#### 4.3.2 修改接口（FUNC-02）

- **输入**: `if_no` + 任一描述性字段
- **校验**: `BR-07`（终态拒绝）→ `BR-05`（非「定义中」时拒改两端 / ICD 内容）→
  `BR-01`（**改后整体**两端非空且相异）→ `BR-02` / `BR-08`
- **处理**: 按字段白名单拼 `UPDATE`（编号与版本不在白名单）
- **输出**: 更新后的接口
- **说明**: 只改一端也可能把两端撞成同一个 —— 校验必须在**合并入参之后**做（同组
  `change_request` 的"改后整体校验"同法）

#### 4.3.3 发布接口（FUNC-03）

- **输入**: `if_no`（无其他参数 —— 首次发布的版本是**定死的 `A`**，不给"发布成第几版"的缝）
- **校验**: 状态守卫（终态 → 已发布 → 定义中 / 变更中二选一）
- **处理**:
  - 从「定义中」：`_notify(..., release, "", "A")`（两条）→ 版本置 `A`、状态 `released`
  - 从「变更中」：状态置 `released`（**不通知** —— 版本没变，变更通知已在 `revise` 发出）
- **输出**: 更新后的接口

#### 4.3.4 版本变更（FUNC-04）

- **输入**: `if_no` + 新版本号 + 变更原因 + 约定内容（选填）
- **校验**: 状态守卫（终态 → 变更中 → 定义中）→ 新版本号非空且 `^[A-Z]$` →
  **严格大于当前版本** → 变更原因非空
- **处理**: `_notify(..., revise, old, new, reason)`（两条）→ 版本置新值、状态置 `changing`
  （若给了 ICD 内容则一并更新）
- **输出**: 更新后的接口
- **说明**: 通知与版本**同事务**（同一应用的同一连接，平台保证一次服务调用一个事务）

#### 4.3.5 冻结接口（FUNC-05）

- **输入**: `if_no` + 冻结说明（选填）
- **校验**: `BR-07` 终态拒绝 → `BR-09` 非「已发布」拒绝
- **处理**: 状态置 `frozen`、写 `freeze_note`
- **输出**: 更新后的接口（记录保留）

#### 4.3.6 变更通知台账（FUNC-08）

- **输入**: 接口编号 / 端（provider|consumer）/ 起因（release|revise）（皆可选）+ 分页
- **处理**: `interface_change JOIN interface` 取出行项与所属接口的名称 / 类型 / 当前状态
- **输出**: `{items, total}`
- **说明**: 这是**查询视图**，不是聚合 —— 它不拥有任何状态（§1.3.2）

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 两端必填且相异

**Given** 定义接口的表单
**When** 提供方留空 / 使用方留空 / 两端填成同一个系统
**Then** 全部拒绝，提示「接口的提供方不能为空」/「接口的使用方不能为空」/「接口的两端不能是同一个系统」（`BR-01`）

#### 6.1.2 标准2: 版本只能递增

**Given** `IF-005` 当前版本 `A`
**When** 以 `A` / `b` / `AB` / 空发起版本变更
**Then** 全部拒绝（`BR-03`）

#### 6.1.3 标准3: 版本变更通知两端（同事务）

**Given** `IF-001` 已发布（版本 `A`，已有 2 条通知）
**When** `revise(IF-001, "B", "舵机控制器换代")`
**Then** 状态 `changing`、版本 `B`、通知记录变 **4** 条，新增两条分别是
`(revise, provider, A→B)` 与 `(revise, consumer, A→B)`，且 `reason` 原样落库
**And given** 随后 `release(IF-001)` **when** 完成变更 **then** 回到 `released` 且通知**仍为 4 条**

#### 6.1.4 标准4: 已定版后两端与 ICD 内容锁

**Given** `IF-005` 已发布
**When** `update` 改使用方 / 改约定内容
**Then** 拒绝（`BR-05`）
**And given** 同时改责任人与所属项目 **when** `update` **then** 成功（描述性字段不锁）

#### 6.1.5 标准5: 冻结是终态且只对已发布开放

**Given** `IF-003` 定义中 / `IF-004` 变更中
**When** `freeze`
**Then** 均拒绝（`BR-09`）
**And given** `IF-002` 已发布 **when** `freeze` **then** 成功；
**and** 对已冻结的 `IF-002` 再 `update` / `release` / `revise` / `freeze` **then** 全部拒绝（`BR-07`）

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms；`list_changes` 同
- 接口编号生成在并发登记下不重复（`BR-06`）
- `get` 未命中**不抛异常**，返回 `None`（供跨应用探测式调用）
- 版本变更与通知记录**同事务**：`revise` 任一校验不通过则整次调用不落库（链测试 TC-27 验证）
- 跨应用校验（`BR-08`）失败时按**业务失败**报错（不静默放行、不静默拒绝）

### 6.3 已知问题或限制

- **两端是文本字段，不接组织/分系统主数据** —— `provider` / `consumer` 当前按文本录入，
  既不校验"这个分系统是否存在"、也不对接人员主数据（`stakeholder`）。卡片上的
  `interface → configuration_item.list` 是本应用**唯一的跨应用调用**（BR-08），
  `stakeholder.list`（选责任人）**本版未接**（与同组 `review` 的处置一致）。
- **不做接口要求的逐条参数** —— 附录 L §3.2 的 mass/structural/fluid/electrical/EMI/…
  只作为 `icd_content` 的正文内容，不建字段树（§1.3.2 的取舍）。若将来要按参数出矩阵，
  应在本聚合内加一张子表（`(if_no, seq)` + 参数名/值/单位），**不影响对外服务签名**。
- **通知只落"已通知"，不落"已确认"** —— 材料 §6.3.1.3 要求跨方变更"unanimous approval"，
  本版把**通知**做成不变量（BR-04），把**回执/批准**留给下一步：若要两端签收，
  可在 `interface_change` 加 `acked_at` / `acked_by` 两列与一个 `ack_change` 服务，
  并加一条"未全部签收不得 release"的规则（属聚合内部结构变更，不影响现有服务签名）。
- **没有跨接口的批量变更** —— 见 §1.3.2 的取舍说明。前端用逐条「版本变更」替代。
- **版本字典止于单个大写字母** —— `A`..`Z`；到 `Z` 之后没有 XX 之类的两位版本
  （正则 `^[A-Z]$` 会拒）。要用时放宽正则并回填一条术语即可。
- **`list` 与 `get` 的字段口径**：主档 12 字段 + `change_total` 一计数**两边一致**；
  变更通知记录**明细只在 `get`**（列表不做 N+1 取子表）。这不是"口径差"，是刻意的分层。
- **组级 `_contracts.md` 尚未收录本应用** —— 本文件的服务名/入参逐字取自
  `interface.py` 的公共方法签名；契约冻结应由第⑤步出口的统一 dump 完成
  （本任务范围不含改 `_contracts.md`）。
