> 产出技能：第⑥步 前端设计（规格 `design-plus/前端设计.md`，规范正本 `VIEW_CONVENTION.md`）
> 输入：`应用详设.md`（US/FUNC/PERM/状态机/§6.3）+ `architecture.md`（聚合根卡 8）
> 后端契约**以 `decision.py` 源码为准**（组级 `_contracts.md` 尚未收录本应用 —— 见 §9 限制）

## 1. 页面定位

| 项 | 内容 |
|---|---|
| key / name | `decision` / 决策 |
| 一句话 | 决策台账：登记议题、定义评价准则、登记备选方案、权衡打分、作出决策（选方案 + 依据）、实施，按评价方法/状态/责任人筛选 |
| 数据来源类型 | **独立创建** —— 因此**保留「新建议题」入口**（与服务契约 `create` 对应） |
| `PAGE_META.order` | `680` —— **组内序不在此复抄**：真值 = 各页 `PAGE_META.order`，组级 view 测试的「菜单序」断言从 `PAGE_META` + `shell.js` 的 `PLATFORM_PAGES` **现算**。本行此前逐页复抄了一遍 —— 复抄必漂：2026-09-25 因 `order` 并列、平台按 key 字母序兜底，「配置项」被渲染到「风险」之前，而复抄的清单还把旧值当成了正确值（见 pitfalls #43）。 |
| 页面构成 | 主列表卡片 + 四个模态（详情/编辑、权衡打分、决策、新建议题） |

## 4. 交互规则（逐条对应后端约束）

| # | 规则 | 依据 |
|---|---|---|
| F-1 | 新建表单里**议题必填**且**评价方法有默认值**（加权决策矩阵），未齐时提交按钮禁用；评价方法用**静态 `<option>`** | `create` 的两个校验 + `BR-07` |
| F-2 | 状态为「提出」但**准则清单为空**时，「启动权衡」**可见但禁用**，并在详情给出原因「还没有评价准则 —— 准则先于备选方案的评估（BR-01）」 | `BR-01`（前端镜像，后端仍是权威） |
| F-3 | 加准则 / 加方案入口**只在编辑态且未冻结**时出现（两张子表都是聚合内结构，与 `review` 的评审项同口径）；只读视图不给写入口 | 两张子表 + `BR-06` |
| F-4 | 「权衡打分」是**独立模态**：先显示**评价准则（含权重）当作打分依据**，再逐行给方案填得分；得分空则该行「保存」禁用；得分框接受 `0`（0 分是有效的分） | `score_option` + `BR-08` |
| F-5 | 「决策」模态的方案清单来自 `get`（列表行没有方案明细）；**未打分的方案 radio 禁用**并标注「未打分（不可选）」 | **卡片 I-1**（前端镜像） |
| F-6 | 选中的方案**不是最高分**时提交禁用，提示「选中的不是最高分方案 —— 必须给出依据（BR-04）」；补齐依据后可提交；选最高分时依据选填 | `BR-04`（材料 §6.8.1.2.5）+ 后端 `_top` 口径 |
| F-7 | 状态为「已决策」「已实施」时**行内「编辑」入口消失**；详情无「保存」、无「加准则」「加方案」 | `BR-06` |
| F-8 | 状态为「已实施」时上述入口同样消失，且**无「实施」按钮**；详情提示「已实施（终态）」 | `BR-06` 后半 |
| F-9 | 「决策」按钮在**方案少于两个**或**一个都没打分**时禁用，并在详情给出原因（两条不同文案） | **卡片 I-2 / I-1** 前端镜像 |
| F-10 | 状态机动作按钮**按当前状态显隐**：提出→[启动权衡]；权衡中→[权衡打分][决策]；已决策→[实施]；已实施→无 | 状态机（§3.4 到达服务表） |
| F-11 | 三个筛选（评价方法 / 状态 / 责任人）变化即刷新（重置到第 1 页）；责任人输入框回车即搜；列表默认按编号升序 | `US-08` |
| F-12 | 模态里所有读 `modal.d` 的绑定都走空安全 helper（`isStatus / inStatus / stName / stCls / frozen / frozenText / chosenText / topText / scoredText / canStart / canDecide / …`），模板里不写裸 `modal.d.status` | 同组 `review` 页实测踩过的 `Cannot read properties of null` |
| F-13 | 「实施」二次确认（`confirm`）—— 终态不可逆 | `BR-06` 后半 |

## 9. 已知限制

- **`modal.d` 的空安全 helper 层**：模态里所有条件绑定都走 `isStatus / inStatus / frozen /
  frozenText / canStart / canDecide / showStartBlock / showDecideBlock / …` 这层 helper，
  模板里**不写裸 `modal.d.<字段>` 做判断**。原因见 `前端测试用例.md` §9 的坑 1
  （`x-if="modal.d"` 的子绑定可能在 `openDetail` 把 `modal.d` 置 null 的那一拍被再求值一次）。
- **枚举下拉全用静态 `<option>`** —— 评价方法在筛选、新建、编辑三处都是**写死的 option 列表**
  （字典只有 11 项且稳定）。刻意**不用** `x-model` + `x-for` 渲染：那样**回填会静默停在第一项**
  （同组实测踩过），而编辑模态必须能正确回填已有的 `eval_method`。
- **「决策」模态的方案选项用 radio，不用 `<select>`** —— 选项来自 `get` 的方案清单（动态），
  radio + `:value="o.seq"` + `x-model.number` 既不受"回填停第一项"的影响，也天然表达"未打分不可选"。
- **打分行逐行保存** —— 「权衡打分」模态每行一个「保存」按钮（一行一次服务调用），
  不做"一次存全部"：多行批量会跨多次事务（打分本身是迭代的，材料 §6.8.1.2.4），
  半途失败时"存了一半"的语义更差。得分相同的方案要改分，直接改数字再点该行「保存」即可。
- **组级 `_contracts.md` 尚未冻结本应用** —— 本页的服务名/入参**逐字取自 `decision.py` 的公共方法签名**
  （`create` / `add_criterion` / `add_option` / `start` / `score_option` / `conclude` / `implement` /
  `update` / `get` / `list`）；契约冻结应由第⑤步出口的统一 dump 完成（本任务范围不含改 `_contracts.md`）。
- **准则不可改 / 不可删** —— `add_criterion` 没有对应的 `update_criterion` / `remove_criterion`
  （准则清单是权衡过程的留痕）。登记错了在结论前补一条正确的即可；结论后一律冻结。
- **方案不可删** —— 同理（`add_option` 无 `remove_option`）：权衡过的方案要留痕，
  这也是 I-2「决策必须有权衡」能站在证据上的原因。
- **没有跨决策的方案汇总页** —— 理由见 `应用详设.md` §1.3.2（卡片 8 无「并入说明」类要求）。
