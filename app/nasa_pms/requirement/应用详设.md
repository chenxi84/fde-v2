## 1. 需求概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `requirement` |
| 类名 | `Requirement` |
| 聚合根 | 需求 |
| 标识 | `req_no` |
| 数据来源类型 | **独立创建**（需求由项目内人员录入，无上游自动生成） |

### 1.2 需求背景

#### 1.2.1 为什么需要这个需求？

系统工程的第一份产出就是需求。材料（NASA SE Handbook Rev 2 §4.2）指出：需求是"把利益相关者期望
翻译成可验证的技术陈述"的产物，且**每条需求都必须有验证方法**——否则它无法在验证矩阵中被检验。
现状是需求散落在文档里，无法追踪"这条需求从哪来、谁来验证、变更后影响了什么"。

#### 1.2.2 期望达到什么目标？

- 每条需求**可编号、可追溯**（来源 → 需求 → 派生 → 验证）
- 每条需求**必须绑定验证方法**，进基线前校验
- 需求变更**经由变更请求**，基线版本可回溯

### 1.3 需求范围

#### 1.3.1 包含哪些功能？

- 需求的创建、修改、查询、列表
- **派生**：从上游需求派生下游需求，保留派生链
- **纳入基线**：把需求集合冻结为一个基线版本
- 需求与本应用之外的**验证项**（`verification`）通过弱引用关联

#### 1.3.2 不包含哪些功能？

- **不做验证执行** —— 验证项与结果属 `verification` 聚合（材料 §5.3 Product Verification）
- **不做需求变更审批** —— 变更流程属 `change_request` 聚合
- **不维护利益相关者** —— 属 `stakeholder`（主数据），本应用只读引用

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 系统工程师 | 录入与维护需求、派生需求 | 材料 §1.3 职责定义 |
| 需求责任人 | 对单条需求的内容负责（`owner` 字段） | 材料 §4.2 需求元数据 |
| 验证负责人 | 只读消费需求（在 `verification` 里） | 材料 §5.3 |

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 录入一条技术需求（优先级：P1）

**作为**一名系统工程师
**我希望**录入一条技术需求（含标题、正文、类型、来源、验证方法）
**以便**后续能对它做验证与追溯

**验收条件**：
- 给定必填项齐备且**已指定验证方法**，当提交时，则新需求以「草稿」状态落库，编号自动生成
- 给定未指定验证方法，当提交时，则**拒绝**并提示「需求必须有验证方法」（`BR-01`）
- 给定类型选了「派生」但未选上游需求，当提交时，则**拒绝**（`BR-05`）

#### 2.1.2 `US-02` 用户故事 — 从上游需求派生（优先级：P1）

**作为**一名系统工程师
**我希望**从一条系统需求派生出技术需求
**以便**保留完整的派生链

**验收条件**：
- 给定已存在需求 `REQ-001`，当以它为上游派生新需求时，则新需求的 `source_req_no` = `REQ-001`
- 给定`REQ-001` 后续被作废，当查看派生需求时，则**仍能看到上游编号与作废状态**（不许悬空）

#### 2.1.3 `US-03` 用户故事 — 纳入基线（优先级：P1）

**作为**一名系统工程师
**我希望**把当前一批需求冻结为一个基线
**以便**后续变更有对照基准

**验收条件**：
- 给定所选需求**全部**已指定验证方法，当执行纳入基线时，则这些需求状态变为「已基线」并记录基线版本
- 给定其中有**任何一条**缺验证方法，当执行时，则**整批拒绝**（不允许部分成功）

#### 2.1.4 `US-04` 用户故事 — 查询需求列表（优先级：P2）

**作为**一名系统工程师
**我希望**按类型 / 状态 / 来源筛选需求
**以便**定位待补验证方法或某来源下的全部需求

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序）

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 需求从期望中产生

1. 系统工程师读取 `stakeholder` 里记录的相关方期望
2. 据此录入**系统需求**（`req_type = system`）
3. 系统需求经评审后，派生出**技术需求**（`req_type = technical`）
4. 技术需求再派生出**接口需求**（`req_type = interface`）
5. 全部需求经「纳入基线」冻结为基线版本

#### 3.1.2 场景2: 需求被验证（跨应用）

1. `verification` 应用读取本应用的需求（`requirement.list`）
2. 为每条需求建立验证项，记录验证方法与结果
3. 若某需求**无对应验证项**，材料要求该缺口必须暴露（见 `BR-01` 的跨应用呼应）

### 3.2 业务规则

#### 3.2.1 `BR-01` 每条需求必须有验证方法

- **规则描述**: `verify_method` 为空的需求不允许保存为「待评审」及之后的状态
- **适用场景**: 创建、修改、纳入基线
- **计算方式**: 校验型（非计算）
- **依赖输入**: `[verify_method(实体字段), 状态(实体字段)]`
- **输出**: 状态字段 `requirement.status`（不满足则拒绝流转）
- **生效点**: `requirement.create → 校验` / `requirement.baseline → 校验`
- **示例**: 录入「系统应支持 1000 并发用户」但未填验证方法 → 拒绝
- **依据**: 材料 §4.2「Requirements Metadata」与附录 D「需求验证矩阵」——矩阵按需求逐行验证，
  无验证方法的需求在矩阵里无行可落

#### 3.2.2 `BR-02` 派生需求必须保留上游来源

- **规则描述**: `req_type = derived` 时，`source_req_no` 必填，且该上游需求必须存在（弱引用可悬空但**不许为空**）
- **适用场景**: 创建、修改
- **计算方式**: 校验型
- **依赖输入**: `[req_type(实体字段), source_req_no(实体字段)]`
- **输出**: `requirement.source_req_no`
- **生效点**: `requirement.create → 校验` / `requirement.update → 校验`
- **示例**: `REQ-002`（派生）的上游填写 `REQ-001`；若 `REQ-001` 被作废，`REQ-002` 仍显示其编号与状态

#### 3.2.3 `BR-03` 需求编号唯一且不可变

- **规则描述**: `req_no` 落库后不得修改；**全局唯一**（`REQ-` + 三位序号，取当前最大值递增）
- **适用场景**: 创建、修改
- **计算方式**: 唯一性校验（生成时取全局最大号 +1）
- **依赖输入**: `[req_no(实体字段)]`
  —— ⚠ **不含 `project_no`**（2026-09-25 口径确认）：材料没有要求"编号在项目内唯一"，
  实现取的是**全局递增**（比"项目内唯一"**更强**：跨项目也不会撞号）。原先写"同一项目内不得重复"
  而实现并不看 `project_no` —— 属**文档与实现不一致**，现按"有意收紧"口径统一为**全局唯一**。
  若将来确实要按项目分段编号（如 `EO3-REQ-001`），那是**改编号形如**的独立需求，
  会波及全部用例、演示数据与前端展示，别顺手做。
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `requirement.create` / `requirement.update`（update 时拒绝编号变更）
- **示例**: 试图把 `REQ-001` 改为 `REQ-100` → 拒绝

#### 3.2.4 `BR-04` 已基线需求不得直接改写

- **规则描述**: 状态为「已基线」的需求，其正文 / 验证方法不得直接修改，须经 `change_request`
- **适用场景**: 修改
- **计算方式**: 校验型（按状态拦截）
- **依赖输入**: `[status(实体字段), change_no(入参 —— 已批准的变更号)]`
- **输出**: `requirement.change_no`（记下本次改写所依据的变更号）、`requirement.title` / `requirement.statement` /
  `requirement.verify_method`（改写后的内容）
- **生效点**: `requirement.update → 校验 → 须携带变更号（BR-04）`
- **示例**: 直接改已基线需求正文 → 拒绝，提示「请先提交变更请求」；带上变更号 → 放行并记下该号
- **⚠ 口径（2026-09-25）**：本应用只校验「**带没带**变更号」，「变更**批准没批准**」由 `change_request` 保证
  （跨应用校验属可补项，见 §6.3）；且**不改状态** —— 此前写的「改为变更中」随 `in_change` 一并收敛。

#### 3.2.5 `BR-05` 类型必填且受字典约束

- **规则描述**: `req_type` 取值限 `system / technical / interface / derived` 四类
- **适用场景**: 创建、修改
- **计算方式**: 字典校验
- **依赖输入**: `[req_type(实体字段)]`
- **输出**: `requirement.req_type`
- **生效点**: `requirement.create` / `requirement.update`
- **示例**: 类型填「其它」→ 拒绝
- **依据**: 材料 §4.2 与术语表——`技术需求`/`系统需求`/`接口需求`/`派生需求` 是材料里的四类

### 3.3 业务数据

#### 3.3.1 数据1: 需求编号（req_no）

- **数据描述**: 需求的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`REQ-` + 序号）
- **示例值**: "REQ-001"

#### 3.3.2 数据2: 需求标题（title）

- **数据描述**: 一句话概括，用于列表展示
- **数据类型**: 文本（≤120 字）
- **数据来源**: 人工录入
- **示例值**: "系统应支持 1000 并发用户"

#### 3.3.3 数据3: 需求正文（statement）

- **数据描述**: 需求的完整陈述，应可验证（材料附录 C「如何写好一条需求」）
- **数据类型**: 长文本
- **数据来源**: 人工录入
- **示例值**: "在 8 vCPU / 32 GB 环境下，系统应支持 1000 并发用户，响应时间 P95 ≤ 2s"

#### 3.3.4 数据4: 需求类型（req_type）

- **数据描述**: 需求所属类别
- **数据类型**: 字典：system / technical / interface / derived
- **数据来源**: 人工选择
- **字典对应业务名**: 系统需求 / 技术需求 / 接口需求 / 派生需求（术语表）
- **示例值**: "technical"

#### 3.3.5 数据5: 验证方法（verify_method）

- **数据描述**: 该需求将如何被验证（材料附录 D 的验证矩阵按此列展开）
- **数据类型**: 字典：inspection / analysis / demonstration / test
- **数据来源**: 人工选择
- **示例值**: "test"

#### 3.3.6 数据6: 上游需求编号（source_req_no）

- **数据描述**: 派生需求的上游需求（弱引用，允许悬空但派生类型时必填）
- **数据类型**: 文本
- **数据来源**: 人工选择（本应用内已存在的 `req_no`）
- **示例值**: "REQ-001"

#### 3.3.7 数据7: 状态（status）

- **数据描述**: 需求在生命周期中的位置
- **数据类型**: 字典：draft / pending_review / baselined / obsolete
  （⚠ `in_change`（变更中）**已收敛**：2026-09-25 —— 需求侧「变更中」的语义由 `change_request` 应用承载，需求侧只保留 BR-04 的轻量口径「已基线须带变更号才可改写」）
- **数据来源**: 系统按流转规则变更
- **示例值**: "baselined"

#### 3.3.8 数据8: 责任人（owner）

- **数据描述**: 对这条需求内容负责的人
- **数据类型**: 文本
- **数据来源**: 人工选择（材料 §4.2 需求元数据要求有 owner）——**视图层**提供候选：
  「责任人」输入框挂 `datalist`，候选来自页面字面量 `svc("stakeholder", "list")`；
  值仍是**文本姓名**，后端**不调** `stakeholder`（不做存在性校验，2026-09-25 口径）
- **示例值**: "张三"

### 3.4 状态机

```
draft（草稿）
   │ create 完成（已填验证方法）
   │
   │ submit_review（提交评审）—— 2026-09-25 补：此前**没有服务能进入 pending_review**
   ▼
pending_review（待评审）
   │ baseline（整批纳入基线；**评审门**：草稿不能直接进基线）
   ▼
baselined（已基线）
   │  **不是终态**：携带变更号即可改写正文/验证方法（BR-04，记下 `change_no`）
   │  （需求侧的「变更中」**不设独立状态** —— 变更全流程在 `change_request` 应用里，2026-09-25 收敛）
   │
   └──► obsolete（已废弃）  ← 任意状态可作废（作废后派生需求仍可见其编号，BR-02）
```

## 4. 功能描述

### 4.1 功能清单

| 编号 | 功能 | 对应 US | 说明 |
|---|---|---|---|
| `FUNC-01` | 录入需求 | US-01 | create |
| `FUNC-02` | 派生需求 | US-02 | derive |
| `FUNC-03` | 纳入基线 | US-03 | baseline（整批，全或无） |
| `FUNC-04` | 修改需求 | US-01 | update（受 BR-04 拦截） |
| `FUNC-05` | 需求列表 | US-04 | list |
| `FUNC-06` | 需求详情 | US-04 | get |
| `FUNC-07` | 作废需求 | US-02 | obsolete（**不删除**：下游派生需求仍须可见其编号与状态，BR-02） |

### 4.2 功能模块结构图

```
需求 requirement
├── 录入与维护
│   ├── FUNC-01 录入需求
│   ├── FUNC-04 修改需求
│   └── FUNC-02 派生需求
├── 基线管理
│   └── FUNC-03 纳入基线
└── 查询
    ├── FUNC-05 需求列表
    └── FUNC-06 需求详情
```

### 4.3 功能详细说明

#### 4.3.1 录入需求（FUNC-01）

- **输入**: 标题、正文、类型、验证方法、上游需求（派生时）、责任人
- **校验**: `BR-01`（必须有验证方法）、`BR-02`（派生必须有上游）、`BR-05`（类型字典）
- **处理**: 生成 `req_no` → 落库 → 状态置 `draft`
- **输出**: 新需求记录

#### 4.3.2 纳入基线（FUNC-03）

- **输入**: 需求编号列表 + 基线版本号
- **校验**: 所选需求**逐条**满足 `BR-01`；**全或无**（任一条不合格则整批拒绝）
- **处理**: 批量置状态 `baselined`，记录基线版本
- **输出**: 基线记录

#### 4.3.3 修改需求（FUNC-04）

- **输入**: `req_no` + 待改字段
- **校验**: `BR-03`（编号不可改）、`BR-04`（已基线须带已批准变更号）
- **输出**: 更新后的需求

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 无验证方法的需求进不了基线

**Given** 存在一条 `verify_method` 为空的需求
**When** 把它与其它需求一并纳入基线
**Then** **整批拒绝**，并指出是哪一条不满足（`BR-01`）

#### 6.1.2 标准2: 派生链不悬空

**Given** `REQ-002`（派生）的上游是 `REQ-001`
**When** `REQ-001` 被作废后查看 `REQ-002`
**Then** 仍显示 `REQ-001` 的编号与「已废弃」状态（`BR-02`）

#### 6.1.3 标准3: 已基线需求不可直接改写

**Given** 一条状态为 `baselined` 的需求
**When** 不带变更号直接修改正文
**Then** 拒绝，提示需先提交变更请求（`BR-04`）

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms
- 需求编号生成在并发录入下不重复（`BR-03`）

### 6.3 已知问题或限制

- **本项目尚未接入 `change_request`** —— `BR-04` 的"携带已批准变更号"在 `change_request` 应用建成后才能真正闭环
  （当前只能校验"是否带了变更号"，不能校验"变更是否已批准"）
- 需求与 `verification` 的**双向完整性**（每条基线需求都有验证项）依赖跨应用检查，本应用侧不做强校验
