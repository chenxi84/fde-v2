# 应用详设：工作分解结构元素（wbs）

> 产出技能：第②步 应用设计（规格 `design-plus/应用设计.md`）
> 输入：`architecture.md` 聚合根卡 12 + 材料 `brd/WBS-第NN章-*.md`（NASA/SP-20250006071，2025-06）
> 依据说明：本应用是 SE 手册 6.1 把细则**外链**出去的那本《NASA WBS Handbook》的落地 ——
> 编号体系、字典字段、全包含性、元素级变更控制，逐条都能回指到原文小节。

## 1. 应用概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `wbs` |
| 类名 | `Wbs` |
| 聚合根 | 工作分解结构元素 |
| 标识 | `wbs_no`（点分**十进制层级码**，如 `123456.02.07`） |
| 数据来源类型 | **独立创建**（由项目团队按产品结构分解而来，无上游自动生成） |

### 1.2 应用背景

#### 1.2.1 为什么需要这个元素？

WBS 是"把项目工作**按产品**切成一块块可计划、可归集、可跟踪的工作"的那张表。SE 手册 6.1 把它与
SEMP、进度表**并列**，都置于配置控制之下 —— 但它自己的规则（怎么编号、字典写什么、什么时候能改）
不在这本书里，而是外链给《NASA WBS Handbook》。

#### 1.2.2 期望达到什么目标？

- 一棵**编号自洽**的元素树：分层十进制码、父号 = 子号去掉最后一段、最多 7 层
- 一份**可交付的字典**：每个元素有名称、编号、内容描述、范围出处、关联规范、预算与报告号
- 基线之后**改动留痕**：任何修订都要带已批准的变更号，并与配置管理过程一致

### 1.3 应用范围

#### 1.3.1 包含哪些功能？

- 建立与分解元素树（`create` / `add_child` / `update`）
- 元素级基线（`baseline`）与变更（`change`，含版次递增与修订授权）
- 关闭（`close`）
- 字典读取（`get` / `list`）、树与索引（`tree`）
- 需求覆盖对账（`coverage`）

#### 1.3.2 不包含哪些功能？

- **不做 OBS（组织分解）与成本归集**：控制账户 / 工作包 / 规划包收成元素的 `kind` 属性，
  「谁负责」落在 `owner` 文本上（见 `术语表.md` 附「本版口径」#1）
- **不做挣值（EVM）计算**：本应用只保证 WBS 这一侧的数据正确，绩效测算是财务侧的事
- **不实现第 7 层以下**的财务 workaround（口径 #2）
- **不维护需求内容**：与需求的关系是**交叉引用**（`req_nos`），需求本身归 `requirement`

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 项目经理（PM） | 建立与维护 WBS 与字典；**批准基线** | 材料 §3.2 |
| 项目团队 | 共同开发：系统工程 / 项目管理 / 业务管理 / PP&C / 技术专业 / 安全与任务保证 | 材料 §3.2 的 a–f |
| 控制账户经理（CAM） | 对某个 CA 层的元素负责（`owner`） | 材料 §3.3.4 |
| 配置与变更管理员（CM） | 基线后的修订经其走变更（跨应用 `change_request`） | 材料 §3.3.6 |

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 建立 WBS 根元素（优先级：P1）

作为**项目经理**，我要为一个项目建一个顶层元素，以便开始分解工作。

- **验收**：给定编号 `123456` 与名称「遥感卫星系统」，创建后状态为 `草稿`、层级 1、无父元素
- **依据**：材料 §3.4.2「每个 NASA 项目（第 1 层）分配一个六位数字码，如 123456」

#### 2.1.2 `US-02` 逐层分解（优先级：P1）

作为**项目团队**，我要在某个元素下继续分解，以便细分到"工作被计划、成本被归集"的那一层。

- **验收**：对 `123456` 调 `add_child` 得到 `123456.01`；父元素不存在时被拒
- **依据**：材料 §3.3.4（分层到 CA 为止）、§3.5.4（错误的层级是常见错误）

#### 2.1.3 `US-03` 基线一个元素（优先级：P1）

作为**项目经理**，我要把定稿的元素纳入基线，以便它受配置控制。

- **验收**：缺范围出处的元素不能基线；父未基线时子不能基线
- **依据**：材料 §3.1（基线在 Phase B 后期）、§3.3.5（不得含未授权范围）

#### 2.1.4 `US-04` 变更已基线的元素（优先级：P1）

作为**配置与变更管理员**，我要对已基线的元素发起修订，以便范围变化有据可查。

- **验收**：`change` 必填变更号，且该变更必须**已批准**；元素进入 `变更中`
- **依据**：材料 §3.3.6「基线 WBS 的任何修订都要按配置管理过程留文档，含变更理由与 PM 批准」

#### 2.1.5 `US-05` 落实变更（优先级：P1）

作为**项目经理**，我要在修订完成后重新基线，以便版次递增、修订授权落库。

- **验收**：`变更中` 的元素再次 `baseline` → 版次 +1、`修订授权` 记为该变更号、状态回 `已基线`
- **依据**：材料 §3.4.4g「日期、版次、修订授权与已批准变更」是字典必备字段

#### 2.1.6 `US-06` 关闭元素（优先级：P2）

作为**项目经理**，我要关闭已完成的元素，以便树反映真实状态。

- **验收**：有未关闭子元素的元素不能关闭；处于 `变更中` 的元素不能直接关闭
- **依据**：材料 §3.3.6（修订须先走完流程才谈得上收口）

#### 2.1.7 `US-07` 查看树与索引（优先级：P2）

作为项目成员，我要看缩进的索引与树形图，以便理解层级关系。

- **验收**：`tree` 返回嵌套结构；`list` 支持按状态 / 类型 / 父元素筛选并分页
- **依据**：材料 §3.4.3（元素树图）、§3.4.4 图 3-12（WBS 索引：缩进列出以体现层级）

#### 2.1.8 `US-08` 需求覆盖对账（优先级：P2）

作为**系统工程**，我要核对"哪些需求还没有 WBS 元素"，以便补全范围。

- **验收**：`coverage` 返回两类清单：有需求但无元素、有元素但无需求出处
- **依据**：材料 §3.3.3 图 3-5（交叉引用矩阵：矩阵里没有 X 的位置就是缺口）

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1：一棵 WBS 的一生（对齐状态机）

`create`（草稿）→ 逐层 `add_child` → `baseline`（已基线，进配置控制）→
范围变了 → `change`（变更中）→ 落地修订 → `baseline`（已基线，版次 +1）→ 全枝完成 → `close`（已关闭）

#### 3.1.2 场景2：变更号从哪来（跨应用）

元素基线后要改，得先有**已批准**的变更：在 `change_request` 里提出 → 影响分析 → 审批通过，
拿到 `cr_no` 后回到本应用 `change(wbs_no, change_no=…)`。**两个应用、两个事务** —— 变更的审批
不需要与 WBS 的修订同事务（同 `configuration_item` 的发版口径）。

### 3.2 业务规则

#### 3.2.1 `BR-01` 编号与层级自洽

- **规则描述**: `wbs_no` 是点分十进制层级码：顶层是 6 位数字；每下一层追加 `.` + 两位数字；
  **最多 7 层**、**含句点不超过 24 字符**；非顶层元素的父号必须等于其编号**去掉最后一段**
- **适用场景**: 创建、自动分配子号
- **计算方式**: 格式校验 + 派生校验（父号由编号推出）
- **依赖输入**: `[wbs_no(服务实参), parent_no(服务实参)]`
- **输出**: `wbs.level`（由编号段数派生并落库）
- **生效点**: `wbs.create → 校验` / `wbs.add_child → 生成`
- **示例**: `create(wbs_no="123456.02.07.05.02.06.03.01")` → 拒绝「最多 7 层」；
  `create(wbs_no="123456.02.07", parent_no="123456.99")` → 拒绝「父号与编号不自洽」
- **依据**: 材料 §3.4.2「Each WBS element is assigned a unique element code … A simple decimal
  coding system that logically indicates the level … A maximum of seven levels is allowed …
  containing a maximum of 24 characters including all the periods」

#### 3.2.2 `BR-02` 父先于子

- **规则描述**: 建子元素时父元素必须已存在；**父元素未基线，子元素不得基线**（自上而下）
- **适用场景**: 创建、自动分配子号、基线
- **计算方式**: 存在性校验（本聚合内自引用）
- **依赖输入**: `[parent_no(服务实参), status(父元素字段)]`
- **输出**: 无（拒绝：父不存在或父未基线时整条基线请求被拒，不产生新字段）
- **生效点**: `wbs.create → 校验` / `add_child → 校验` / `baseline → 校验`
- **示例**: 对 `123456.01` 基线时若 `123456` 仍是草稿 → 拒绝「父元素未基线」
- **依据**: 材料 §3.1（初步 WBS 迭代、稳定后才建基线）、§3.5.4
  （Incorrect Element Hierarchy 是常见错误：层级关系错会让人读不出工作结构）

#### 3.2.3 `BR-03` 不得含未授权范围

- **规则描述**: 没有**范围定义出处**（`scope_ref`）的元素不得基线。范围出处是"SOW / 需求文档里的
  哪一段授权了这块工作"
- **适用场景**: 基线
- **计算方式**: 非空校验
- **依赖输入**: `[scope_ref(实体字段)]`
- **输出**: 无（拒绝：基线请求被拒，`status` 不变）
- **生效点**: `wbs.baseline → 校验`
- **示例**: 只填了名称、没填范围出处的元素 `baseline` → 拒绝
- **依据**: 材料 §3.3.5「A WBS should include all … work and products defined in the project
  scope of work. **The WBS should never contain unauthorized work scope.**」+ §3.4.4e
  （字典必备字段：scope definition paragraph number）

#### 3.2.4 `BR-04` 产品导向

- **规则描述**: 元素名不得是**职能 / 组织 / 阶段 / 工种**词。拦的是材料 §3.5.2 点名的那些例子
  （中英对照），**这是例子不是穷举** —— 拦不住的一律靠人
- **适用场景**: 创建、自动分配子号、修改
- **计算方式**: 关键词拦截
- **依赖输入**: `[title(服务实参)]`
- **输出**: 无（拒绝：名称命中非产品词即拒，`title` 不落库）
- **生效点**: `wbs.create → 校验` / `add_child → 校验` / `update → 校验`
- **示例**: 名称写「设计」「工程部」「A 阶段」「装配工」→ 拒绝；写「星务计算机」→ 通过
- **依据**: 材料 §3.5.2「WBS elements should be predominantly product oriented. For example,
  **Design, Engineering, Manufacturing, Phase A, Pipe Fitters, Direct Labor** are not products …
  **Rework, Retesting and Refurbishing** are additional non-product oriented terms」

#### 3.2.5 `BR-05` 基线后修订走变更流程

- **规则描述**: 元素一旦基线，**不能直接改**（`update` 只允许在 `draft` 与 `in_change` 上）；
  要改必须先 `change` 进「变更中」，而 `change` 的 `change_no` **必填**、且该变更在 `change_request`
  里必须是**已批准**状态（跨应用校验，非同一事务）
- **适用场景**: 修改、变更
- **计算方式**: 校验型（按状态拦截）+ 非空校验 + 跨应用状态校验
- **依赖输入**: `[status(实体字段), change_no(上游服务实参 —— change_request 选择已批准的变更)]`
- **输出**: `wbs.change_no`
- **生效点**: `wbs.update → 按状态拦截` / `wbs.change → 校验`
- **示例**: 对已基线元素 `update(owner=…)` → 拒绝「必须走变更流程」；
  `change("123456.01", "CR-999")`（不存在）→ 拒绝；对草稿元素 `change` → 拒绝「还是草稿」
- **依据**: 材料 §3.3.6「Whenever the baseline WBS is revised … formal documentation of the
  revision must be maintained according to the project's configuration and data management
  process to include the associated change rationale and project manager approval」

#### 3.2.6 `BR-06` 未收口的元素不得关闭

- **规则描述**: 有**未关闭子元素**的元素不得关闭；处于 `变更中` 的元素不得直接关闭
  （须先落实变更回到已基线）
- **适用场景**: 关闭
- **计算方式**: 校验型（按子元素状态 + 自身状态拦截）
- **依赖输入**: `[status(实体字段), status(子元素字段)]`
- **输出**: `wbs.close_note`（关闭说明落库）
- **生效点**: `wbs.close → 校验`
- **示例**: 子元素还在草稿时关闭父元素 → 拒绝；变更中直接关闭 → 拒绝
- **依据**: 材料 §3.3.6（修订要按流程走完才算落实）；聚合根卡 12 的 I-5 之延伸

#### 3.2.7 `BR-07` 编号落库后不可变

- **规则描述**: `wbs_no` 由调用方给定或由 `add_child` 生成，**落库后不得修改**
  （`update` 的字段白名单里没有编号）
- **适用场景**: 修改
- **计算方式**: 字段白名单（无从改起）
- **依赖输入**: `[wbs_no(实体字段)]`
- **输出**: 无（拒绝：编号不可变 —— 改编号没有入口，违反编码规则即报错，不产生新字段）
- **生效点**: `wbs.update`（白名单不含编号）
- **示例**: `update(wbs_no="123456.01", wbs_no="123456.02")` → 该参数不存在，服务不接受
- **依据**: 材料 §3.4.2「a unique element code to be used as a reference point for its technical
  and financial identification **throughout the life of the project**」

### 3.3 业务数据

| 字段 | 类型 | 必填 | 说明 | 依据 |

| `owner` | string | 否 | 责任方（含 CA 经理） | §3.2 |
| `req_nos` | string | 否 | 关联需求编号（逗号分隔）—— 交叉引用矩阵的 X | §3.3.3 |
| `rev_no` | integer | 是（默认 0） | 版次（每次落实变更 +1） | §3.4.4g |
| `rev_authorization` | string | 否 | 修订授权（落实变更时记该变更号） | §3.4.4g |
| `change_no` | string | 否 | 当前挂着的变更号 | §3.3.6 |
| `status` | string | 是 | 见状态机 | — |
| `close_note` | string | 否 | 关闭说明 | — |

### 3.4 状态机

```
草稿 draft ──baseline──▶ 已基线 baselined ──change──▶ 变更中 in_change
                             │                              │
                             │                          baseline（落实变更，
                             │                           版次 +1、记修订授权）
                             │                              │
                             └──────────close◀──────────────┘
                                          ▼
                                    已关闭 closed（终态）
```

| 迁移 | 触发服务 | 闸门 |
|---|---|---|
| ∅ → `draft` | `create` / `add_child` | BR-01 编号自洽 · BR-02 父存在 · BR-04 产品导向 |
| `draft` → `baselined` | `baseline` | BR-02 父已基线 · BR-03 有范围出处 |
| `baselined` → `in_change` | `change` | BR-05 变更号已批准 |
| `in_change` → `baselined` | `baseline` | 版次 +1、记 `rev_authorization` |
| `baselined` → `closed` | `close` | BR-06 子元素全关、自身不在变更中 |
| `closed` → × | — | 终态，任何改写一律拒绝 |

## 4. 功能描述

### 4.1 功能清单

| # | 服务 | 用途 |
|---|---|---|
| 1 | `create` | 建立元素（顶层或指定父元素） |
| 2 | `add_child` | 在父元素下**自动分配子号**并建立子元素 |
| 3 | `get` | 按编号取元素（字典条目） |
| 4 | `list` | 按状态 / 类型 / 父元素 / 责任方筛选并分页 |
| 5 | `update` | 修改字典字段（基线后须带变更号） |
| 6 | `baseline` | 纳入基线 / 落实变更（版次递增） |
| 7 | `change` | 发起修订（须带已批准的变更号） |
| 8 | `close` | 关闭元素 |
| 9 | `tree` | 返回嵌套树（前端画树 / 索引） |
| 10 | `coverage` | 需求覆盖对账（跨应用读 `requirement`） |

### 4.2 功能模块结构图

```
wbs（聚合根 = 工作分解结构元素）
├── 元素树       create / add_child / update / tree
├── 配置控制     baseline / change / close
├── 字典与检索   get / list
└── 覆盖对账     coverage ──▶ requirement.list（跨应用，只读）
                    └──────▶ change_request.get（跨应用，只读）
```

### 4.3 功能详细说明

- **`add_child`**：查同父子元素的最大末段序号，+1 生成两位子号（`01`、`02`…）；
  父元素处于 `已关闭` 时拒绝（树的收口之后不再长新枝）
- **`baseline`**：两种入边（`草稿` 与 `变更中`）共用，靠当前状态分流 ——
  从 `变更中` 回来时 `rev_no + 1`、`rev_authorization = change_no`，并把 `change_no` 留在元素上
- **`coverage`**：读 `requirement.list` 全量，与本聚合所有元素的 `req_nos` 求差 ——
  返回「未覆盖需求」清单；同时返回「未挂需求出处的元素」清单（§3.3.3 矩阵的两侧）
- **`tree`**：一次读全表在内存组树，返回嵌套 `children`；`root` 为空时返回全部顶层

## 5. 权限要求

### 5.1 功能权限

平台注入 `self.ctx`（`userno / departmentno / role`），**应用不实现鉴权**；
页面授权由平台按「页→服务」隐式放行（`X-Fde-Page`）。四个角色的工具面由
`_roles.py` 收窄：本应用挂在 `nasa_planner`（技术计划与评审主管）名下。

### 5.2 数据权限

本应用数据**不按人隔离**：WBS 是项目级共享数据（§3.2：由项目团队共同开发、PM 批准），
不属于"谁建的谁看"那一类。写操作的身份由平台自动记进审计列。

## 6. 验收标准

### 6.1 功能验收标准

| # | 验收项 | 判据 | 对应用例 |
|---|---|---|---|
| 1 | 编号规则 | 7 层上限、24 字符上限、父号自洽 | `TC-01` / `TC-02` |
| 2 | 父先于子 | 父不存在 / 父未基线时拒绝 | `TC-03` / `TC-09` |
| 3 | 范围出处 | 缺 `scope_ref` 不得基线 | `TC-10` |
| 4 | 产品导向 | 非产品词名称被拒 | `TC-04` |
| 5 | 变更闸门 | 变更号必填且须已批准；草稿不可 change | `TC-11` / `TC-12` |
| 6 | 版次递增 | 变更落实后 `rev_no` +1、记修订授权 | `TC-13` |
| 7 | 关闭闸门 | 有未关闭子元素 / 变更中不得关闭 | `TC-15` / `TC-16` |
| 8 | 编号不可变 | `update` 无编号参数 | `TC-05` |
| 9 | 覆盖对账 | 返回未覆盖需求与无出处元素两侧 | `TC-20` |
| 10 | 契约形状 | `list` 返回 `{items,total}` | `TC-06` |

### 6.2 非功能验收标准

- 分页默认与同组其它应用一致（`page` / `size`，返回 `{items, total}`）
- 全部失败路径 `raise FdeError("人话")`，跨调用原样传播
- 审计列由平台自动维护

### 6.3 已知问题或限制

- **不建 OBS**：CA/WP/PP 只作 `kind` 属性（口径见 `术语表.md` 附 #1）
- **非产品词拦截是例子不是穷举**（BR-04）：材料给的是示例清单，漏网的靠人
- **`coverage` 只在"需求挂了 req_nos"这一层对账**：需求侧的分解是否合理（一条需求该拆成几个元素）
  是设计判断，机械判不了
