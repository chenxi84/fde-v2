## 1. 配置项概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `configuration_item` |
| 类名 | `ConfigurationItem` |
| 聚合根 | 配置项 |
| 标识 | `ci_no` |
| 数据来源类型 | **独立创建**（配置项由项目内人员标识并录入，无上游自动生成） |

### 1.2 配置项背景

#### 1.2.1 为什么需要这个配置项？

材料（NASA SE Handbook Rev 2 §6.5）把配置管理称为企业结构的 **"backbone"**：
"CM ensures that the configuration of a product is known and reflected in product information,
that any product change is beneficial and is effected without adverse consequences, and that
changes are managed."。而 CM 的**第二步**就是 Configuration Identification ——
"selecting, organizing, and stating the product attributes"，并**为产品与其配置文档发唯一标识**。

材料同时给出反面代价（引 SAE/EIA 649B）："improper configuration management may result in
incorrect, ineffective, and/or unsafe products being released"。
现状是工作产品（软件、文档、模型、数据）散落在各人手里，**没有唯一标识、没有版本、没有基线归属**，
既答不出"当前基线是什么"，也无法判断一次改动到底动了哪一版。

#### 1.2.2 期望达到什么目标？

- 每个受控工作产品**有唯一编号**（`ci_no`），可被变更请求、接口、审计**按号引用**
- 每个配置项**有版本，且版本只能递增** —— 历史版本不可改写（材料要求 version control & comparison：
  "track history of an object or product"）
- 每个配置项**可归属到某条基线**（材料 §6.5.1.2.2 的四条基线），使"当前基线"这个问句可回答
- 版本变更**必须经由已批准的变更请求** —— 与 `change_request` 应用跨应用协作（I-2）

### 1.3 配置项范围

#### 1.3.1 包含哪些功能？

- 配置项的创建、修改、查询、列表
- **提交受控**：把草稿纳入配置管理（材料 §6.5.1.1「Designated configuration items to be controlled」）
- **发版**：把受控的当前版本冻结为已发布版本
- **版本变更**：递增版本（须带已批准的变更请求号）
- **纳入基线**：归属到四条基线之一
- **归档**：已发布配置项的收尾（终态，记录保留）
- 配置项与**变更请求**（`change_request`）通过弱引用（`change_no`）关联

#### 1.3.2 不包含哪些功能？

- **不做变更审批** —— 变更请求的提出/影响分析/审批属 `change_request` 聚合（材料 §6.5.1.2.3
  Manage Configuration Change Control）；本应用只**引用**已批准的变更号，不判它是否已批准
- **不做配置审计（Configuration Audits）** —— 材料 §6.5.1.2.5 的 Configuration Verification
  由评审/验证类应用承载，本应用只保证"版本与状态可查"（CSA 的数据面）
- **不维护 CM 计划本身** —— CM Plan 属 `tech_plan`（计划类文档，见聚合根卡 10）
- **不做技术数据管理（§6.6）** —— 那是并行的另一条过程，本应用只管"纳入配置控制"的那部分

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 配置管理员（CM） | 标识配置项、提交受控、纳基线、发版、归档 | 材料 §6.5.1.2.2 / §6.5.1.2.4 |
| 配置项责任人 | 对单个配置项的内容负责（`owner` 字段） | 材料 §6.5.1.2.4 CSA 要求"who" |
| 变更提出方 | 只读消费配置项（在 `change_request` 里选影响范围） | 材料 §6.5.1.2.3 |

> 术语表未收「配置管理员」，按材料语境（CM office / Configuration Management Organization，
> §6.5.1.2.1）就地取名为**配置管理员（CM）**并回填（见 §7.4）。

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 用户故事 — 标识并录入一个配置项（优先级：P1）

**作为**一名配置管理员
**我希望**把一个工作产品登记为配置项（含名称、类型、责任人），系统给它一个唯一编号
**以便**后续能为它建版本、纳基线、接变更

**验收条件**：
- 给定名称与类型齐备，当提交时，则新配置项以「草稿」状态落库，编号自动生成（`CI-001` 起），**初始版本为 v1**
- 给定名称为空，当提交时，则**拒绝**并提示「配置项名称不能为空」
- 给定类型填了字典外的值，当提交时，则**拒绝**（`BR-05`）

#### 2.1.2 `US-02` 用户故事 — 提交受控（优先级：P1）

**作为**一名配置管理员
**我希望**把草稿配置项提交受控
**以便**它从此纳入配置管理、可被基线冻结与变更控制

**验收条件**：
- 给定一个 `draft` 的配置项，当提交受控时，则状态变为 `controlled`
- 给定已是 `controlled` 的配置项，当再次提交受控时，则**拒绝**并提示「已经是受控状态」
- 给定一个草稿配置项，当尝试直接纳入基线时，则**拒绝**（未受控不能进基线）

#### 2.1.3 `US-03` 用户故事 — 发版（优先级：P1）

**作为**一名配置管理员
**我希望**把受控的配置项发版
**以便**产出一个"已交付给下游使用"的确定版本

**验收条件**：
- 给定一个 `controlled` 的配置项（从未发版），当发版时，则状态变为 `released`、`released_ver` = 当前版本，**无需变更号**
- 给定一个 `draft` 的配置项，当发版时，则**拒绝**并提示只有受控状态才能发版
- 给定一个**曾经发版过**的配置项（`released_ver` 非空）重新走到受控后再次发版，当**不带变更号**时，则**拒绝**（`BR-03`：非首次发版属于版本变更）

#### 2.1.4 `US-04` 用户故事 — 版本变更（优先级：P1）

**作为**一名配置管理员
**我希望**在变更请求获批后，把配置项的版本升到新版本
**以便**版本历史可回溯、且每次版本变更都有据可查

**验收条件**：
- 给定已存在 `CI-001` v1 且有一个已批准的变更请求 `CR-001`，当 `bump_version(CI-001, 2, CR-001)` 时，则版本变为 v2、`change_no = CR-001`，且状态**回落为「受控」**（新版本尚未发布）
- 给定 `bump_version(CI-001, 1, CR-001)`（新版本不大于当前），当提交时，则**拒绝**（`BR-01`：只能递增）
- 给定**不带**变更号，当执行版本变更时，则**拒绝**（`BR-03`：必须经由已批准的变更请求）

#### 2.1.5 `US-05` 用户故事 — 纳入基线（优先级：P1）

**作为**一名配置管理员
**我希望**把配置项归属到某条基线（功能/分配/产品/部署）
**以便**"当前基线是什么"可被回答，变更也有对照基准

**验收条件**：
- 给定一个受控的配置项，当纳入「产品基线」并给基线版本 `B1` 时，则 `baseline = product`、`baseline_ver = B1`
- 给定基线名不在四条基线之内，当提交时，则**拒绝**
- 给定配置项已在某条基线中，当再次纳入**同一条**基线时，则**拒绝**（不能重复纳入）

#### 2.1.6 `US-06` 用户故事 — 归档（优先级：P2）

**作为**一名配置管理员
**我希望**把已交付的配置项归档
**以便**收尾，同时保留完整历史（材料 §6.5.1.2.4 要求 historical traceability）

**验收条件**：
- 给定一个 `released` 的配置项，当归档时，则状态变为 `archived`
- 给定一个 `draft` / `controlled` 的配置项，当归档时，则**拒绝**（未交付不能归档）
- 给定已归档的配置项，当尝试修改名称 / 版本变更 / 纳入基线时，则**拒绝**（终态）
- 归档后**记录仍在**（不删除）

#### 2.1.7 `US-07` 用户故事 — 修改配置项内容（优先级：P2）

**作为**一名配置项责任人
**我希望**修改配置项的名称 / 类型 / 责任人
**以便**纠正登记错漏

**验收条件**：
- 给定一个 `draft` / `controlled` 的配置项，当修改名称时，则成功
- 给定一个 `released` 的配置项，当**不带变更号**直接修改名称时，则**拒绝**（`BR-02`）；带了变更号则允许，并记录该变更号
- 给定一次不带任何字段的 `update`，则**拒绝**（「没有要修改的内容」）

#### 2.1.8 `US-08` 用户故事 — 查询配置项列表（优先级：P2）

**作为**一名变更提出方 / 配置管理员
**我希望**按类型 / 状态 / 基线筛选配置项
**以便**定位"某条基线里都有什么"或"哪些还没受控"

**验收条件**：给定筛选条件，当查询时，则返回匹配列表（默认按编号升序），**分页返回 `{items, total}`**

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1: 一个配置项的一生（对齐状态机）

1. 配置管理员识别出需受控的工作产品（材料 §6.5.1.1 的 "Designated configuration items to be controlled"）
2. `create` 登记 → 草稿（`draft`，v1）
3. `control` 提交受控 → 受控（`controlled`）—— 从此纳入配置管理
4. `assign_baseline` 纳入某条基线（如产品基线 B1）—— 有了变更的对照基准
5. `release` 发版 → 已发布（`released`，v1 冻结）
6. 需要改动时：先提变更请求，获批后 `bump_version` → v2、状态回落「受控」
7. 重新 `release`（**这次必须带变更号**）→ 已发布 v2
8. 交付完成后 `archive` → 已归档（终态，记录保留）

#### 3.1.2 场景2: 变更请求引用配置项（跨应用）

1. `change_request` 应用读取本应用的配置项（`configuration_item.list`）**选择影响范围**
2. 变更经 CCB 审批通过，得到变更号 `CR-00x`（材料 FIGURE 6.5-4 的 "Disposition change request"）
3. 变更实施时，本应用以 `bump_version(ci_no, n, CR-00x)` 应用该变更 ——
   **本应用只校验"带了变更号"，"变更是否已批准"由 `change_request` 负责**（见 §6.3 已知限制）

### 3.2 业务规则

#### 3.2.1 `BR-01` 配置项版本只能递增

- **规则描述**: `version` 只增不减，且**只能经 `bump_version` 变更**（`update` 的字段白名单里没有版本）
- **适用场景**: 版本变更
- **计算方式**: 比较校验（新版本 > 当前版本）
- **依赖输入**: `[version(实体字段), new_version(服务实参)]`
- **输出**: `configuration_item.version`
- **生效点**: `configuration_item.bump_version → 校验`
- **示例**: `CI-001` 当前 v2，执行 `bump_version(CI-001, 1, CR-001)` → 拒绝
- **依据**: 材料 §6.5.1.2.4（CSA 关键属性："Version control and comparison（track history of an object or product）"）
  —— 版本不递增就无历史可回溯；聚合根卡 3 的 I-1 前半

#### 3.2.2 `BR-02` 已发布版本不可改写；归档为终态

- **规则描述**: 状态为 `released` 时，名称 / 类型 / 责任人不得直接修改，必须携带已批准的变更号；
  状态为 `archived` 时，**任何**修改（含版本变更与纳入基线）一律拒绝
- **适用场景**: 修改、版本变更、纳入基线
- **计算方式**: 校验型（按状态拦截）
- **依赖输入**: `[status(实体字段), change_no(上游服务实参 —— change_request 选择已批准的变更)]`
- **输出**: `configuration_item.status`（改后记 `change_no`）
- **生效点**: `configuration_item.update → 校验` / `bump_version → 校验` / `assign_baseline → 校验`
- **示例**: 直接改已发布的 `CI-001` 名称 → 拒绝，提示「请先提交变更请求」
- **依据**: 聚合根卡 3 的 I-1 后半；材料 §6.5.1.2.3 "manage approved designs and the
  implementation of approved changes" —— 已批准的设计是变更的基准，不能绕过变更直接改写

#### 3.2.3 `BR-03` 版本变更必须经由已批准的变更请求

- **规则描述**: `bump_version` 的 `change_no` 必填；**非首次发版**的 `release` 同样必须带 `change_no`
  （第二次发版本身就是一次版本变更）
- **适用场景**: 版本变更、非首次发版
- **计算方式**: 校验型（非空校验）
- **依赖输入**: `[change_no(服务实参 —— change_request 提供), released_ver(实体字段)]`
- **输出**: `configuration_item.change_no`
- **生效点**: `configuration_item.bump_version → 校验` / `release → 校验`
- **示例**: `bump_version(CI-001, 2, "")` → 拒绝「版本变更必须经由已批准的变更请求」
- **依据**: 聚合根卡 3 的 I-2；材料 §6.5.1.2.3 与 §6.6 末段
  （"Changes to information under configuration control require a Change Request (CR) and are
  typically approved by a Configuration Control Board"）

#### 3.2.4 `BR-04` 配置项编号唯一且不可变

- **规则描述**: `ci_no` 系统生成（`CI-` + 三位序号）、落库后不得修改
- **适用场景**: 创建、修改
- **计算方式**: 唯一性校验
- **依赖输入**: `[ci_no(实体字段)]`
- **输出**: 无（拒绝：编号由系统生成、落库后不可变 —— 改编号没有入口，违反唯一性即报错，不产生新字段）
- **生效点**: `configuration_item.create`（生成）/ `update`（**字段白名单里没有编号**，无从改起）
- **示例**: `update(ci_no="CI-001", ci_no="CI-100")` → 该参数不存在，服务不接受
- **依据**: 材料 §6.5.1.2.2 "Identification requires unique identifiers for a product and its
  configuration documentation"；聚合根卡 3

#### 3.2.5 `BR-05` 类型必填且受字典约束

- **规则描述**: `ci_type` 取值限 `hardware / software / document / model / data` 五类
- **适用场景**: 创建、修改
- **计算方式**: 字典校验
- **依赖输入**: `[ci_type(实体字段)]`
- **输出**: `configuration_item.ci_type`
- **生效点**: `configuration_item.create` / `update`
- **示例**: 类型填「其它」→ 拒绝
- **依据**: 材料 §6.5.1.3 Outputs —— CSA 报表是"all the items, **documents, hardware, software,
  models**, etc."的清单，即受控对象的类别；术语表未收类型名，第②步就地取名并回填

#### 3.2.6 `BR-06` 未受控的配置项不能纳入基线

- **规则描述**: 草稿（`draft`）状态不能 `assign_baseline`；且同一配置项不能重复纳入**同一条**基线
- **适用场景**: 纳入基线
- **计算方式**: 校验型（按状态 + 按已有归属拦截）
- **依赖输入**: `[status(实体字段), baseline(实体字段), baseline(服务实参)]`
- **输出**: `configuration_item.baseline` / `baseline_ver`
- **生效点**: `configuration_item.assign_baseline → 校验`
- **示例**: 对草稿项 `assign_baseline(CI-002, "product")` → 拒绝；对已在产品基线的项重复纳入 → 拒绝
- **依据**: 材料 §6.5.1.1 输入清单把 "Designated configuration items to be controlled" 列为
  CM **前置输入** —— 先受控，后基线；§6.5.1.2.2 "The approved 'current' baseline defines the
  basis of subsequent change"（基线是基准，重复纳入即失去基准意义）

### 3.3 业务数据

#### 3.3.1 数据1: 配置项编号（ci_no）

- **数据描述**: 配置项的唯一标识，落库后不可变
- **数据类型**: 文本
- **数据来源**: 系统生成（`CI-` + 三位序号）
- **示例值**: "CI-001"

#### 3.3.2 数据2: 配置项名称（name）

- **数据描述**: 工作产品的名字，用于列表展示与人工辨识
- **数据类型**: 文本（≤120 字）
- **数据来源**: 人工录入
- **示例值**: "飞控软件"

#### 3.3.3 数据3: 配置项类型（ci_type）

- **数据描述**: 配置项的类别（受控对象是硬件还是文档，决定其变更控制权威 —— 材料 §6.5.1.2.2
  "determining the appropriate change control authority"）
- **数据类型**: 字典：hardware / software / document / model / data
- **数据来源**: 人工选择
- **字典对应业务名**: 硬件 / 软件 / 文档 / 模型 / 数据（术语表，本步回填）
- **示例值**: "software"

#### 3.3.4 数据4: 当前版本（version）

- **数据描述**: 配置项的当前版本，**只能递增**（BR-01）
- **数据类型**: 整数（从 1 起）
- **数据来源**: 系统（创建时置 1，之后经 `bump_version` 递增）
- **示例值**: 2

#### 3.3.5 数据5: 已发布版本（released_ver）

- **数据描述**: 最近一次发版冻结的版本号；为空表示**从未发版**（非首次发版须带变更号，BR-03）
- **数据类型**: 整数（可空）
- **数据来源**: 系统（`release` 时写入）
- **示例值**: 1

#### 3.3.6 数据6: 所属基线（baseline）

- **数据描述**: 配置项归属的基线（材料 §6.5.1.2.2 的四条基线，随项目阶段演进：
  功能基线 SDR → 分配基线 PDR → 产品基线 CDR → 部署基线 ORR）
- **数据类型**: 字典：functional / allocated / product / as_deployed
- **数据来源**: 人工选择
- **字典对应业务名**: 功能基线（Functional Baseline）/ 分配基线（Allocated Baseline）/
  产品基线（Product Baseline）/ 部署基线（As-Deployed Baseline）（术语表，本步回填）
- **示例值**: "product"

#### 3.3.7 数据7: 基线版本标记（baseline_ver）

- **数据描述**: 该基线这一版的标记（材料 §6.5.1.2.2 的基线是"at a point in time"，需要有标记）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入
- **示例值**: "B1"

#### 3.3.8 数据8: 状态（status）

- **数据描述**: 配置项在生命周期中的位置
- **数据类型**: 字典：draft / controlled / released / archived
- **数据来源**: 系统按流转规则变更
- **示例值**: "released"

#### 3.3.9 数据9: 责任人（owner）

- **数据描述**: 对该配置项内容负责的人（CSA 要求记录 "who"，材料 §6.5.1.2.4）
- **数据类型**: 文本
- **数据来源**: 人工录入
- **示例值**: "张三"

#### 3.3.10 数据10: 变更请求号（change_no）

- **数据描述**: 最近一次驱动本配置项变更的变更请求号（BR-03）
- **数据类型**: 文本（可空）
- **数据来源**: 人工录入（来源：`change_request` 已批准的变更 —— **该应用待建成**）
- **示例值**: "CR-001"

### 3.4 状态机

```
draft（草稿）  v1
   │ control（提交受控）
   ▼
controlled（受控）◄──────────────────────────┐
   │ release（发版，首次无需变更号）          │ bump_version（版本递增，
   ▼                                        │ 须带已批准的变更请求号，BR-03）
released（已发布）──────────────────────────┘
   │
   │ archive（归档）
   ▼
archived（已归档，终态：不可再修改 / 变更版本 / 纳基线）
```

**每个状态的到达服务**（详设 §4.1 的 FUNC 与服务一一对应）：

| 状态 | 到达服务 |
|---|---|
| `draft` | `create` |
| `controlled` | `control`（草稿→受控）/ `bump_version`（版本变更后回落，新版本尚未发布）|
| `released` | `release` |
| `archived` | `archive` |

> **合法迁移**：`draft→controlled`、`controlled→released`、`released→controlled`（经 `bump_version`）、
> `released→archived`。
> **拦截迁移**：`draft→released`（须先受控）、`draft|controlled→archived`（须先发布）、
> `archived→*`（终态，全部拒绝）。

## 4. 功能描述

### 4.1 功能清单

| 编号 | 功能 | 对应 US | 说明 |
|---|---|---|---|
| `FUNC-01` | 登记配置项 | US-01 | create（编号自动生成，初始 v1） |
| `FUNC-02` | 提交受控 | US-02 | control（草稿 → 受控） |
| `FUNC-03` | 发版 | US-03 | release（受控 → 已发布；非首次须带变更号，BR-03） |
| `FUNC-04` | 版本变更 | US-04 | bump_version（BR-01 递增 + BR-03 须带变更号） |
| `FUNC-05` | 纳入基线 | US-05 | assign_baseline（BR-06：须先受控、不可重复） |
| `FUNC-06` | 修改配置项 | US-07 | update（BR-02 拦截；字段白名单不含版本与编号） |
| `FUNC-07` | 归档 | US-06 | archive（**不删除**：材料要求 historical traceability） |
| `FUNC-08` | 配置项列表 | US-08 | list（分页 `{items, total}`） |
| `FUNC-09` | 配置项详情 | US-08 | get（未命中返回 None，不抛异常） |

### 4.2 功能模块结构图

```
配置项 configuration_item
├── 登记与维护
│   ├── FUNC-01 登记配置项
│   ├── FUNC-02 提交受控
│   ├── FUNC-06 修改配置项
│   └── FUNC-07 归档
├── 版本与基线
│   ├── FUNC-03 发版
│   ├── FUNC-04 版本变更
│   └── FUNC-05 纳入基线
└── 查询
    ├── FUNC-08 配置项列表
    └── FUNC-09 配置项详情
```

### 4.3 功能详细说明

#### 4.3.1 登记配置项（FUNC-01）

- **输入**: 名称、类型、责任人、所属项目
- **校验**: 名称非空、`BR-05`（类型字典）
- **处理**: 生成 `ci_no`（`CI-<序号>`）→ 落库 → 状态置 `draft`、版本置 1
- **输出**: 新配置项记录

#### 4.3.2 版本变更（FUNC-04）

- **输入**: `ci_no` + 新版本号 + 变更请求号
- **校验**: `BR-01`（新版本严格大于当前）、`BR-03`（变更号必填）、`BR-02`（归档终态拒绝）
- **处理**: 写入 `version`、`change_no`，状态**回落为 `controlled`**
- **输出**: 更新后的配置项
- **说明**: 状态回落是刻意的 —— 已发布版本不可改写（BR-02），新版本要重新发版才算发布

#### 4.3.3 纳入基线（FUNC-05）

- **输入**: `ci_no` + 基线类型 + 基线版本标记
- **校验**: 基线字典、`BR-06`（草稿不能进、已归档不能进、同一条基线不可重复纳入）
- **处理**: 写 `baseline` / `baseline_ver`
- **输出**: 更新后的配置项

#### 4.3.4 归档（FUNC-07）

- **输入**: `ci_no` + 归档原因
- **校验**: 状态须为 `released`（未交付不能归档）；已归档 → 拒绝
- **处理**: 状态置 `archived`（终态）
- **输出**: 更新后的配置项（含 `reason` 回显）

## 6. 验收标准

### 6.1 功能验收标准

#### 6.1.1 标准1: 版本只能递增

**Given** `CI-001` 当前版本为 v2
**When** 执行 `bump_version(CI-001, 1, CR-001)`
**Then** 拒绝，提示「配置项版本只能递增」（`BR-01`）

#### 6.1.2 标准2: 版本变更须有变更请求，且归档后不可再变

**Given** `CI-001` 处于受控状态
**When** 不带变更号执行版本变更
**Then** 拒绝，提示「必须经由已批准的变更请求」（`BR-03`）
**And given** `CI-001` 已归档，**when** 执行版本变更 / 修改 / 纳基线，**then** 全部拒绝（终态）

#### 6.1.3 标准3: 已发布版本不可直接改写

**Given** 一个状态为 `released` 的配置项
**When** 不带变更号直接修改名称
**Then** 拒绝，提示需先提交变更请求（`BR-02`）

#### 6.1.4 标准4: 未受控不能进基线

**Given** 一个 `draft` 状态的配置项
**When** 把它纳入产品基线
**Then** 拒绝，提示「尚未受控」（`BR-06`）

#### 6.1.5 标准5: 非首次发版须带变更号

**Given** `CI-001` 曾发布过 v1，现在版本为 v2 且状态为 `controlled`
**When** 不带变更号发版
**Then** 拒绝，提示「再次发版属于版本变更」（`BR-03`）

### 6.2 非功能验收标准

- 列表查询（1000 条内）响应 P95 ≤ 500ms
- 配置项编号生成在并发登记下不重复（`BR-04`）
- `get` 未命中**不抛异常**，返回 `None`（供跨应用探测式调用）

### 6.3 已知问题或限制

- **本项目尚未接入 `change_request`** —— `BR-03` 的"已批准的变更请求"当前只能校验"是否带了变更号"，
  不能校验"该变更是否已批准"（`change_request` 应用建成后应改为跨应用校验 —— 即卡片上的
  `change_request.get`）。**因此本应用当前不做任何 `self.fde.call`**（跨应用调用只有这一处，且依赖未建成）。
- **状态机比材料的过程链条略窄** —— 材料 FIGURE 6.5-4 的变更控制流程含 CCB 审批、action items、
  minutes 等环节，那些属 `change_request` 的职责，本应用只保留"状态 + 变更号"这一数据面。
- **未做配置审计（Configuration Audits）** —— 材料 §6.5.1.2.5 的 functional / physical
  configuration audit 不在本应用，需由评审/验证类应用承载。
- **`baseline` 为单值字段** —— 同一配置项同时只能归属一条基线。材料里四条基线是随阶段**演进**的
  （功能 → 分配 → 产品 → 部署），故单值符合实际；若将来需要"跨基线并存"，本字段要改为子表
  （属聚合内部结构变更，不影响对外服务签名）。
