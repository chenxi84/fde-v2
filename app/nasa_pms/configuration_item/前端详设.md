## 1. 页面定位

| 项 | 内容 |
|---|---|
| key / name | `configuration_item` / 配置项 |
| 一句话 | 配置项台账：登记、提交受控、发版、版本变更、纳入基线、归档，按类型/状态/基线筛选 |

## 3. 交互规则（逐条对应后端约束）

| # | 规则 | 依据 |
|---|---|---|
| F-1 | 登记表单里**名称与类型为必填**，未填时提交按钮禁用 | `BR-05` + 名称非空 |
| F-2 | 当前版本**只读显示为 `v{n}`**（不是输入框）—— 版本只能经「版本变更」递增 | `BR-01` |
| F-3 | 详情里**配置项编号为纯文本**（不可编辑） | `BR-04` |
| F-4 | 状态为「已发布」时**名称/类型/责任人置灰**；须先填「变更号」解锁，解锁后提示"本次修改将记为 CR-xxx" | `BR-02` |
| F-5 | 类型/状态/基线为**下拉字典**（硬件/软件/文档/模型/数据；功能/分配/产品/部署基线） | `BR-05` |
| F-6 | 「归档」需二次确认，文案强调**记录保留**且**归档后不可再改**（终态） | 状态机 + `BR-02` |
| F-7 | 列表默认按编号升序；筛选变化即刷新（重置到第 1 页） | `US-08` |
| F-8 | 「版本变更」是**独立模态**：新版本号与变更请求号均必填，且新版本须**大于**当前版本才可提交 | `BR-01` + `BR-03` |
| F-9 | 状态机动作按钮**按当前状态显隐**：草稿→[提交受控]；受控→[发版][版本变更][纳入基线]；已发布→[版本变更][纳入基线]；已归档→无 | 状态机（§3.4 到达服务表） |

## 7. 已知限制

- **变更号 / 责任人都尚未接候选**：两处仍是文本输入。`change_request` 与 `stakeholder` 均**已建成**，
  要接只是各挂一个 `datalist`（照 `requirement` 页 `VT-ACT-51` 的范式，值仍存文本、不动契约）；
  变更号的"已批准"校验另需后端加一行 `self.fde.call("change_request", "get", ...)`。
- **跨应用调用方向表里 `configuration_item` 是"只被调用"** —— 本页自身确实不发跨应用调用
  （与 `应用详设.md` §6.3 一致），这是**有意的设计**，不是"因为对方没建成"。
- **版本为整数**：`v1 / v2 / v3…`，不支持 `A.1` 这类复合版本号（详见详设 §3.3.4）。

## 附：状态/枚举下拉的「回填静默失败」缺陷（2026-09-25 已修）

**现象**：Alpine 的 `x-model` + `x-for` 生成 `<option>` 时，**数据→DOM 的回填会静默停在第一项** ——
`x-model` 的「数据→DOM」effect 跑在 `x-for` 把选项插进 DOM **之前**，`select.value = "<真实值>"`
当时无此选项、静默失败；选项插入后 `selectedIndex` 落到 0，而该 effect 的依赖此后不再变 ⇒ **永不重跑**。

**影响不只是显示**：用户看着错的选项去改别的字段并保存，会把"他看到的那个值"当成事实。

**修法**：本页的枚举下拉**一律改用静态 `<option>`**（元素静态 → 无时序问题）；
**数值型字段用 `:value` 绑定**（`:value="1"`）以保留数字类型，别写成 `value="1"`（会字符串化）。

**同一缺陷曾存在于本组另外两个应用**（`requirement` / `risk` / `configuration_item` 各 2 处），
已于同批统一修复并复跑全部通过。规格侧对应 `design-plus/view-convention/patterns.md` §4。
