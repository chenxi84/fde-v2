# 前端详设：验证项（verification）

> 产出技能：第⑥步 前端设计（规格 `design-plus/前端设计.md`，规范正本 `VIEW_CONVENTION.md`）
> 输入：`应用详设.md`（US/FUNC/PERM/状态机/§6.3）+ `architecture.md`（聚合根卡 6）
> 后端契约**以 `verification.py` 源码为准**（组级 `_contracts.md` 尚未收录本应用 —— 见 §7 限制）

## 1. 页面定位

| 项 | 内容 |
|---|---|
| key / name | `verification` / 验证项 |
| 一句话 | 验证矩阵：把一条需求挂成一行，规划方法/阶段、开始执行、记录判定、关闭，按需求/方法/阶段/状态筛选 |
| 数据来源类型 | **跨应用派生** —— 因此**保留「规划验证项」入口**（与服务契约 `create` 对应），且该入口的**对应需求必选** |
| `PAGE_META.order` | `660` —— **组内序不在此复抄**：真值 = 各页 `PAGE_META.order`，组级 view 测试的「菜单序」断言从 `PAGE_META` + `shell.js` 的 `PLATFORM_PAGES` **现算**。本行此前逐页复抄了一遍 —— 复抄必漂：2026-09-25 因 `order` 并列、平台按 key 字母序兜底，「配置项」被渲染到「风险」之前，而复抄的清单还把旧值当成了正确值（见 pitfalls #43）。 |

## 3. 交互规则（逐条对应后端约束）

| # | 规则 | 依据 |
|---|---|---|
| F-1 | 规划表单里**对应需求 / 验证方法 / 验证阶段三项必填**，未齐备时提交按钮禁用；三项都**不给默认值**，须显式选择 | `BR-01` + `BR-05` |
| F-2 | 对应需求是**强关联**：详情 / 编辑里以**纯文本**回显（`req_no` + 需求标题），**没有下拉可改** —— 换需求等于换矩阵的一行，应另建验证项 | `BR-01` |
| F-3 | 验证方法（检验/分析/演示/测试）与验证阶段（8 个）为**字典下拉**，选项值须与后端校验值**完全一致** | `BR-05` |
| F-3b | 已关闭项的详情**显示关闭说明**（`close_note`；2026-09-25 起落库，此前只回显） | `BR-02` / 组内留痕口径 |
| F-4 | 「记录判定」是**独立动作**：判定结果必选、**验证证据必填**（`BR-02`）；选「不通过」时**后续处置也必填**，未填齐则提交按钮禁用 | `BR-02` |
| F-5 | 已判定（通过 / 不通过）后**验证方法与验证阶段置灰锁定**，**成功判据与责任人仍可编辑** | `BR-03` |
| F-6 | 「关闭」是终态动作：关闭后**动作按钮全部收起**（含「编辑」），记录保留在列表里 | `BR-03` + 状态机 |
| F-7 | 状态机动作按钮**按当前状态显隐**：规划→[开始执行]；执行中→[记录判定]；通过/不通过→[关闭]；关闭→无 | 状态机（§3.4 到达服务表） |
| F-8 | 筛选控件与后端 `list` 的可过滤参数**一一对应**：需求 / 验证方法 / 验证阶段 / 状态；筛选变化即刷新（重置到第 1 页） | `US-06` |
| F-9 | 判定结果与证据在详情里恒为**纯文本**（判定只能经「记录判定」产生，没有可填控件） | `BR-03` + `BR-06` |
| F-10 | 页眉给一条**验证矩阵覆盖读数**：「已基线需求 N 条 · 已覆盖 M 条 · 缺口 K 条」（I-1）；有缺口时转琥珀色提示 | I-1（组合级口径，见 `应用详设.md` §3.2.1 的落点说明） |
| F-11 | 枚举 select（方法/阶段/判定结果）**一律静态 `<option>`**，不用 `<template x-for>` 生成选项 | `patterns.md` §4 + 本步实测踩坑（见 §8） |

## 7. 已知限制

- **组级 `_contracts.md` 尚未冻结本应用** —— 该文件当前只收录 `requirement`。本页的服务名 / 入参
  **逐字取自 `verification.py` 的公共方法签名**；契约冻结应由第⑤步出口的统一 dump 完成
  （本任务范围不含改 `_contracts.md`）。
- **对应需求建成后不可改** —— 这是刻意的（`BR-01`），不是缺功能：判定/证据构成了这一行的身份，
  换需求会让验证记录张冠李戴。要换需求就另建一行、关闭旧行。
- **验证阶段不参与判定校验** —— `phase` 是"在哪个执行序列位置验"，与判定结果无关；
  后端只做字典校验，不校验"前后阶段顺序"（材料 TABLE D-1 允许多次验证跨阶段）。
- **覆盖读数不统计"通过率"** —— 它只回答 I-1 的"有没有"，不回答"好不好"。
  判定为「不通过」的验证项**仍然算已覆盖**（需求确实被验证过，结论是不合格）——
  材料的矩阵语义如此（Result 列记录结论，不是"通过才算验过"）。
- **责任人尚未接候选** —— 仍是文本输入。`stakeholder` 已建成，要接只是挂一个 `datalist`
  （照 `requirement` 页 `FE-51` 的范式，值仍存文本姓名、不动契约）；本页本轮未接线。
- **不校验"需求是否已基线"** —— 规划下拉给全部需求（含未基线草稿，便于提前准备）；
  "已基线但未覆盖"的口径只体现在覆盖读数里（见 `应用详设.md` §6.3）。

## 8. 本轮踩到并修正的坑（记录）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | **编辑模态里「验证阶段」显示成「研制前声明阶段」**（实际存的是 `end_to_end`），而「验证方法」看起来是对的（纯属巧合 —— 它恰好是选项里的第一项） | 枚举 select 的选项由 `<template x-for>` 生成时，Alpine 的 `x-model`「数据 → DOM」回填是**一次性 effect**，**跑在 `x-for` 把 option 插进 DOM 之前**：`select.value = "end_to_end"` 当时无此 option、静默失败，随后插入 option 时 `selectedIndex` 落到 0。且回填 effect 的依赖（`modal.d.phase`）此后再不变 ⇒ **永不重跑**。用户看到错误的阶段、改别的字段保存时会把错的阶段一起写回 | 枚举 select 改为**静态 `<option>`**（`patterns.md` §4 的写法）—— 选项在模板克隆时就存在，与 effect 顺序无关。7 处枚举 select（筛选 2 + 模态 3 + 表单 2）全部改掉 |
| 2 | 详情里断言「方法/阶段」时 `inner_text()` 会把 `<select>` 的全部 option 文本吃进来 | 同上：`<select>` 的 `inner_text` 含未选中项 | 只读信息条与关键只读单元格加 `data-role`（`ver-head`/`ver-req`/`ver-evidence`/`ver-followup`），断言只读它们；需要读 select 的值时用 `input_value()` |
| 3 | 关闭 / 开始执行后断言「按钮已消失」假红 | 动作按钮用 `x-show` 隐藏（元素仍在 DOM，仅 `display:none`），`count()` 照样数到 | 选择器一律加 `:visible` |
| 4 | 「状态文本已变、动作按钮还没变」——等错了对象 | 状态单元格与行内动作按钮是 Alpine 的两处**独立绑定**，重渲染不在同一拍上；`wait_for_timeout` 后直接断言按钮会读到中间态 | 等待条件与断言对象**同一个**：`wait_text(row.locator("td").nth(4), "通过")` 轮询状态单元格，**断言用返回的那个快照**（不重新求值） |

> 坑 #1 是**结构性**的：同组既有的 `requirement` / `risk` / `configuration_item` 三个页面
> 的模态里也有「`<select x-model>` + `<template x-for>` 生成选项」的写法（如 `ci_type` / `category`），
> 同样存在"回填静默失败、显示停在第一项"的风险 —— 本页按 `patterns.md` §4 的静态选项写法绕开了它，
> **未改动那三个应用**（不属本次任务范围），在此记录以供后续统一处置。
