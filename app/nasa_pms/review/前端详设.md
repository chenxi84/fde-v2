# 前端详设：评审（review）

> 产出技能：第⑥步 前端设计（规格 `design-plus/前端设计.md`，规范正本 `VIEW_CONVENTION.md`）
> 输入：`应用详设.md`（US/FUNC/PERM/状态机/§6.3）+ `architecture.md`（聚合根卡 5，含「并入说明」）
> 后端契约**以 `review.py` 源码为准**（组级 `_contracts.md` 尚未收录本应用 —— 见 §7 限制）

---

## 1. 页面定位

| 项 | 内容 |
|---|---|
| key / name | `review` / 评审 |
| 一句话 | 评审台账：计划、登记评审项、启动、出结论（带行动项）、跟踪行动项、关闭，按类型/阶段/状态/结论筛选 |
| 数据来源类型 | **独立创建** —— 因此**保留「新建评审」入口**（与服务契约 `create` 对应） |
| `PAGE_META.order` | `650` —— **组内序不在此复抄**：真值 = 各页 `PAGE_META.order`，组级 view 测试的「菜单序」断言从 `PAGE_META` + `shell.js` 的 `PLATFORM_PAGES` **现算**。本行此前逐页复抄了一遍 —— 复抄必漂：2026-09-25 因 `order` 并列、平台按 key 字母序兜底，「配置项」被渲染到「风险」之前，而复抄的清单还把旧值当成了正确值（见 pitfalls #43）。 |
| 页面构成 | 主列表卡片 + **行动项汇总卡片**（跨评审查询视图）+ 三个模态（详情/编辑、出结论、新建） |

## 3. 交互规则（逐条对应后端约束）

| # | 规则 | 依据 |
|---|---|---|
| F-1 | 新建表单里**标题 / 类型 / 阶段 / 评审对象四项必填**，未齐时提交按钮禁用（类型与阶段**不给默认值**） | `BR-05` + 两个非空校验 |
| F-2 | **计划态不给「出结论」**：页脚只出现「启动评审」，并提示"先启动进入进行中" | 状态机守卫（`conclude` 要求 `in_progress`） |
| F-3 | 「出结论」是**独立模态**：结论必选、纪要选填、行动项按行增删；**任一已加的行动项必须填全**（内容/责任人/期限） | `BR-02` |
| F-4 | 结论选「**有条件通过**」且行动项为 0 条时提交禁用，并给出原因文案 | `BR-01`（前端镜像，后端仍是权威） |
| F-5 | 详情里**评审项清单与行动项都直接展示**（`get` 一次带回，不做二次请求） | `get` 返回 `items` / `actions` |
| F-6 | 状态为「已结论」「行动项跟踪中」时**行内「编辑」入口消失**；详情无「保存」、无「加评审项」 | `BR-06` 前半（结论是快照） |
| F-7 | 状态为「已关闭」时上述入口同样消失，详情提示「已关闭（终态）」 | `BR-06` 后半 |
| F-8 | 「关闭评审」在**行动项未清零**时禁用，并在详情给出「还有 N 条行动项未完成」（不是只藏按钮） | `BR-07` |
| F-9 | 状态机动作按钮**按当前状态显隐**：计划→[启动评审]；进行中→[出结论]；已结论/跟踪中→[关闭评审]；已关闭→无 | 状态机（§3.4 到达服务表） |
| F-10 | 行动项汇总按状态用 `fchip` 收敛（未完成/已完成/全部），行内可「完成」（二次确认）；完成后主列表的行动项计数同步刷新 | `BR-07` + `list_actions` |
| F-11 | 四个筛选下拉变化即刷新（重置到第 1 页）；列表默认按编号升序 | `US-08` |

## 4. 字段展示（业务名取自术语表，列名见后端）

| 列 / 字段 | 后端字段 | 展示 |
|---|---|---|
| 评审编号 | `review_no` | `mono` 等宽，点击开详情 |
| 评审标题 | `title` | 截断 240px |
| 评审类型 | `review_type` | **两行**：上行码（`PDR`）+ 下行中文全名（`初步设计评审（PDR）`）—— 台账要短码，业务名要全称 |
| 阶段 | `phase` | 中文字典映射（b→B 阶段） |
| 评审对象 | `subject` | 截断 200px |
| 依据计划 | `plan_no` | `mono`；空显示 `—`（**默认隐藏列**） |
| 状态 | `status` | `.st` 彩色徽标（计划/进行中/已结论/行动项跟踪中/已关闭） |
| 结论 | `conclusion` | `.st` 徽标（通过=green / 有条件通过=amber / 不通过=red）；空显示 `—` |
| 行动项 未/总 | `action_open` / `action_total` | `mono` 的 `未/总`（如 `1/2`）—— 一列看出"还剩几条" |
| 责任人 | `owner` | 空显示 `—` |
| 评审纪要 | `minutes` | 截断（**默认隐藏列**） |
| 关闭说明 | `close_note` | 截断（**默认隐藏列**） |
| 所属项目 | `project_no` | 空显示 `—`（**默认隐藏列**） |
| 评审项 | `items[].seq/item/criterion` | 只在详情模态的子表里（列表无此项） |
| 行动项 | `actions[].seq/content/owner/due_date/status` | 详情子表 + 汇总卡片 |

`col_default_hidden`：**"依据计划,评审纪要,关闭说明,所属项目"** ——
本页把 `list` 返回的**全字段都渲染成列**（CONVENTION §7：数据层给全字段，列自选才有东西可选），
非关键的四列默认隐藏，经平台「列设置」按需开启。
⚠ 与同组 `requirement` / `risk` / `configuration_item`（只渲染关键列）**不同口径**，本页取 CONVENTION 的正解。

## 7. 已知限制

- **`modal.d` 的空安全 helper 层**：模态里所有读取 `modal.d` 的绑定都走
  `isStatus / inStatus / stName / stCls / conclCls / conclName / frozenText / showCloseBlock / closeBlockText`
  这层 helper，模板里**不写裸 `modal.d.status`**。原因见 `前端测试用例.md` §8 的坑 1
  （`x-if="modal.d"` 的子绑定可能在 `openDetail` 把 `modal.d` 置 null 的那一拍被再求值一次）。
- **类型列显示两行**（码 + 全名）：台账列宽有限，短码可扫读；业务名（术语表的正式名）仍在同一格里，
  不丢可读性。
- **组级 `_contracts.md` 尚未冻结本应用** —— 本页的服务名/入参**逐字取自 `review.py` 的公共方法签名**
  （`create` / `add_item` / `start` / `conclude` / `close_action` / `close` / `update` / `get` /
  `list` / `list_actions`）；契约冻结应由第⑤步出口的统一 dump 完成（本任务范围不含改 `_contracts.md`）。
- **评审项不可删** —— `add_item` 没有对应的 `remove_item`（评审项清单是评审过程的留痕，加了就保留）；
  登记错了只能在结论前手工改正内容（当前也没有 `update_item`，属已知缺口：若需要，加一个
  字段白名单为 `item` / `criterion` 的服务即可）。
- **行动项不能改内容 / 期限** —— 只能「完成」（`close_action`）；要改期限得由后端加服务
  （属对外操作扩展，不是前端自造）。
- **没有批量完成行动项** —— 逐条「完成」，理由见 `应用详设.md` §6.3（跨评审批量写会越过聚合边界）。
