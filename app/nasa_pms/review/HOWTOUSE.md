# review 使用要点

**管什么**：一次技术评审 —— 评审项清单、结论，以及**与结论同事务产生**的行动项（并入本聚合，无独立标识）。跨评审的「行动项汇总」走 `list_actions` 查询视图。回答「哪些评审还没结论、还欠哪些行动项」用它。

## 标准工作流（按此顺序）

1. `create` — 建评审，落「计划」，编号自动生成（`RV-001` 起）；标题 / 评审类型 / 阶段 / 评审对象必填
2. `add_item` — 逐条登记评审项（可带判据）；计划 / 进行中都可加，**清单为空不能出结论**
3. `start` — 启动：计划 → **进行中**（不能跳过它直接出结论）
4. `conclude` — 出结论（**唯一**写结论入口，也是行动项的唯一产生点）：进行中 → 有行动项落「行动项跟踪中」、无则落「已结论」；结论与行动项**同事务**落库
5. `close_action` — 逐条了结行动项（只在「行动项跟踪中」可动）
6. `close` — 关闭：已结论 / 行动项跟踪中 → **已关闭**（硬终态），要求行动项**全部完成**

查询：`list`（按类型 / 阶段 / 状态 / 结论 / 依据计划筛）→ `get`（含评审项与行动项明细）；`list_actions` 跨评审汇总行动项（按责任人 / 状态筛）。

## 前置条件与禁忌

- **状态闸与守卫顺序（负例的报错取决于它）**：`conclude` 依次查 —— 已关闭（终态）→ 已出过结论 → 非进行中（报「须先启动评审」）→ 结论字典 → **评审项清单非空** → 行动项逐条校验 → 结论为「有条件通过」必须给行动项。`close_action` 依次查 —— 已关闭 → 非跟踪中 → 序号不存在 → 该条已完成。
- **结论是快照**：`conclude` 之后主档内容与评审项清单**一起冻结** —— 不能再 `update`、不能再 `add_item`；此后唯一能变的只有「行动项跟踪中」下的行动项。
- **已关闭是硬终态**：关闭、修改、加评审项、动行动项**一律拒绝**；但记录仍在（不删除，含评审项与行动项）。
- **行动项只在「行动项跟踪中」能逐条关闭**：计划 / 进行中 / 已结论 / 已关闭都不行；**没有批量闭环的服务**，要一条条 `close_action`。
- **`plan_no`（依据计划）是弱引用**：只作**文本**存，可留空、可悬空 —— 本应用**不做任何跨应用校验**，别去 `tech_plan` 求证它是否存在。
- 字典：评审类型 `mcr/srr/sdr/pdr/cdr/sir/trr/prr/orr/frr/sar`；阶段 `pre_a/a/b/c/d/e`；结论 `pass/conditional/fail`。
- 行动项必须给**责任人与期限**（`YYYY-MM-DD`），期限上界不校验；序号 `seq` **只在本次评审内唯一**，跨评审操作必须带上 `review_no`。
- 结论 / 纪要**不在** `update` 的字段白名单里（只能经 `conclude` 写）；编号落库不可变。
- `get` 未命中返回 `None`，不抛异常。

## 出错时

读本应用详设（`doc` 取值见 `fde_platform/agent_common.py::_APP_DOC_FILENAMES`）；
**不要凭猜重试**——本应用的报错话术里都写着"缺哪一步"。
