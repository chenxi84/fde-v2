# 应用详设：进度活动（activity）

> 产出技能：第②步 应用设计（规格 `design-plus/应用设计.md`）
> 输入：`architecture.md` 聚合根卡 13 + 材料 `brd/SCH-第NN章-*.md`（NASA/SP-2010-3403 Rev 1）
> 依据说明：WBS 管"按什么分解"，本应用管"**什么时候做**" —— 材料 §4.3 说得很清楚：
> 任务与里程碑是**为最底层 WBS 元素**识别的，带 `duration / sequencing / responsibility /
> WBS coding` 进排程工具，汇成 IMS。

---

## 1. 应用概览

### 1.1 基本信息

| 项 | 内容 |
|---|---|
| 应用名 | `activity` |
| 类名 | `Activity` |
| 聚合根 | 进度活动（含里程碑） |
| 标识 | `act_no`（`ACT-001` 起，系统生成） |
| 数据来源类型 | **独立创建**（由项目团队把 WBS 叶子元素分解成活动与里程碑） |

### 1.2 应用背景

#### 1.2.1 为什么需要这个元素？

WBS 回答"要交付什么、按产品怎么分"，但它**不含日期** —— 材料 §4.3 把日期归给进度侧：
活动（tasks）与里程碑（events）挂在**最底层 WBS 元素**上，带工期与逻辑链进排程工具，
汇成 **IMS（Integrated Master Schedule）**。本应用就是那棵"活动网络"。

#### 1.2.2 期望达到什么目标？

- 一张**无开口端、无冗余链接、无环**的活动网络（横向可追溯，§5.5.8）
- **日期由逻辑与工期派生**，而不是为凑完成日填出来的（§5.5.9.3）
- 一次**基线**（冻住的时间相位）+ 之后的改动**受变更控制**，而**回填实绩不动基线**（§7.3）

### 1.3 应用范围

#### 1.3.1 包含哪些功能？

- 建活动与里程碑（`create` / `add_milestone`），挂到 WBS **叶子**元素上
- 逻辑链（`link` / `unlink`）与网络体检（`check_network`）
- 派生排程视图（`schedule_view`：正推日期 + 浮时）与关键路径（`critical_path`）
- 基线（`baseline`）与基线后修订（`change`）
- 回填实绩（`record_progress`）

#### 1.3.2 不包含哪些功能？

- **日历只做到"项目日历"这一层**：材料 §5.5.9.2 要求用"代表性日历"区分工作日与非工作日
  —— 本版建了**工作日历**（假日表 + 工期口径 `days` 工作日 / `edays` 日历天，§5.5.9.1），
  排程按它跳过周末与假日。**资源日历**（按人/按资源的日历）**仍不做** —— 那属资源加载
  （§5.5.12），在本版范围外（口径见 `术语表.md` 附「本版口径」#2）
- **不做资源与成本加载**（§5.5.12）、**不做资金时间相位**（§5.5.13）、**不做风险映射**（§5.5.14）
  —— 那三节要的资源/成本/风险台账不在本组范围内
- **不提供硬约束（constraints）**：§5.5.8 明说活动"不应被任意约束"，本版从建模上就不给这个入口
- **不管 WBS 元素本身**（属 `wbs`）：本应用只**挂靠**叶子元素，不维护分解

### 1.4 涉及角色

| 角色 | 职责 | 来源 |
|---|---|---|
| 进度工程师（P/S） | 建活动、连逻辑、估工期、维护与汇报进度 | §5.5.5 / §7.3（"P/S" 贯穿全篇） |
| 技术负责人（WBS 元素责任人 / CAM） | 与 P/S 一起定活动描述；对活动工期负责 | §5.5.5「work with the Technical Lead that is responsible for the activity」 |
| 项目经理（PM） | 批准进度基线 | §7.3（基线 = 经批准的时间相位计划） |
| 配置与变更管理员（CM） | 基线后的修订经其走变更 | §7.3「maintained … supported by CM/DM and controlled through the P/p's change control process」 |

## 2. 用户故事

### 2.1 核心用户故事

#### 2.1.1 `US-01` 建一个活动（优先级：P1）

作为**进度工程师**，我要把某个 WBS 叶子元素分解成一条带工期的活动。

- **验收**：必须挂**叶子**元素；工期 > 0；名称唯一
- **依据**：§5.5.7.1「The WBS is "decomposed" into discrete measurable tasks and milestones」；§5.5.5 唯一性

#### 2.1.2 `US-02` 建里程碑（优先级：P1）

作为**进度工程师**，我要在接口点 / 阶段结论处放一个里程碑。

- **验收**：里程碑工期恒为 0；可挂前置与后续
- **依据**：§5.5.7.1「These interface points, such as phase conclusions and giver/receiver "handoffs", are places in the schedule where milestones would be appropriate」

#### 2.1.3 `US-03` 连逻辑链（优先级：P1）

作为**进度工程师**，我要给活动连前置关系，让网络能横向追溯。

- **验收**：禁止冗余链接（A→B、B→C 时 A→C 冗余）；禁止成环；前置必须存在
- **依据**：§5.5.8「Network logic must be complete, accurate, and realistic」+ 冗余链接的原文例子

#### 2.1.4 `US-04` 网络体检（优先级：P1）

作为**进度工程师**，我要一键看出网络的问题：开口端 / 冗余 / 环 / 工期异常 / 关系不合法 /
挂靠非叶子，以及**哪些最底层 WBS 元素还没有活动**。

- **验收**：返回问题清单与计数；无问题时报「无」
- **依据**：§5.5.8「no "open ends"」；§6 的 assessment 精神（可机械判定的部分）；
  WBS 手册 §4「The lowest level of each WBS element should have at least one task or activity」

#### 2.1.5 `US-05` 看排程与关键路径（优先级：P1）

作为**项目经理**，我要看每条活动的派生日期、浮时与关键路径。

- **验收**：日期由工期与逻辑链**正推**得出；零浮时的链标为关键路径
- **依据**：§5.5.9.3（日期由 logic 与 durations 决定）；§5.5.10（识别关键路径）

#### 2.1.6 `US-06` 建立进度基线（优先级：P1）

作为**项目经理**，我要把选定的活动基线化，作为绩效测量的基准。

- **验收**：基线时把**派生日期**冻进 `baseline_start` / `baseline_finish`；只对传入的活动生效
  （材料允许"只基线化关键里程碑子集"）
- **依据**：§7.3「two general methods … Baseline the entire IMS / Baseline a subset …」

#### 2.1.7 `US-07` 基线后修订走变更（优先级：P1）

作为**进度工程师**，基线之后要改工期或逻辑，得先有已批准的变更。

- **验收**：已基线的活动改计划字段必须带已批准的变更号
- **依据**：§7.3「The schedule baseline … is controlled through the P/p's change control process」

#### 2.1.8 `US-08` 回填实绩（优先级：P1）

作为**进度工程师**，我要登记实际开始 / 完成与完成百分比。

- **验收**：`record_progress` **不修改任何基线字段**（材料原话：不动基线数据）
- **依据**：§7.3「This procedure does not change any baseline data within the Schedule Database but reports actuals and current performance against that baseline」

## 3. 业务场景

### 3.1 业务流程描述

#### 3.1.1 场景1：一段进度的诞生

`create` 建活动（挂 WBS 叶子）→ `link` 连逻辑链 → `check_network` 体检（无开口端/冗余/环）→
`schedule_view` 看派生日期 → `baseline` 冻住基线 → 工作做了 → `record_progress` 回填实绩
（基线不动）→ 需要改工期时 `change`（带已批准的变更号）→ 改完再 `baseline` 重新冻基线。

#### 3.1.2 场景2：与 WBS 的边界（跨应用）

本应用**只读** `wbs`：建活动时校验"挂靠的元素存在**且是叶子**"（`wbs.get` + 查有无子元素）。
WBS 元素被关闭 / 分解出新子元素后，原本挂它的活动就**不再合规** —— `check_network` 会把
"挂到了非叶子元素"列出来（不自动搬家：搬哪去是人的判断）。

### 3.2 业务规则

#### 3.2.1 `BR-01` 禁开口端

- **规则描述**: 除两个**边界里程碑**（`phase == "start"` / `phase == "finish"`）外，每个活动与里程碑
  都必须**至少一个前置、至少一个后续**。边界里程碑只有单向（起始无前置、完成无后续）
- **适用场景**: 建活动、连逻辑、网络体检
- **计算方式**: 图论校验（入度/出度）
- **依赖输入**: `[act_no(实体字段), predecessors(实体字段), phase(实体字段)]`
- **输出**: `activity.phase`（起始/完成边界里程碑的标记落库）
- **生效点**: `activity.check_network → 报出` / `link → 校验` / `create → 校验`
- **示例**: 建了一个活动谁都不连 → 体检报「开口端」
- **依据**: 材料 §5.5.8「Every milestone and activity in the schedule should have at least one
  predecessor and at least one successor (i.e., no "open ends")」

#### 3.2.2 `BR-02` 逻辑链的写法：四类型 + 滞后 + 非 FS 给理由 + 禁冗余

- **规则描述**: 每条前置关系由 **关系类型（FS/SS/FF/SF 四值枚举）+ 滞后（整数天，可负=lead）
  + 理由** 三部分构成；**非 FS 必须写理由**（材料要求把非标准依赖的缘由记进 BoE）；
  且**禁冗余链接**（A 已是 B 的前置、B 是 C 的前置时，再连 A→C 即冗余）
- **适用场景**: 连逻辑、建活动时一次性给出前置、改逻辑链
- **计算方式**: 枚举校验 + 整数校验 + 理由非空校验 + 传递闭包校验
- **依赖输入**: `[predecessors(实体字段), predecessor_no/rel_type/lag_days/reason(服务实参)]`
- **输出**: `activity.predecessors`（结构化写法：`ACT-001` / `ACT-002:SS:2` / `ACT-003:FF:1:理由`）
- **生效点**: `activity.link → 校验` / `create → 校验` / `update → 校验`
- **示例**: `link(C, A)`（A→B→C 已存在）→ 拒绝「冗余链接」；
  `link(C, B, rel_type="SS")` 不带理由 → 拒绝「非标准关系必须写明理由」
- **依据**: 材料 §5.5.8.2「There are **four relationship models** for the activities: • Finish-to-Start (FS)…」
  与「a **finish-to-start relationship and a 5-day lag** will result in the successor task's start being
  delayed until 5 days after the completion of the predecessor」；
  以及「document the rationale for **non-standard dependencies** between activities (e.g., relationships
  other than Finish-to-Start), as well as the use of **leads, lags, or constraints**」；
  冗余链接见 §5.5.8 的原文例子

#### 3.2.3 `BR-03` 逻辑链完整且无环

- **规则描述**: 前置活动必须**存在**；连链后不得成环（有环就没有可行执行序）
- **适用场景**: 连逻辑、网络体检
- **计算方式**: 存在性校验 + 环检测
- **依赖输入**: `[predecessors(实体字段), predecessor_no(服务实参)]`
- **输出**: 无（拒绝：前置不存在或成环时拒绝，不产生新字段）
- **生效点**: `activity.link → 校验` / `create → 校验`
- **示例**: `link(A, C)` 造成 A→B→C→A → 拒绝「成环」
- **依据**: 材料 §5.5.8「Network logic must be complete, accurate, and realistic」—— 有环的网络
  连"有序执行"都谈不上

#### 3.2.4 `BR-04` 里程碑工期为 0，活动工期为正

- **规则描述**: `kind = milestone` 的工期必须为 0；`kind = activity` 的工期必须 > 0
- **适用场景**: 建活动、建里程碑、修改
- **计算方式**: 按类型的取值校验
- **依赖输入**: `[kind(实体字段), duration_days(实体字段)]`
- **输出**: `activity.duration_days`
- **生效点**: `activity.create → 校验` / `add_milestone` / `update → 校验`
- **示例**: `add_milestone(duration_days=3)` → 拒绝（里程碑是事件，不占工期）
- **依据**: 材料 §5.5.7.1（milestones 是 events，activities 是 tasks with durations）

#### 3.2.5 `BR-05` 活动必须挂在 WBS 的叶子元素上

- **规则描述**: `wbs_no` 必填，且该元素在 `wbs` 里**必须存在、且没有子元素**（叶子）——
  跨应用校验（`wbs.get` + 查该元素的子元素），**非同一事务**
- **适用场景**: 建活动、建里程碑、修改挂靠
- **计算方式**: 跨应用存在性 + 父子关系校验
- **依赖输入**: `[wbs_no(服务实参 —— wbs 提供)]`
- **输出**: `activity.wbs_no`
- **生效点**: `activity.create → 校验` / `update → 校验`
- **示例**: 挂到有子元素的 `400000`（父）→ 拒绝「请挂到最底层元素」
- **依据**: 材料 §4.3「Tasks and events are identified for the effort contained in **each
  lowest-level WBS element**」

#### 3.2.6 `BR-06` 活动名称唯一

- **规则描述**: 活动与里程碑的名称**全组唯一**（材料要求"描述必须唯一、可区分"）
- **适用场景**: 建活动、建里程碑、改名
- **计算方式**: 唯一性校验
- **依赖输入**: `[name(服务实参)]`
- **输出**: `activity.name`
- **生效点**: `activity.create → 校验` / `update → 校验`
- **示例**: 再建一条「装配舱板」→ 拒绝「已存在同名活动」
- **依据**: 材料 §5.5.5「In order to describe the work to be accomplished without ambiguity,
  activity and milestone descriptions need to be unique」
  > ⚠ 材料另有一条**语言学**约定（离散活动名含动词、汇总活动名不含动词）—— 机械判不了，
  > 只写进 `HOWTOUSE.md` 提示，**不做成闸门**（口径见 `术语表.md` 附 #3）

#### 3.2.7 `BR-07` 基线后修订走变更流程

- **规则描述**: 已基线（`baseline_start` 非空）的活动，改**计划字段**（工期 / 前置 / 挂靠 / 名称）
  必须走变更：先 `change(act_no, change_no)` 挂上**已批准**的变更号，再 `update`
- **适用场景**: 修改计划字段
- **计算方式**: 按基线标志拦截 + 跨应用状态校验
- **依赖输入**: `[baseline_start(实体字段), change_no(上游服务实参 —— change_request 选择已批准的变更)]`
- **输出**: `activity.change_no`
- **生效点**: `activity.update → 校验` / `change → 校验`
- **示例**: 对已基线活动直接 `update(duration_days=20)` → 拒绝「必须走变更流程」
- **依据**: 材料 §7.3「The schedule baseline … is maintained through routine updates supported by
  CM/DM and **controlled through the P/p's change control process**」

#### 3.2.8 `BR-08` 回填实绩不动基线

- **规则描述**: `record_progress` 只写 `actual_start` / `actual_finish` / `percent_complete` / 状态，
  **绝不修改** `baseline_start` / `baseline_finish` / `duration_days` / `predecessors`
- **适用场景**: 回填实绩
- **计算方式**: 服务分工（写集合固定，且不含基线列）
- **依赖输入**: `[percent_complete(服务实参), baseline_start(实体字段)]`
- **输出**: `activity.percent_complete` / `activity.actual_start` / `activity.actual_finish`
- **生效点**: `activity.record_progress`
- **示例**: 回填 100% 后，该活动的 `baseline_start` **一字未变**
- **依据**: 材料 §7.3「This procedure **does not change any baseline data** within the Schedule
  Database but reports actuals and current performance against that baseline」

### 3.3 业务数据

| 字段 | 类型 | 必填 | 说明 | 依据 |
|---|---|---|---|---|
| `act_no` | string | 是 | 活动编号（`ACT-001` 起，系统生成），主键 | §5.5.5 |
| `name` | string | 是 | 名称（全组唯一） | §5.5.5 |
| `kind` | string | 是 | `summary` / `activity` / `milestone` | §5.5.5 |
| `phase` | string | 否 | 边界标记：`start` / `finish`（只有这两个可以单向前置/后续） | §5.5.8 |
| `wbs_no` | string | 是 | 挂靠的 **WBS 叶子元素**（跨应用弱引用） | §4.3 / §5.5.7 |
| `duration_days` | integer | 是 | 工期（**工作日**）；里程碑恒 0 | §5.5.9 |
| `predecessors` | string | 否 | 逻辑链，结构化写法 `编号[:类型[:滞后[:理由]]]`，逗号分隔 | §5.5.8.2 |
| `owner` | string | 否 | 责任方 | §5.5.5 |
| `status` | string | 是 | `planned` / `in_progress` / `completed` | — |
| `percent_complete` | integer | 是（默认 0） | 完成百分比 | §7.3 |
| `actual_start` / `actual_finish` | string | 否 | 实绩日期（`record_progress` 写） | §7.3 |
| `baseline_start` / `baseline_finish` | string | 否 | 基线日期（`baseline` 时由派生日期冻住） | §7.3 |
| `change_no` | string | 否 | 基线后修订挂的变更号 | §7.3 |
| `note` | text | 否 | 备注（材料提到 IMS 的 notes 字段记来源） | §5.5.6 |

> ⚠ **表里没有"计划开始 / 计划完成"** —— 那是**派生量**（由工期与逻辑链正推），见
> `schedule_view()`。材料 §5.5.9.3 的要求正是"日期由逻辑与工期决定，而不是为了凑某个完成日"。

### 3.4 状态机

```
计划 planned ──record_progress(开工)──▶ 进行中 in_progress ──record_progress(完成)──▶ 已完成 completed
     ▲                                          │                                        （终态）
     └────────── 返工：record_progress(percent<100) ─┘
```

| 迁移 | 触发服务 | 闸门 |
|---|---|---|
| ∅ → `planned` | `create` / `add_milestone` | BR-01 前置存在 · BR-03 无环 · BR-04 工期 · BR-05 叶子 · BR-06 唯一 |
| `planned` → `in_progress` | `record_progress`（给了 `actual_start` 或 `percent>0`） | BR-08 不动基线 |
| `in_progress` → `completed` | `record_progress`（`percent=100` 且给了 `actual_finish`） | BR-08 不动基线 |
| `completed` → `in_progress` | `record_progress`（`percent<100`） | 返工；同样**不动基线** |

> **基线是正交维度**：`baseline_start` 非空即"已基线"，它不改 `status`。
> 计划字段的改动由 BR-07 拦（要变更号），与状态机无关。

## 4. 功能描述

### 4.1 功能清单

| # | 服务 | 用途 |
|---|---|---|
| 1 | `create` | 建活动（挂 WBS 叶子） |
| 2 | `add_milestone` | 建里程碑（工期恒 0 的便捷入口） |
| 3 | `get` / `list` | 查活动（按状态 / 类型 / 挂靠元素 / 责任方筛，分页） |
| 4 | `update` | 改计划字段（基线后须变更号） |
| 5 | `link` / `unlink` | 连 / 断逻辑链 |
| 6 | `check_network` | 网络体检：开口端 / 冗余 / 环 / 工期 / 关系不合法 / 非叶子挂靠 / **叶子无活动** |
| 7 | `schedule_view` | **派生排程**：正推日期 + 浮时 + 关键路径标记 |
| 8 | `critical_path` | 只取关键路径（零浮时链） |
| 9 | `baseline` | 建立进度基线（把派生日期冻住） |
| 10 | `change` | 基线后修订（须带已批准的变更号） |
| 11 | `record_progress` | 回填实绩（**不动基线**） |
| 12 | `create_calendar` / `update_calendar` / `get_calendar` / `list_calendars` | 工作日历：假日表 + 工期口径（days / edays） |

### 4.2 功能模块结构图

```
activity（聚合根 = 进度活动）
├── 活动网络     create / add_milestone / update / link / unlink
├── 排程计算     schedule_view（正推+浮时）/ critical_path / check_network
├── 基线与变更   baseline / change
├── 实绩         record_progress（只写实绩，不碰基线）
└── 检索         get / list
      ├──▶ wbs.get + wbs.list（挂靠叶子校验，跨应用只读）
      └──▶ change_request.get（变更已批准校验，跨应用只读）
```

### 4.3 功能详细说明

- **`check_network`**：一次读全表在内存建图，报五类**图论 / 格式**问题 —— 开口端（非边界活动的
  入度/出度为 0）、冗余链接（直接边被传递闭包包含）、环、工期异常（里程碑工期 ≠ 0 / 活动工期 ≤ 0）、
  关系不合法（类型不在四值里 / 非 FS 没写理由）。另报两类**跨应用**问题（都读 `wbs`）：
  ① **挂靠非叶子** —— 元素下面长了新子元素，原本挂它的活动不再合规；
  ② **叶子无活动** —— 还空着的最底层元素（材料 WBS 手册 §4 的反方向判据；只报**未收口**的元素，
  已关闭的不再要求补活动）。⚠ 这一类是**报告项不是闸门**：它拦不住任何一次写入（建活动本就不必
  依赖别的活动存在），所以只能做体检，不能做 BR。
- **`schedule_view`**：按 `project_start`（服务实参，默认取全网络最早的可开工日）与**工作日**正推 ——
  每条活动的最早开始 = 其前置的最早完成之最大值；浮时 = 最晚开始 − 最早开始；浮时为 0 的标关键路径
- **`baseline`**：对传入的 `act_nos` 逐个把 `schedule_view` 算出的日期写进 `baseline_start/finish`；
  已在基线里的活动重跑会覆盖（= 变更落实后的重新冻基线）
- **`record_progress`**：写集合**固定为**实绩与百分比 + 派生出的状态；**基线列不在写集合里**（BR-08）

## 6. 验收标准

### 6.1 功能验收标准

| # | 验收项 | 判据 | 对应用例 |
|---|---|---|---|
| 1 | 编号与名称 | 编号系统生成；名称重复被拒 | `TC-01` / `TC-12` |
| 2 | 工期规则 | 里程碑 0、活动 > 0 | `TC-03` / `TC-13` |
| 3 | 叶子挂靠 | 非叶子元素被拒（跨应用） | `TC-12b` |
| 4 | 逻辑链 | 前置存在 / 无环 / 禁冗余 | `TC-05` `TC-06` `TC-07` `TC-09` |
| 5 | 派生排程 | 日期由工期与逻辑正推；零浮时标关键路径 | `TC-10` `TC-11` |
| 6 | 基线 | 基线时冻住派生日期 | `TC-14` |
| 7 | 变更闸门 | 已基线后改计划字段须已批准变更号 | `TC-16` `TC-17` `TC-18` |
| 8 | 实绩不动基线 | 回填后基线列一字未变 | `TC-20` `TC-21` |
| 9 | 网络体检 | 七类问题都能报出（含**叶子无活动**的进/出报告） | `TC-05` `TC-13` `TC-22` `TC-36` |
| 10 | 契约形状 | `list` 返回 `{items,total}` | `TC-24` |

### 6.2 非功能验收标准

- 分页默认与同组其它应用一致（`page` / `size`，返回 `{items, total}`）
- 全部失败路径 `raise FdeError("人话")`，跨调用原样传播
- 排程计算在**内存**完成（一次读全表建图），不按层往返查库

### 6.3 已知问题或限制

- **不做资源 / 成本加载、资金时间相位、风险映射**（§5.5.12–5.5.14）
- **"活动名要含动词"不机械校验**（口径 #3）
- **资源日历不做**：只有项目级的**工作日历**（假日表 + 工期口径）；按人/按资源的日历属资源加载（§5.5.12）
- **不做约束（constraints）**：材料把 constraints 与 leads/lags 并列提到，但本版从建模上就不给硬约束入口
- **汇总活动也只能挂叶子元素**：材料里 IMS 的汇总活动通常卷起**跨多个 WBS 元素**的一批活动、对齐到 WBS
  的**汇总元素**；本版为统一约束（`_need_leaf` 对 `kind` 一视同仁，少一个特例）要求汇总活动同样挂叶子，
  于是"汇总"实际只能卷**同一条叶子下**的活动 —— 语义比材料的窄
- **关系理由存在**predecessors 字符串**里**（第 4 段）：理由里不能出现**冒号**（会被当成第 5 段并报错）
  或**半角逗号**（会被当成分隔符）—— 全角逗号 `，` 是合法字符
