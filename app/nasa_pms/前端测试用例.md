## §0 测试数据字典（冻结 · 组级最小集）

| 别名 | 类型 | 造数服务 | 关键参数 |
|---|---|---|---|
| REQ-001 | 需求（受限会话 VT-PERM-03 隐式放行断言 + 看板非零读数用） | `requirement.create` | `title=系统需求A, statement=…, req_type=system, verify_method=test` |

> 说明：
> - **看板不做零值兜底豁免**：本组看板不做「失败即 0」的静默降级（`svc(..., {quiet:true})` 只压 toast，
>   形状不对仍会红），故 VT-DASH-01 **同时断言非零读数**（REQ-001 落库后 `对象总数 == 1`），
>   比只断「渲染出来了」多一层——**空库时 KPI 全 0 也能过**的写法等于没测数据通路。
> - **造数在进入业务页之前完成**（登录页同源 fetch 播种）：看板是默认落地页，页一打开就拉 11 个 `list`，
>   落在看板渲染之后再播种只会读到 0。
> - **受限角色 / 用户不在浏览器造**：`limited_role` + `limited_nasa` 经 `fde_platform.users` 在平台子进程启动前播种
>   （平台无建用户端点），照第⑨步范式。
> - **影子库起点为空表**：`shadow_clear("nasa_pms")` + `shadow_clear_prefs()` ⇒ 本组 11 个业务库在脚本内全空，
>   故 REQ-001 是本组**唯一**一条数据，KPI 期望值可精确到 `1/0/0/0`。

## §1 壳与菜单 / dashboard

### VT-SHELL-01 壳启动与菜单序

- **页面**：`nasa_pms:dashboard`（壳启动，覆盖全部页面菜单序）
- **前置造数**：无（登录 admin 即可）
- **操作**：登录 admin → `GET /view/nasa_pms/` → 等侧栏 `.rail .nav-item` 渲染
- **断言**：
  - 侧栏品牌 `.brand .name` 文本 == `FDE·NASA_PMS`（`boot_manifest` 约定推导 `FDE<em>·</em>NASA_PMS`）
  - 栏首为**平台置顶页** `AI管家`（`shell.js` 的 `PLATFORM_PAGES` 里 `workbench` 带 `top: true`，
    按 `[...top, ...biz, ...rest]` 拼装 ⇒ 排在全部业务页之前）
  - 其后为**业务页 12 项**，按 `PAGE_META.order` 升序：

| 序 | key | order | 菜单中文名 |

| — | （平台置顶） | — | AI管家 |
| 1 | dashboard | 1 | 系统工程看板 |
| 2 | process | 5 | 流程总览 |

| 3 | risk | 620 | 风险 |

| 11 | tech_plan | 700 | 技术计划 |
| 12 | stakeholder | 710 | 利益相关者 |
| 13 | wbs | 720 | WBS |

- **⚠ 期望表不手抄**：`verify_view_nasa_pms.py` 的 `EXPECTED_MENU` **从页面自己声明的 `PAGE_META` 现算**
  （扫 `app/nasa_pms/*/view.js` + `app/nasa_pms/*.js`），平台置顶页从 `view/lib/shell.js` 的 `PLATFORM_PAGES` 现算。
  上表是**人读的快照**。手抄会漂——PSC 那份漂了三处（漏页 + 序位错 + 没算平台置顶页）。

- **§7 订正 #1（本轮）**：本表在原稿中 `risk` / `configuration_item` **同为 620**、`change_request` / `review` /
  `verification` **同为 630**、`decision` / `interface` **同为 640** ⇒ 平台排序键是
  `(order 缺省, order, key)`（`view_registry.boot_manifest`），**并列时静默按 key 字母序**落位 ——
  实测菜单把「配置项」排到了「风险」前面，**与 `architecture.md` ① 聚合根清单总表声明的序（风险在配置项之前）矛盾**。
  处置：把 11 页的 order 重排为 **610 起、步长 10、逐页唯一**（610/620/630/…/710），
  令菜单序与架构声明序一致。**不是**去改平台排序键。详见 `pitfalls.md #43`。

### VT-DASH-01 看板页渲染与读数

- **页面**：`nasa_pms:dashboard`（默认落地页）
- **前置造数**：REQ-001（在进入本页之前播种）
- **操作**：`GET /view/nasa_pms/` → 等 `main .kpi` 可见 → 等 300ms 收敛
- **断言**：
  - `.kpi` 卡 == **6** 张（需求总数 / 已基线需求 / 待评审需求 / 未了结告警 / 审批中变更 / 缓解中风险）——每张的 `.v` 是**可点按钮**（与 PSC 同款），点第一张 → `#/requirement`
  - 主区文本含「**各应用状态分布**」
  - `.pipe-col` == **7** 段（4 个职能域 + 3 列待办），主区文本含「四个职能域」「待办队列」
  - **非零读数**：`[1,0,0,0,0,0]`（影子库只播了 REQ-001 ⇒ 只有「需求总数」为 1）；「需求与验证」段内出现「草稿」
  - **状态必须中文**（2026-09-25 修）：主区文本含「草稿」且**不含**英文原文 `draft` —— 原来 10 个应用的字典是空的，界面显示 `draft`/`baselined`
- **为什么断读数**：本组看板**不吞错**（形状不对就红），但「渲染出来了」不代表数据通路通 ——
  KPI 全是 `0` 也能渲染出 4 张卡。断到 `1/0/0/0` 才证明 11 个 `list` 的聚合真的跑通了。
- **已知限制（非缺陷）**：看板对 11 个应用**逐个调 `list`**，而 `svc(a.app, …)` 的应用名是**变量** ⇒
  静态扫描器派不出「页→服务」边 ⇒ 受限用户（仅授 `nasa_pms:dashboard` + `nasa_pms:requirement`）打开看板时，
  未授权应用的 10 次 `list` 会拿到 **HTTP 403**，看板上表现为 0。
  这是**全组一致**的平台行为（PSC 同样如此），本组不单独放宽；`quiet:true` 已压掉 toast，用户不见报错。

## §1b 流程总览（组级页 · 2026-09-25 补，仿 PSC 的 `VT-PROCESS-01`）

> 页面：`#/process`（`app/nasa_pms/process.js` + `process.html`，无后端应用的组级聚合页）。
> 拓扑与 PSC 不同：**四个职能域**（与 `_roles.py` 的四个角色同构），域内是一条小链。

| 编号 | 用例 | 预期 |
|---|---|---|
| `VT-PROCESS-01` | 打开 `#/process` | 渲染出 SVG（`[data-role="process-svg"] svg`）；**4 个域胶囊 + 11 个应用节点**（= 组内 11 个聚合根，一个不漏）；图例含「绿 / 灰」说明 |
| `VT-PROCESS-02` | 节点读数 | 每个节点的摘要来自**该应用自己的服务**（如需求节点含「已基线 N」、技术度量节点含「未了结告警 N」）—— 不是硬编码 |
| `VT-PROCESS-03` | 点节点/域名 | 跳到对应台账（`location.hash` 变 `#/<应用>`，事件委托靠 `data-page`） |
| `VT-PROCESS-05` | **文字不得溢出节点/胶囊**（机械判据） | 逐个量 `text.getBBox().width` 与其所在 `rect` 的 width：**无一超出 `rect - 20px`**（溢出即版面坏了；「字太大 / 串行」肉眼能看出、不写断言就抓不到 —— 2026-09-25 用户实测反馈过一次） |
| `VT-PROCESS-06` | **无横向滚动条** | `.scroll-x` 的 `scrollWidth <= clientWidth`（画布过宽会出现横向滚动条 —— 2026-09-25 用户实测反馈过一次；尺寸按「两列自然放得下」设计，且 SVG **不放大、可缩小**） |
| `VT-PROCESS-06b` | **右栏收起时不得被放大**（反面） | 收右栏后内容区变宽（~1000px）：画布渲染宽 ≤ 自然宽（`max-width` 封顶） ⇒ 不放大、不出横向滚动。**两条一起才守得住**：只封上限会在窄容器出滚动条、只放下限会在宽容器把字放大 |
| `VT-PROCESS-04` | 「已声明的流程」表 | 列出本组**全部** `_flow_*.yaml`（当前 3 条），每条显示节点数与「智能体 N / 直调 N」构成；有「去流程编排页」入口 |

> ⚠ 流程的**执行**不在本用例范围（`agent` 节点需 LLM）：本页只断言**声明与渲染**。
> 执行半的验证方式见 `app/nasa_pms/_flow_*.yaml` 与 `pitfalls #47`（真跑一次）。

## §5 受限用户菜单收敛

受限角色 `limited_role` 授权页：`nasa_pms:dashboard`、`nasa_pms:requirement`、`_platform:workbench`。

### VT-PERM-01 菜单收敛

- **操作**：以 `limited_nasa` 登录 → `GET /view/nasa_pms/` → 等 `.rail .nav-item`
- **断言**：侧栏菜单 == `['AI管家', '系统工程看板', '需求']`（**精确等值**，不是「包含」）

### VT-PERM-02 直访无授权 hash 路由回落

- **操作**：`location.hash = '#/risk'`（未授权页）→ 等 1200ms
- **断言**：`header.top h1` 文本 == `EXPECTED_MENU[0]`，即**菜单首项** ——
  现算是 `AI管家`（平台置顶页排业务页之前，`shell.js` 的 `syncRoute` 回落 `menu[0]`）。
  `syncRoute` 渲染回落页但**不回写 `location.hash`** ⇒ 断言渲染内容，不断 hash。
- **不写死中文名**：`view/lib/shell.js` 是平台公共基座（只 import 不改），平台置顶页变更时本断言应
  跟着**现算值**走，而不是跟着快照走。

### VT-PERM-03 隐式放行有数据

- **操作**：`location.hash = '#/requirement'`（已授权页）→ 等 `button.b-link.mono:has-text("REQ-001")`
- **断言**：行首编号按钮回显 `REQ-001`（≥1 个）
- **测的是什么**：需求页源码里是**字面量** `svc("requirement", "list", …)` ⇒ 扫描器派生出
  `requirement.list` 边 ⇒ 该页可经 `X-Fde-Page` 头**隐式放行**，无需个人特授服务级权限。

## §6 0 报错红线（本会话）

- **硬指标**：0 console error · 0 pageerror · 0 HTTP≥400
- **豁免仅三类**：`/favicon.ico`、`.map`、**受限会话的 403**（预期执法）。
- **豁免也要受检**：收集到的 `ignored` 逐条核对豁免理由是否成立，
  否则任何新形态的 4xx / console error 都能混进来而无人发现（PSC 2026-09-17 补的那条纪律）。
