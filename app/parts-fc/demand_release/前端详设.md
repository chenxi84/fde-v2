# demand_release（需求发布）前端详设
> 来源：app/parts-fc/_contracts.md（冻结契约）+ app/parts-fc/demand_release/应用详设.md；产出供第⑦步前端编码 / 第⑧步前端测试用例
> 落位：`app/parts-fc/demand_release/view.js` + `app/parts-fc/demand_release/view.html`（与 `demand_release.py` 同文件夹，落盘即进启动清单与授权清单，零接线）；import 一律绝对路径 `/view/lib/*`；模板经 `new URL("view.html", import.meta.url)` 抓取；工厂 `export default function pageDemandRelease()`（保留专名）

## 1. 页面元数据 PAGE_META

| 字段 | 值 | 说明 |
|---|---|---|
| key | `demand_release` | = 应用文件夹名，page_id 为 `parts-fc:demand_release` |
| name | 需求发布 | 侧栏菜单名 |
| ic | 🚀 | 菜单图标字 |
| title | 毛需求发布 | 主区页面头 |
| crumb | 加工链终点 · 消耗量+事件=发布量 · R版冻结·唯一出口 | 头部副题 |

- 页面零鉴权：无任何权限判断；菜单按页面授权渲染在 shell，数据范围由后端闸门执法，401 由 api.js 自动跳登录。
- 本应用契约**无 update / delete / import_batch** → 无编辑入口、无删除按钮；单据变更仅经状态机动作（create_draft / add_line / checklist_verify / publish / revise）。
- `rel_qty` 由系统强制计算（= cons_qty + Σ event_items.qty），前端仅展示、不进表单（BR-02）。

## 2. 区块构成

### 2.1 列表区（查）—— 三段式：过滤条 / 表格 / 分页条

**用途**：发布单台账，按版本/状态筛选，承载行内状态流转动作（校验/发布/修订/版本比对）。

**过滤控件（与 `demand_release.list(rel_version, status)` 可过滤参数一一对应；契约无 keyword 参数 → 不设关键字搜索框，禁止前端假过滤）**：

| 控件 | 对应参数 | 选项 |
|---|---|---|
| 发布版本输入 | `rel_version` | input，格式 R+YYYYMM(.x) |
| 状态 chips | `status` | 全部 / 草稿 / 待发布 / 已发布 / 已替代（BR-10 枚举，原值传参） |
| 分页 | `page` / `page_size` | `pageable()` 分页条（契约签名 string 型，照传即可） |

**表格列（`.tbl.tight` + `.scroll-x`；全部为详情字段子集；字段序与详情/表单一致）**：

| 列 | 字段 | 渲染 |
|---|---|---|
| 发布单号 | `rel_no` | `.b-link`，点击开详情模态 |
| 发布版本 | `rel_version` | 正文，R版号 |
| 锚定期间 | `base_period` | YYYY-MM |
| 前版本 | `prev_version` | 正文，空值 `dash()` |
| 状态 | `status` | `hue()` 徽章（草稿/待发布/已发布/已替代） |
| 发布人 | `publisher` | 正文，空值 `dash()` |
| 发布时间 | `publish_date` | `fmtTime()`，空值 `dash()` |
| 创建时间 | `created_at` | `fmtTime()` |
| 操作 | — | 按 `status` 的行内动作，`x-show`（见 §5.1） |

**交互**：任一过滤变化 → 重置回第 1 页重载；状态动作成功后刷新当前页；空结果显示空态文案（不喷 toast）。

### 2.2 详情模态（查全）—— 三段式：墨青头带 + 状态徽章 / KV 分组体 + 明细子表 / 状态操作页脚

**用途**：点 `rel_no` 弹出，展示 `demand_release.get` 返回的**全部**业务字段（单头 + 明细）。

| 分组（`.sec`） | 字段 | 渲染 |
|---|---|---|
| 头带 | `rel_no` + `status` 徽章 | 墨青头带，徽章 `hue()` |
| 基本信息 | `rel_no` / `rel_version` / `base_period` / `prev_version` | `.kv`；`rel_no` 注明「系统生成 · 全局唯一」；`prev_version` 空值 `dash()` 注明「首次发布」 |
| 发布信息 | `publisher` / `publish_date` | `.kv`；`publisher` 注明「须为总部计划角色」；空值标注「待发布」 |
| 发布明细（子表） | 见下方明细子表 | `.tbl.tight` 子表格，含构成列示（cons_qty + event_items → rel_qty） |
| 时间信息 | `created_at` / `updated_at` | `fmtTime()`；`updated_at` 注明「状态变更时刷新」 |
| 原始数据 | get 返回全量 JSON | 底部折叠 |

**明细子表（`.tbl.tight`，get 返回的 detail lines）**：

| 列 | 字段 | 渲染 |
|---|---|---|
| 零件号 | `part_no` | 正文 |
| 客户·车型 | `veh_model` | 正文，通用件显示「多客户」 |
| 期间 | `period` | YYYY-MM |
| 消耗驱动量 | `cons_qty` | `fmt(0)`，注明「来自 D08 final_qty（终端口径）」 |
| 事件加项 | `event_items` | `tryParse()` 展开为 [{event_no, qty}] 列表，空数组 `dash()`；注明「仅 D06 生效事件」（BR-03） |
| 发布量 | `rel_qty` | `fmt(0)`，加粗；注明「系统强制 = cons_qty + Σ event_items.qty，不可编辑」（BR-02） |
| 拆回量 | `split_qty` | `tryParse()` 展开为 [{oem_code, qty}]，空值 `dash()`；注明「通用件客户拆回量」 |
| 主要依据 | `basis` | `.cell-ellipsis` 省略，空值 `dash()`；注明「基线来源+修正核对要点+客户对齐结论」（BR-05） |
| 链路线索 | `lineage` | `tryParse()` 展开为 {proc_batch, agg_no?, bw_no}，标注「D04→D07→D08 可追溯」 |

**交互**：页脚 `.modal-ft` 按当前状态放状态机按钮（逻辑同 §5.1，与行内动作共用一处 `x-show` 判定）；动作成功后用返回对象原地刷新模态字段 + 列表行。

### 2.3 生成草稿表单（create_draft）—— 模态表单

**用途**：覆盖 `demand_release.create_draft` 接受的参数（base_period）。系统自动汇总 D04/D06/D07/D08 结果生成发布草稿。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `base_period` | input，placeholder=YYYY-MM | ★ 必填 | BR-10（M0 对应会计期间） |

- **不进表单**：`rel_no` / `rel_version` / `status`（系统生成）、明细行（系统自动汇总）、`publisher` / `publish_date`（发布时记录）、`created_at` / `updated_at`（系统写入）。
- 提交成功：toast 带出新 `rel_no` + 汇总条数 → 关闭模态 → 重置过滤重载列表（新发布单恒「草稿」）。
- 注明：草稿生成涉及跨 4 个聚合取数（D04/D06/D07/D08），响应可能较慢，提交按钮显示 loading 态。

### 2.4 添加明细行表单（add_line）—— 模态子表单

**用途**：覆盖 `demand_release.add_line` 接受的参数，用于草稿状态下向发布单逐行添加明细。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `rel_no` | 隐藏域（从当前发布单取） | ★ 必填 | — |
| `part_no` | input | ★ 必填 | BR-11（引用物料主数据） |
| `veh_model` | input | ★ 必填 | BR-11（通用件记「多客户」） |
| `period` | input，placeholder=YYYY-MM | ★ 必填 | BR-11（覆盖 M0~M+N） |
| `cons_qty` | input[type=number]，min=0 | ★ 必填 | BR-11（Decimal >= 0，来自 D08 final_qty） |
| `event_items` | textarea，placeholder=[{"event_no":"...","qty":...}] | ★ 必填 | BR-11（JSON 数组，仅 D06 生效事件；空数组传 `[]`） |
| `basis` | textarea | ★ 必填 | BR-11（基线来源+修正核对要点+客户对齐结论） |
| `lineage` | textarea，placeholder={"proc_batch":"...","bw_no":"..."} | ★ 必填 | BR-11（JSON 对象，链路线索） |
| `split_qty` | textarea，placeholder=[{"oem_code":"...","qty":...}] | 可选，收进「更多字段 ▾」折叠区 | BR-11（通用件客户拆回量） |

- 校验：必填红星 + toast 警告；`event_items` / `lineage` / `split_qty` 提交前 tryParse 校验 JSON 格式，非法 JSON → toast 提示且不发请求。
- 提交成功：toast「明细已添加」→ 关闭子表单 → 刷新已开模态明细子表。
- `rel_qty` 由系统强制计算 = cons_qty + Σ event_items.qty，前端不传。

### 2.5 版本修订表单（revise）—— 模态子表单

**用途**：覆盖 `demand_release.revise` 接受的参数，用于已发布版本产生子版本。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `rel_no` | 隐藏域（从当前发布单取） | ★ 必填 | — |
| `reason` | textarea | ★ 必填 | BR-06 / BR-07（修订原因充分；旧版标记「已替代」，新版含新 rel_no + rel_version） |

- 提交成功：toast「已生成修订版本 · REL…」→ 关闭子表单 → 刷新列表。

## 3. svc 字面量清单（授权派生依据——必须字面量 svc("应用","服务")）

| 区块 | 调用（应用.服务） | 参数 | 说明 |
|---|---|---|---|
| 列表区 | `svc("demand_release","list")` | `{rel_version, status, page, page_size}` | 过滤查询；空条件传 undefined 不带 |
| 详情模态 | `svc("demand_release","get")` | `{rel_no}` | 全字段详情（单头+明细+lineage） |
| 生成草稿表单 | `svc("demand_release","create_draft")` | `{base_period}` | 自动汇总 D04/D06/D07/D08 生成草稿；返回含 rel_no 的发布单对象 |
| 添加明细子表单 | `svc("demand_release","add_line")` | `{rel_no, part_no, veh_model, period, cons_qty, event_items, basis, lineage, split_qty}` | 添加发布明细行；rel_qty 由系统强制计算 |
| 行内 / 模态页脚 | `svc("demand_release","checklist_verify")` | `{rel_no}` | 执行五项校验；全部通过 → status=待发布；失败返回明细 |
| 行内 / 模态页脚 | `svc("demand_release","publish")` | `{rel_no}` | 正式发布·R版冻结；联动锁定 D04/D03 |
| 行内 / 模态页脚 | `svc("demand_release","revise")` | `{rel_no, reason}` | 版本修订；旧版→已替代，生成新版 R x.1 |
| 行内 / 模态页脚 | `svc("demand_release","version_diff")` | `{rel_no}` | 版本比对 R_n vs R_{n-1} 逐零件×期间差异 |

> 以上 8 处必须在 view.js 中以字面量逐项书写（可包在闭包里），**勿用变量拼名**——这是页面授权隐式放行派生扫描的唯一来源。

## 4. 数据来源与下拉

**本页无跨应用下拉**：列表过滤中 `status` 为固定枚举，不需从其他应用拉取主数据。

**契约 payload → 区块字段映射**：

| 来源 | payload 字段 | 去向 |
|---|---|---|
| `demand_release.list` 项 | rel_no, rel_version, base_period, prev_version, status, publisher, publish_date, created_at, updated_at | 列表区表格列（1:1） |
| `demand_release.get` | 单头字段（同上全量）+ 明细行数组 [{part_no, veh_model, period, cons_qty, event_items, rel_qty, split_qty, basis, lineage}] | 详情模态 KV 分组 + 明细子表 + 原始数据折叠 |
| `demand_release.create_draft` 返回 | 发布单对象（含 rel_no，status=草稿，明细已填充） | toast 展示 rel_no → 列表重载 |
| `demand_release.add_line` 返回 | 更新后的发布单对象（明细行新增） | 原地刷新已开模态明细子表 |
| `demand_release.checklist_verify` 返回 | checklist 结果（通过/不通过及明细） | 展示校验结果（通过 toast / 不通过列明细）→ 刷新列表+模态 |
| `demand_release.publish` 返回 | 发布单对象（新 status=已发布，publisher/publish_date 已记录） | 原地更新已开模态 + 列表行 |
| `demand_release.revise` 返回 | 新版发布单对象（含新 rel_no，新 rel_version，prev_version=旧版） | toast 展示新版 rel_no → 列表重载 |
| `demand_release.version_diff` 返回 | 差异视图（逐行旧值/新值/差异量/说明） | 弹出差异对比模态展示 |

**明细行 `event_items` / `split_qty` / `lineage` 为 `*_json` 字段**：详情模态中 `event_items` 用 `tryParse()` 展开为事件列表；`split_qty` 用 `tryParse()` 展开为客户拆回量列表；`lineage` 用 `tryParse()` 展开为链路线索 KV。列表区不展示这些 JSON 字段。

## 5. 交互要点

1. **按状态的行内动作（状态机，行操作列与模态页脚共用判定）**：
   - `status=草稿` → 【添加明细】【checklist 校验】；
   - `status=待发布` → 【发布】；
   - `status=已发布` → 【修订】【版本比对】；
   - `status=已替代` → 终态，无任何按钮（旧版永久保留，仅审计引用）（BR-07）。
   - 动作成功：toast（如「checklist 五项全部通过 · 已转待发布」「已发布 · R…」「已修订 · R…」）+ 刷新列表；非法流转由后端 FdeError 经 api.js 统一 toast，页面不硬编状态机校验。
2. **checklist 校验结果展示**：`checklist_verify` 返回后，全部通过 → toast 成功 + 刷新列表；部分失败 → 弹出结果模态列出五项逐项状态（PASS/FAIL）+ 失败明细（具体零件/事件/原因），方便定位修复（US-04-AC2/AC3/AC4）。
3. **版本比对模态**：点【版本比对】→ 弹出差异对比模态，展示 R_n vs R_{n-1} 逐零件×期间差异表（旧值 → 新值 + 差异量 + 修订原因），标记新增行/删除行/变更行（US-07-AC1）。
4. **明细子表**：在详情模态中以 `.tbl.tight` 子表格呈现，列含构成列示（cons_qty → + event_items → = rel_qty），`event_items` / `split_qty` / `lineage` 用 `tryParse()` 结构化展示。
5. **模态**：统一三段式；加载态等待消失后再断言内容；头带墨青 + `hue()` 状态徽章。
6. **折叠「更多字段 ▾」**：add_line 表单中 `split_qty` 收入折叠区。
7. **展示工具**：`hue()`（状态徽章）、`dash()`（空值）、`fmtTime()`（时间字段）、`fmt()`（数量字段）、`tryParse()`（event_items / split_qty / lineage JSON 字段）。
8. **toast**：生成草稿成功 / 明细添加成功 / checklist 通过 / 发布成功 / 修订成功 / 必填未填警告；其余错误一律由 api.js 统一呈现。
9. **JSON 校验**：add_line 表单 `event_items` / `lineage` / `split_qty` 提交前前端 tryParse 校验 JSON 格式，非法 JSON → toast 提示且不发请求。

## 6. 验收关注点（供第⑧步前端测试用例）

1. **路由渲染**：`#/demand_release` 挂载出列表三段式（过滤条 + 表格 + 分页条），**页面无 `.kpi`**（防看板挂载粘滞假过）；菜单「🚀 需求发布」按 order=110 定位。
2. **造数后列表有数据**：经 `demand_release.create_draft` 生成草稿 → 列表行数正确，rel_no / rel_version / base_period / status 列非空。
3. **过滤一一对应**：status=已发布 chips 仅已发布行；rel_version 输入筛选；无匹配显示空态且不抛错。
4. **模态全字段 + 明细子表**：点 rel_no 开模态，断言单头字段（rel_no / rel_version / base_period / prev_version / publisher / publish_date）全部可见；明细子表含 cons_qty / event_items（tryParse 展开）/ rel_qty / split_qty（tryParse 展开）/ basis / lineage（tryParse 展开）列 + 「原始数据」可展开。
5. **生成草稿落库**：create_draft 表单填 base_period → 提交 → 列表出现新发布单且 status=草稿（US-01-AC1）。
6. **添加明细落库**：草稿行【添加明细】→ 填 part_no / veh_model / period / cons_qty / event_items / basis / lineage → 提交 → 模态明细子表新增一行，rel_qty 系统计算正确（US-01-AC1）；event_items 非法 JSON → toast 警告且不发请求。
7. **checklist 校验**：草稿行【checklist 校验】→ 全部通过 toast + status→待发布（US-04-AC1）；部分失败 → 结果模态列五项 PASS/FAIL + 失败明细（US-04-AC2/AC3/AC4）。
8. **发布操作回显**：待发布行【发布】→ status=已发布，publisher + publish_date 非空（US-05-AC1）；草稿行点发布 → 后端拒绝 toast（US-05-AC2）。
9. **修订操作回显**：已发布行【修订】→ 填 reason → 旧版 status=已替代，列表出现新版 R x.1（US-06-AC1）。
10. **版本比对**：已发布行【版本比对】→ 弹出差异对比模态展示逐行差异（旧值→新值+差异量+修订原因）（US-07-AC1）。
11. **干净控制台**：全程 0 console error / 0 pageerror / 0 HTTP≥400（受限会话 403 属预期执法单独豁免）。
