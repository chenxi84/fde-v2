# demand_processing（需求加工）前端详设
> 来源：app/parts-fc/_contracts.md（冻结契约）+ app/parts-fc/demand_processing/应用详设.md；产出供第⑦步前端编码 / 第⑧步前端测试用例
> 落位：`app/parts-fc/demand_processing/view.js` + `app/parts-fc/demand_processing/view.html`（与 `demand_processing.py` 同文件夹，落盘即进启动清单与授权清单，零接线）；import 一律绝对路径 `/view/lib/*`；模板经 `new URL("view.html", import.meta.url)` 抓取；工厂 `export default function pageDemandProcessing()`（保留专名）

## 1. 页面元数据 PAGE_META

| 字段 | 值 | 说明 |
|---|---|---|
| key | `demand_processing` | = 应用文件夹名，page_id 为 `parts-fc:demand_processing` |
| name | 需求加工 | 侧栏菜单名 |
| ic | ⚙ | 菜单图标字 |
| title | 毛需求加工 | 主区页面头 |
| crumb | 核心加工 · 统计基线→销售修正→修正核对 · 核定毛需求 | 头部副题 |
| order | 50 | 已按业务序预分配，直接用；升序即菜单序 |

- 页面零鉴权：无任何权限判断；菜单按页面授权渲染在 shell，数据范围（销售仅本人负责零件）由后端闸门执法，401 由 api.js 自动跳登录。
- 本应用为复杂加工聚合页——五层结构（H/B/A/C/L）统一管理；行级状态机（待生成基线→待修正→待核对→已核定/已退回）与批次级状态机（进行中→全部核定→已锁定）双层流转。

## 2. 区块构成

### 2.1 列表区（查）—— 三段式：过滤条 / 表格 / 分页条

**用途**：加工批次台账，按客户、状态筛选，承载行内批次级动作与行级操作入口。

**过滤控件（与 `demand_processing.list(oem_code, status)` 可过滤参数一一对应；契约无 keyword 参数 → 不设关键字搜索框，禁止前端假过滤）**：

| 控件 | 对应参数 | 选项 |
|---|---|---|
| 客户下拉 | `oem_code` | 来自已有数据去重动态生成（见 §4）；选项 value=oem_code |
| 状态 chips | `status` | 全部 / 进行中 / 全部核定 / 已锁定（value 为后端真实值，原样传参） |
| 分页 | `page` / `page_size` | `pageable()` 分页条 |

**表格列（`.tbl.tight` + `.scroll-x`；全部为详情字段子集；字段序与详情/表单一致）**：

| 列 | 字段 | 渲染 |
|---|---|---|
| 加工批次 | `proc_batch` | `.b-link`，点击开详情模态 |
| 客户 | `oem_code` | 文本 |
| 工厂 | `plant_code` | 文本 |
| 预测版本 | `fcst_version` | 文本，注明关联 D03 V 版本 |
| 状态 | `status` | `hue()` 徽章（进行中=蓝 / 全部核定=绿 / 已锁定=灰） |
| 开始时间 | `start_time` | `fmtTime()` |
| 完成时间 | `finish_time` | `fmtTime()`，空值 `dash()` |
| 创建时间 | `created_at` | `fmtTime()` |
| 操作 | — | 按 `status` 的行内动作，`x-show`（见 §5） |

**交互**：任一过滤变化 → 重置回第 1 页重载；状态动作成功后刷新当前页；空结果显示空态文案（不喷 toast）。

### 2.2 详情模态（查全）—— 三段式：墨青头带 + 状态徽章 / KV 分组体 + 三个行级子表 / 状态操作页脚

**用途**：点 `proc_batch` 弹出，调用 `demand_processing.get(proc_batch)` 展示**全部**业务字段——批次头 + 基线明细子表（D04-B）+ 修正明细子表（D04-A）+ 核对明细子表（D04-C）。

**分组（`.sec`）**：

| 分组 | 字段 | 渲染 |
|---|---|---|
| 头带 | `proc_batch` + `status` 徽章 | 墨青头带，徽章 `hue()` |
| 基本信息 | `proc_batch` / `oem_code` / `plant_code` / `fcst_version` | `.kv`；`proc_batch` 注明「系统生成 · 格式 PRC-YYYYMM-NNN」 |
| 时间信息 | `start_time` / `finish_time` / `created_at` / `updated_at` | `fmtTime()`；`finish_time` 空值 `dash()` 注明「未完成」 |
| 人员信息 | `created_by` / `updated_by` | `.kv` |
| 基线明细子表 | D04-B 字段：`part_no` / `veh_model` / `period` / `base_qty` / `base_path` / `base_method` / `source_ref` / `causal_qty` / `deviation` / `deviation_reason` / `generator` / `gen_time`（字段均来自 `SELECT * FROM d04_baseline`，源码级验证） | `.tbl.compact` 子表格；`base_qty` / `causal_qty` 使用 `fmt()`；`deviation` 百分比 + 超阈（>15%）时行标黄；`deviation_reason` 空值 `dash()`；`base_path` 标注颜色（时序外推=蓝 / 借用=橙 / 因果推演=绿）；`generator` 注明基线生成人；`gen_time` 使用 `fmtTime()` |
| 修正明细子表 | D04-A 字段：`part_no` / `veh_model` / `period` / `base_qty` / `adj_qty` / `adj_delta` / `adj_pct` / `adj_reason_cat` / `adj_evidence` / `adj_owner` / `submit_status` / `submit_time` | `.tbl.compact` 子表格；`adj_qty` / `adj_delta` 使用 `fmt()`；`adj_pct` 百分比带符号；`adj_evidence` `.cell-ellipsis` 省略；`submit_status` `hue()` 徽章（待提交=灰 / 已提交=蓝 / 逾期=红）；**行内嵌入提交修正按钮**（仅待修正/已退回行） |
| 核对明细子表 | D04-C 字段：`part_no` / `veh_model` / `period` / `chk_round` / `chk_result` / `chk_reason` / `chk_adj_qty` / `approved_qty` / `checker` / `chk_time`（字段均来自 `SELECT * FROM d04_check`，源码级验证；注：核对人参考的 `base_qty`/`adj_qty` 来自 D04-A 修正子表，前端展示时通过修正子表数据关联呈现） | `.tbl.compact` 子表格；`chk_result` `hue()` 徽章（通过=绿 / 退回=红）；`chk_reason` `.cell-ellipsis` 省略；`approved_qty` 使用 `fmt()`；`chk_round` >= 2 时行标橙（升级预警）；**行内嵌入核对按钮**（仅待核对行） |
| 调整日志子表 | D04-L 字段：`part_no` / `veh_model` / `period` / `adj_seq` / `actor_role` / `before_qty` / `after_qty` / `reason_cat` / `evidence` / `actor` / `action_time`（字段均来自 `SELECT * FROM d04_log`，源码级验证） | `.tbl.compact` 子表格，默认折叠；每行展示调整序号/角色/调整前后量/原因/动作时间；`actor_role` `hue()` 徽章（销售=蓝 / 核对人=绿）；`before_qty`/`after_qty` 使用 `fmt()`；供审计追溯每一次修正与校准的完整轨迹 |
| 原始数据 | get 返回全量 JSON | 底部折叠 |

**交互**：页脚 `.modal-ft` 按当前 `status` 放批次级状态机按钮（生成基线等）；四个子表可分别折叠展开（调整日志子表默认折叠）；子表行内动作（修正提交 / 核对）与模态页脚批次动作独立。

### 2.3 创建表单（增）—— 模态表单

**用途**：覆盖 `demand_processing.create_batch` 接受的**全部**可写业务参数（fcst_version / oem_code / plant_code）。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `fcst_version` | input，maxlength=20 | ★ 必填 | 收集 V 版本号；关联 D03 |
| `oem_code` | select（客户下拉，见 §4） | ★ 必填 | 客户编码 |
| `plant_code` | select（工厂下拉，见 §4） | ★ 必填 | OEM 工厂 |

- **不进表单**：`proc_batch`（系统自动生成，格式 PRC-YYYYMM-NNN）、`status`（系统初始=进行中）、`start_time` / `finish_time` / `created_at` / `updated_at` / `created_by` / `updated_by`（系统写入）。
- 布局：必填先行、底部右对齐提交按钮；校验 = 必填红星 + toast 警告。
- 提交成功：toast 带出新 `proc_batch` → 关闭模态 → 重置过滤重载列表（新批次恒「进行中」）。

### 2.4 销售修正子表单（submit_adjustment）—— 模态子表单

**用途**：对基线明细行提交销售修正，调用 `submit_adjustment(proc_batch, part_no, veh_model, period, adj_qty, adj_reason_cat, adj_evidence)`。三件套强制登记。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `proc_batch` | 锁定（来自选中批次） | ★ 必填 | — |
| `part_no` | 锁定（来自选中行） | ★ 必填 | — |
| `veh_model` | 锁定（来自选中行） | ★ 必填 | — |
| `period` | 锁定（来自选中行） | ★ 必填 | — |
| `adj_qty` | input type=number，step=0.0001 | ★ 必填 | 销售修正值；展示 baseline=`base_qty` 作为参照 |
| `adj_reason_cat` | select：客户侧情报 / 份额量纲 / 生命周期 / 节奏 / 外部验证背离 / 水位校准 / 其他（value 为后端真实值，原样传参） | ★ 必填 | 三件套之一：原因类别（BR-04） |
| `adj_evidence` | textarea，maxlength=2000 | 条件必填 | 三件套之一：数据依据；|adj_pct| > 20% 时强制非空（BR-05 分级举证） |

- 系统自动计算并展示 `adj_delta` = adj_qty − base_qty、`adj_pct` = adj_delta / base_qty × 100%（只读预览）。
- 超阈（|adj_pct| > 20%）时 adj_evidence 为空 → 前端拦截 + toast "幅度率超阈必须附数据依据"（不提交）。
- 提交成功后关闭子表单，刷新模态中的修正明细子表。

### 2.5 核对子表单（review）—— 模态子表单

**用途**：对已提交修正行执行核对，调用 `review(proc_batch, part_no, veh_model, period, chk_result, chk_reason, chk_adj_qty)`。核对结论为通过或退回。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `proc_batch` | 锁定（来自选中批次） | ★ 必填 | — |
| `part_no` | 锁定（来自选中行） | ★ 必填 | — |
| `veh_model` | 锁定（来自选中行） | ★ 必填 | — |
| `period` | 锁定（来自选中行） | ★ 必填 | — |
| `chk_result` | radio / select：通过 / 退回 | ★ 必填 | 核对结论（BR-10 退回须书面理由） |
| `chk_reason` | textarea，maxlength=2000 | 条件必填 | `chk_result=退回` 时必填：「哪个视角不通过 + 需要什么证据/调整」（BR-10） |
| `chk_adj_qty` | input type=number，step=0.0001 | 可选 | 核对人直接校准调整值（非零时在 D04-L 登记三件套，BR-13） |

- `chk_result=退回` 且 `chk_reason` 为空 → 前端拦截 + toast "退回必须填写理由"（不提交）。
- 提交成功后关闭子表单，刷新模态中的核对明细子表。

### 2.6 基线确认子表单（confirm_baseline）—— 模态子表单

**用途**：对基线明细行进行人工确认/裁决，调用 `confirm_baseline(proc_batch, part_no, veh_model, period, base_qty, deviation_reason)`。通常用于交叉偏差超阈的场景。

| 字段 | 控件 | 必填 | 约束来源 |
|---|---|---|---|
| `proc_batch` | 锁定（来自选中批次） | ★ 必填 | — |
| `part_no` | 锁定（来自选中行） | ★ 必填 | — |
| `veh_model` | 锁定（来自选中行） | ★ 必填 | — |
| `period` | 锁定（来自选中行） | ★ 必填 | — |
| `base_qty` | input type=number，step=0.0001 | 可选 | 人工裁决后的基线值；为空则保持系统生成值 |
| `deviation_reason` | textarea，maxlength=1000 | 条件必填 | 交叉偏差超阈时必填，记录排查原因 |

- 提交成功后关闭子表单，刷新模态中的基线明细子表。

## 3. svc 字面量清单（授权派生依据——必须字面量 svc("应用","服务")）

| 区块 | 调用（应用.服务） | 参数 | 说明 |
|---|---|---|---|

| 批次级动作（页脚） | `svc("demand_processing","lock")` | `{proc_batch}` | 锁定批次（D09 发布联动触发）；仅全部核定可锁定 |

> 以上 9 处必须在 view.js 中以字面量逐项书写（可包在闭包里），**勿用变量拼名**——这是页面授权隐式放行派生扫描的唯一来源。

## 4. 数据来源与下拉

**客户下拉（过滤条与创建表单共用一份 oemList）**：
- oem_code 从 `demand_processing.list` 已有数据去重动态生成下拉选项；若无数据则从 `demand_collection.list` quiet 探测获取 OEM 列表。
- 工厂下拉同理——从已有数据去重或外部服务获取。

**契约 payload → 区块字段映射**：

| 来源 | payload 字段 | 去向 |
|---|---|---|
| `demand_processing.list` 项 | proc_batch, oem_code, plant_code, fcst_version, status, start_time, finish_time, created_at, updated_at, created_by, updated_by | 列表区表格列（1:1） |
| `demand_processing.get` | 批次头（同上全量）+ 基线明细列表[D04-B 字段] + 修正明细列表[D04-A 字段] + 核对明细列表[D04-C 字段] + 调整日志列表[D04-L 字段] | 详情模态 KV 分组 + 四个子表 + 原始数据折叠 |
| `demand_processing.create_batch` 返回 | 批次对象（含 proc_batch，status=进行中） | toast 展示 proc_batch → 列表重载 |
| `demand_processing.generate_baseline` 返回 | 基线生成结果 | toast → 刷新模态基线子表 |
| `demand_processing.confirm_baseline` 返回 | 基线确认结果 | toast → 刷新基线子表对应行 |
| `demand_processing.submit_adjustment` 返回 | 修正明细行 | toast → 刷新模态修正子表 |
| `demand_processing.review` 返回 | 核对明细行 | toast → 刷新模态核对子表 |
| `demand_processing.lock` 返回 | 更新后的批次对象（新 status） | 原地更新已开模态 + 列表行 |
| `demand_processing.get_status` 返回 | 行级状态快照 | 用于子表行级按钮显隐判定 |

## 5. 交互要点

1. **按批次状态的批次级动作（模态页脚）**：
   - `status=进行中` → 【生成基线】【锁定】（锁定需全部核定后系统触发）；
     - 【生成基线】→ 调用 generate_baseline，展示进度提示，完成后刷新基线子表。
   - `status=全部核定` → 【锁定】（通常由 D09 联动触发，前台也可手动触发）。
   - `status=已锁定` → 终态，无任何按钮。
   - 动作成功：toast + 刷新列表与模态。

2. **按行级状态的行内动作（三个子表内联按钮）**：
   - 基线子表：
     - deviation 超阈行 → 【确认基线】→ 打开 confirm_baseline 子表单。
   - 修正子表：
     - submit_status=待提交 / 已退回·待重报 → 【提交修正】→ 打开 submit_adjustment 子表单。
     - submit_status=已提交 → 显示已提交，无按钮（等待核对）。
     - submit_status=逾期 → 显示「按基线上报」灰色标记。
   - 核对子表：
     - 行状态=待核对 → 【核对】→ 打开 review 子表单。
     - 行状态=已核定 → 通过绿色标记，无按钮。
     - 行状态=已退回·待重报 → 退回红色标记，等待销售重报。
     - chk_round >= 2 且 chk_result=退回 → 行标橙「升级产销平衡会」。
   - 动作成功：toast + 刷新对应子表；行内动作同时影响批次统计展示。

3. **模态**：统一三段式；加载态等待消失后再断言内容；头带墨青 + `hue()` 状态徽章；基线子表默认展开，修正/核对/日志子表默认折叠，点击展开/折叠。

4. **销售修正三件套校验（前端拦截）**：
   - adj_reason_cat 为空 → toast "请选择原因类别"，不提交。
   - |adj_pct| > 20% 且 adj_evidence 为空 → toast "幅度率超阈值 20%，必须附数据依据"，不提交。
   - adj_owner 由系统自动带出当前用户，无需手动填写。

5. **核对退回理由校验（前端拦截）**：
   - chk_result=退回 且 chk_reason 为空 → toast "退回必须填写理由（视角 + 所需证据）"，不提交。

6. **quiet 探测性加载**：客户/工厂下拉 quiet + 零值兜底，失败不喷 toast；列表本身正常加载，错误走 api.js 统一通道。

7. **展示工具**：`hue()`（状态徽章）、`dash()`（空值字段）、`fmtTime()`（时间字段）、`fmt()`（base_qty / adj_qty / adj_delta / causal_qty / approved_qty / chk_adj_qty 等数值）、百分比直接渲染（deviation / adj_pct）。

8. **toast**：批次创建成功 / 基线生成完成 / 修正提交成功 / 核对完成 / 必填未填警告；其余错误一律由 api.js 统一呈现。

## 6. 验收关注点（供第⑧步前端测试用例）

1. **路由渲染**：`#/demand_processing` 挂载出列表三段式（过滤条 + 表格 + 分页条），**页面无 `.kpi`**（防看板挂载粘滞假过）；菜单「⚙ 需求加工」按 order=50 定位。

2. **造数后列表有数据**：通过 `demand_processing.create_batch` 造多个批次（覆盖进行中/全部核定/已锁定）→ 列表行数正确，proc_batch / oem_code / fcst_version / status 列非空。
