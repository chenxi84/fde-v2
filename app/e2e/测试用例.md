## §2 主业务链（task）

| 用例 | 步骤 | 期望 |
|---|---|---|
| `TC-MC-01` 创建任务 | `task.create(title=写方案, description=…, assignee_member_no="M002", priority="high")` | 返回 `task_no` 非空、`status == "待办"`、`assignee_member_no == "M002"`、`priority == "high"`、`title == "写方案"` — **BR-7 / BR-8** |
| `TC-MC-02` 走跨应用链 | 由 `TC-ERR-05`（指派不存在成员）**反向证明** `task.create → member.get` 真的被调用：若成员不存在则创建失败 | 见 `TC-ERR-05` — **BR-6**（其 `生效点` 是 `task.create → member.get`） |
| `TC-MC-03` 查任务详情 | `task.get(task_no=T1)` | `task_no == T1`、`title/description/assignee_member_no/priority/status` **逐字段**与创建时一致 |
| `TC-MC-04` 列表无条件 | `task.list()` | 返回 `{"items": [...], "total": 1}`（**形状闸**：与 `member.list` 同形，CONVENTION §7）；`total == len(items) == 1` 且 `items[0]["task_no"] == T1` |
| `TC-MC-05` 启动任务（待办 → 进行中） | `task.start(task_no=T1)` | `status == "进行中"` — **BR-10**；且 `updated_at` **晚于**创建时（**BR-15**） |
| `TC-MC-06` 退回任务（**进行中 → 待办**） | `task.reopen(task_no=T1)` | `status == "待办"` — **BR-12** |
| `TC-MC-07` 再启动并完成（进行中 → 已完成） | `task.start(task_no=T1)` 然后 `task.complete(task_no=T1)` | 先 `status == "进行中"`，再 `status == "已完成"` — **BR-10 / BR-11**；`updated_at` 再次更新（**BR-15**） |

> ⚠ **状态机链不是「待办→进行中→已完成→待办」** —— **「已完成」是终态**：
> `BR-13` 明确「已完成任务禁止 start/complete/reopen」。
> `reopen` 只允许 **进行中 → 待办**（`BR-12`）。
>
> 这一点本轮**踩过一次**（2026-09-17）：初版把主链写成"完成后还能退回"，
> 与本文档 §3 的 `TC-ERR-16`（断言已完成不可流转）**自相矛盾**，
> 一跑就撞 `FdeError: 已完成任务不能退回`。
> **用例集自身的自洽性，目前没有任何检查在看** —— 见 §6 待确认 6。

> **`TC-MC-02` 为什么用「反向证明」**：本组没有任何"直调内部链"的 API
> （`platform.call` 只能调公共服务）。所以"那条链真的被走到"这件事，
> 只能用**它的失败行为**来证明 —— 指派一个不存在的成员必须失败（`TC-ERR-05`）。
> 这与 PSC 那条 `BR-06` 的问题正好相反：PSC 是**该失败却没失败**（富余档静默走不到）。

> ⚠ **下面这一段的标记区间由 `python scripts/br_coverage.py -g e2e --write` 生成，不要手改**。
> 手改必漂：2026-09-18 本节 `BR-11`/`BR-12` 的引用用例被手抄成了**对方的那条**
> （`TC-MC-06` ↔ `TC-MC-07`），而 T4 是**按输出的字段名**匹配的 —— `task.status` 三条状态类 BR
