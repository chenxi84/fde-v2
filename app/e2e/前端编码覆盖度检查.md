## 三、本报告检查不到什么

**PSC 那三份报告的教训：只自检代码与文档本身、从不查「文档 ↔ 脚本 ↔ 页面」的对应，于是「100%」里混着假账。本报告的边界：**

1. **不运行页面** —— 所有结论都是静态读码 + `node --check`。页面能不能渲染出内容、断言会不会红，属第⑨步（`verify_view_*`）。本报告 §五 抄的 `run_gates` 结果只是**证明下游跑通了**，不是第⑦步自己的成绩。
2. **不查「用例文档 ↔ 脚本」的对应** —— 那是 `scripts/view_coverage.py` 的 V1–V7（本组实测「七条全过」），本报告不重复也不替代它。
3. **不查字段级取值是否正确** —— 例如 `member` 的「创建时间」列在页面上恒为「—」（`created_at` 不在服务返回里，见第⑥步 D1），静态读码**看不出**，只有跑起来断言才暴露（第⑧步 `VT-MODAL-02` 就是为此而写）。
4. **不查 `x-if`/`x-for` 的结构合法性** —— 那是 `view_coverage.py` 的 V6 判据。
5. **菜单真值不在此手工核** —— 项数/顺序真值取自 `PAGE_META`，由 `view_coverage.py` 现算；本报告只核「`PAGE_META` 与详设一致」。
6. **`node --check` 的能力边界**（工具链原文自己注明）：查不出漏默认导出、查不出未定义变量、查不出逻辑错 —— 本报告另外单独核了默认导出名，其余仍看不出来。

### F2 专项：看板任务类 KPI 恒 0（机器取证）

```
$ python … -c "shadow_dbs(); FdePlatform().call('e2e/task','list')"
--- e2e/member.list() -> type=dict
{"total": 0, "items": []}
--- e2e/task.list()   -> type=list
[]
```

- **根因**：`task.py::list()` 在 `page is None and size is None` 时 `return [dict(row) for row in rows]` —— **裸数组**；`member.py::list()` 则恒返回 `{total, items}`。
- `dashboard.js:28-29` 用 `svc("task","list",{}, {quiet:true})`（无 `page`/`size`）⇒ 拿到的是数组：
  - `const tasks = (t && t.items) || []` → 恒 `[]`
  - `kpi.tasks = (t && t.total) ?? tasks.length` → `undefined ?? 0` → **恒 0**
  - ⇒「任务总数 / 进行中任务 / 已完成任务」三张卡与状态分布三行计数 **永久为 0**
- `dashboard.js` 的注释（「page/size 缺省 → 服务端返回全量 `{total, items}`（见 `member.py` / `task.py` list）」）对 `member` 成立、对 **`task` 不成立**；`dashboard.md` §2.1/§3 也照抄了这个假设 —— 详设与代码**同源同错**，这正是「第⑥步没查出来、第⑧步用例也没断到」的那类缺陷。
- **为什么测试没抓到**：组级脚本 `verify_view_e2e.py` 的断言是
  `right_mono[0] == kpi_vals[1]`（第一个 `.pipe-col .right.mono` = `kpi.tasks`，比 `kpi_vals[1]` = 也是 `kpi.tasks`）——**0 == 0**，恒真。而第⑧步组级用例 `VT-DASH-01` 写的是「`.pipe-col` 右上角 `.right.mono` 的**同一个数**也 == `1`」，指的是**第二个** `.right.mono`（= `kpi.members`）—— 文档与脚本口径不一致，掩盖了任务类 KPI 从未被真正断言。
- **建议**（不属本步范围，登记待决策）：`dashboard.js` 改传 `{page: 1, size: 200}`（走 `{total, items}` 分支），并把断言改成「任务类 KPI 非零 + 与状态分布求和一致」。
