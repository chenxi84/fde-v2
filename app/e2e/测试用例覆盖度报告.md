## 三、本报告检查不到什么

**本报告只做一件事**：把 `architecture.md` + 2 份《应用详设.md》与 `测试用例.md` **逐项对照**（文档 ↔ 文档）。它**不跑用例、不读脚本、不查库**。

因此，下面这些**机械判据**才是对应维度的真正凭据。以下为**实跑结论原文**（跑于 2026-09-18，`PYTHONIOENCODING=utf-8`）：

| 工具 | 覆盖本报告的哪一项 | 实跑结论（原文） |

| `python scripts/scan_structure.py -g e2e` | 2.5（T4 字段级覆盖）、以及**文档→脚本**的落地质量 | `通过 8 · 失败 0 · 跳过 2` / `VERIFY_RESULT: PASS`；其中 → `✓ PASS T1 用例文档 → 脚本 逐参一致 —— 备注：26 组配对通过`；`✓ PASS T2 [e2e] 空转断言计数为 0（第⑤步门禁） —— 备注：35 个 TC 步全部有业务断言`；`✓ PASS T4 [member] BR 输出字段级覆盖（第④步门禁）`；`✓ PASS T4 [task] BR 输出字段级覆盖（第④步门禁）` |

**⚠ 口径差异要说清（否则会误以为机械判据已覆盖本报告）：**

- **T4 / `br_coverage` 只认「字段名」**。它回答的是「`task.status` 这个字段名有没有在某条用例的断言里出现过」——**它不知道那条用例测的是哪个状态、更不知道用例编号与断言的对应关系对不对**。本组就有一处这样的缺陷（`测试用例.md` §4 的 `BR-11`/`BR-12` 引用用例编号互换），**T4 判 PASS 而文档确实自相矛盾** ⇒ 见「执行期发现」1。
- **T1 / T2 查的是「用例文档 → 脚本」的落地**，不是「详设 → 用例」的生成。把某条 US 的 happy path 用例整条删掉，T1/T2/T4 **一个都不会报** —— 只有本报告 2.1 / 2.2 会红。
- **`[chain] 后端主链端到端`（第⑤步）跑的是脚本，不是本报告**。本报告不验证「用例的期望值与实现是否一致」——那是第⑤步 `verify_chain_e2e.py` 的职责。
- **用例集自身的自洽性没有检查**（`测试用例.md` §6 第 6 项自己承认：「初版把状态机链写成'完成后可退回'，与 `TC-ERR-16` 直接矛盾，**静态检查一个都没报**」）。本报告 2.3 只能人工核「每条转换有没有用例」，**核不出「两条用例对同一 (服务, 前置状态) 给出相反期望」**。
- 本报告**不核**「40 条用例编号 ↔ 脚本 `step()` 的一一对应」（40 条编号由 **36 个 `step()`** 承载：`TC-ERR-08/09/10` 与 `TC-ERR-11/12` 以**区间写法**合并，`TC-MC-02` 按设计由 `TC-ERR-05` 反向证明而无独立步骤 —— 已逐条核过 `verify_chain_e2e.py:313-323`，实际都执行到位，**无遗漏**）。但「用例覆盖度 = 100%」这一条属**第⑤步门禁**，不在本报告范围。
- 本报告的每一项都是**人读对照、编号逐条数过**；40 条用例、9 个 US、28 条 BR、4 条状态机转换均由我逐条数出，非从别处抄录。

## 四、执行期发现

1. **§4 的 `BR-11` / `BR-12` 引用用例编号互换**（`app/e2e/测试用例.md:139-140`）：
   - 第 139 行 `BR-11`（输出 `task.status` → **已完成**）写「`TC-MC-06`（`status == "已完成"`）」—— 但 §2 第 63 行定义 `TC-MC-06` 是**退回任务（进行中 → 待办）**，断言是 `status == "待办"`；
