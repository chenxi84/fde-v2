# 第1章 业务背景与目标

## 1.1 业务场景

一个团队要把「谁在做什么、做到哪一步」管起来。现场的做法通常是：一份成员名单（谁在团队里、什么角色、怎么联系）
＋ 一叠任务单（这事交给谁、现在什么状态）。两样东西分开放，麻烦就出在**对不上**：

- 任务单上写了一个人名，但那人早就不在名单里（或编号写错）—— 任务派给了一个不存在的人，**没有任何人发现**；
- 谁都能把任务从「进行中」改回「待办」或直接标成「已完成」，**状态是随手写的，不是走出来的**；
- 想知道「有几件事在做、几件已完成」，得把任务单翻一遍。

## 1.2 业务目标

| # | 目标 | 达成方式（业务口径） |
|---|---|---|
| G1 | 任务只能指派给**真实存在**的成员 | 指派时以成员名单为准做校验，成员不存在就**拒绝创建**（不是建完再提醒） |
| G2 | 任务状态**只能沿合法路径流转** | 明确状态机：待办 → 进行中 → 已完成，且允许「进行中 → 待办」的退回；`已完成` 是终态 |
| G3 | 成员名单与任务单**各自有唯一权威**，不重复维护 | 成员信息只在成员名单里维护；任务只引用成员编号，不复制姓名/邮箱 |
| G4 | 能**一眼看到全貌** | 首页看板给出「成员总数 / 任务总数 / 进行中 / 已完成」与任务状态分布 |
| G5 | 权限**按人收窄**，不是人人看得见全部 | 管理员看全部；普通成员只看得到、也只推得动**指派给自己的**任务 |

## 1.3 业务边界（明确不做）

| 不做的事 | 原因 |
|---|---|
| 成员信息的修改、停用、删除 | 本期不开放（见第 3 章 §3.4）—— 名单一旦被引用，改动的影响面由线下流程处理 |
| 登录、认证、令牌、密码 | 由平台统一承担，业务应用**不做鉴权**（第 2 章） |
| 组织架构、部门、上下级 | 本期场景里没有这层结构 |
| 任务正文的修改、删除、评论、附件、子任务、工时 | 本期只做「创建 + 指派 + 流转 + 查询」闭环 |
| 任务批量操作、提醒、通知、消息推送 | 本期不做 |
| 报表统计与看板视图（含导出） | 统计口径由看板（第 5 章 §5.3）承担，不做导出 |
| 独立变更单、逆向单据 | 状态退回（reopen）已覆盖本期的撤回诉求 |

## 1.4 关键业务约束

1. **成员编号全局唯一**：编号是任务引用的锚点，重复即引用歧义。
2. **任务标题必填、有长度上限**：标题是列表里唯一可读的标识，空标题的任务等于没有信息。
3. **状态流转是"走出来"的**：每一次流转都有前置状态要求，不满足即拒绝，且**拒绝时任务状态不变**。
4. **跨应用的关系只有一条**：任务创建时向成员名单要一次「这个人存在吗」，之后不再反向依赖；
   成员名单**不反过来调用任务**（第 3 章 §3.5）。
