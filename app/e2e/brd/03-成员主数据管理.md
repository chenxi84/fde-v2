# 第3章 成员主数据管理

## 3.1 业务定位

成员名单是**主数据**：它是任务指派的对象来源，**先有名单、才有任务**。
名单只回答「谁在团队里、什么角色、怎么联系」，不承载任务状态。

## 3.2 单据与字段

**单据名：成员（`member`）**　标识：`member_no`

| 字段 | 含义 | 业务要求 |
|---|---|---|
| `member_no` | 成员编号 | 必填、**全局唯一**、创建后不可变更；任务引用它 |
| `name` | 成员姓名 | 必填 |
| `email` | 成员邮箱 | 必填、**全局唯一**、须符合基本邮箱格式（含 `@` 与域名部分） |
| `role` | 成员角色 | 必填，取值只能是 `admin` 或 `member` |
| `created_at` | 创建时间 | 系统写入，用于排序与审计 |

> **审计列**：创建人/修改人/修改时间等由平台在库表上自动补齐，业务字段表里不列。

## 3.3 业务流程

### 3.3.1 建成员（管理员）

1. 管理员提交成员编号、姓名、邮箱、角色。
2. 系统校验：编号必填且未被占用；姓名必填；邮箱必填、格式合法且未被占用；角色在枚举内。
3. 校验通过 → 落库，**返回该成员完整信息**。
4. 任一项不满足 → **拒绝并说明原因**（人话），**不落库**。

### 3.3.2 查成员

- 按成员编号查详情：查不到即**报错**（不返回空对象 —— 空对象会让调用方以为"人存在但没信息"）。
- 查列表：可按关键字（编号/姓名/邮箱模糊）与角色筛选；两个条件同时给出时**取交集**；
  没有匹配时**返回空列表而不是报错**（"筛出来是空的"是正常结果，不是异常）。

## 3.4 业务规则

> ⚠ **本节用 `R3.x` 编号，不用 `BR-n`** —— `BR-n` 是本组《应用详设》里的规则编号（第②步的产出）。
> 两边若用同一套编号，就会变成"同名不同义"：BRD 的 `BR-1` 与详设的 `BR-1` 不是同一条。
> 需求条目一律带**章节前缀**（第 3 章 → `R3.x`，第 4 章 → `R4.x`），对账表里也这样引。

| 需求条目 | 规则 | 违反时 |
|---|---|---|
| R3.1 | `member_no` 必填 | 拒绝 |
| R3.2 | `member_no` 全局唯一，不允许重复创建 | 拒绝 |
| R3.3 | `name` 必填 | 拒绝 |
| R3.4 | `email` 必填 | 拒绝 |
| R3.5 | `email` 须符合基本邮箱格式 | 拒绝 |
| R3.6 | `email` 全局唯一 | 拒绝 |
| R3.7 | `role` 必填且在 `admin` / `member` 之内 | 拒绝 |
| R3.8 | 查详情时 `member_no` 必填 | 拒绝 |
| R3.9 | 查详情查不到该成员 = 业务异常 | 拒绝 |
| R3.10 | 列表筛选 `role` 非法 | 拒绝 |
| R3.11 | 列表无匹配 → 返回空列表 | 正常返回 |
| R3.12 | **成员创建后不开放修改 / 停用 / 删除** | 系统不提供这些操作 |
| R3.13 | 成员名单**不主动调用**其他应用 | ——（架构约束） |

## 3.5 与其他模块的关系

| 方向 | 关系 |
|---|---|
| 成员 → 任务 | **无**。名单不知道有哪些任务引用了它（保证名单是纯主数据） |
| 任务 → 成员 | 建任务时按 `member_no` 要一次「存在吗」（第 4 章 §4.3）。**这是全系统唯一的跨应用关系** |

> 这条「单向」是刻意的：一旦名单反过来依赖任务，改名单就会牵动任务，主数据就不再是主数据。
