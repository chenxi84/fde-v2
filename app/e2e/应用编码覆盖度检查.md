## 六、执行期发现

1. **`task.list` 的返回结构不统一，且不符合 CONVENTION §7** —— `app/e2e/task/task.py:138-140`：当 `page`/`size` **都是 None** 时**返回裸 list**；带分页时（`:163-172`）返回一个含 **8 个键**的 dict：`total / page / size / items / data / rows / list / records`（后 6 个是 `items` 的别名）。CONVENTION §7 要求「统一返回 `{"items": [...], "total": total}`」。同组的 `member.list`（`:96` / `:107`）是**符合**的 ⇒ **本组两个应用的同名方法两种返回形状**，消费方（前端 `pageable()`）拿不拿到 `total` 取决于是否传分页参数。`测试用例.md` §6 第 4 项已自述此问题。
2. **4 处 `raise FdeError` 在详设 BR 表里找不到对应规则**（门禁是「BR → 代码」单向，故**不计失败**，属实现超出详设）：
   - `member.py:27`「邮箱已存在」—— 依据在详设 §4.2 字段表的 `UNIQUE` 约束与 §4.3.2 说明里，**没有升格为 BR**；
   - `member.py:122`「分页参数非法」、`task.py:146`「分页参数不合法」、`task.py:149`「页码必须大于等于1」、`task.py:151`「每页条数必须大于等于1」—— **分页校验 4 条无 BR**（其中 member 1 条、task 3 条）。
3. **`member` 详设 §4.3.5 的说法与实库不符**：详设写「本表**不包含** `updated_at`，因为成员主数据默认不开放修改」，但平台按 CONVENTION §6 注入 4 个审计列——实测 `member.db` 的 `member` 表**含** `updated_at TEXT, created_by TEXT, updated_by TEXT`。这是**详设描述的库**与**平台的库**之间的口径差（不是代码 bug），但会让按详设写 SQL 的人误判列的存在性。
4. **`member` 的索引需求在详设里没有上游**：`member/schema.sql:8-12` 建了 3 个索引（`idx_member_role` / `idx_member_name` / `idx_member_created_at`），而 `member/应用详设.md` §4.2 **没有「索引需求」节**（`task` 详设有 §4.3，且与 `task/schema.sql:10-16` 逐条一致）。代码超出详设，无害，但**规范要求"详设 §4 字段表每列 → DDL 列"只覆盖了列、没覆盖索引**。
5. **详设的对外服务签名未同步分页形参与返回结构**（与第②步报告同一处）：
   - `member/应用详设.md` §4.4.3 声明 `member.list(keyword: str | None = None, role: str | None = None) -> list[dict]`，实现是 `list(keyword, role, page, size)`（`member.py:62`）且返回 `{"total","items"}`；
   - `task/应用详设.md` §4.4 的 `list` 同缺 `page`/`size`，返回列写「任务对象列表」。
   - 该改名是本轮 2026-09-17 的订正（代码注释见 `member.py:57-61`、`task.py:82-86`），**详设尚未回填**。
