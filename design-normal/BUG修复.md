# BUG 修复 · 第⑤步回路技能规格（测试失败 → 提案 → 批准 → 应用 → 重测）

> **版本**: v1.0  **创建日期**: 2026-08-02
> **适用人员**: 应用构建第⑤步测试执行之后的回路执行体（AI 提案 + 人工批准 + 平台应用）
> **目的**: 把第⑤步测试报告里的失败用例**逐条 triage 并转化为最小修复**，经人工批准后落码，再自动重测对账消项——形成「测试 → 修复 → 重测」的收敛回路。
> **第一铁律：LLM 只提案，人批准，平台才落码。** 改码权始终在人手里。

---

## 🧭 使用契约：作为「BUG 修复」技能（第⑤步回路）

### 技能定位（⑤ 的回路步，不占全局步号）

```text
第⑤步  测试执行（《测试执行.md》）   测试用例.md → verify_chain_<组>.py 沙箱跑 → app/<组>/tests/测试报告_<组>.md（三态 verdict）
            ↓ 报告含失败用例
★回路  BUG 修复（本文件）          失败用例 → 逐条提案（old→new）→ 页面批准 → 应用 + 备份 + 语法门
            ↓ 应用后自动派生
第⑤步  测试执行（重测）            重跑 → 转绿用例对账勾销（提案 resolved、BUGS_<组>.md ✅）
```

### 输入
| 来源 | 位置 | 说明 |
|---|---|---|
| ① 测试报告（**必需**） | `app/<组>/tests/测试报告_<组>.md` | 第⑤步产出；从逐例结果表取未通过用例（`✗` 行）。无失败例 → 无需修复。 |
| ② 测试用例 | `app/<组>/测试用例.md` | 取失败用例对应用例块（步骤 / 数据 / 期望），判断是脚本校准错还是用例措辞错。 |
| ③ 相关应用当前代码 | `app/<组>/<应用>/<应用>.py` | 按用例块涉及的应用摘录全文；提案的 `old` 必须从中**逐字拷贝**。 |
| ④ 数据契约 + 服务签名 | 运行时静态抽取 | `_init_db` 建表字段 / 必填列 + 公共方法签名（与第⑤步同源），防止臆造字段名。 |

### 产出
- `app/<组>/tests/修复提案_<组>.md` + 提案入库（`bugfix_proposals` 表，status=`pending`）——**不碰任何代码文件**。
- 批准并应用后：目标文件被最小修改（原文备份于 `app/<组>/.bugfix_backup/<时间戳>/`）+ 自动派生重测任务。

---

## triage 三分类（每条失败例必居其一）

| 类别 | 判据 | 提案动作 |
|---|---|---|
| **app_bug** | 应用代码真实缺陷：校验缺失 / 状态机错 / 跨应用契约不符，改脚本绕不过 | 对目标应用 `.py` 提 `old→new` 精确替换 |
| **case_calibration** | 测试用例的数据 / 步骤 / 期望措辞与应用真实契约不符（如入参形态、枚举全称、字段名） | 对《测试用例.md》提回填替换（修用例，下轮测试执行自然用新用例重新生成脚本） |
| **design_issue** | 设计层缺陷，非单文件可修（详设本身错了） | 不出 old/new，rationale 说明需人工修订详设；**批准即转「待人工处理（manual）」**，不进代码应用 / 重测流程 |

**跨应用契约不符一律改调用方**——被调方签名是冻结契约，不让被调方迁就调用方（同《工具链使用说明》契约对齐铁律）。

## 提案形态铁律

- **逐字 `old→new` 精确替换对**（非模糊 diff）：`old` 从给出的当前文件内容逐字拷贝（含缩进 / 换行 / 中文标点）；平台按**精确匹配**落码，不匹配即失败、不强改。
- **最小单处**：一条提案只改一处连续片段（各 ≤100 行），严禁整文件重写。
- 输出为单个 JSON：`{category, target_file, old, new, rationale, risk}`。

## 应用阶段铁律（平台执行，非 LLM）

- **白名单**：只允许改 `app/<组>/` 下文件；越界目标一律拒绝。
- **改前备份**：被改文件原样拷入 `app/<组>/.bugfix_backup/<时间戳>/`（人工可还原）。
- **语法门**：`.py` 替换后必须 `ast.parse` 通过，不过即该提案失败、**原文件不动**。
- **scanner 顾问检查**：应用后跑 `python -m fde_platform.scanner`，报问题仅警告（不自动回滚，留人判断）。
- **自动重测**：应用成功后自动派生一次第⑤步测试执行（worker 串行，天然不与运行中的测试抢资源）。
- **对账消项**：重测后，已应用提案对应的用例若转绿 → 提案标 `resolved`、`BUGS_<组>.md` 条目打 ✅；仍红则保持 open（说明定性或方案有误，回人工判断，不循环重试）。

## 平台化入口

`/groupbuild` 页面 ⑦ 测试执行块内的「BUG 修复回路」子块（任务 `kind="bugfix"` 提案 / `kind="bugfix-apply"` 应用，`fde_platform/groupbuild_runner.py`）：

1. **生成修复提案**：`gather`（失败例 + 逐例上下文）→ `propose`（逐例 LLM 提案，并发 ≤ `GROUPBUILD_BUGFIX_PARALLEL`，默认 3）→ `write`（app/<组>/tests/修复提案_<组>.md）。
2. **提案列表**：每条带类别 / 目标文件 / 根因 / 风险 / diff，**逐条批准 / 驳回**。
3. **应用已批准并重测**：白名单 + 备份 + 精确替换 + 语法门 → 派生重测 → 对账消项。

### 验收标准

- 每条失败用例都有 triage 结论（三类之一）；app_bug / case_calibration 提案含可落码的逐字 old→new。
- 应用只改已批准提案；越界 / 不匹配 / 语法错的提案落 `failed` 且原文件不动。
- 重测后转绿用例的提案 `resolved`、`BUGS_<组>.md` 打 ✅；未转绿保持 open。

### 命名与边界

- 本技能**不自动改码**（提案须批准）；不修 `design/`、`fde_platform/` 任何文件（白名单外）。
- 提案错误由备份兜底（人工还原）；重测仍红 → 回人工，不循环。
- 与手动流程的关系：你也可以跳过本技能、直接按 `BUGS_<组>.md` 手改应用代码后重跑第⑤步——两条路同构。
