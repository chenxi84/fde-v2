# 智能体角色声明（`_roles.py` · 组级声明，可选增强）

> 状态：已定稿。本文档固化**组级角色声明文件**的格式正本，供应用组声明智能体角色（九步法第⑩步，可选增强）。
> 本文档自包含（内联样例），不依赖任何实现文件路径；「声明文件落点」是本规范的组成部分，非外部引用。

## 一、背景与定位

- **可选增强**：九步法把「业务 → 可用工作台」闭环；角色声明是「让这组应用**可被智能体编排**」的可选步（九步法第⑩步），不做也满足九步法完成门禁。
- **组级声明**：`app/<组>/_roles.py`，平台扫描装配，**零平台代码改动**。
- **作用**：声明本组的智能体角色（英文 `type` + 中文 `label` + 可用应用集 `apps`），供智能体建队按角色派活、flow 节点按 `role` 过滤工具。

## 二、落点与命名

- 落点：`app/<组>/_roles.py`（一个组一份）。
- 平台扫描 `app/<组>/_roles.py` 装配业务角色；某份文件出错**仅跳过该组**，不阻断平台启动。
- 加新组 = 建目录 + 丢一份 `_roles.py`。

## 三、ROLES 结构

导出 `ROLES` 列表，每项一个角色：

| 字段 | 必填 | 说明 |
|---|---|---|
| `type` | 是 | 角色英文标识，**全局唯一**；被智能体建队的 `subagent_type` 与 flow 节点的 `role` 引用 |
| `label` | 否 | 中文显示名（缺省回落 `type`） |
| `apps` | 是 | 该角色可用的应用集，形如 `组/应用`；驱动工具过滤（该角色只能调这些应用的服务） |

## 四、内联样例

```python
# app/<组>/_roles.py
ROLES = [
    {"type": "sales", "label": "销售/需求专家",
     "apps": ["<组>/sales_forecast", "<组>/md_customer"]},
    {"type": "planning", "label": "计划/排产专家",
     "apps": ["<组>/master_plan", "<组>/demand"]},
]
```

## 五、装配与冲突规则

- `type` **全局唯一**：不同组声明同名 `type` 时，按目录名排序**后者覆盖前者**——先规划好命名，避免跨组撞名。
- `type` 或 `apps` 为空的项被跳过。
- 平台角色（integration/scheduler）**不在此声明**，保留在平台级。

## 六、与流程编排的关系

- flow 节点的 `role` 引用本文件 `type`：命中则按角色过滤工具；未命中（或本组无 `_roles.py`）用全量工具。详见《流程编排方案.md》。
- 二者均为可选增强（九步法第⑩⑪步）：可只声明角色、只声明流程、或两者都做。

## 七、组级 Agent 工具声明（`_agent_tools.py`）

与 `_roles.py` **同目录、同约定**（一个组一份，平台扫描装配，单份出错仅跳过该组），
声明「本组应用在 Agent 眼里的样子」。导出两个**可选**常量：

```python
# app/<组>/_agent_tools.py

# ① 哪些服务**不给 Agent 调**（黑名单）
HIDDEN_FROM_AGENT = {
    "psc/md_material": ["set_fit_params"],   # 内部回填：由 strategy_fitting.approve 调用
    "psc/demand_pool": ["on_inbound"],       # 外部回执：ERP 回调入口
    "psc/sales_forecast": ["calc_baseline"], # 被 batch 版取代的单行版
}

# ② 组描述提示：什么时候该激活这个应用、和哪个相邻应用别搞混
GROUP_HINTS = {
    "psc/demand": "毛需求与净需求的合成发布。**不是『需求池』（那里是补库单）**",
}
```

### 7.1 `HIDDEN_FROM_AGENT`：为什么用黑名单

白名单要为**每个**服务逐一表态，加应用就要同步改，维护不动；而「Agent 不该碰」的服务是
少数、稳定、有明确特征的三类：

| 类别 | 例子 | 为什么摘 |
|---|---|---|
| 内部回填 | `md_material.set_fit_params` | 由 `strategy_fitting.approve` 在流程中调用；Agent 直接调会**绕过复核** |
| 外部回执 | `demand_pool.on_inbound` | ERP 回调入口，不是 Agent 发起的动作 |
| 被 batch 版取代的单行版 | `sales_forecast.calc_baseline` | Agent 该用 `calc_baseline_batch`；逐行调既慢又容易只改一半 |

> **只影响 Agent 的工具表，不影响 `self.fde.call`**——应用之间该怎么调还怎么调。
> 摘错了会让 Agent 少一条路，所以**不确定的宁可不摘**：工具面膨胀是概率问题，功能缺失是确定问题。

### 7.2 `GROUP_HINTS`：为什么需要它

组描述默认取前端 `PAGE_META` 的中文名与 crumb，而**相邻应用的 crumb 高度同构**
（都是「计划/排产专家域：xxx」这种），模型分不出该开哪个组。

实测中这是工具面收敛后**最大的新增失败模式**：`demand_pool` 被选成 `demand`、
`md_project` 被选成 `master_plan`。提示层专门写「什么时候用它、什么时候该用隔壁那个」。

每条提示写成**一句话用途 + 「查 X 用它，查 Y 用『另一个』」**的句式。

### 7.3 校验

`scripts/verify_agent_tools.py` 会检查：

- 两个声明里的服务名**都真实存在**（写错 = 静默失效，等于没声明）
- 声明文件里**没有重复的字典键**（Python 字典字面量重复键是**静默丢弃**的，肉眼看不出来）
- 角色绑定的应用**都有 `HOWTOUSE.md`**（见 `CONVENTION.md` §11；漏写会静默地不注入）
