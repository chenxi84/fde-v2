# 多智能体方案（Agent 编排层）

> 本文件是 Agent 编排层的**设计正本**。实现见 `fde_platform/agent_service.py`（编排后端）、
> `fde_platform/agentscope_bridge.py`（工具桥接）、`fde_platform/agent_roles.py`（角色装配）、
> `fde_platform/agent_tool_filter.py`（工具过滤 middleware）。
>
> 回归门禁：`python scripts/verify_agent_tools.py`（32+ 项，见 §八）。

---

## 一、分层：谁在干活

| 层 | 是谁 | 工具面 | 说明 |
|---|---|---|---|
| **leader** | 每个应用组一个（`<!--FDE_GROUP:<组>-->` 标记），另有总编排 | 平台工具白名单 + 业务工具按组懒加载 | 用户直接对话的入口；复杂任务自己建团队派活 |
| **worker** | 团队内成员，按业务角色（销售/计划/库存/交付…） | 平台工具白名单 + 业务工具按角色收窄后按组懒加载 | 只干本域的事，干完 `TeamSay` 回报 leader |
| **平台运维角色** | `integration`（接口集成）/ `scheduler`（定时任务） | 绑定的平台工具集合 | 仅 admin 可建 |

角色声明下沉到各组 `app/<组>/_roles.py`（见 `design-plus/智能体角色声明.md`）。

---

## 二、角色声明与装配

- `app/<组>/_roles.py` 导出 `ROLES = [{type, label, apps}]`；平台扫描装配。
- 角色 `type` 全局唯一，冲突时按目录名排序后者覆盖前者。
- 组级 Agent 工具声明（`app/<组>/_agent_tools.py`）见 `智能体角色声明.md` §七。

## 三、权限

> 本节被 `fde_platform/agent_roles.py` 的模块 docstring 引用。

**角色不是权限单位，「应用下的开放服务」才是。**

- 授权维度是 `应用.服务`（如 `psc/md_material.update`）。能否调用某服务，取决于是否被授权该服务；
  能否进入某应用，取决于该应用下是否有 ≥1 个被授权服务。admin 全通。
- 智能体的工具面**由该用户的授权 fail-closed 派生**——工具列表里不出现的东西，模型调不到；
  即便绕过（幻觉调用），`bridge.execute` 那一层也会按授权拒绝。
- 因此**角色只决定「工具面的形状」（收窄到哪些应用），不决定「能不能调」**。
  授权变更即时生效（每次组装 agent 时重新计算工具面）。

## 四、工具面收敛

> 本节内容为 2026-09 新增，起因见「为什么」一段。

### 4.1 为什么

工具数直接决定选择准确率。外部证据（arXiv:2605.24660）显示单次呈现超过 ~60 个工具即进入
选择塌陷区，且**多余的候选会主动伤害准确率**；实测改前 worker 把角色可见工具全部平铺，
`sales` 一个角色就有 **66 个**。

### 4.2 做法：统一按应用分组懒加载

- **leader 与 worker 都走同一条路**：常驻少量（平台工具白名单）+ 业务工具装进 `ToolGroup`，
  模型先调 `reset_tools` 激活需要的那一组，再在组内选工具。
- **分组维度是「应用」不是「角色」**。按角色分曾导致 psc 的 `sales` 一组就有 58 个工具
  （6 个应用合在一起），一激活直接进塌陷区。
- 分组口径收敛到 `agent_service._split_by_app()` **一个实现**，工厂与回归测试共用——
  两边各写一份迟早对不上，而「对不上」正是这类事故的形态。

实测：单次呈现 **44.3 → 14.9**；leader 最大组 58 → 14。

### 4.3 平台工具走显式白名单

`_LEADER_PLATFORM_TOOLS`（下发给 leader）与 `_LEADER_PLATFORM_DENIED`（不下发，admin 配置类）
两张**显式表**。新增平台工具未登记 → **启动告警 + 回归测试失败**。

> 曾用 `if ... continue` 隐式排除，结果把流程编排工具（`platform_run_flow` 等）连同 admin 配置工具
> 一起丢掉了——「让数字员工跑工作流」整条路不通，而工具定义在、middleware 放行，
> **运行期完全静默**。显式登记表就是为防这一类。

### 4.4 剪枝与组描述

| 机制 | 位置 | 作用 |
|---|---|---|
| `HIDDEN_FROM_AGENT` | `app/<组>/_agent_tools.py` | 摘掉 Agent 永远不该调的服务（内部回填 / 外部回执 / 被 batch 版取代的单行版） |
| `GROUP_HINTS` | 同上 | 组描述写清「何时激活、和谁别搞混」——相邻应用的 crumb 高度同构时，模型分不出该开哪个 |
| `_AGENT_HIDDEN_BUILTINS` | `agent_service.py` | Agent 面只留 `read_file`；`list_files`/`write_file` 会在组内**抢选择** |
| `_GROUP_INSTRUCTIONS` | `agent_service.py` | 随组激活下发「转域前先停用本组」，防止多组叠加把工具面涨回去 |

### 4.5 常驻文档：HOWTOUSE 而非 README

应用级文档见 `CONVENTION.md` §11。要点：**常驻注入的是 `HOWTOUSE.md`（约 500 tokens/应用）**，
完整 `README.md` 按需读。实测角色 prompt **14,170 → 3,404 tokens**。

## 五、角色工具隔离（软隔离 + 硬兜底）

> 本节被 `fde_platform/agent_service.py` 的模块 docstring 引用。

两层，缺一不可：

| 层 | 实现 | 作用 |
|---|---|---|
| **软隔离** | `agent_tool_filter.RoleToolFilterMiddleware.on_model_call` | 把越界的 FDE 工具**从喂给 LLM 的 schema 里剔除**——模型根本看不见 |
| **硬兜底** | 同类的 `on_check_permission` | 即使模型幻觉调用，也返回 `DENY` |

- 只过滤 FDE 工具（`platform_*` 或含 `__`），AgentScope 内置工具（`TeamSay`/`TeamCreate`…）不受影响
  ——worker 仍需 `TeamSay` 回报 leader。
- 角色识别靠 system_prompt 里的 `<!--FDE_ROLE:<role>-->` 机器标记，**不依赖 LLM 起名**。
- leader 侧用 `LeaderToolFilterMiddleware`：去掉平台配置工具；`scheduled` 会话额外禁 `ScheduleCreate`
  （防失控循环）。
- **读写边界交给 AgentScope 原生 `permission_mode`**，不在本层重复实现（见 §六）。

## 六、危险操作的 HITL（人在环）

### 6.1 判据：显式声明，不按名字猜

**曾用名字子串匹配**（delete/publish/cancel/approve/close…），两头都不准：

- **漏网**：`demand.calc_net` 会**联动冻结月度版本**（全链转只读），但名字里只有 `calc`；
  `freeze` / `disable` / `rollback` 同样漏掉。
- **误伤**：`outbound_plan.close_expired` 只是「到期自动关闭」的惰性结算，拦它等于每次查列表都要点确认。

现改为两条判据，任一成立即拦：

1. **需要人拍板**（即使技术上可逆）——它是「对全公司的宣布」或「要人担责的复核」：
   `publish` / `approve` / `reject`
2. **不可逆**（现有服务里没有能回到原状的操作）：
   `delete` / `disable` / `rollback` / `cancel`

外加一类「名字看不出但副作用不可逆」：`calc_net`（会冻结版本）、`freeze`。

**平台工具**用它们自己声明的 `_meta.dangerous`（定义处标注，18/31 为 True）。

> ⚠️ **声明必须被消费。** `_meta.dangerous` 曾长期是死字段——定义处标了 18 个 True，
> 而工厂从来没读过它，唯一生效的是那套名字匹配。这类「标了不用」与「工具静默消失」
> 是同一类失效。回归测试现在盯着 `_meta` 各键都有消费者（见 §八）。

### 6.2 三条执行路径的差异（关键）

| 路径 | 经过 HITL？ |
|---|---|
| 智能体对话里调工具 | ✅ 经过 |
| **API 定时任务**（`scheduler`） | ❌ 走 `_platform.call` 直调服务 |
| **流程节点内调工具**（`flow`） | ❌ 走 `bridge.execute` 直调 |

**这条差异是刻意的**：无人值守的任务不能被确认框卡死。所以**不能把「写操作一律 ASK」当解法**。

数字员工定时任务若要写数据，应在**创建时就选** `permission_mode=bypass`
（**授权在配置时，而不是执行时无人可问**）；默认 `dont_ask` 下 ASK 转 DENY，是安全兜底。

> 被拒的写操作必须有可见信号（告警 / 任务状态），否则又是「静默失败」。

## 七、工作纪律注入

`agent_roles.AGENT_DISCIPLINE` 注入每个业务角色的 system prompt：

- 能用工具查证的事，一律先调工具再回答
- 参数不全也先用工具查，确实查不到再问用户
- 一次调一个工具，拿到结果再决定下一步；**发现调错了立刻换**

**起因（恢复率实测）**：失败分两类，命运完全不同——
「**选错工具**」拿到真实返回后约一半能在下一轮自己换对（实测 3/6，平均 1.5 轮）；
「**压根不调工具 / 不开组**」直接回一段文字，对话就此结束，**没有任何纠错机会**。

后者是终端失败，而 HOWTOUSE 管的是「按什么顺序调」，管不到「该动手时不动手」，
所以这条纪律单独写死。

## 八、回归门禁

`python scripts/verify_agent_tools.py` —— 守四类失效（都是「静态看不出、运行期静默」那种）：

| 守卫 | 防什么 |
|---|---|
| 平台工具登记完整性 | 工具**静默消失**（漏登记即失败） |
| 剪枝声明有效性 + AST 查字典重复键 | 声明写错/写重 → 静默失效（Python 字典重复键是**静默丢弃**的） |
| 各路径分组规模上界 | 工具面**静默膨胀** |
| HITL 清单有效性 | 该拦没拦 / 误伤 / `_meta` 死字段 |

另有 `fde_platform/scanner` 的**规范引用完整性**检查：源码里引用的
`design-plus/<文档>` 必须真实存在——互指断裂后实现演化了规范却不会有人察觉。
