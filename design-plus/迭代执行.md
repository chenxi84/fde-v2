# 迭代执行（修改现有应用/组）

> 面向「**对已构建应用组提出改动需求**」的场景：加字段 / 改规则 / 加服务 / 改前端等。
> 执行体（AI 代理如 Claude Code / workbuddy，或工程师）**动手前必读本清单**，按「先读 → 改代码 → 同步改文档 → 跑测试」推进——**别只改代码，漏改文档、漏跑测试、漏重冻结契约**。
> 本清单是九步法（`工具链使用说明.md`）的「迭代版」：构建是端到端九步，迭代是围绕改动点做**定向重执行**。

## 一、迭代前必读（先读，缺即补/确认）

按依赖顺序读，理解现状再动手：

| 顺序 | 读什么 | 用途 |
|---|---|---|
| 1 | `design-plus/工具链使用说明.md` | 九步法全景 + 门禁 + 契约冻结纪律 |
| 2 | `app/<组>/architecture.md` | 组级架构：聚合根清单 + 关系，定位改动落在哪个应用 |
| 3 | `app/<组>/<应用>/应用详设.md` | 后端详设（US/BR/FUNC/PERM），改后端必读 |
| 4 | `app/<组>/_contracts.md` | 冻结的服务契约（服务名/入参/返回），改签名前必读 |
| 5 | `app/<组>/测试用例.md` | 后端测试用例（主链 + 分支），改逻辑必读 |
| 6 | `app/<组>/<应用>/前端详设.md` + `前端测试用例.md` | 前端详设/用例，改前端必读 |
| 7 | `design-plus/CONVENTION.md`（后端）/ `VIEW_CONVENTION.md`（前端） | 编码规范正本，唯一来源 |
| 8 | `app/<组>/术语表.md`（**若存在**） | **命名的唯一来源**：改业务名（字段/对象）前必读，否则会造出"源与投影不一致" |

## 二、改代码 + 同步改文档

改动落地时，代码与文档**同步更新**（不脱节）：

| 改了什么 | 同步改什么 |
|---|---|
| 改后端逻辑（规则/字段/服务） | `应用详设.md` 对应 US/BR/FUNC/PERM |
| 改了服务签名 / 入参 / 返回 | **无条件重跑 `python -m fde_platform.contract_dump <组>`**，重新冻结 `_contracts.md` |
| 改了业务逻辑 | `测试用例.md` 中受影响的用例 |
| 改前端页面 | `前端详设.md` + `前端测试用例.md` |
| **改/加/删了业务名（字段名、对象名）** | **先改 `app/<组>/术语表.md`，再改产出**（详设 / `architecture.md` / 页面标签）。见下 |

### 业务名改动：术语表是源，先改表

术语表是**命名的唯一来源**，所以命名类改动**必须从表改起**，再改依赖它的产出（②的字段表、
`architecture.md` 的聚合根列、页面表头）。反过来做（先改产出、表放着）会造成**源与投影不一致** ——
而"命名核对"（《工具链使用说明》第 3 步门禁 / 第②步门禁的「业务名合规」）会把它查出来。

- **新增名**：直接在表里加行（原词 / 语境 / 业务名）。
- **改名**：改表里那一行的业务名，然后**回改所有已引用它的产出**。
- **废弃名**：**不要删行** —— 标成 `~~业务名~~（已废弃，v<版本> 起由 <新名> 取代）`。
  理由：删了之后，历史产出里的旧名就再也查不到出处；标注废弃既保留了追溯，也让人知道别再用。

> **契约是两级的**：改后端代码后，`_contracts.md` 里的旧冻结已过期，必须重跑 `contract_dump` 重新冻结，否则前端详设/测试消费过期契约（依赖屏障）。

## 三、跑测试（顺序，红线不可逾越）

1. **静态扫描入闸**：`python -m fde_platform.scanner` → 退出码 0（校验 `self.fde.call` 目标与参数契约）。
2. **dev server 不用停**：影子库只做**只读复制**、无锁冲突（实测：服务在跑的同时跑链测试与 view e2e 均 PASS）。只有改用 `dbguard`（移库）时才必须先停 —— Windows 下运行中的 `main.py` 占 `.db` 句柄会让文件移不动。
3. **后端主链**：`python app/<组>/tests/verify_chain_<组>.py`（影子库隔离，跑绿）。
4. **前端单页**（若改前端）：`python app/<组>/tests/verify_view_<组>_<应用>.py`。

## 四、红线（不可逾越，规格见 `design-plus/测试执行.md` / `前端测试执行.md`）

1. **数据库隔离（最高优先）**：verify 脚本在**影子库**（`fde_platform/shadowdb.py`）下跑 —— 业务库只读复制到临时目录，真库零字节接触，绝不污染用户 demo 数据（`dbguard` 移库是备用路径，代价是要先停服）。
2. **并行粒度**：影子库各用各的临时目录 ⇒ **不同组可并行**；**同一个组不要并行**（争同一份业务数据口径）。`dbguard`（移库）那条路仍带跨进程锁（`.dbguard.lock`），并行会被拒绝。
3. **跑前杀 dev server**。
4. **静态扫描入闸**（scanner 退出码 0）。
5. **前端零报错**：0 console error · 0 pageerror · 0 HTTP≥400。

## 五、一句话

**迭代 = 先读组文档 → 改代码 + 同步改文档（含契约重冻结）→ 跑 scanner + verify_chain + verify_view**。缺任何一环都会造成代码/文档/契约漂移。
