# 前端测试执行 · 第⑨步技能规格（测试用例 → 可运行视图验收脚本）

> **版本**: v1.1（2026-08-08 粒度重构：逐应用执行 + 组级补充脚本）  **创建日期**: 2026-08-02
> **适用人员**: 应用构建第⑨步的执行体（AI / 工程师）
> **目的**: 把第⑧步产出的用例**逐应用翻译成可直接运行的 playwright 视图验收脚本**（每应用一个），另把组级补充用例翻译成一个组级脚本，在**影子库**隔离 + 无头 Chromium 下真实驱动浏览器跑通，每个脚本各自达成 **0 console error · 0 pageerror · 0 HTTP≥400** 的硬指标。
> **本步只消费第⑧步用例文件**——它们是怎么测的唯一设计来源；本规格规定「如何把用例落成脚本并跑通」，不另起测试设计、不绑定具体应用组。

## 🧭 使用契约：作为「前端测试执行」技能（应用组构建 · 第⑨步）

### 技能定位（九步法）

```text
第⑥步  前端设计（《前端设计.md》）          _contracts.md + 各应用详设 → 逐应用 前端详设.md + dashboard 设计  ← 已定义
            ↓
第⑦步  前端编码（《前端编码.md》）          前端详设.md → app/<组>/<应用>/view.{js,html}            ← 已定义
            ↓
第⑧步  前端测试用例（《前端测试.md》）      逐应用前端详设 → 逐应用 前端测试用例.md + 组级补充一份   ← 已定义
            ↓
★第⑨步  前端测试执行（本文件）              逐应用用例 → app/<组>/tests/verify_view_<组>_<应用>.py + app/<组>/tests/verify_view_<组>.py（0 报错跑通） ← 本规格
```

> 第⑧步与第⑨步即「生成与执行分离」的两半（与后端 ④⑤ 同构）：第⑧步产出**用例（数据）**，第⑨步把用例**逐应用翻译成 playwright 脚本并运行**。
>
> **粒度（v1.1 重构）**：逐应用脚本各管一页（admin 会话：本页渲染/列表/模态/表单 + 本会话 0 报错），可单独跑、单独 triage、单页演进只改一个脚本；组级脚本 `verify_view_<组>.py` 管壳/菜单序/dashboard/受限用户。逐应用脚本是范式 `design-plus/前端验收样板/verify_view_e2e.py` 的**按页切片**，组级脚本与之**同构**（去掉逐应用段）。

### 必给参数
- 英文应用组名 `<组>`（snake_case），逐字绑定 `app/<组>/`。
- （可选）`<应用名>` 子集：只翻译/运行指定应用的脚本；缺省＝全部逐应用脚本 + 组级脚本。
- 会话范围：**逐应用脚本恒为 admin 单会话**；受限会话（受限用户菜单收敛）**仅在组级脚本**。

- **逐应用**：`app/<组>/tests/verify_view_<组>_<应用>.py`——可独立运行的单页验收脚本。

## 用例五要素 → 脚本映射（核心方法论）

| 用例要素 | 脚本落地（照 `verify_view_e2e.py` 范式） |
|---|---|
| **页面** `<组>:<key>` | `goto` 入口 URL + `location.hash = '#/<key>'`；逐应用脚本只切到本页（切页后断言主区重建，`page-in` 实例换新）；组级脚本遍历菜单。 |
| **前置造数** `应用.服务(参数)` | `pg.evaluate` 内 `fetch('/api/apps/<应用>/call/<服务>', {method:'POST', body: JSON.stringify(参数)})`——带会话 Cookie 走**真实 REST**（pitfalls #18），不绕平台直连 DB；单据号从响应 `data` 捕获串联。逐应用脚本按本用例 §0 字典**自足造数**（含跨应用前置），不依赖其他脚本的残留数据。 |
| **操作** 浏览器动作 | playwright locator：点单号 `button.b-link:visible:has-text("<精确单号>")`、填表 `fill`、点按钮 `button:visible:has-text(...)`（隐藏 ≠ 不存在，pitfalls #14）。 |
| **断言** 模态全字段 | `wait_modal()`：轮询 `.modal-mask:visible .loadbox` 消失再断言（pitfalls #16）；多 `.modal-bd` 取 `.first.inner_text()`（#15）；逐字段标签/值 `assert in`。 |
| **断言** 挂载防粘滞 | 非看板页 `assert pg.locator(".kpi").count() == 0`（看板特征元素，pitfalls #2）——**不可省**，否则首页粘滞会假过。dashboard 页断言相反（`.kpi` > 0），在组级脚本。 |
| **断言** 受限菜单（**仅组级脚本**） | 播种受限角色 `users.set_role_page_grants("limited_role", [...])`（清单逐字取自组级用例 §5）→ 新 browser context 登录 → 菜单项集合断言 + 直访无授权 hash 回落断言（目标 = 菜单首项，pitfalls #38）。 |
| **断言** 0 报错 | 每个脚本会话起始挂 `page.on("console"/"pageerror"/"response")` 收集器；结尾 `assert` 三个集合为空（favicon 404 除外；受限会话 403 属预期执法，豁免）。 |

## 执行环境与隔离（铁律，见 VIEW_CONVENTION §工作流第 4 步与 pitfalls #39）

1. **路径锚定**：脚本在 `app/<组>/tests/` 下，项目根经范式 `_project_root()` **向上查找 `fde_platform/`** 定位（落点深度不固定，勿写死 `parents[N]`）；`os.chdir(ROOT)`；`sys.path` 加 `ROOT`（import `fde_platform`、`fde_platform.shadowdb`）。
2. **数据库隔离**：进入即 `shadow_dbs(env=True, inprocess=False, config=True).__enter__()` + `atexit` 注册退出；随后**必须 `shadow_clear(<组>)` + `shadow_clear_prefs()`**——副本是**真库的拷贝**，不清表会撞造数主键、且结果取决于谁的机器上跑过什么（偏好是操作者本机状态）。`env=True` 是必需的：view e2e 是 `subprocess.Popen([python, main.py])` 起平台的，进程内补丁过不去，只有**环境变量能穿透子进程**。**每个脚本各自隔离**：脚本间不共享数据，各自从空表造数。
3. **不用停 dev server**（影子库路径）：只读复制无锁冲突，实测「服务在跑的同时跑链测试与 view e2e 均 PASS」。**只有改用 `dbguard`（移库）时才必须先停**——Windows 下运行中的 `main.py` 占 `.db` 句柄会让文件移不动。
4. **动态端口起平台子进程**：脚本自行 subprocess 起 `main.py`（随机空闲端口），跑完（含失败，经 atexit）终止；不依赖外部已起的服务器。注意：逐应用脚本也起**全组平台**（页面依赖跨应用服务与壳），隔离粒度在数据库、不在平台。
5. **并行粒度**：影子库各用各的临时目录（`tempfile.mkdtemp(prefix="fde_shadow_")`）⇒ **不同组可并行**。**同一个组不要并行**（会争同一份业务数据口径），逐应用脚本按序跑也更易 triage。⚠ `dbguard` 那条路仍持跨进程独占锁（`fde_platform/.dbguard.lock`），并行会被干净拒绝——**勿绕**（2026-07-30 并行踩踏曾洗掉用户库）。
6. **playwright 前置**：`pip install playwright && python -m playwright install chromium`（无头 Chromium）。

## 执行铁律

- **真实链路**：造数走 REST、页面经平台壳真实渲染（动态 import 工厂 + x-html 装配），不 mock 前端、不直连 DB。
- **数据字典只引用不新造**：§0 冻结标识贯穿全脚本；单据号一律从造数响应捕获串联。
- **逐应用先、组级后**：先跑绿全部（或指定）逐应用脚本，再跑组级脚本——单页渲染不通时，菜单/受限断言连环 fail，无从 triage。逐应用脚本内部单会话直跑（无 phase 之分）。
- **切页必 reload 场景意识**：注册表 mtime 缓存——新写/改页面后首次验证要 `pg.reload()` 才重扫（pitfalls #6）。
- **期望值从页面元数据现算，不手抄**（2026-09-17 补，**实测踩过**）：
  菜单序这类「另一个文件里已经声明过一次」的期望值（各页 `PAGE_META.order`、平台页 `PLATFORM_PAGES`），
  脚本要**现场读源文件算**，不要把清单抄进脚本。PSC 实测：手抄的 `EXPECTED_MENU` 与真值差三处
  （漏 `material_360`、序位错、没算排在最前的平台置顶页），**组级脚本因此一直是红的**。
  **抄一份就多一处会漂的地方**。
- **豁免列表必须受检**（2026-09-17 补）：`ignored` 这类"预期内异常"的收集，**光收不看等于给静默吞掉开口子**
  —— 任何新形态的 4xx / console error 落进豁免分支就此消失，而「0 报错」照样显示通过。
  收尾要逐条核对豁免理由（favicon / sourcemap / 受限会话 403），并把本次豁免条数与样例打印出来。
- **脚本必须自己钉住 stdout 编码**（2026-09-25 补，**实测踩过**）：脚本顶部（imports 之后、任何输出之前）必须有
  ```python
  try:
      sys.stdout.reconfigure(encoding="utf-8", errors="replace")
  except Exception:
      pass
  ```
  原因：本机控制台代码页默认 GBK，而断言文案里常有 `⇒` `✓` `✗` `⚠` `−` 这类**非 GBK 码位**
  （`≥ ≤ × →` 有码位、**不会**崩）。没有这一行时，`print`/日志封装**自己**抛 `UnicodeEncodeError` ——
  症状是**断言算完了却报不出来**（`FAIL @` 那行都打不出），**其后用例全部不执行**，而现场看起来像断言失败。
  实测：`verify_view_nasa_pms_stakeholder.py` 的 `FE-32` 就这么"消失"过一次；同批 22 个脚本有同一缺陷。
  `errors="replace"` 是有意的：产出不该因一个箭头符号中断（宁可打成 `?`）——**别忘了这一行由闸门兜底**：
  `scripts/verify_test_script_encoding.py`（`run_gates.py` static 层「测试脚本输出编码」）会扫
  `print`/`assert`/`raise`/**任何函数调用实参**里的字符串，命中即红。
- **软断言只作报告、不入闸**（2026-09-17 补）：前端有一类用例的**规格本身就是计数/存在断言**
  —— 渲染步（`main .card > 0` 且 `.kpi == 0`）、豁免步（"按钮集合恰为 …"）、终态步（"无可见操作按钮"）。
  把它们当闸会**误红**，而常红的闸会训练人绕过它。故 `view_coverage.py` 里：
  **「无断言步」入闸（V7，无歧义）**，**「仅软断言步」只打印计数**（供人复查）。
  实测分布：214 步中仅软断言 14 步（多为上述三类，正当）、无断言 6 步（已补）。
- **`VT-` 编号必须写进脚本**（2026-09-17 补）：脚本里每段断言上方标注它对应哪条用例
  （`# §N VT-XXX-NN 用例名`）。PSC 实测 **11 个脚本一条编号都没有** —— 用例与断言的对应关系
  只存在于作者脑子里，删用例、删断言都无人能发现。编号写进来之后，`scripts/view_coverage.py`
  才能做「文档 ↔ 脚本」双向对账（V1–V5）。

## 失败 triage（首轮几乎不会全绿，须归类）

用例是**未运行**生成的，选择器/字段标签为推断，故首跑必有出入。每个 FAIL 归三类（报告按脚本名定位应用）：

1. **脚本 / 用例翻译错**——选择器没加 `:visible`、模态 `.modal-bd` 撞 strict mode、字段标签文案不符、造数入参名不对 → **修脚本或回填用例**（并据实修正对应用例文件 §7 待确认）。
2. **前端代码 bug**——第⑦步视图缺陷（漏字段、svc 变量拼名致受限 403、reactive 未同步建好喷 null、漏默认导出空页）→ **记录**，反馈第⑦步修复，不在本步擅自改 `view.*`。
3. **真实应用 bug**（少见）——后端服务返回结构与契约不符等 → 记录，反馈第③步。

报告须能逐条定位：失败在哪个脚本、哪个 `step`、哪条用例、实际 DOM/报错是什么。

## 验收标准

- **每个脚本**可独立运行：`python app/<组>/tests/verify_view_<组>_<应用>.py` / `python app/<组>/tests/verify_view_<组>.py`（跑前无 dev server、无并行 verify）。
- 全部逐应用脚本 + 组级脚本用例**全绿**，或每个 FAIL 已明确 triage 并记录。
- **0 console error · 0 pageerror · 0 HTTP≥400**（favicon 除外；受限会话 403 豁免）——**按脚本会话计**，任一脚本任一非豁免报错即该脚本不通过。
- 运行**不污染用户真实数据**（影子库只读复制，测试写入落在副本、退出即弃）。
- 报告逐脚本、逐条 PASS/FAIL + 失败定位 + triage 归类；向用户报告入口 URL + 页面清单 + 各脚本验证结果。

- **覆盖度门禁**：本步产出须经独立的覆盖度检查——对照本规格规定的上游输入，逐项验证覆盖完整性。覆盖度 < 100% 不得进入下一步。具体门禁条件见 `design-plus/工具链使用说明.md` 对应步骤的「完成门禁」段。
- **可追溯性判据 V1–V6**（2026-09-17 补，机械判据 = `python scripts/view_coverage.py`，由 `scan_structure.py` 接进闸）：

  | 判据 | 问的是 | 为什么要它（PSC 实测） |
  |---|---|---|
  | **V1 可追溯** | 每个脚本至少引用一条 `VT-` 编号 | 11 个脚本零编号，"用例与断言无对应关系" |
  | **V2 脚本→文档** | 脚本引用的编号必须在它的用例文档里 | 防自造编号；实测有脚本独有断言未回写文档 |
  | **V3 文档→脚本** | 用例文档每条编号必须被脚本引用 | **防"写了没测"**：实测 29 条（含"某页三条过滤用例整体无覆盖"） |
  | **V4 有脚本必须有文档** | 逐应用脚本要有对应用例文档（组级页由组级文档覆盖） | 实测 2 个组级页有脚本无用例、`sales_history` 有脚本无文档 |
  | **V5 豁免受检** | 收集了 `ignored` 就必须校验它 | 17 个脚本有这个口子 |
  | **V6 x-if 单根** | 每个 `<template x-if>` 只能有**一个**顶层子元素 | Alpine 只挂载 `firstElementChild`，多根**静默丢弃**：实测「批量导入的提交按钮」与「工作台的最近错误内容」两处凭空消失，**读 HTML 读不出来** |
  | **V7 无断言步** | 每个 `step(...)` 里至少有一条 `assert` | 整步一条断言都没有 = **只证明「没抛异常」**；PSC 实测 214 步里有 6 步如此（补断言后归零） |

  > 判据本体的三处自纠也值得记：段名正则漏数字段名（`VT-360-01`）、`for x in ignored` 没被认成"已校验"、
  > **正文里的交叉引用被当成"本页用例"**（`sales_forecast` 文档引用了 `md_customer` 的编号）——
  > 最后一条与后端 `scan_structure.py` 为 TC 编号写的规矩同源：**只认行首的编号**。
- **⚠ 顺序警告**：本步产物是「用例 → 脚本」，脚本跑通后若补写了用例，**必须同时回写用例文档**
  （PSC 实测：`sales_history` 是"先有脚本、后补用例文档"，`inventory_projection` 的日历视图整块
  约 50 行断言文档里连章节都没有）。**「先有脚本」不是合法顺序**，但一旦发生，就得把事实固化成可对账的形态。

## 收尾衔接

- **白名单**：新脚本的精确命令（逐应用 `Bash(python app/<组>/tests/verify_view_<组>_<应用>.py)` ×N + 组级 `Bash(python app/<组>/tests/verify_view_<组>.py)`）加进 `.claude/settings.json`。
- **页面演进同步**（pitfalls #38）：此后新增/调整页面——新应用各加一个逐应用脚本；**组级脚本**里 `limited_role` 授权清单与直访回落断言、菜单序断言必须逐字对齐当前菜单（本耦合极易漏，改页面即改组级脚本）。
- **视图资源红线自检**：验收中如发现需要 `/app/<名>/<path>` 通配 serve 才能过——**是设计错误**（视图只经写死端点 `/app/<名>/view.{js,html}`，同目录 `.py`/`.db` 绝不暴露；见 README §测试与验收红线），修页面而非改平台。

## 命名与边界

- 脚本落点 `app/<组>/tests/`（产物随应用组归档）：
  - 逐应用 `app/<组>/tests/verify_view_<组>_<应用>.py`（应用名逐字取文件夹名，如 `sales` 组的 `sales_order` 应用 → `verify_view_sales_sales_order.py`）；
  - 组级 `app/<组>/tests/verify_view_<组>.py`（与范式 `verify_view_e2e.py` 同构）。
  与后端第⑤步**同落点**——前后端测试产物统一随组归档于 `app/<组>/tests/`（各带 `verify_view_` / `verify_chain_` 前缀与组后缀报告，互不冲突）。
- 本步**只翻译并运行测试**，不改前端 / 应用代码；发现的 bug 分别反馈第⑦ / 第③步。
- 测试设计**只来自第⑧步用例文件**（逐应用 + 组级补充），不凭前端详设另起用例（保持「生成与执行」单一数据源）。

## 平台化入口（第⑨步自动化任务）

平台 `/groupbuild` 页面 ⑫ 前端测试执行（任务 `kind="fverify"`，`fde_platform/groupbuild_runner.py`）
把本步产品化为一键任务（生成 + 运行一体）：

- `gather`：硬预检逐目标应用 `前端测试用例.md` + 组级补充用例（⑪产出，缺 → 失败指回⑪）+ `playwright` 可导入（不可用 → 失败带安装命令 `pip install playwright && python -m playwright install chromium`）+ 范式 `design-plus/前端验收样板/verify_view_e2e.py` 存在。
- `gen`：N 应用脚本 + 1 组级脚本同池摊平生成（`GROUPBUILD_FVERIFY_PARALLEL` 默认 4）；每脚本输入 = 铁律 preamble（基建段照抄范式 / 造数组限定 REST / 选择器规避 / **stdout 编码钉 utf-8** / PASS·FAIL@STEP 骨架 / 只写脚本不改码）+ 执行规格摘要 + 范式全文 + pitfalls + 对应用例全文；门禁（语法可编译 + PASS/FAIL@ 骨架 + **影子库隔离** + playwright 启动）
（⚠ 门禁里的「隔离」= 脚本含 `shadow_dbs(...)` + `shadow_clear(<组>)` + `atexit` 注册退出；**别再按 `isolate_dbs` 卡**——那是备用路径）不过 → 整份重出（≤`GROUPBUILD_FVERIFY_REPAIR` 轮，默认 2）。
- `run`：脚本落 `app/<组>/tests/verify_view_<组>_<应用>.py` + `app/<组>/tests/verify_view_<组>.py`，**逐脚本串行真跑**（影子库各用各的临时目录，**同组仍不并行**；单脚本动态端口子进程 + 超时 `GROUPBUILD_FVERIFY_RUN_TIMEOUT` 默认 600s）；verdict 按 rc + PASS 打印解析，失败步取 `FAIL @`/`ERROR @` 行；单脚本失败 → LLM 修脚本重跑 ≤2 轮（错误签名去重提前终止；triage 纪律：脚本错自动修，前端/后端 bug 保持忠实断言只记录）；单脚本失败不阻断后续，全败才 raise。
- `write`：报告 `app/<组>/tests/前端测试报告.md`（逐脚本 verdict 表 + 失败尾摘 + triage 去向）；最终判据 = 全部脚本 PASS ∧ 各会话 0 报错。

API：`POST/GET/DELETE /api/groupbuild/groups/<组>/fverify`（POST body `{app_names?}` 缺省全部已有用例的应用；GET `?report=1` 下载报告、`?zip=1` 脚本包；DELETE 删该组全部脚本 + 报告）。隔离语义：**影子库只读复制**（`shadow_dbs`）——真库零字节接触，运行期间可照常使用平台；测试写入落在临时副本、退出即弃 ⇒ **用户数据零污染**。跑前对副本 `shadow_clear(<组>)` + `shadow_clear_prefs()`，起点 = 空表。
