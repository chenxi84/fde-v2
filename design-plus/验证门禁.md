> **版本**：v1.0（2026-09-15 首版，与 PSC 那轮体检同步产出）
> **适用**：改完应用代码 / 加完服务之后——`python scripts/run_gates.py`
> **正本入口**：`scripts/run_gates.py`（门禁）· `scripts/verify_psc_oracles.py`（对账体检）· `scripts/scan_structure.py`（结构检查）

## 一、为什么要有这一层

`design-plus/测试执行.md` 规定的第⑤步（`verify_chain_<组>.py`）是**必要的**，
但它有一个结构性局限，必须认清：

> 它的用例来自《测试用例.md》，而《测试用例.md》和**代码**都是从同一份《应用详设.md》生成的
> —— **同源 ⇒ 同一个盲点**。它只能证明「我设计的那条路走得通」。

**实证**：2026-09-15 对 PSC 做了一轮体检，共处理 **9 项问题**，**没有一项**是 `verify_chain_psc.py`
能抓到的（它有 89 条用例、全部通过）：

| # | 缺陷 | 为什么同源测试抓不到 |
|---|---|---|
| B-01 | 预测「双源合成」退化成单源：客户没报数时，算好的统计基线被丢弃、最终预测静默归零（三个月合计 6025.88 件没进毛需求） | 演示的客户预测只覆盖 4 个物料，用例全在「有预测」那条主链上 |
| B-04 | `build_gross` 在无预测可合成时返回「**成功，共 0 个物料**」——什么都没做却声称成功 | 用例从不构造「空输入」 |
| B-05 | 单行 `calc` 与 `calc_batch` 对冲选型**结论相反**（`BYD-HAN-BRK`：速度对冲 vs 库存对冲，差 1415 件组批库存） | 批量路径修过、单行路径没修，用例只覆盖了批量 |
| B-07 | `list` 服务漏取字段 ⇒ **键在、值恒为 None**（`strategy_fitting` 漏 6 个、`md_material` 漏 `sigma_l`） | 用例只查键存在、不比对跨路径同值 |
| — | 前序链成环写入侧不拦（只拦自指） | 用例只测「前序不存在」 |
| — | 两个死适配器（声明了外部数据来源、全仓无调用点） | 结构性问题，用例不扫描 |

**更根本的一条观察**：这些缺陷里 **4 个是「同一件事只修了一半」**——
速度对冲只修批量路径、静默降级只修推移表、BR-15 只实现了四分之二、`list` 漏字段只修了一个应用。
**修的都是「被报告的那个症状的那条路径」，而不是「这一类」。**

> **只有校验器能守住「同一件事的所有路径」。** 靠人记得，一定会漏。

## 三、三条纪律（改体检脚本前必读 —— 这是它可信的全部理由）

### 1. 直连 SQLite，**绝不 import `app/` 下的任何代码**

对账器一旦复用被测代码，就退化成自证 —— 代码错了它跟着错，且完全看不出来。
对账的期望值只能来自**业务文档**（如 `销售预测与库存策略说明.md` 的公式），不能来自实现。

### 2. 靠「**冗余**」而不是「复算」

不去猜实现约定（「近 12 期」怎么取、取哪些客户），只断言**两条已知口径必须给出同一个数**。
本项目已复用的冗余关系：

- 同一个量的两条独立推导路径（日需求：A 支 vs B 支）
- 同一份数据的两个服务（`get` vs `list`、`calc_batch` vs `calc`、`*_batch` vs 逐行）
- 跨应用同源（毛需求 = 预测汇总 + 水位上限；主计划 = 净需求）
- 明细聚合 vs 汇总表

### 3. 每条对账**先验分母非空**

空集上的断言是真空。本项目踩过一次：`verify_agent_quality.py` 的 `x_planner_surface`
因空集让整条断言变成摆设。所以体检脚本里有 `find()` 闸——空集一律 **SKIP**，
并在报告里写明「本条不构成证据」。

> **⚠ 分母闸必须加在「真正在做比较的那一层」（2026-09 补，两次踩坑换来的）**
>
> `find()` 只保证**外层**集合非空。若判据内部还有一层筛选/循环，**内层可能被全部跳过** ——
> 那时外层分母是满的，报告显示 PASS，而**一个字都没比**。
>
> 实例：新增的 `A14`（BR-09 合并转移）首版就是如此 —— 一个日期格式笔误
> （`_shift_month` 只认 `YYYY-MM`，而版本号是 `YYYYMM`）让每个比对组合都被 `continue`，
> 外层「物料对」非空所以 `find()` 通过，**判据报 PASS 却零比对**。
>
> 规矩：**凡是「计数型」的内部循环，都要给计数加闸** —— `if checked == 0: FAIL(...)`
> 并写明「判据成了空规则，本次 PASS 不可信」。同理，静态规则收窄后若进入判据的方法数为 0，
> 也要 FAIL（见 `scan_structure.py` 的 `report_funnel`）。
>
> 为什么这条值钱：**「空规则永远通过」是这类工具最致命的失效方式** ——
> 它不会报错、不会变红，只会让人以为查过了。ArchUnit 的文档把它列为已知陷阱
> （"a rule matching zero types always passes"）。

### 附：**下断言前先读 docstring / 详设**

本轮对账器**自己犯了 3 次**同一类错：把**设计行为**当缺陷。
（补库单分级补齐的两张单、库存对冲 `C=B=0`、前序链「成环在已访问处断链」）
判据的粒度/范围必须对齐**业务的真实身份**，过粗的键会把设计行为报成缺陷。

## 四、八组判据

| 组 | 判据 | 期望值从哪来 | 能挖出什么 |
|---|---|---|---|
| **A** | 对账（冗余双路径） | 从业务文档重算 / 另一条路径 | 算错了 |
| **C** | 不变式（引用完整性 / 枚举 / 非负 / 唯一性 / 审计列 / 状态机） | 永远必须成立 | 不该发生的发生了 |
| **S** | 静态探针（死适配器、空转断言、分页约定） | 结构 | 写了但没接上的东西 |
| **G** | 零触达服务（`get`==`list`、投影==列表、稀疏 payload 不清空字段） | 两条读/写路径 | 零证据的角落 |
| **D** | 变形与幂等（连跑两次结果相同、换序必须报错） | 不需要期望值 | 不确定性 / 顺序依赖 |
| **E** | 边界与对抗注入（环、负值、日期边界、自反） | 规则应当拒绝 | 校验缺口 |
| **F** | **静默降级反证**（取不到数必须 raise，而不是按 0/空继续） | 不该静默 | 最难发现的一类 |
| **H** | **穿透**（把 stub 适配器换成非零受控值，验证从未在非零输入下跑过的公式） | 注入受控值 | 恒零/stub 掩盖的错 |

**F 组价值最高**——本轮 9 项里有一半属于「不报错、不崩溃、只是答案错」。
做法是人为制造「应该取到数却取不到」的局面，断言**必须报错**。

## 四之二、隔离机制选型（**场景 × 机制**，2026-09-17 定）

**没有一种机制能满足全部场景**，所以按场景选 —— 它们**不是新旧关系，是两条路**：

| 场景 | 用什么 | 为什么不用另一个 |
|---|---|---|
| 链测试 `verify_chain_*` | **影子库** + 副本上清表 | 移库要求停服；清表会洗真库 |
| 前端 e2e `verify_view_*` | **影子库**（`config=True`） | 它要播种 admin（写 `config/auth.db`），config 不影子化就污染真库。⚠ 2026-09-18 收窄：`config=True` **只复制 auth.db**（唯一认 `FDE_CONFIG_ROOT` 的库）——原先整份 `config/`（103 MB，其中 agent 会话库 102.6 MB）每脚本白拷一遍、一轮 2.3 GB |
| 对账体检（破坏性注入） | **影子库**（不清表） | 移库会把数据移走、检查无从下手；清表会洗掉对账对象 |
| **eval** | **真库 + 数据指纹** | ⚠ **不能用影子库**：ground truth 在它本进程算，而智能体对话走 HTTP 打到**另一个已跑着的平台** —— 只影子化本进程 ⇒ ground truth 看副本、智能体写真库 ⇒ **指纹失效而污染照旧**，比不改更糟 |
| 备用 | `dbguard.isolate_dbs()`（移库） | 要停服，但真库被移走、最保险 |

**`FDE_DB_ROOT` / `FDE_CONFIG_ROOT` 为什么要两个**：业务库与平台库的隔离需求不同 ——
view 要影子化 `auth.db`（不然播种落到真库），而 eval 要**真的 `llm.db`**（不然"没配模型"跑不起来）。

## 五、影子库：破坏性检查的安全底座

`verify_psc_oracles.py` 的 `shadow_sandbox()`：把 17 个业务库**复制**到临时目录，
在**本进程内**把 `fde_platform.db.get_connection` 的路径重定向到副本。

- **平台代码一行不改**（不动 `runtime.py`）
- **不需要停 dev server**
- **真库零字节接触**——每轮跑完自动比对 20 张表的行数+内容哈希

因此可以放心做破坏性检查：注入负值、构造环、连跑十次、清空某张表看下游反应。
（`E` 组与 `F` 组就是这么做的。）

> 环检测这类**可能挂死**的检查必须再隔离一层：**子进程 + 超时**（见 `scenario_boundary` 的
> `_CYCLE_CHILD`）。进程内跑若真挂死，整个体检就卡住了。

### 五之一、副本的**目录布局**必须与解析规则一致（2026-09-18 修 + 固化）

影子库把库**复制**到临时目录，再由 `FDE_DB_ROOT` / `FDE_CONFIG_ROOT` 把读写导向副本。
这里有个**谁都不报错**的失败方式：**复制到一个位置、运行期去另一个位置找**。

实测过（2026-09-18）：`_copy_all` 按**仓库树形**落盘（`<影子>/app/<组>/<应用>/<应用>.db`），
而 `runtime.py` / `users.py` / 体检自带的 `shadow_sandbox()` 三处都按**扁平**找
（`<影子>/<库名>.db`）⇒ 找不到副本 ⇒ SQLite **新建空库**顶上。后果：

- 真库**确实**零接触（安全承诺成立）—— 所以"真库没变"这条证据**证明不了**"跑在副本上"；
- 链测试 / view e2e 本来就要空表起步，**结果一样是空库**，于是长期没暴露；
- 出事的是「想读真演示数据、又不想有任何风险」的用法：它**静默拿到空库**，不报错、不变红，
  只会得出"数据是空的"这种结论。

**修法**：让**复制方**去适配运行期规则（扁平落盘），而不是让解析器猜两种布局 ——
运行期的解析规则是唯一真相，把不一致留在系统里就又造了一个"同名不同义"。

**固化成三层**：① `shadow_dbs()` 入口自检（`missing_shadows`，不一致当场抛错）；
② `shadow_clear()` 找不到库时**不许静默返回 0**；③ 独立脚本 `verify_shadow_isolation.py` 四条判据进 static 闸。
（误判风险：这条自检只可能"更早地喊出来"，不会把正常的空库当成错 —— 它比的是**副本文件在不在**。）

**修好布局后，四处旧假设当场暴露**（三处是测试自身的缺陷，形态都是"不报错、只是答案错"）：

| # | 旧假设 | 现形方式 | 处置 |
|---|---|---|---|
| 1 | 「副本是空的」 | 平台第一次真读到副本 ⇒ 真演示数据连主键一起进测试，造数**撞主键**（`成员编号已存在`） | **22 个 view 脚本**新增 `shadow_clear("<组>")`（2 个链脚本本就有 / 已按扁平修正）；`shadow_clear` 连 `sqlite_sequence` 一起归零（否则自增序列仍接着真库走，起点取决于演示数据） |
| 2 | 「测试只见自己的数据」 | `config/auth.db` 的 **`user_prefs`** 带进测试：真库里 `cols:psc:sales_forecast=["基线方法","版本"]` ⇒ 以 admin 登录后**「版本」列不渲染**，用例红 | 新增 `shadow_clear_prefs()` 清副本里的个人偏好；**页面声明的 `col_default_hidden` 不受影响**（那是应用设计，照常生效） |
| 3 | 「隐藏列的值可以拿去断行文本」 | `md_breakpoint` 的 `bp_id` 列声明为默认隐藏，此前"巧合命中"（空库下主键是 1/2，别的单元格里也有这个数字），主键变 32 后暴露 | 改为「接口证明落库 + 行文本只断可见列」，并加反向断言「隐藏列不该出现在行文本里」 |
| 4 | 「脚本卡住就是脚本的错」 | `strategy_fitting` 的 §4 批量拟合 会**间歇**把 chromium 渲染进程搞崩（`Page crashed`），崩溃后脚本卡在崩溃页上逐个 wait 超时 ⇒ 表现为"挂住"。实测：单跑约一半概率触发、连跑两次一次崩一次过、**内存曲线全程平稳**（不是内存压力）、且**那一步的业务已完成**（toast 已出、落表断言在崩溃点之前） | ① 超时按层给（view 300s）⇒ 从"半小时无输出"变成"5 分钟一条 FAIL"；② `run_gates` 对 `Page crashed` **重试一次**（见下），且重试必须响亮记下来 |

> **共同教训**：这三条都是「**前置条件没写下来，于是没人检查它**」——
> "副本是空的"、"只有我造的数据"、"列都渲染出来" 全是真的**隐含前提**。
> 隐含前提一旦被环境变化推翻，表现不是报错，而是**断言读到别的东西**。
> 所以 `shadow_clear` / `shadow_clear_prefs` 这类调用宁可显式写出来，
> 让人一眼看到"起点是什么"。

### 五之三、`config/` 的隔离（2026-09-18 发现 → 当天修复）

`FDE_CONFIG_ROOT` 目前**只有 `users.py` 认**：

| 模块 | 路径 | 认不认 |
|---|---|---|
| `users.py`（`auth.db`） | `Path(FDE_CONFIG_ROOT)/auth.db` | ✅ |
| `scheduler.py` / `integration.py` / `llm.py` / `flow.py` / `alerts.py` / `logging_config.py` | 硬编码 `PROJECT_ROOT/config/…` | ❌ |

**实测后果**：测试脚本起的平台子进程会 `scheduler.start_engine()` → **读真 jobs、按真 cron 触发**。
收尾核对真库 mtime 时发现真 `config/scheduler.db` 多出一条**当天 02:00** 的 run 记录
（当时**没有** dev server 在跑），就是某个 view/chain 测试的子进程发的。

- 业务写入**安全**（那些子进程带着 `FDE_DB_ROOT`，job 的写落副本）；
- 平台写入**不安全**（run 记录落真库）；
- **风险窗口**：`verify_agent_quality.py`（eval，按设计用真库 + 指纹、不设隔离变量）
  若恰逢 cron，job 的**真实写入**会打破指纹 ⇒ eval 莫名其妙失败；
- 另外 `config/logs/`、`flow_runs.db`、`agent_alerts.db` 同样会被测试进程写。

**已按方案 ① 修复（2026-09-18）**：新增 **`fde_platform/config_paths.py`**（`config_dir()` / `config_path()`），
把"`config/` 下的路径"收成**一处解析**；七个模块改为**调用时解析**（认 `FDE_CONFIG_ROOT`）：
`users`（auth.db，原先就认）、`scheduler`、`integration`、`llm`（含主密钥）、`flow`、`alerts`、

> 在 import 期求值 —— 进程内测试"先 import、后设环境变量"的常见顺序会把路径**冻在真 config/ 上**，
> 于是判据看着是通的、写却落在真库。收成函数后这个坑不存在了。

那个 102.6 MB 是 Agent **对话记录**（由 :4100 的 agent_service 进程管理，测试不碰），
其余 config 库加起来只有 0.6 MB ⇒ 隔离名副其实，代价从 103 MB/脚本降到 ~1.6 MB/脚本。

断言都在影子目录内 —— ⚠ 必须**调函数现算**，不能读模块级常量（常量恰好会绕过这条判据）。

### 五之一之二、view 脚本**卡住时必须有现场**（2026-09-18 落地）

**问题**：view 脚本偶尔在某一步**静默卡住**（页面冻死 / 渲染进程崩溃后 playwright 调用不返回），
脚本不抛错、不打印 ⇒ 跑手只能超时判 FAIL，而**现场全丢**：脚本收集的 console/pageerror/HTTP 错误
只在末尾断言时才可见。实测（`strategy_fitting` 的「§4 批量拟合」）连续多轮都是这样，
连"卡在哪一句"都无从判断 —— 最后是靠**残留副本里的数据库**才证明后端已执行完（台账 §8/§9）。

**落地**：`fde_platform/view_watchdog.py`（与 `shadowdb.py` 同类的测试支撑模块，**平台运行时不加载**），
**22 个 view 脚本全部接入**：

```python
from fde_platform.view_watchdog import install_watchdog
...
errors, ignored = [], []
install_watchdog(errors, step_getter=lambda: STEP)     # STEP 由脚本的 step() 维护
```

- 守护线程每 5s 看一次"当前步骤"；**步骤变化 = 有进展**，重新计时；
- 连续 `stall_s`（默认 120s，可用 `VIEW_WATCHDOG_STALL_S` 调小）没进展 ⇒ 打出现场：
  **最后完成的步骤 + 已收集的错误 + chromium 内存/CPU 采样**，之后每 `repeat_s` 再报一次；
- **只打印、不终止进程**（诊断不许改变被测脚本的行为）；**线程里不碰 playwright**（非线程安全），
  内存/CPU 从 **OS 侧**采（`tasklist` / PowerShell）。

**它一次就把方向定住了**（判据表，可直接复用于任何"页面卡住"）：

| 观察 | 含义 |
|---|---|
| 错误列表**为空** | 不是 JS 抛异常（那会有 console/pageerror） |
| 内存**平稳** | 不是"边循环边分配" ⇒ 不是 OOM 型崩溃 |
| CPU 涨速 ≈ 15% 核（自旋会是 ~100%） | **不是 JS 死循环** |
| 步骤停在某一步、且该步的断言在卡住点**之前**已通过 | 后端多半已返回，卡在"页面收到响应之后" |

> **教训**：遇到"间歇失败"，先**让失败留下现场**，再谈改成什么。
> 这次的前两轮猜测（ECharts 曲线渲染、内存压力）都是靠现场数据推翻的。

**收尾（2026-09-18）**：定位到环境层（该机器上浏览器网络服务不稳 ⇒ 页面下一次 `fetch` 不 settle），
按用户决定**只记账、不换浏览器运行时**。另在 `run_gates` 里加了一条防脱敏提示：
失败的输出里若出现过 `[watchdog]`，单独打一行「**伴随卡住现场（页面冻住，非断言失败）**」——
这类红看起来像断言红，性质却完全不同，不标出来就会误导排查方向。

### 五之二、什么时候可以「重试一次」（2026-09-18 定）

**默认不重试** —— 重试会掩盖真缺陷，而本仓最怕的就是"看起来绿"。
只开一个**极窄的口子**，同时满足三条才允许：

1. **只认一种特征**：输出里出现 `Page crashed`（chromium 渲染进程死亡）。断言失败、超时、
   业务报错、连不上服务……**一律不重试**。
2. **必须响亮记下来**：跑手打印「第 1 次遇到渲染进程崩溃 —— 重试一次」，通过时再打
   「本次结果来自**重试**，别当成一次干净通过」。**藏起来就变成了静默吞掉**。
3. **重试也只给一次**：第二次仍崩 → 按 FAIL 处理（那已经不是偶发，得去看）。

为什么这一条值得开口子：它**不是断言失败**，而是**基础设施偶发** ——
业务动作已经完成（`批量拟合` 的 toast 已出、落表断言在崩溃点之前就已通过），
崩的是浏览器进程。把它算成"应用有缺陷"，会训练人对红灯脱敏；
而把断言失败也算进去重试，就是拿闸门开玩笑。**这两件事必须分开。**

> 现状：这条口子只被 `strategy_fitting` 用到（同一步骤单跑约一半概率触发）。
> 若将来第二个脚本也崩在同一处，说明不是偶发，应当去查渲染负担而不是继续重试。

## 六、怎么加一条新检查

```python
def a_my_check(conn):
    """A 组：<一句话说明这条在验什么、为什么值得验>。"""
    rows = q(conn, "SELECT ... FROM {应用}.{表} ...")      # `应用.表` 会自动改写
    rows = find("A", "A99 我的靶点名", rows, "分母说明")   # ← 分母非空闸，必须
    if rows is None:
        return
    bad = [r for r in rows if <违规条件>]
    REP.viol("A", "A99 我的靶点名", bad,
             "<期望：一句话说清>",
             lambda r: f"{r['x']} ...",                      # 违规行怎么展示
             "<可选备注>")
```

然后登记进 `SECTIONS`（读类）或 `SCENARIOS`（要写/要跑平台的类）。

**加检查时的三条自检**：

1. **分母会不会为空？** 空了必须 SKIP 而不是通过。
2. **这条断言能失败吗？** 若把被测实现改坏它仍通过，说明它是真空的。
   （可以刻意改坏一次验一下，或者像 `canary()` 那样放一条必然违规的断言。）
3. **我是把设计行为当缺陷了吗？** 先读 docstring / 详设。

### 六之二、**应用组数据隔离**（2026-09-26 加，`scripts/verify_group_isolation.py`）

**为什么单独有一条**：用户报「AI管家里的 SKILL / 告警 / 运转动态没有做应用组隔离」——
根因是**数据本身就不带组**（`skill` / `agent_alerts` / `flow_run_history` 三张表都没有组字段），
其中「库存预警」那条来源还硬编码直调 `psc/inventory_projection`。这类缺陷**没有任何测试会红**：
端点返回 200、页面渲染正常、数字甚至还很丰富。

**口径**（与代码同源）：组视角 = **本组 ∪ 平台级**（`module` 为空 = 平台级，按约定各组可见但要标出来）；
平台视角（不带 `group`）= 全量。写入路径由 `agent_service` 的闭包按 leader / worker 取到组、
经 `bridge.execute(..., module=)` 落到 `propose_skill` / `raise_alert` 上。

**判据六条**：① 写入带归属（真调一遍两个平台工具）② 组视角不串组 ③ 各组并集 ∪ 平台级 == 全量
（平台级不丢数据）④ 平台视角 == 全量 ⑤ 注入面同样按组收窄（`published_skills`）⑥ 前端取数带 `group=`
（源码级代理判据：抓 `get(...)` 表达式，要求它自带 `group=` 或拼的是本文件里含 `group=` 的变量）。

**两个踩过的坑**（都写进脚本注释了）：`skills.DB_PATH` 是**模块级常量**，测试必须在 import 之前设
`SKILL_DB`；迁移里的 `UPDATE` **必须显式 commit** —— 调用方（`list_skills` / `list_runs`）全是只读路径，
没有 commit，否则 ALTER 与回填在 `close()` 时整笔回滚（现象很迷惑：**列留下了、值没了**，
第二个 `if 列不在` 判断从此永假 ⇒ 回填再没有第二次机会）。

## 七、known-issues 基线的纪律

`scripts/psc_oracles_known.txt` 每行一个「已登记为待决策」的靶点名。门禁**只为不在清单里的
新回归变红**。理由：几项长期待决策的失败会让门禁**常红**，而**常红的闸会训练人无视红灯，
比没有闸更坏**。

> ⚠ **修好一项必须立刻从清单删掉** —— 留在清单里的已修项会**掩盖它日后的回归**。
> 每增一条都必须同时在 `app/<组>/BUGS_<组>_<日期>.md` 台账里记账。

**门禁口径（这条最要紧）**：闸只卡**不变量**——不越权、不改业务数据、不泄漏未授权信息、
平台链算得对、同一件事的不同路径给出同一答案。
**「答得好不好」（`verify_agent_quality.py` 的 B 类开放题）作为报告项，不卡闸** ——
那类本来就会波动，拿它当闸会天天红。

## 七之二、判据自身出错的两类（2026-09-18，判据自纠）

**判据出错比代码出错更贵** —— 它会把「没查」伪装成「全过」。本轮在推广到 `app/e2e` 时立刻撞到两类，**都是同一根因：判据认的「词表/载体」只覆盖了一半场景**。

### 1. 分母为 0 的假绿（`br_meta_check.py`）

`br_meta_check` 只认 **PSC 的编号小节（bullet）载体**（`^- \*\*输出\*\*:`）。`app/e2e` 用的是
**PRD 表格载体**（「BR 结构化信息」表）⇒ 工具对 e2e **一条 BR 都读不出来**，然后打印：

```
核对：2 个应用 / 0 条 BR 的三要素内容
✓ 全部对得上：`输出` 的列名与 `生效点` 的服务名都能在代码里找到
```

—— 看上去是绿的。而 `br_coverage.py` **早就认这张表**（`_table_outputs`）：**同一件事的两种载体，
两个工具各认一半**（同一个坑本仓踩过第三次：T4 的「派生量/中间量」、`view_coverage` 的 V3 gap-note）。

**修法**：① 补表格载体（表头不写死，按含「输出」「生效点」「依赖输入」的列定位）；
② 补 **`AUDIT_COLUMNS`**（`updated_at` 等平台注入列，`schema.sql` 里不写但运行期真有；
`br_coverage` 也早就并了）；③ 加 **分母闸**：某应用声明了 BR 却一条都读不出来 ⇒ 报 FAIL
（"不是全对，是没看"）；④ 输出里**逐应用打印「核到/声明」**（`member 12/12、task 16/16`），
分母为 0 一眼可见。

### 2. 静默丢条目（`br_coverage.py`）

BR 块的边界写的是 `(?=^####\s+3\.2\.|^###\s)` —— **每节最后一条 BR 会被丢掉**：
若它后面跟的是 `#### 3.3.x`（既不是 `3.2.x`、也不是 3 个 `#`），lookahead 无处可落 ⇒
整个匹配失败 ⇒ 该 BR 不进报告。`sales_history BR-11` 就这样长期**不在分母里**（报 192，实为 193）。

**修法**：边界放宽成 `(?=^#{2,6}\s|\Z)`，并补**分母自检**：详设里声明了 BR 标题却没进字典的，
一律按「读不出输出」计入（宁可吵，不可静默漏）。

> **推广到别的组/别的载体时的自查两条**：
> ① 新写完一条判据，先问「**它现在能看到几条？**」—— 把分母打印出来，0 与「全过」必须长得不一样；
> ② 同一件事的**载体/词表**若在多个工具里实现，改动时**全部一起改**，
> 并在每个工具的注释里点名「必须与 `xxx` 一致」。

### 跑手自身的两条（2026-09-18）

- **每层单条命令的超时改为按层给**（`scripts/run_gates.py` 的 `TIER_TIMEOUT`：static 300s / oracle 900s /
  chain 600s / view 300s）。此前统一 1800s ⇒ **某个 view 脚本挂住时，整层以"半小时没动静"的形式呈现**，
  而且看不出是哪一支（实测：PSC 全量跑里一个 view 脚本挂住 25 分钟，控制台一个字节都没有）。
  参考量级：view 单脚本正常 20~40 秒，300s 已经是 5~10 倍余量。
- **并跑 ≠ 安全**：`view` 层每个脚本都要 `subprocess.Popen` 起一个平台 + 一个 chromium。
  同机再并跑另一组的 view 层时，观察到一个脚本卡住不收敛（单跑 15 秒过）。
  脚本层面已按「等待条件必须与断言对象同一个」加固（`pitfalls.md` #42），
  但**跑闸时仍旧不要跨组并跑 view 层** —— 影子库不冲突，**资源会**。

- 19 个脚本各自的 `ignored` 列表**收集了却从不校验**（favicon/`.map` 的 4xx 被静默吞掉）；
- 断言偏软：大量 `assert page.locator("main .card").count() > 0` 而非精确值。

**这是与后端对账体检同级的一大片空白，但改动面大**（要动 19 个脚本 + 17 份用例文档），
建议单独排期，不要与后端体检混在一起做。

### 远端 CI 接线（暂不做）

仓库远端是 **Gitee**，其 CI（Gitee Go）配置格式厂商专有，未凭猜测写配置。
`run_gates.py` 已是对外唯一入口，接任何 CI 都只是套一层壳：
在 CI 里跑 `python scripts/run_gates.py`（`static`+`oracle` 两层不需要任何外部服务），
exit code 非 0 即失败。

**CI 里能跑、本地不能跑的部分**：`chain` / `view` 两层会清业务数据并需要停服，
在 CI 的临时 runner 上是免费的；本地要显式 `--tier chain` / `--all`。

## 十一、与九步法的接口（2026-09 补：已写进各步规范）

这一层不是平行的一套东西，它**从第②步就开始挂钩**，到第⑤步收口：

| 步骤 | 规范改动 | 挂钩点 |
|---|---|---|
| **第②步**《应用设计.md》 | 每条 BR 新增 **`依赖输入`**（要哪些输入、**各由谁产生**）、**`输出`**（产物落在哪个字段）、**`生效点`**（在哪条调用链上生效） | 这三个字段是下游能被**机器校验**的唯一依据。缺任一，第②步门禁不通过。其中 `依赖输入` 指向**本步最该问、也最常被跳过的一问**：「这个输入系统里由谁产生」 |
| **第③步**《工具链使用说明.md》 | 门禁新增：**每条 BR 的 `依赖输入` 有承载** + **跑 `scan_structure.py` 未登记失败为 0** | 第②步的人工审查在第③步有机械兜底 —— 代码写完后，`scan_structure.py` 查的就是「参数被当判定条件、但全部生产调用点都省略它 ⇒ 分支不可达」 |
| **第④步**《应用测试.md》 | 覆盖要求新增两个维度：**BR 输出字段级覆盖**、**内部调用链覆盖**；编写规则新增「计算/规则类期望值必须由详设公式现算」；「参数名以详设为准，不一致须标待确认，不得静默删参」 | `输出` → 字段级覆盖；`生效点` → 链路覆盖 |
| **第⑤步**《测试执行.md》 | 禁空转断言、逐参一致、**断言可失败性验证（变异测试）**、分母非空闸、跑结构检查、**BR 输出字段级覆盖（T4）** | 把前三步的声明变成**可判定的门禁** |
| **各步完成门禁**《工具链使用说明.md》 | 第②④⑤步的门禁各加了对应条款；覆盖度口径明确**不以「BR 能对到一条用例」为准** | — |

### 覆盖度的口径变化（这条最要紧）

```
旧：每条 BR 能对到至少一条用例          → 100% ✅
     实测：其中「补货量分档」的输出从没被任何断言检查过，两条用例只断言「建单成功」

新：每条 BR 的「输出字段」被至少一条用例的「断言」引用过
     计算类用例的期望值由详设公式现算，且断言引用该输出字段
     声明了「生效点」的 BR 有用例走那条链
```

**「有编号对应用例」与「规则被验证」是两件事。** 前者是文档工作，后者才是测试。

## 十二、门禁强度与存量处理

新条款对现存项目是**不合规**的（17 份详设、19 个测试脚本都缺 `输出`/`生效点`、有大量空转断言）。
所以强度定为：

- **新增 / 改动的应用组 → 必须满足新条款**（硬性）
- **存量 → 按 known 基线登记**（`scripts/structure_known.txt`、`scripts/psc_oracles_known.txt`），
  随迭代自然收敛

理由与第 4 项待办同一个口径：**几项长期不合规的失败会让门禁常红，而常红的闸会训练人无视红灯 ——
比没有闸更坏。**

> ⚠ **登记纪律**：known 清单里的一项**修好后必须立刻删掉** —— 留在清单里的已修项会
> **掩盖它日后的回归**。每登记一条都要在 `app/<组>/BUGS_<组>_<日期>.md` 台账里记账。

### 已落地与**尚未**落地的（2026-09-17，PSC）

| 判据 | 状态 | 存量处理的代价（都要认） |
|---|---|---|
| BR 三要素完整性（`scan_structure.py` T3） | **已落地且全绿**：PSC 17 个应用 / 192 条 BR 全部可机器读出（先做 6 个出问题的、当晚铺满全组） | 曾经登记过 10 个应用、**已按纪律全部删除**；今后新增应用 / 新增 BR 缺三要素会当场变红 |
| 三要素**内容**核对（`scripts/br_meta_check.py`） | **已落地**（独立脚本，未接进 `scan_structure`）：`输出` 的列名、`生效点` 的服务名逐个对代码核验 | 它抓的是 T3 抓不到的：字段/服务名**拼错**了 T3 照样过，而下游会被指向一个不存在的东西 |
| 输出字段级覆盖（`scan_structure.py` T4，取证在 `br_coverage.py`） | **已入闸**：立项粒度 = **一应用 + 一 BR**；PSC 189/191 被断言引用，**2 条登记**（见下） | `T4 [strategy_fitting] BR-09/BR-10`：产物是简化实现里的**常量**，**给常量补断言 = 把 stub 固化成标准** —— 那是假覆盖，比空着更坏。等库存拟合真正落地再补真断言 |
| 前端可追溯性 + `x-if` 单根（`scan_structure.py` V1–V6，取证在 `view_coverage.py`） | **已入闸且全绿**：19 个脚本 · 用例文档 ↔ 脚本 ↔ **页面元数据** 三方对账 · 豁免清单受检 · **模板层 `x-if` 多根**（V6，全仓 2 处已修完） | 首轮报出 **191 条**（V3 就 134 条）+ **组级脚本一直是红的**；且「先有脚本后有用例」的三处已回写。**它顺手挖出一个真实前端缺陷**：批量导入的提交按钮被 Alpine `x-if` 的多根约束静默吞掉（见台账）——**「文档写了没测」的地方，就是缺陷能藏最久的地方** |

**「先补断言、再入闸」为什么是硬顺序**：T4 首次取证报出 **21/104 未覆盖**。此时入闸就是一条
常红的闸 —— 而常红的闸会训练人无视红灯，**比没有闸更坏**。所以顺序是：
① 取证（`br_coverage.py`，只出表）→ ② 补断言（21 → 0）→ ③ 才接进 `scan_structure.py`。
**补完还要证明断言不是空转的**：抽样改坏实现三处（去掉净需求钳零 / 预测层清零 / 预警分级错位），
对应用例当场变红（`TC-PEN-02` / `TC-MC-08` / `TC-PEN-04`），还原后全绿 —— 见
`app/psc/测试用例.md` §4.9 的证据表。前端那一层照同一顺序走了一遍（V1–V5 先出表、再收敛、最后入闸）。

**立项粒度本身也是踩出来的**：T4 最初是「全组一条」，改「一应用一条」，最终改「**一应用 + 一 BR 一条**」——
每粗一级，都会让一条 BR 的欠账把同应用/全组其它 BR 的回归**一起静音**。known 基线能精确到一行，
前提是靶点足够细。

## 十三、术语对照（这套东西在行业里对应什么）

| 本仓库的说法 | 行业对应概念 | 标准化程度 |
|---|---|---|
| 元数据 / 声明（概念·字段·规则·动作） | **本体 Ontology** | W3C 标准（RDF/OWL）；本仓库只用轻量形态（YAML 清单），**不做推理、不上 RDF** |
| 规则做成可校验的约束 | **SHACL**（Shapes Constraint Language） | W3C 标准。它提供的正是我们需要的**封闭世界**校验（"查不到使用点"就是"没有使用点"） |
| 字段集 + 质量规则 + 责任方 | **数据契约 Data Contract** | 有开放标准 **ODCS**（Bitol / Linux Foundation，YAML + JSON Schema） |
| **本文的对账体检与结构检查** | **架构适应度函数 Architectural Fitness Function** | 方法论（《Building Evolutionary Architectures》）；工具代表 **ArchUnit** |
| `*_known.txt` 基线 | ArchUnit 的 **`freeze()`** | 现成能力：让遗留代码库先冻结既有违规再逐步收敛 |
| 分母非空闸 + canary | ArchUnit 的已知陷阱："**a rule matching zero types always passes**" | 该领域的经典坑 |
| 「断言只从文档派生、绝不从实现派生」 | 行业的警告："**fitness functions can lie** —— 照当前（可能有 bug 的）代码写规则，会把 bug 固化成标准" | 独立印证了本文件第三节的第 1 条纪律 |
| 「闸只卡不变量，不卡答得好不好」 | 警告："**over-constraint can make architecture rigid**" | 独立印证了门禁口径 |
