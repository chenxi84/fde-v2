# FDE 轻量技能工具链 · 使用说明（手工执行轨）

> 面向 **`fde-v2/design-plus/` 轻量技能体系**的**手工执行**使用手册——执行体（**Claude Code 等 AI 代理**或工程师）按本说明与 `design-plus/` 各规格**直接逐步执行**，产物直接落 `app/<组>/`，不经平台任务系统。
> **平台轨**（`/groupbuild` 页面一键任务卡片）另见 **《groupbuild使用说明.md》**。两轨**同规格、同产物、可互换**：同一应用组可一轨起步、另一轨续跑（产物互相认账）。
> 本体系以「技能（Skill）」为单位组织能力：每个技能职责单一、轻量、可独立调用。当前已定义**九个技能**（后端五步 + 前端四步）：
> **后端段**——第①②④步为**分析型**（产出文档）：**第①步 `fde-aggregate-identification`**（聚合根识别，规格 **《架构设计.md》**）、**第②步 逐聚合根应用设计**（规格 **《应用设计.md》**）、**第④步 测试用例生成**（规格 **《应用测试.md》**）；第③步为**编码型**：**第③步 应用编码**（规格 **《应用编码.md》**，编码规范正本 **《CONVENTION.md》**）；第⑤步为**执行型**：**第⑤步 测试执行**（规格 **《测试执行.md》**，把第④步用例翻译成可运行测试脚本并跑通）。
> **前端段**（契约冻结后开工，镜像后端段「设计 → 编码 → 用例 → 执行」结构）——第⑥⑧步为**分析型**：**第⑥步 前端设计**（规格 **《前端设计.md》**，逐应用前端详设 + 组级看板设计）、**第⑧步 前端测试用例**（规格 **《前端测试.md》**，逐应用各一份 + 组级补充一份、只生成不运行）；第⑦步为**编码型**：**第⑦步 前端编码**（规格 **《前端编码.md》**，视图约定正本 **《VIEW_CONVENTION.md》**）；第⑨步为**执行型**：**第⑨步 前端测试执行**（规格 **《前端测试执行.md》**，把第⑧步用例逐应用翻译成 playwright 脚本 + 组级脚本并 0 报错跑通）。

## 一、工具链全景：应用构建九步法

把一个业务变成 FDE v2 应用（含可运行的浏览器工作台），分九步推进；工具链按步组织技能：

```
★ 第①步  fde-aggregate-identification   业务整体说明 → 聚合根清单（每个聚合根一张卡）   ← 已定义
            ↓
  第②步  逐聚合根应用设计               architecture.md + brd/ → 每个聚合根一份 app/<组>/<应用名>/应用详设.md   ← 已定义
            ↓
  第③步  按 CONVENTION 生成应用         详细设计 → app/{名}/{名}.py（聚合根类 + 公共方法
                                        + FdeError 校验 + self.fde.call 跨应用调用）      ← 已定义（规格见《应用编码.md》）
            ↓
  第④步  测试用例生成                   architecture.md + 各详设 + _contracts.md → app/<组>/测试用例.md
                                        （整组一份：主链 + 分支 + 异步回执模拟，含测试数据）  ← 已定义（规格见《应用测试.md》）
            ↓
  第⑤步  测试执行                       app/<组>/测试用例.md → app/<组>/tests/verify_chain_<组>.py（可运行）
                                        （翻译用例为脚本并跑通：清表初始化 + stub + 真实联通 + 回执模拟 + triage）  ← 已定义（规格见《测试执行.md》）
            ↓（契约**最终冻结**：跑绿后无条件重跑 dump app/<组>/_contracts.md——前端段唯一前置，依赖屏障；两级冻结见第 6 步）
  第⑥步  前端设计                       _contracts.md + 各应用详设 → 逐应用 app/<组>/<应用>/前端详设.md
                                        + 组级 app/<组>/前端详设/dashboard.md（必备）      ← 已定义（规格见《前端设计.md》）
            ↓
  第⑦步  按 VIEW_CONVENTION 生成视图    前端详设 → app/<组>/<应用>/view.{js,html}（与后端同文件夹、零接线）
                                        + app/<组>/dashboard.{js,html}（组级看板）        ← 已定义（规格见《前端编码.md》）
            ↓
  第⑧步  前端测试用例生成               各前端详设 → 逐应用 app/<组>/<应用>/前端测试用例.md
                                        + 组级补充 app/<组>/前端测试用例.md（壳/受限/dashboard）  ← 已定义（规格见《前端测试.md》）
            ↓
  第⑨步  前端测试执行                   逐应用用例 → app/<组>/tests/verify_view_<组>_<应用>.py + 组级 app/<组>/tests/verify_view_<组>.py（可运行）
                                        （playwright + dbguard 隔离，0 console error / 0 pageerror / 0 HTTP≥400）  ← 已定义（规格见《前端测试执行.md》）
```

- 第①步回答「**有哪几个应用、各管什么、如何协作**」，是后续一切的地基。
- 第②步回答「**每个应用内部的业务规则 / 功能 / 权限需求**」，逐聚合根产出《应用详设》（即《用户需求规格说明书》，US/BR/FUNC/PERM）。
- 第③步回答「**怎么落成代码**」。
- 第④步回答「**怎么验证整组联通**」——产出覆盖主业务链 + 分支 + 异步回执模拟的测试用例（含自洽测试数据）；本步**只生成用例、不运行**（生成与执行分离）。
- 第⑤步回答「**把用例真正跑起来**」——将《测试用例.md》翻译成可运行测试脚本，真实驱动应用组跑通主链与分支，暴露并 triage 跨应用集成问题。
- 第⑥步回答「**每个应用的前端页面长什么样**」——契约冻结后，逐应用产出《前端详设》（PAGE_META / 区块构成 / svc 字面量清单 / 验收关注点）+ 组级 dashboard 设计。
- 第⑦步回答「**前端怎么落成代码**」——`view.js` + `view.html` 写进后端同文件夹，落盘即进菜单与授权清单，零接线。
- 第⑧步回答「**怎么验证整个工作台**」——逐应用产出前端测试用例（本页渲染防粘滞 / 列表 / 模态 / 表单 / 0 报错）+ 组级补充一份（壳与菜单序 / 受限用户菜单收敛 / dashboard）；本步**只生成用例、不运行**（与④⑤同一「生成与执行分离」约定）。
- 第⑨步回答「**把前端用例真正跑起来**」——翻译成 playwright 脚本，无头 Chromium 真实驱动浏览器，0 报错通过即工作台验收完成。

**核心约定（CONVENTION v2，正本 `design-plus/CONVENTION.md`）**：一个聚合根 = 一个 FDE 应用 = 一个同名文件夹 = 一个同名类 = 一个同名 SQLite 库 = 一个独立事务/一致性边界。识别聚合根，本质就是在决定应用怎么拆。

**前端约定（VIEW_CONVENTION v1，正本 `design-plus/VIEW_CONVENTION.md`）**：一个应用页 = 该应用后端文件夹里的 `view.js` + `view.html` 两个文件（自描述 PAGE_META + 默认导出工厂），壳 / 品牌 / 菜单 / 授权由平台约定推导，零接线、零框架文件。前端段与后端段的「设计 → 编码 → 用例 → 执行」结构完全对称。

## 二、基本概念

| 概念 | 说明 |
|---|---|
| **应用组（`<组>`）** | 一批相关应用的集合，用一个**英文 snake_case 名**标识，对应 `app/<组>/` 目录。例：`sales`、`finance`、`crm_ext`。 |
| **BRD** | Business Requirements Document，应用组的**整体业务设计**，放在 `app/<组>/brd/`，是技能的主要输入。 |
| **聚合根** | 一致性边界的唯一对外门面；本体系中**一个聚合根对应一个 FDE 应用**。 |
| **架构文档（第①步产出）** | `app/<组>/architecture.md`（固定、唯一）：聚合根清单总表 + 聚合根卡 + 聚合关系图。 |
| **应用详设（第②步产出）** | **每个聚合根一份** `app/<组>/<应用名>/应用详设.md`（同名应用文件夹）：按《应用设计.md》模板填写的《用户需求规格说明书》（US/BR/FUNC/PERM）。 |
| **约定正本** | 后端 `design-plus/CONVENTION.md`（CONVENTION v2）+ 前端 `design-plus/VIEW_CONVENTION.md`（VIEW_CONVENTION v1，参考 `design-plus/view-convention/`）——第③步与第⑦步编码的唯一规范来源，两份正本均只引用、不复制。 |
| **前端详设（第⑥步产出）** | **每个应用一份** `app/<组>/<应用>/前端详设.md` + 组级 `app/<组>/前端详设/dashboard.md`（必备）：PAGE_META / 区块构成 / svc 字面量清单 / 验收关注点。 |
| **前端测试用例（第⑧步产出）** | **逐应用一份** `app/<组>/<应用>/前端测试用例.md`（本页渲染 / 列表 / 模态 / 表单 / 0 报错）+ **组级补充** `app/<组>/前端测试用例.md`（壳与菜单序 / 受限用户菜单收敛 / dashboard）；造数数据字典逐应用自足。 |

## 三、操作步骤（手工执行）

> 执行体：AI 代理（Claude Code 等）或工程师。**逐步按各规格执行、产物直接落盘、验证直接运行**；逐聚合根 / 逐应用步骤可并行派多个子代理各自执行以提速。平台一键任务不属本轨（见《groupbuild使用说明.md》）。

### 第 1 步：创建应用组并上传设计 ★起点

所有工作从「**给应用组起名 + 放业务设计**」开始。

1. **确定英文应用组名**（snake_case）。
   - **铁律：组名按字面绑定**——用户给什么名就是什么名，技能不改写、不另起别名、不因"名字太泛"而替换。组名**只决定工作目录**（`app/<组>/`），与业务内容无关。
2. **建立工作目录** `app/<组>/`（不存在则创建）。
3. **放入整体业务设计（BRD）**到 `app/<组>/brd/`：
   - 形式不限：Markdown / HTML / 图片均可，可带 `images/` 等子目录；
   - 建议覆盖：**业务背景与目标、主流程（用户旅程/操作步骤）、涉及的业务数据、角色与职责**；
   - 可一份综述，也可多份分主题文档；越完整，识别越准。
   - **`brd/` 允许缺省或为空**——此时改为在第 2 步调用技能时直接提供一段文字业务说明（见来源②）。

> 本步骤的产物是 `app/<组>/`（含 `brd/`），属于技能的**输入侧准备**，先于技能运行。

### 第 2 步：运行 `fde-aggregate-identification`（第①步）

技能从两类来源读取业务输入并识别聚合根：

| 来源 | 位置 / 形式 | 说明 |
|---|---|---|
| ① 组级业务设计 | `app/<组>/brd/` | 成体系的整组 BRD；**可空** |
| ② 随调用的文字 | 调用技能时直接给出的一段话 | 背景/流程/数据/角色，自然语言即可；可补充或替代① |

**输入完备性（不臆造）**：若 `brd/` 为空**且**无任何文字说明，则没有可分析的业务输入——技能**停下来向用户索取**，不自行填充、不套用内置样例。

**识别方法（详见《架构设计.md》）**：提取业务实体 → 区分主数据 / 值对象 / 流程单据 → 按**一致性边界**划定聚合 → 为每个聚合根填卡 → 绘制聚合关系图 → 命名审核。

### 第 3 步：产出并评审 `architecture.md`

- **固定、唯一落点**：`app/<组>/architecture.md`。
- 文件应包含（即规格的 §输出结构，全部写入这一个文件）：
  1. **聚合根清单总表**（# / 聚合根 / 应用名 / 类名 / 一句话定义 / 标识 / 是否主数据）；
  2. **聚合根卡**（每个一张）：标识、核心属性、对外操作、关键不变量（界定一致性边界，2–5 条；字段级校验规则留给第②步）、引用的聚合、跨应用调用、状态机；
  3. **聚合关系图**（mermaid/ASCII：弱引用与跨应用调用方向）；
  4. 建议附：**关键设计决策**与**待确认**清单。
- 产出后**与业务方评审**：聚合划分、边界、命名、跨应用关系是否正确，修正理解偏差。

▶ **完成门禁（硬性，未通过不得进入第 4 步）**：
  执行体须对照 `app/<组>/brd/` 全部文件，逐项检查 `architecture.md`：
  - BRD 中每张业务单据是否被识别为聚合根、子实体或明确排除（含排除理由）
  - BRD 中每条主流程是否在聚合关系图中有对应链路
  - BRD 中每类角色是否在聚合根卡中有职责描述
  产出 `app/<组>/architecture_review.md`（业务覆盖度检查报告），**业务覆盖度 = 100%** 方可进入第 4 步。

### 第 4 步：运行第②步——逐聚合根应用设计

以 `app/<组>/architecture.md`（必需）+ `app/<组>/brd/` 全部文件为输入，**逐聚合根**产出 `app/<组>/<应用名>/应用详设.md`（同名应用文件夹，一份《用户需求规格说明书》）。映射：对外操作→功能清单（US/FUNC）、关键不变量 + **本步补全的逐字段校验**→业务规则（BR）、核心属性→业务数据/字段表、状态机→§3.4、引用/`self.fde.call`→外部依赖、角色→权限（PERM）。规格详见《应用设计.md》。

▶ **完成门禁（硬性，未通过不得进入第 5 步）**：
  执行体须对照 `app/<组>/architecture.md`（聚合根卡）+ `app/<组>/brd/` 全部文件：
  - 每个聚合根卡的对外操作 → 对应详设中的 US/FUNC 编号
  - 每个聚合根卡的关键不变量 → 对应详设中的 BR 编号
  - 每个聚合根卡的状态机 → 对应详设 §3.4
  - 每个聚合根卡的跨应用调用 → 对应详设 §7.3
  - BRD 中每张单据的字段 → 对应详设 §4 字段表
  逐聚合根出具覆盖度，**每个聚合根覆盖度 = 100%** 方可进入第 5 步。

### 第 5 步：运行第③步——应用编码（详设 → 可运行代码）

规格见《应用编码.md》，编码规范一律以《CONVENTION.md》为准。逐个聚合根把《应用详设》落成代码：

1. **输入就位**：每个聚合根需有 `app/<组>/<应用>/应用详设.md`（第②步产出，**主输入**，缺失则停下、先跑第②步）；另读 `app/<组>/architecture.md`（定引用 / 跨应用调用 / 命名）与 `design-plus/CONVENTION.md`（编码依据）。
2. **逐聚合根生成**（每个产出两件，落同名应用文件夹）：
   - `app/<组>/<应用>/<应用>.py`——聚合根类（PascalCase）+ 公共方法（服务）+ `_init_db` 幂等建表。映射：详设 §4 功能/字段表→`schema.sql` 建表 + 公共方法；§3.2 业务规则 BR→方法内校验，违反 `raise FdeError("人话")`；§3.4 状态机→状态字段 + 转换方法；§4.3/§7.3 引用的聚合→`self.fde.call("应用","服务",**params)`（只认名不 import）；外部系统（SAP/MOM/WMS…）→应用内 `_` 前缀适配器方法；§5 权限→**不实现鉴权**，仅读 `self.ctx`。
   - `app/<组>/<应用>/README.md`——写给该应用 Agent 的操作指南（CONVENTION §11 五章）。
   - **不手写** `<应用>.db` 与 `resource/`：二者由平台**运行期加载时自动创建**（CONVENTION §1/§10）。
3. **编码铁律**（关键几条，详见 CONVENTION）：文件顶 `from fde import FdeError`；⚠️ **公共方法禁写返回类型注解**（§12.1，内省陷阱）；不 `sqlite3.connect`（用 `self.db`）、不 `import` 其它应用（用 `self.fde.call`）；不写 `__init__`、不写鉴权、不手动 commit/rollback。

▶ **完成门禁（硬性，未通过不得进入第 6 步）**：
  执行体须对照各 `应用详设.md`：
  - 详设 §4 每个 FUNC → 代码中有对应公共方法
  - 详设 §3.2 每条 BR → 代码中有对应 `raise FdeError` 校验
  - 详设 §4 字段表每列 → `schema.sql` 中有对应 DDL 列
  - 详设 §7.3 每个 `self.fde.call` → 代码中有对应调用
  逐应用出具覆盖度，**每个应用覆盖度 = 100%** 方可进入第 6 步。

### 第 6 步：契约对齐与整组验收 + 契约冻结 ★编码后必做

代码首轮生成后，跨应用调用（`self.fde.call`）的实参常与被调方详设签名对不上，必须对齐再验收：

1. **跑扫描**：`python -m fde_platform.scanner`，列出跨应用调用的契约不匹配（目标应用 / 服务 / 参数）。
2. **契约对齐铁律：以「被调方」详设签名为准，改「调用方」实参**——被调方的服务签名是其详设冻结的契约，不要让被调方迁就调用方。首轮扫描常报出若干处不匹配，均按此原则调整调用方至归零。
3. **整组验收**（可机器化）：平台加载全组应用无错；scanner 退出码 0；公共方法无返回类型注解；详设 §3.2 每条 BR 在代码中有对应 `raise FdeError`；页面 / 服务调用（含 qualname `组/名`）实测通过。
4. **契约冻结（两级）**：运行 `python -m fde_platform.contract_dump <组>` dump `app/<组>/_contracts.md`（组内各应用真实服务签名 + 尽力真实 list 返回）。手工模式默认**不造数**——取库中现有数据取样，不搬移 / 不污染真实库、无需停平台服务器（`--seed` 会写库，仅建议空库 / 测试库使用，且需组内提供造数链 `app/<组>/seed_contracts.py`，可选）。`_contracts.md` 运行时不加载。

## 五、最佳实践与注意事项

- **按一致性边界拆，不按 UI/表拆**：判据是「能否容忍 A 已成功、B 暂失败、稍后补偿」——能则拆成两个聚合、跨应用调用协作；不能则合并为同一聚合。
- **聚合尽量小**：只包含「必须一起变」的最小实体集；避免上帝聚合，也避免把必须强一致的拆散。
- **聚合间弱耦合**：用 ID 弱引用 + `self.fde.call` 跨应用调用，不共享对象、不共享事务；一致性靠幂等/补偿（CONVENTION 无分布式事务）。
- **主数据独立成基础应用**：被多方引用的主数据/字典（客户、物料、组织等）单独成应用，供 by ID 引用。
- **外部系统不建聚合**：ERP/MES/WMS 等外部域的对象只在自有聚合内弱引用其标识、经接口交互，不建模为本域聚合根。
- **大体量 BRD 并行处理**：BRD 文档多或大时，可并行派多个抽取代理各读一份、结构化提炼（业务对象 / 状态机 / 外部边界 / 业务规则 / 待确认），再汇总识别——既避免单上下文读不下，又显著提速。
- **产出文件用英文名**：本体系产出统一用英文文件名（`architecture.md`）；`brd/` 内上传文件可任意命名。
- **第③步契约对齐以「被调方」签名为准**：跨应用调用报契约不匹配时，改**调用方**实参去就**被调方**详设冻结的服务签名，不让被调方迁就——被调方签名是契约源头。改完复跑 scanner 至退出码 0。
- **契约冻结是两级的，最终冻结是硬门禁**：第③步收尾的初始冻结只作第④步用例的签名参照；第④⑤步测试 triage 几乎必然改后端代码，故**第⑤步跑绿后、第⑥步开工前必须无条件重跑 `contract_dump`**——不要依赖「代码变更后手动刷新」的自觉（极易漏，漏则前端详设消费过期契约）。重跑出的 seed 样例顺手目检一遍：字段形状异常（如快照字段全空）常是集成 bug 的信号。
- **第③步逐聚合根并行编码**：各聚合根代码相互独立（协作只靠 `self.fde.call` 名字契约），可并行生成显著提速；唯一需要串行收口的是生成后的**契约对齐**（跨应用签名比对）。
- **第④步测试数据先冻结、后引用**：整组用例共享一套贯穿全链的标识（客户/物料/组织/单据号），先冻结成数据字典，主链/分支用例只引用不新造——这是用例自洽、可执行的命门。
- **第④步模拟的是「回执」而非「出向」**：外部系统出向适配器默认走本地 stub（无需模拟）；联通测试要闭环，须在异步点主动调 `on_*_result` 回写服务模拟外部系统回执（成功/失败两路）。
- **第⑤步联通测试是跨应用契约的最后一道关**：静态 scanner 只查签名/参数，查不出**值域错位、返回结构不一致、字段名不统一**这类集成 bug——必须真实跑通主链才能逼出来。
- **第⑤步失败先 triage 再修**：每个失败先分清「脚本/用例翻译错」（修脚本、回填用例）还是「真实应用 bug」（记入 `app/<组>/tests/BUGS_<组>.md` 反馈第③步），不在测试里绕过；共性 bug（字段名/返回结构不统一）应推动冻结 `_contracts.md`。
- **第⑥步契约先行，不猜字段**：详情展示字段（`get` 返回）≠ 表单可写字段（create/update 接受参数）——模态按 `get` 真实返回设计、表单按写服务签名设计，两者一律以 `_contracts.md` 为准。
- **第⑥/⑦步 dashboard 是必备不是可选**：平台壳默认路由写死 `dashboard`，缺看板的模块首屏即静默崩溃（VIEW_CONVENTION pitfalls #36）；新建组的第一份前端产物就是看板（设计 → 代码各一份）。
- **第⑦步 svc 字面量是授权命脉**：页面调服务一律 `svc("应用","服务")` 字面量（可闭包逐项写）；变量拼名/三元拼名派生扫描扫不到 → 受限用户该调用 403（pitfalls #8）。
- **第⑦步 reactive 状态同步先行**：工厂体内一切被模板引用的状态须在**第一个 await 之前**同步建好（含空 `items:[]` 的 `list`），再 await 拉数——先 await 后建对象，模板一注入即喷 null 错（pitfalls #37）。
- **第⑧⑨步受限断言随页面同步**：新增/调整页面后，用例与脚本的受限角色授权清单（`<组>:<key>` 逐项）、直访回落断言要逐字对齐当前菜单——此耦合极易漏，漏则受限阶段误报 403（pitfalls #38）。
- **第⑨步 0 报错是硬指标**：任一非豁免 console error / pageerror / HTTP≥400 即不通过；运维红线（dbguard 隔离 / 跨进程串行 / 跑前杀 dev server）与后端第⑤步完全一致，勿绕（pitfalls #39）。
