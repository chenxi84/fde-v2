# 数据库层评估（2026-09-26 · 对一份外部评审意见的逐条核对）

> 缘起：有人指出「本项目的数据库层有很大问题」，列了 6 条并建议**换 SQLAlchemy / Alembic 接管数据层**。
> 本文逐条对着**代码**核对（不是对着印象），并把"该修什么"按性价比排序。
> 结论先说：**6 条里 2 条事实成立且值得修、2 条部分成立（批评者把 DDL 与 DML 混为一谈）、
> 1 条是配置不是设计、1 条基本无风险；"整体换 SQLAlchemy/Alembic" 在本项目里不划算**
> （理由见 §4），但它里面的**两个具体做法值得直接抄**（见 §5 的 1 与 2）。

---

## 1. 事实核准（对着代码）

平台的数据层是 `fde_platform/db.py`（约 480 行）+ `fde_platform/ddl.py`（sqlglot DDL）。
核心承诺（`CONVENTION.md`）：**应用只写 `self.db.execute(sql, params)`，裸 SQL、`?` 占位符；
配 `DATABASE_URL` 即切 PostgreSQL，应用零改动。** 下面是逐条核对。

### ① 「SQL 方言硬编码：`dialect_of()` 用 `isinstance(conn, _PgConnection)`」—— 事实成立，但**不是缺陷**

```python
def dialect_of(conn) -> str:
    return "postgres" if isinstance(conn, _PgConnection) else "sqlite"
```

这是**2026-09-20 修掉一个真 bug 之后**的写法，docstring 写得很清楚：连接池是**懒建**的，
`using_postgresql()` 在建池之前恒为 False，而 `runtime._load` 恰好先算方言再建连接 ⇒
PG 部署下建表与对账**全按 SQLite 走**、`PRAGMA table_info` 在 PG 上语法报错、平台起不来。
从**连接对象本身**判断则没有时序问题。

按类型分派本身没有错 —— SQLAlchemy 内部同样是 `isinstance` 到具体 DBAPI 实现。
真正的差别是：它自己在 ~150 行里手写了一个**双模适配器**（`_PgConnection` / `_PgCursorWrapper`），
而不是复用成熟适配器。**风险不在 `isinstance`，在"手写适配器要自己跟上方言差异"** —— 而
方言差异里最难的那块（DDL 生成）**已经交给 sqlglot 了**（见 ②）。

### ② 「审计列注入用正则 `re.sub()` 解析 INSERT/UPDATE」—— **部分成立：DDL 早已不是正则，DML 是**

- **DDL 层**（建表）：`ddl.py` 用 `sqlglot.parse(read="sqlite")` → 注入审计列 → transpile 到目标方言，
  文件头明写「**替代 `db.py` 里 `_add_audit_columns` / `_translate_ddl` 的正则 DDL 改写**」。
  它有两条门禁守着：`verify_ddl_reconcile.py`（列对账）、`verify_dialect_render.py`（多方言渲染，
  支持 postgres / mysql / tsql / oracle 四个方言，纯函数、不用装数据库）。
- **DML 层**（每次服务调用）：仍是正则，`db.py:_inject_audit`（SQLite 版）与 `_PgConnection.execute`
  内联（PG 版）各一份。**这条我说成立**，而且我实测出三个边界（§2）。

### ③ 「lastrowid 兼容性 Hack：`_pg_seq_pk()` 查 `pg_index`/`pg_attribute`/`pg_get_serial_sequence`」—— **成立，且是最该改的一条**

事实：`cursor.lastrowid` 在 psycopg2 下恒为 **0**（现代 PG 无 OID），而应用按约定写
`return self.get(cur.lastrowid)` ⇒ 插入成功却按 0 回查 ⇒ 报「记录不存在」并被回滚。
作者的办法是**惰性取 `currval(...)`** 回填 —— 不改写 INSERT，对既有写路径零影响，但它确实是个 hack：
要查系统表、要缓存、依赖"本会话刚用过该序列"。

**正解是 PG 原生的 `INSERT ... RETURNING <pk>`**（见 §5-2）。批评者这条方向是对的。

### ④ 「占位符替换 `sql.replace("%", "%%").replace("?", "%s")`」—— **成立（有实证边界），但修法不是换 SQLAlchemy**

这段有长注释解释顺序为什么不能反（先转义字面量 `%`，再把 `?` 换成 `%s`），
且它是 **2026-09-20 两个线上缺陷的修复**：顺序写错 ⇒ 所有 `LIKE '%' || ? || '%'` 模糊搜索全崩
（`IndexError: tuple index out of range`）；审计注入自己写 `%s` ⇒ 被转义成 `%%s` ⇒ 占位符消失
（`not all arguments converted`）。

**它现在是对的**（我扫了应用里 ~297 条 SQL：没有任何一条写 `%s`、没有 `INSERT OR`、
没有多行 `VALUES (…),(…)`、`?` 也从不出现在引号内 —— 模糊搜索统一写 `LIKE '%' || ? || '%'`）。
但它是一条**窄契约**：换个写法就出事，而且是**静默**或**莫名其妙的 TypeError**。§2 是我实测的三条。

### ⑤ 「Schema 自动创建 `CREATE SCHEMA IF NOT EXISTS {app_name}`」—— 基本无风险

`get_connection()` 里 `CREATE SCHEMA IF NOT EXISTS <app_name>` + `SET search_path TO <schema>`，
`app_name` 由应用 qualname 归一化（`/`→`_`），不是外部输入，注入面很小。
**"缺乏权限管理与迁移历史"这半句是真的**，但它是**定位问题**而不是缺陷：
本项目的 DDL 真相源是 `app/<组>/<应用>/schema.sql`，平台**加载时**解析建表
（`CREATE TABLE IF NOT EXISTS` 语义 ⇒ **不会 ALTER 已有表**）。真要演进表结构，今天得手写 ALTER。
这块**值得补**（§5-4），但补法见 §4 对 Alembic 的评估。

### ⑥ 「连接池小 min=2 max=10，而 waitress 64 线程」—— 事实成立，**是配置不是设计**

`ThreadedConnectionPool(2, 10)`。但要看**连接持有时间**：本项目每次服务调用**开/关一条连接**
（`runtime` 在调用前 `get_connection`、调用后 `close()`），持有时间是毫秒级，
**⚠ 订正（2026-09-26 复查）**：我先前写的"`getconn()` 池空时阻塞等待"是**错的** ——
psycopg2 的 `ThreadedConnectionPool` 在无空闲连接时**立刻抛 `PoolError: connection pool exhausted`**，
它**不会等**（这是 psycopg2 池的已知特性，配它就得自己加信号量）。这一句错判让第 ⑥ 条的危害被低估了：
池是**全局共用一个**（所有应用的所有 PG schema 共用 `_PG_POOL` 那 10 条），而**一个看板页会并发调十几个应用**
（`nasa_pms` 看板聚合 13 个应用）⇒ PG 部署下**一次页面加载就可能直接报"连接池耗尽"**，不是排队。
CLAUDE.md 里"超出的排队等而不报错"讲的是 **waitress 线程**，不是这个池，我把它错记到池上了。
真正的天花板是 `min(池大小, PG 的 max_connections)`。**修法是一行**（环境变量化，见 §5-3）。
⚠ 别把池开大就完事：PG 默认 `max_connections=100`，多个组 × 多个进程一起开大会把它打满。

## 2. 我实测出来的三个边界（`_PgConnection.execute`，PG 分支）

用现成的假连接跑（`verify_pg_translate.py` 里已有这个 harness），**不需要真 PG**：

| 输入 | 实际结果 | 后果 |
|---|---|---|
| `INSERT INTO t (a,b) VALUES (?,?), (?,?)` | 渲染成 `… VALUES (1, 2), (3, 4, NOW(), NOW(), tester, tester)` | **列数与第一行值数不匹配** ⇒ PG 报 `more target columns than expressions`（大声） |
| `SELECT … WHERE note = 'why?' AND x = ?` | 引号里的 `?` 也被换成 `%s` | `TypeError: not enough arguments for format string`（大声，但看不出根因） |
| `INSERT INTO t (a) SELECT x FROM y WHERE z = ?` | 审计列**没注入**，但 params 多塞了两个 | `not all arguments converted…`（大声） |

**关键限定**：这三种形态**应用里目前一处也没有**（我扫过了）。所以这不是"线上有 bug"，
而是**契约边界没写明、也没守**：今天谁按直觉写了一条多行 INSERT，就会撞上一个莫名其妙的 TypeError。

## 3. 评价这份意见本身

- **对的部分**：lastrowid hack（③）、占位符替换的脆弱（④）、池大小（⑥）都指到了真东西；
  三条的**修法方向**（用数据库原生能力、别手写脆弱替换、把池参数化）也对。
- **错的部分**：把 **DDL 层**说成"正则解析 SQL"（②）—— DDL 2026-09-20 就换成 sqlglot 了，
  还有两条门禁；把 `isinstance` 叫做"硬编码方言"（①）—— 它是修 bug 的产物，且与 SQLAlchemy 同类做法。
- **没提到的**：真正值得担心的不是"手写适配器"，而是**边界没有显式失败**（§2）——
  一个 150 行的适配器只要**把不支持的形态大声拒掉**，它就能一直是可信的。

## 4. 「换 SQLAlchemy / Alembic 接管数据层」值不值

**结论：本项目的定位下不划算**，四条理由：

1. **换不掉 SQL 文本**。平台最值钱的教具属性是「**一个聚合根 = 一个文件夹 = 一个 `schema.sql` =
   一个类，里面直接写 SQL**」。SQLAlchemy **Core** 的绑定参数是 `:name`，`text()` 也一样 ——
   也就是说 **297 条应用 SQL 的占位符风格全要改**（那正是 ④ 的问题的一个更贵的解）。
   ORM 更会把"事务边界 = 聚合根"这条主线换成 session/identity-map 的另一套心智。
2. **它解决不了这里的两个真痛点**。方言 DDL 已由 sqlglot 解决；DML 参数风格换 SQLAlchemy 也要改文本。
3. **Alembic 与现有真相源冲突**：本项目的 DDL 真相源是应用目录里的 `schema.sql`（平台加载时建表、
   `verify_ddl_reconcile` 对账、九步法 ①→⑨ 全照它推）。Alembic 引入第二份真相（迁移脚本），
   两套一旦漂移，门禁与迁移顺序谁说了算就不清楚了。
4. **风险面**：数据层是**全平台 40 个应用模块共用**的地基，重写的回归面远大于收益；
   而这份意见里真正该修的三条，**都在 100 行以内能修完**（§5 的 1–3）。

**什么时候值得考虑**：如果将来要给"平台自己的库"（`config/` 下的 skills / alerts / flow_runs /
auth / scheduler / integration …，这些是平台代码、改动可控、且真的需要结构演进）做正式迁移，
那时**只在那几个库上**用 SQLAlchemy + Alembic 是合理的；**应用侧保持裸 SQL**。这不是现在的优先项。

## 4之二、「不考虑工作量」时，技术最优是什么（2026-09-26 补，用户追问后写清）

§4 论证的是"**值不值**"——那是**在现有约束下**的结论（成本、演示在跑、九步法链条）。
它**没有**回答另一个问题：**把工作量、风险、迁移成本全部排除之后，哪个才是技术上正确的做法？**
两者混在一起会得出"用 A′ 最好"这种含混结论。分开写：

| 要保证的东西 | **A**（现状：手写适配器 + 正则手术） | **A′**（sqlglot 统一 DML） | **C-text**（SQLAlchemy，应用仍写裸 SQL，占位符 `:name`） |
|---|---|---|---|
| 参数风格翻译 | 手写字符串替换 | 我写（真解析器） | **框架**（二十年差异库） |
| 审计列注入 | 正则 | 我写（AST 层 ≈50 行） | **框架 event hook**（语义层） |
| lastrowid / RETURNING | `currval` hack | 我写 | **框架** |
| 池 / 健康检查 / 断线重连 / 超时 | 裸 `ThreadedConnectionPool(2,10)` | 我写（或换更好的池） | **框架** |
| 类型适配（date / decimal / json） | 手写 `_to_jsonable` | 我写 | **框架** |
| 谁保证它一直对 | 我 + 5 条门禁 | 我 + 门禁 | **成熟库 + 跨库测试矩阵** |
| DML **语义层**方言翻译（不是参数） | 无 | **有**（sqlglot transpile） | 无（`text()` 只转参数） |
| 单一心智模型 | 无（DDL 用 sqlglot、DML 用正则） | **有** | 无（文本编译 + 框架元数据两套） |
| 应用 SQL 与生成规范 | — | **一个字不改** | 改 `:name` + 规范 / 提示词 / 存量 |

**结论三条，别混着说**：

1. **技术最优（无条件）= C-text**。前六行它全胜，而且赢的不是"写法漂亮"，是**那一类缺陷不再存在**：
   多行 `VALUES`、CTE、`INSERT…SELECT` 这些在 A/A′ 里要一处处照顾的形态，在语义层注入下根本不是问题。
   若"允许改应用侧 SQL 的写法"成立，这就是答案 —— 应用仍可写裸 SQL（`text("… :x …")`），
   `schema.sql` 仍作真相源，Alembic 只当 diff / 演进工具（不接管真相源）。
2. **A′ 只剩两条「不是成本」的理由**：① 数据层只有**一个心智模型**（"SQLite 方言文本 → 解析 → 目标方言"，
   DDL 与 DML 同源 —— 现在这个不一致本身就是隐患）；② 保住"**应用写 SQLite 方言、平台负责翻译语义**"
   的能力（C-text 只翻参数）。这两条成不成立，取决于一个前提：**"应用 SQL 与生成规范一个字不改"算不算硬约束**。
3. **无条件最优（连那个前提也不当约束）= 混合形态**：应用侧照旧写 SQLite 方言裸 SQL + 平台用 sqlglot 统一编译
   DML 与 DDL（一个心智模型、语义层翻译都在），**但池 / 类型适配 / 健康检查 / 重试 / 平台自有库的迁移**
   改用 SQLAlchemy 的 Engine 与 Alembic（只借基建，不碰应用 SQL 的样子）。这样上表七行都不吃亏。

**所以在本文里，项目条件下的推荐仍是 A′** —— 但要如实标明理由的性质：**不是省工时，是产出物的一致性**。
这个项目的应用 SQL 是 AI 按规范**批量生成**的，规范里"裸 SQL + `?` + `schema.sql` 就是全部"这句话同时是
给 AI 的生成提示、九步法第③步的验收面、契约与门禁的锚点；动它要改的是**生成侧**（提示词 / 模板 / CONVENTION 等式），
存量 297 处反而是小事。**若把这个前提去掉，第 1 条（C-text）才是技术最优**，届时本文 §5 的 1–3 项就不必单独做了。

## 4之三、路线决策与落地（2026-09-26 当天定 + 当天落）

### 决策

| # | 决策 | 依据 |
|---|---|---|
| 1 | **路线 = 混合形态**（应用侧不改 SQL，DML/DDL 统一走 sqlglot 编译；运行期基建以后借 SQLAlchemy Engine） | 用户确认**「会引入更多数据库」**。多方言下真正的要求是"**语义层**逐方言翻译"（`\|\|`→`CONCAT`、字面量重转义、LIMIT…），而能提供它又不改应用 SQL 的只有 sqlglot 编译；`text()` 只翻参数不翻语义，旧的正则层更做不到 |
| 2 | **先做第一半 + 小修，Engine 等触发** | 编译层是"多方言 + 边界消失"的必需项；Engine（pre-ping/重连/类型适配）的收益与方言多样性成正比，第三种库落地时再借，避免现在扛两个新依赖与最大改动面 |
| 3 | **Alembic 不引** | 用户质疑得对：平台自有库文件少、改动低频；而**应用库的加列演进已经有机制**（`ddl.execute_schema` 对账补列 + `verify_ddl_reconcile` 门禁，只做加法）。Alembic 能给的是版本史/downgrade/数据迁移的住处 —— 前两者对本项目是负收益（加法纪律不该给 downgrade 留门），后者是每次变更自己的业务逻辑。**同时订正 §5-4**：那里写的"把 `verify_ddl_reconcile` 扩成能生成 ALTER"是**过期信息，它已经能了** |

### 当天落地了什么

| 件 | 位置 | 说明 |

| 池参数 | `db.py` | `FDE_PG_POOL_MIN` / `FDE_PG_POOL_MAX`（默认仍 2/10，注释写明天花板是 `min(池, PG max_connections)`） |

### 复查：我先前口述里的 5 处修正（都是当天写原型/跑测试抓到的）

| # | 我先前说的 | 实际 |
|---|---|---|
| ① | "AST 注入审计列" | INSERT 的列清单是**裸标识符**，不能复用 `ddl` 建表用的 `ColumnDef` —— 混用会生成 `created_at TEXT` 塞进 INSERT 列清单的非法 SQL |
| ② | "占位符归一成命名参数即可" | 目标不是"方言"而是 **（方言 × 驱动 paramstyle）**：sqlglot 给 mysql 生成 `:name`（mysql-connector prepared 风格），**pymysql 只认 `%(name)s`** ⇒ 按驱动补一次改写 |
| ③ | "RETURNING 由 SQLAlchemy 原生解决" | 混合形态里 SQL 由 sqlglot 编译，RETURNING 同样由**我们的编译器**追加；且 **MySQL 不支持 RETURNING** ⇒ 主键取回是**按方言的策略表**（pg=RETURNING / mysql·sqlite=驱动 lastrowid），不是零代码 |
| ④ | "把字面量里的 `%` 转义" | 漏了条件：**取决于驱动会不会插值**。psycopg2/pymysql 只在**传了参数**时才做 %-插值 —— 无脑转义会把 `'%'` 变成 `'%%'`，**只在不带参数的查询上出错**，最难发现。已按此实现（门禁 ⑪ 两个用例钉住） |
| ⑤ | （没提到） | **占位符不能按 AST 遍历顺序编号**：`find_all()` 的次序**不是文本次序**（AND 链是嵌套二元节点，先到右子树）⇒ `WHERE a=? AND b=? AND c=?` 被错位成 p1/p2/p0，**静默往库里写错值**。当天被 `tech_plan` 的链测试当场抓住（TC-32 唯一性校验查不到已批准的计划）。修法：走 tokenizer 的**词法位置**（`token.start/end`，闭区间，切片要 `end+1`）。这条已固化成门禁用例 ⑥ |

### 多方言的边际代价（为"将来会引入更多数据库"而记）

| 项 | 内容 | 量级 |
|---|---|---|
| 驱动 paramstyle | 选驱动 + 一行改写规则（②） | 1 行 + 1 条门禁 |
| 主键取回策略 | mysql 无 RETURNING ⇒ lastrowid（③） | 1 行 |
| 内省适配 | `runtime._load` / `verify_ddl_reconcile` / `sqlc.pk_column` 现在只认 sqlite(PRAGMA) 与 pg(information_schema)；mysql 也是 information_schema 但列名/大小写有别 | ~50 行/方言 |
| "schema" 语义 | pg 是 `CREATE SCHEMA` + `search_path`；**mysql 的 schema 就是 database**，要 `USE` 或全限定 | 小但必须 |
| **读数归一** | bool：pg 回 `True/False`、mysql/sqlite 回 `0/1`；date/decimal 各驱动返回类型也不同 ⇒ `_to_jsonable` 要按方言归一，否则**前端一处 true 一处 1**（不报错、是读数漂移） | 中，且要进契约门禁 |
| **真实服务器暴露周期** | 静态渲染便宜（`verify_dialect_render` 纯函数）；真行为要真库跑。2026-09-20 一天在真 PG 上撞四个的教训：**每加一个方言 = 一轮暴露**。混合形态把暴露面收窄（字面量语义、连接符、占位符、LIMIT 在编译层就对了），但收不到零 | 主导成本 |

### 第二半（范围 A）：部署侧取连接方式换成 Engine（2026-09-26 当天落）

| 件 | 位置 | 说明 |
|---|---|---|
| Engine 注册表 | `db.py::engine_for(url, limits)` | 键 = **(URL, 池参数)**；换库/换池参数都必须拿到新 Engine（否则就是 `skills.DB_PATH` 那类"模块级缓存"陷阱的重演）。**懒连接**，不发网络请求 ⇒ 可离线断言 |
| 取连接/归还 | `db.py::_checkout()` / `_PgConnection.close()` | Engine 走 `engine.raw_connection()`（⚠ **刻意走 raw**：别让 SQLAlchemy 再编译一遍我们已编译好的 SQL，`%%` 会被二次转义）；归还 = `conn.close()`。**SQLite 路径一行未动** |
| 池参数 | `FDE_PG_POOL_MIN/MAX/TIMEOUT/RECYCLE` | 默认 2/10 + 等待 30s + 回收 1800s；`db_mode()` 横幅里一并报出来（部署后据此核对） |
| 回落 | `import sqlalchemy` 失败 → psycopg2 原生池 | 保住"本地 SQLite 开发零依赖"这条属性（未装 SQLAlchemy 也能跑） |
| 池耗尽 | 两条路都**明确报错** | 原生池是"立即抛 PoolError"，Engine 是"等到超时"；两者都包成可读的 `RuntimeError`，报出池容量与 `FDE_PG_POOL_MAX` 提示 |
| 门禁 | `verify_pg_translate.py` 新增 **C 段**（⑯⑰⑱） | 池参数默认/生效、注册表按 URL 与池参数取值、池耗尽报错可读 —— 全部离线可跑 |

**收益（今天 vs 接 MySQL）**：① 池满从"立即 500"变成"等待 + 超时"（psycopg2 原生池不等待，见 §1⑥ 的订正）；
② `pool_pre_ping` 顶掉陈旧连接；③ `pool_recycle` 是 MySQL `wait_timeout` 的必需品，现在先搭好；
④ URL 解析（ssl/options）交给成熟实现。代价：+1 运行期依赖（有回落）、Engine 注册表要防"换库不换 Engine"。

### 明确**不做**的：SQLite 也池化（原范围 B）

用户判断：**SQLite 只是 Windows 上的开发底座，商业部署走服务器 PG（容器化）** ⇒ B 不做。理由比"不值得"更硬：
① SQLite 路径靠标准库启动（clone 下来 `python main.py` 就能跑，不需要装任何库），池化会把这个属性打薄；
② 池对 SQLite **没有并发收益**（单文件单写者，写入本来就串行），只省下毫秒级开关销；
③ 会把风险放进最安全的地方 —— 影子库隔离靠"复制文件 + 环境变量换根"，每次调用新开连接让这件事天然正确，
池化就要引入"换根时失效旧池"的机制（`skills.DB_PATH` 同款陷阱）。
⇒ 混合形态的口径因此是**刻意不对称**：**开发底座 = stdlib sqlite3 每次开/关**；**部署目标 = Engine 池**。

### 现场验证（2026-09-26 在测试服务器上跑，PG 容器 + 真数据）

| 检查 | 结果 |
|---|---|
| `scripts/verify_pg_live.py`（legacy） | **PASS**（多行 VALUES 与参数不匹配记为**已知边界**，见下） |
| `scripts/verify_pg_live.py`（sqlglot 编译层） | **PASS**（含多行 VALUES 每行补审计、`RETURNING` 取回自增主键、`LIKE '%' \|\| ? \|\| '%'`、边界报 FdeError） |
| 32 个应用只读 `list`（legacy / sqlglot 各一遍） | **各 0 失败** |
| 池的等待语义（池压到 4 条、12 并发 / 默认 10 条、30 并发） | 全部成功（0.3–0.4s）——Engine **排队**而不是 psycopg2 原生池那样**立即报错** |
| 容器横幅 | `PostgreSQL … · Engine 2–10 条 · 等待 30s · 回收 1800s · DML 编译层 sqlglot` |

**现场实证的两条 legacy 已知边界**（应用里目前**一处都没有**这两种形态，编译层分别修好/换成可读错误）：
① 多行 `VALUES` ⇒ PG 报 `INSERT has more target columns than expressions`（正则只补最后一个 tuple）；
② 参数个数不匹配 ⇒ 驱动层 `IndexError: tuple index out of range`（编译层给的是可读 FdeError）。

**切换落地**：默认已切 `sqlglot`（`sqlc.DEFAULT_MODE`），退回用 `FDE_SQL_COMPILER=legacy`；
legacy 分支保留一个版本后删（第 3 步）。

## 5. 该做什么（按性价比排序）

> 下面这一节是**在 §4 的约束下**（不换框架）的清单；技术最优与另两条路线见 §4之二，
> **路线决策与落地状态见 §4之三**。状态（2026-09-26）：**1–3 已落地**（编译层 + 池参数 + 主键策略），
> **4 订正为"已存在"**（`ddl.execute_schema` 的对账补列 + `verify_ddl_reconcile` 门禁），**5 暂不做**。

1. **给适配器的边界加"显式失败"**（半天）
   在 `_inject_audit` / `_PgConnection.execute` 里，对四种形态直接抛
   `FdeError("这条 SQL 形态不支持，请改写：…（多行 VALUES / INSERT…SELECT / 引号内 ? / 应用写了 %s）")`，
   并把 §2 的三条用例**加进 `verify_pg_translate.py`**（那个脚本已有现成的假连接 harness，
   加一条 = 抄 5 行）。价值：把"莫名其妙的 TypeError"变成"一眼看懂的业务错误"，
   顺带把契约写进门禁。
2. **PG 的 `lastrowid` 换成 `INSERT … RETURNING <pk>`**（半天）
   PG 原生支持，psycopg2 直接 `fetchone()` 拿到主键 ⇒ `_pg_seq_pk` / `currval` / 那张系统表查询
   与缓存**整套可以删掉**（约 60 行）。注意点：只在"该表主键由序列支撑"时追加 `RETURNING`，
   且要确认应用不会在同一 INSERT 后自己 `fetchone()`（当前没有这种写法）。
   SQLite 侧保持 `lastrowid`（老版本 SQLite 没有 RETURNING）。
3. **池参数环境变量化**（10 分钟）
   `FDE_PG_POOL_MIN` / `FDE_PG_POOL_MAX`，默认仍 2/10；启动横幅打印实际池大小与
   `SELECT setting FROM pg_settings WHERE name='max_connections'`，让"池 < 线程数"这件事**可见**。
4. **（可选）schema 演进**（1–2 天）
   把 `verify_ddl_reconcile.py` 从"只检测列差"扩成"**能生成 ALTER**"的最小迁移脚本：
   `schema.sql` 仍是唯一真相源，但提供 `--plan / --apply` 两条命令，并记一份
   `config/db_migrations.log`（谁、何时、哪张表加了哪列）。这样既不动真相源，又补上"演进历史"。
5. **（可选）小规模引入 ORM 的位置**：只限 `/agent-admin` 这类**平台自建页面**的新库。
   应用侧不动。

> 本文不是"评审意见全错"式的辩护：③ 与 ④ 我认，并且已经把 ④ 的边界实测出来了；
> 但"整层换 SQLAlchemy"这个结论，与本项目"裸 SQL + 双模零改动 + schema.sql 单一真相源"
> 的核心取舍冲突，代价与收益不成比例。**该抄的是它的两个做法（RETURNING / 池参数），
> 不是它这套框架。**
