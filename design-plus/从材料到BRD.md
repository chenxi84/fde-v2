# Skill 规格：fde-material-to-brd

> **Skill 名**：`fde-material-to-brd`
> **类型**：**产出文档型**（把外部材料转成 BRD 与对象清单，**不产出代码**）
> **对应方法论**：本体驱动（本体 = 实体 / 属性 / 关系 / 约束）—— 从**材料**里忠实提炼领域对象
> **上游**：无（本 Skill 是整条链路的最上游）
> **后置**：《工具链使用说明》第 1 步 —— 分章 md 落 `app/<组>/brd/`、**辅助产物落组根**，九步法从 ① 开始

---

## 定义

> 给【`app/<组>/book/` 下的一批原始材料（书 / 手册 / 标准 / 零散笔记）】，产出【`brd/` 下的分章 md + 一份分类框架 + 一份对象候选清单 + 一份术语表】，解决【上游材料不是业务方直接交付的 BRD，而是一堆现成资料时，怎么把它变成九步法能吃的输入，并让下游各步的**命名与术语保持一致**】。

| 维度 | 内容 |
| :--- | :--- |
| **输入** | ① `app/<组>/book/` 下的原始材料，**任意格式**（pdf / epub / docx / html，或已是 md / txt）② 英文应用组名 `<组>` |
| **输出** | ① `app/<组>/brd/第NN章-<标题>.md`（分章**正文** —— 唯一的索引源）② `app/<组>/kg_config.json`（**从材料提炼的分类框架**）③ `app/<组>/本体对象.md`（对象候选清单，带出处与源块）④ `app/<组>/术语表.md`（**原词 → 业务名，全链路命名的唯一来源**） |
| **作用** | 把「一坨外部资料」变成「一份可被第①步消费的 BRD」——**它只负责忠实呈现材料里有什么，不决定要建什么系统** |

**边界（明确不做）**：

- ❌ **不划聚合边界**、不判"哪些对象该独立成应用" —— 那是第①步《架构设计.md》的事
- ❌ **不做范围取舍**（哪个进范围、哪个排除） —— 那是 `architecture_review.md` 的**处置表**的事
- ❌ **不产代码**、不写 `architecture.md`
- ❌ **不按"想建什么系统"裁剪分类** —— 分类**忠实于材料**（见下方「为什么」）

---

## 使用方式（输入契约）

**调用时必给**：**英文应用组名 `<组>`**（snake_case），逐字绑定工作目录 `app/<组>/`，并假定材料已放进 `app/<组>/book/`。

调用形态（与原工具链同构）：

```
请基于 design-plus/从材料到BRD.md，将 app/<组>/book 下的内容转化到 brd
```

**⚠ 不需要声明"要建什么系统"**。理由见下一节——这也是本 Skill 与《架构设计.md》最大的差别：**这里不引入目标，目标在 ① 才登场**。

**输入完备性（不臆造）**：`book/` 不存在或为空 → **停下并索取**，不自行编材料、不套样例。

## 在工具链中的位置

```
[book/ 原始材料] --fde-material-to-brd--> [brd/ 分章 md]  ──①架构设计──> ...
                                          [组根: 本体对象.md · 术语表.md] ↑
                                                九步法从这里的"BRD 进"开始
```

- 本 Skill 是**上游**。《工具链使用说明》的起点**仍是 BRD**，一个字都不往后挪。
- 产物交给《工具链使用说明》第 1 步；《本体对象.md》的**用法与警告**（候选、非事实、处置记进 `architecture_review.md`）写在那份文档里，本文档不重复。
- 与《从 BRD 到系统》成对：设计侧讲「材料 → BRD」，平台侧讲「BRD → 系统」。

## 为什么分类要忠实于材料（而不是按目标裁剪）

`entity_types` 是**分类框架**（描述性的：材料里有哪些类对象），**不是范围声明**（规范性的：我要建什么）。两者差在：

- 按目标裁剪 → **抽取阶段就把材料里别的对象滤掉，不可逆**（图里再也没有了）；而且目标一变，3 小时级的索引要重建。
- 忠实提炼 → 材料里的对象全在，**取舍留到 ① 的处置表**（那里本来就是干这个的）。

同一本手册，做"项目管理系统"还是"需求追溯系统"，**都不该改变抽取结果**——变的是 ① 里哪些对象被采纳。**先抽全，后取舍。**

## 前置检查（Step 0）

**逐项确认，缺哪条就报哪条，不臆造、不跳过、不带着缺口往下跑**：

| 项 | 怎么查 | 缺了怎么办 |
| :--- | :--- | :--- |
| **材料在** | `app/<组>/book/` 存在且非空 | 停下索取 |
| **转换器**（材料需转换时） | `python -c "import markitdown"` | `pip install 'markitdown[pdf,docx]'`（约 27 MB，验证于 0.1.8）。若是 md/txt **不需要** |
| **抽取模型** | 平台「大模型配置」页（`/llm`）的 `operator` 已配 | 停下提示配置；未配置时索引必然失败 |
| **embedding 服务** | `python -m fde_platform.embed_service` 在跑（默认 `:9800`） | 起它。**它是常驻进程，目前无自启** |
| **索引依赖** | `import lightrag` 可用（`requirements.txt` 已含 `lightrag-hku`） | 按 requirements 装 |

## 执行步骤

### Step 1：转换与切章

```bash
python scripts/book_to_brd.py <组>          # → app/<组>/brd/第NN章-<标题>.md
```

- **切章依据自动降级**：Markdown 一级标题 → **文档自身的编号结构**（`1.0 xxx` / `Appendix A`）→ 按长度兜底。
  真实 PDF 常常**没有 Markdown 标题**（实测一本 297 页手册只认出 1 个，还是假的），所以第二种是常态——脚本已处理，**无需人工介入**。
- **不覆盖已有 BRD**：`brd/` 里已有 .md 时默认拒绝；要重建用 `--force`；只看看产出用 `--dry-run`。
- ⚠ **转完先确认产出非空**：扫描版 PDF 的 OCR 是插件、没配 `llm_client` 时**静默跳过**。脚本会以「产出过少」拦下并报错 —— 拦截失败时才需人工看看。

### Step 2：从材料提炼分类框架

读 Step 1 产出的分章 md（**抽样若干章即可**，不必通读全书），写出 `app/<组>/kg_config.json`：

| 键 | 怎么定 |
| :--- | :--- |
| `entity_types` | **从材料里提炼**：这份材料自己把领域对象分成哪几类。优先用材料里的**原词**（它怎么称呼这类对象，就怎么命名），可给类型附一句说明（抽取更准） |
| `language` | 材料是什么语言就写什么（中文材料 → `"Simplified Chinese"`） |
| `gleaning` | 密集散文（书/手册）→ 1；结构化文档 → 0（默认） |
| `llm_max_async` / `max_parallel_insert` | 取默认（4 / 3）即可，**别指望调它大提速**（见「成本预估」） |

⚠ 配置**只在建索引时生效**：Step 5 校验不过要调整时，**必须 `--force` 重建**，否则旧图不动。

### Step 3：建索引

```bash
python -m fde_platform.knowledge_graph index <组>            # 全量建索引
python -m fde_platform.knowledge_graph viz <组>              # 可选：出图谱 HTML，人工过目
```

**同一份材料不要重复索引**：`book/` 的原始件与 `brd/` 的 md 转写是同内容两份——原始件**天然不入索引**（收集器只认 `brd/*.md` 与应用详设），不要为了"全面"去放开。

### Step 4：导出对象清单

```bash
python -m fde_platform.knowledge_graph export <组>           # → app/<组>/本体对象.md（组根）
```

**这份清单是什么**（写在这里，也印在文件头部 —— 下游读文件时看得到）：

| | |
| :--- | :--- |
| **它是** | 从材料抽出的「**实体提及清单 + 共现图**」—— 文本里提到过哪些概念性名词、谁和谁常一起出现 |
| **它不是** | **不是本体**（无层级 / 属性 / 公理）；**也不是领域模型**（无标识 / 不变量 / 聚合边界）。名字里的「本体对象」只是惯称 |
| **里面混着三类** | ✅ 能建档管理的领域对象（真候选）· ⚠️ 方法论概念（讲"怎么做"，通常不独立成聚合）· ❌ 文本产物（噪声） |
| **量级** | 动辄**上千条**，真正能建档的是**几十个**量级 —— **别逐条处置**（范围见《工具链使用说明》第 3 步门禁） |

### Step 5：★分类框架的忠实性校验（本 Skill 的核心门禁）

**依据就是 Step 4 产出的那份《本体对象.md》**（每节标题自带数量）：

| 检查 | 判据 | 不过怎么办 |
| :--- | :--- | :--- |
| **空框** | 配置的每个类型都**应有实例**。某类 0 个 → 该类型在材料里不存在，或命名/说明不对 | 回 Step 2 修正或删除该类型，`--force` 重建 |
| **错框** | 「其他类型」一节里若出现**本该属于某配置类型**的对象（典型：字段被抽成独立实体、同义异名分裂） | 回 Step 2 调整类型的**说明**（说明比名字更能约束抽取） |
| **落空率** | 「其他类型」占比应处在合理区间。**参考触发线：> 30% 需复核**（一次小样本实测为 28%，其中确有错框项） | 复核「其他类型」逐项；多半是分类框架没贴住材料 |

⚠ 这是**机械可判**的检查（读导出文件的计数与分节即可），**不设"人必须确认"**——判不了的"哪个对"属于第①步，不属于这里。

### Step 6：产出术语表 `app/<组>/术语表.md`

**为什么放在这一步**（而不是建索引之前）：术语表是给**对象**定业务名的，所以要**等对象清单在手**。
提前定的话只能按"材料里的主要术语"猜，等清单出来往往对不上（粒度不同、多出或少掉），表就形同虚设。

**为什么必须有**（**任何项目都建议有；材料语言 ≠ 产出语言时必须有**）：

术语表是**命名的唯一来源** —— 同一业务概念只在这里定一次名，全链路照它取用。

- **中文材料同样需要**：BRD 里同一个概念常有不同叫法（「客户编码」/「客户编号」/「客户号」），
  不在上游统一，①–⑦ 就会各取各的，最后页面上三种写法并存。
- **跨语言材料（如英文书）则非有不可**：语言会沿链路传播。不定死的结果不是"全英文"，
  而是**不可预测的中英混杂**（同一字段在不同应用里两个名字）。

**结构**：三列，**允许一个原词多行**——同一个词在不同语境可能指不同东西。

| 原词 | 语境 / 所属类型 | 业务名 |
| :--- | :--- | :--- |
| Work Breakdown Structure | 结构 / 业务单据 | 工作分解结构（WBS） |
| review | 活动 / 评审 | 评审 |
| review | 动作 / 流程 | 审查 |

**第三列怎么被下游消费**（不定义它，它就是个摆设）：一个原词对应多行时，
下游按**该对象在《本体对象.md》中所属的分节**（即它的类型）选对应那一行。
⚠ 清单的类型在**分节标题**上（如 `### 评审（2）`），**不在表格行里**——别去找"类型"列。

**四条纪律**（缺一条，术语一致性就会漏）：

1. **核心术语必须照表** —— 对象 / 单据 / 角色 / **聚合根的业务名**取自本表，
   **照抄表里的业务名、不改写**（"怎么找到那一行"是匹配问题，见《架构设计.md》Step 6 的宽松口径）。
2. **合并而来的聚合根不照搬原名** —— 若一个聚合根由多个对象**合并**而成（处置表里的"并入"），
   其业务名按合并后的语义**新取**，**不取其中任一个**。
3. **字段级业务名可就地取名，但取完回填表** —— 表是为"同一字段在别处不再另起名"服务的，
   不是用来卡住 ② 的。表里没有 → **就地取名 + 回填**，**不要回上游重跑**（那是小时级的代价）。
4. **要改名，先改表、再改产出** —— ① 的"与业务方审核命名"若提出改动，同样走这条，保持表是唯一来源。

**表的价值在哪一列**（别把表做成清单的副本）：

- **跨语言项目** → 价值在**译名**：「业务名」列给出产出语言的正式名
  （`Work Breakdown Structure` → 「工作分解结构（WBS）」）。
- **同语言项目** → 价值在**归一**：把材料里同一个概念的多种叫法
  （「客户编码」/「客户编号」/「客户号」）收成**一个**正式名。

⚠ **「业务名」可以等于「原词」，而且常常就该等于** —— 当原来的名字本身就是产出语言的标准名时
（通用缩写如 `WBS`；或同语言项目里本来就规范的名词），**保持原样就是正确做法**。
**不要为了"看起来翻译过"去硬改一个好名字。** 该判断的是"这个名字对不对"，
不是"它跟原词像不像"。

**入口不唯一**：本 Step 是**首选**入口（此时对象清单在手，命名有据）；
但**第①步也能建、也能补缺** —— 若项目没走材料流程（BRD 由业务方直接交付，如 PSC 类），
① 的命名审核环节会顺手把它建起来。**表一旦存在即为唯一来源，此后只增不改。**

**语言约定（默认，可整表改）**：业务名**中英并列**（`工作分解结构（WBS）`）——中文受众看得懂，
英文原词能回到材料。若项目面向英文受众，可整表只留英文原词，**但必须全表一致**。
（平台**没有 i18n 机制**：标签就是纯文本，"中英并列"零成本；但"可切换语言"需要另做，不在本流程范围。）

### Step 7：交接

- **产物四份，位置不要混**：

  | 产物 | 位置 | 说明 |
  | :--- | :--- | :--- |
  | 分章 md | `app/<组>/brd/第NN章-*.md` | 业务正文 —— **唯一索引源** |
  | 本体对象.md | `app/<组>/`（**组根**） | 对象候选清单 |
  | 术语表.md | `app/<组>/`（**组根**） | 命名唯一来源 |
  | kg_config.json | `app/<组>/`（**组根**） | 分类框架 |

- **交接给《工具链使用说明》第 1 步**：`brd/` + 组根的两份辅助产物**一起交给第①步**。
  ⚠ **① 默认只读 `brd/`** —— 组根的辅助产物**必须在 ① 的输入契约里点名**，否则它根本看不到。
- **提醒一句**：对象的取舍（独立聚合 / 并入 / 排除 + 理由）在第①步定，**逐项记进 `architecture_review.md`**
- 若本次只用了部分章节做验证、未索引全书，**如实说明**，别让下游以为清单是全书覆盖

## 判定准则（启发式）

- **类型名用材料的词**：材料说"技术权威"，就别改成"审批角色"。术语一致，下游 ① 与引用才对得上。
- **类型数 6~10 个**：太少 → 全落"其他"；太多 → 彼此重叠、抽取摇摆。
- **「其他类型」不是错误**：材料里本来就有零星对象不属任何类。**要看的是里面有没有"本该归类"的项**。
- **值是对象，不是字段**：字段级的东西（编号、名称、金额）通常属于某个对象，不该各自成类。
- **宁粗勿细**：抽取阶段分得太细会切碎下游的边界判断；粗一点、把细分留到 ①。
- **术语表够不够**：**报告项**（见 §完成门禁 #4），**不按整体命中率判**。要问的是
  「**清单里那些要紧的对象，有没有漏在表外**」—— 判据是**未命中里关联数高的那批**，
  不是"覆盖了百分之多少"（分母里大半是方法论步骤，本就不该进表）。
  （表里缺个别字段级业务名是**正常**的：那本就允许就地取名 + 回填。）
- **表有没有真干活**（**报告项，不做硬门禁**）：看 **「业务名」== 「原词」的行占比**（脚本会报）。
  这条**不能按行判**——单行相同可能是"原来的名字就好"，也可能是"照抄"，机械上分不开。
  按项目类型判读：
  - **跨语言项目**：占比**接近 100%** 才可疑（大概率是清单副本，回 Step 6 重做）；
    个别行相同（通用缩写、无对应译法）属正常。
  - **同语言项目**：占比高**是正常的**（本就不需要译名），此时要看的是**归一**是否发生 ——
    即材料里同义的多个叫法是否被收进同一行。**别把这个比例当质量指标。**

## 输出结构

```
app/<组>/
├── book/                    原始材料（任意格式；不入索引、不入 git）
├── brd/
│   └── 第NN章-<标题>.md      分章正文 —— **唯一索引源**，九步法第①步的输入
├── 本体对象.md               对象候选清单（含出处 / 源块 / 关联数）   ← 组根
├── 术语表.md                 原词 → 业务名，全链路命名的唯一来源      ← 组根
└── kg_config.json           分类框架（+ 语言 / 并发）                ← 组根
config/kg_storage/<组>/      知识图谱（graphml + 向量库 + 缓存；本地、可重建）
```

⚠ **辅助产物为什么放组根、不放 `brd/`**：索引收集器收**全部** `brd/*.md`，
而《本体对象.md》是**从图谱导出**的。放进 `brd/` 的话，**下次索引会把它吃回图谱**——
导出物被重新抽取、灌回同一张图，形成**反馈环**（与我们刻意避开的 `book/` 问题是同源的）。
所以：`brd/` 只放**业务正文**；辅助产物一律组根。**别为了整齐把它们挪回去。**

## ▶ 完成门禁（硬性，未通过不得交给第①步）

1. **转换非空**：`brd/` 下有分章 md，且总量与材料规模相称（脚本的产出过少检查已拦一道）
2. **分类框架校验通过**：无空框；「其他类型」中无明显的错框项；落空率已复核
3. **导出齐备**：《本体对象.md》存在（**组根**），且含【业务对象分节 + 其他类型 + 高频关系】三部分
4. **术语表就位且可用**：《术语表.md》存在（**组根**）且非空，并且——
   - **不编造**：表中每个「原词」都能在 `brd/` 正文里检索到（grep 即判）
   - **核心对象没漏**（**报告项，不设分数线**）：跑 `python scripts/term_coverage.py <组>`，
     看**未命中清单里关联数最高的那批**有没有要紧对象（如 `SEMP`、`需求`、`V&V Plan`）。
     ⚠ **不要拿整体命中率判成败**：实测一份清单有 **2189** 个对象，而术语表只覆盖**几十个核心**
     —— 整体命中率天然很低（分母里大半是**方法论步骤与概念**，本就不该进表）。
     **要判的是"核心有没有漏"，不是"覆盖了百分之多少"。** 脚本按宽松口径匹配（不分大小写、
     容忍缩写/单复数/连字符，且**对象名与「原词」「业务名」两列都比**，以防对象名已被抽成产出语言）。
5. **位置正确**：`brd/` 下**只有业务正文**（**不限于分章** —— 业务方直接交付的多份文档也算正文），
   辅助产物（导出清单 / 术语表 / 配置）不得混入，否则下次索引把它们吃回图谱（反馈环）
6. **如实标注**：若只索引了部分章节，已在交接说明中写明

## 回溯触发

- **分类框架校验不过**（空框 / 错框 / 落空率超线）→ 回 **Step 2**（改类型或说明）→ `index --force` 重建
- **转换产出过少** → 回 **Step 1**（疑似扫描件：装 `markitdown-ocr` 或换 MinerU 自行转出 md 再放回 `book/`）
- **材料明显超出单次可索引规模**（如多卷手册）→ 停下来与用户确认**先做哪一部分**，不要闷头跑几小时再报错

## 成本预估（写在这里，免得后来人低估）

- **抽取耗时由 LLM 服务端吞吐决定**：实测单次抽取调用约 **100 秒**；并发 4→8 实测只快约 **2 倍**（**加并发买不到线性提速**）。
- 一本 300 页 / 87 万字符的书（约 180 个 chunk）**约 2~3 小时**；其中实体合并类调用只占约 9%。
- **估速率要拿一个中大章试跑**：单 chunk 的小文档无法并行、慢得离谱（实测 0.83 次调用/分钟），21 个 chunk 的大章能跑满并发（1.4 次/分钟）—— **大章反而更快，别用前言/附录估算整本**。
- **重跑是增量的**：抽取结果按提示词缓存（`kv_store_llm_response_cache.json`，按组存放），未变的内容重跑命中缓存；但**改了分块就会全部失效**。

## 核心规则

1. **忠实于材料**：分类从材料提炼，不按目标裁剪；先抽全，取舍留给 ①。
2. **不臆造**：材料缺、配置缺、服务没起 → 停下说清楚，不自行填充、不套样例。
3. **只产出文档**：不划边界、不产代码、不写 `architecture.md`。
4. **产物可溯源**：每个对象带出处（文档）与源块（chunk id），能回查原文。
5. **门禁机械可判**：能判的用脚本判；判不了的（哪个对象该进范围）明确交棒给第①步。
6. **成本如实告知**：小时级的索引，跑之前先量、先说明，别让用户干等。
7. **命名集中定一次**：术语表是**全链路命名的唯一来源**。下游照表取名；表里没有 → 就地取名并**回填表**，
   绝不各步自创（否则同一概念会分裂成多个名字）。
8. **正文与辅助产物分家**：`brd/` **只放业务正文**；导出清单与术语表放**组根**——防止下次索引把导出物吃回图谱。
