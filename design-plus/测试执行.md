# 测试执行 · 第⑤步技能规格（测试用例 → 可运行测试脚本）

> **版本**: v1.0  **创建日期**: 2026-08-02
> **适用人员**: 应用构建第⑤步的执行体（AI / 工程师）
> **目的**: 把第④步产出的《测试用例.md》**翻译成一个可直接运行的集成测试脚本**，真实驱动应用组跑通主链与分支，并产出可 triage 的 PASS/FAIL 报告。
> **本步只消费《测试用例.md》**——它是怎么测的唯一设计来源；本规格规定「如何把用例落成脚本」，不另起测试设计、不绑定具体应用组。

---

## 🧭 使用契约：作为「测试执行」技能（应用组构建 · 第⑤步）

### 技能定位（九步法 · 后端段）

```text
第①步  聚合根识别（《架构设计.md》）      业务说明 → app/<组>/architecture.md                 ← 已定义
            ↓
第②步  逐聚合根应用设计（《应用设计.md》） architecture.md + brd/ → 每聚合根一份 应用详设.md    ← 已定义
            ↓
第③步  应用编码（《应用编码.md》）        应用详设.md → app/<组>/<应用>/<应用>.py + README.md   ← 已定义
            ↓
第④步  测试用例生成（《应用测试.md》）    architecture.md + 各详设 → app/<组>/测试用例.md        ← 已定义
            ↓
★第⑤步  测试执行（本文件）               app/<组>/测试用例.md → app/<组>/tests/verify_chain_<组>.py（可运行）  ← 本规格
```

> 第④步与第⑤步即「生成与执行分离」的两半：第④步产出**用例（数据）**，第⑤步把用例**翻译成脚本并运行**。

> 后端段（①–⑤）之后是前端段（⑥–⑨，契约冻结后开工）：《前端设计.md》→《前端编码.md》→《前端测试.md》→《前端测试执行.md》；全景见《工具链使用说明.md》。

### 必给参数
- 英文应用组名 `<组>`（snake_case），逐字绑定 `app/<组>/`。
- （可选）执行范围：`phase1`（§1 主数据 + §2 主链）/ `phase2`（§3 分支）/ `all`；缺省＝先 phase1 跑绿再 phase2。

### 输入
| 来源 | 位置 | 说明 |
|---|---|---|
| ① 测试用例（**唯一测试设计来源，必需**） | `app/<组>/测试用例.md` | 第④步产出：§0 冻结数据字典 + §1–§3 四要素用例（步骤/数据/期望/回执模拟）+ §4 待确认。缺失则停下、先跑第④步。 |
| ② 应用代码（**仅用于签名校准**） | `app/<组>/<应用>/<应用>.py` | 第③步产出。用 `ast` 抽公共方法签名，只为让脚本**入参名/必填项**与代码一致；**不**用它决定测什么（测什么以用例为准）。 |
| ③ 初始化方式 | 脚本内置 `clean()` | **清表式初始化**：清空本组各应用库的全部表（保留库文件、只清数据）——测试环境初始化语义，平台开着也能跑（无文件锁冲突）；`config/` 平台库不受影响。 |
| ④ 脚本样板 | `design-plus/后端验收样板/verify_chain_sample.py` | 现成的主链集成测试范式（`platform.call` + `expect_err` + 数据串联 + 回执模拟），照其骨架写（其 dbguard 隔离为旧式手工保护写法，平台生成脚本已改清表初始化）。 |

### 产出
- `app/<组>/tests/` 脚本集：编排器 `verify_chain_<组>.py`（运行入口）+ `verify_chain_<组>_partN.py` 各 part（结构见「脚本结构」节）。
- 运行报告：逐条用例 PASS/FAIL + 失败所在步骤 + triage 归类（脚本错 / 应用 bug）。

## 用例四要素 → 脚本映射（核心方法论）

《测试用例.md》每条用例含四要素，逐一落地为可执行代码：

| 用例要素 | 脚本落地 |
|---|---|
| **步骤** `<应用>.<服务>(参数)` | `call("<应用>", "<服务>", **参数)`——一律经 `platform.call` **真实路由**（含 `self.fde.call` 跨应用调用、事务、鉴权），**不**直接 `import` 应用类。 |
| **测试数据**（§0 冻结字典） | 脚本顶部定义为常量；主数据标识（`C001`/`CTCT-0001`/手册号/组织号）直接取值；**单据号别名**（`FC1`/`SO1`/`FO1`/`DN1`/`R1`/`CC1`/`RO1`）**从对应 create 的返回值捕获**（如 `so_no = call("sales_order","create",...)["so_no"]`），再代入后续步骤——这是把「用例别名」落到「运行时真实值」的桥。 |
| **期望** `status=X` / 返回某字段 | `assert call(<应用>,"get",<键>=<别名>)["status"] == "X"`（或对应字段断言）。 |
| **期望** 跨应用副作用（"余量被占用""回写 DN"） | 调被影响应用的 `get` 验证（如 `bonded_manual.get` 余量减少、`delivery_note.get` 含 `recon_no`）。 |
| **期望** `抛 FdeError 含『关键词』` | `expect_err(lambda: call(...), "关键词")`（断言抛出且消息含关键词）。 |
| **回执模拟点**（`on_*_result` / `add_inbound` / `add_work_order` / `on_transport_info` 等） | 在该步**直接调用回写服务**模拟外部系统异步回执（成功路/失败路按用例），**不依赖** stub 的自动行为——异步流程能否闭环全靠手动驱动这些回写。 |

## 执行环境与初始化（铁律）

1. **路径锚定**：脚本在 `app/<组>/tests/` 下，项目根经 `_project_root()` **向上查找 `fde_platform/`** 定位（落点深度不固定，勿写死 `parents[N]`）；`os.chdir(ROOT)`；`sys.path` 加 `ROOT`（import `fde_platform`）。
2. **清表式初始化**：`main()` 首行 `clean()`——对本组每个 `app/<组>/<应用>/<应用>.db` 连接后 `DELETE FROM` 全部用户表（**保留库文件、只清数据**）。不删文件，故无 Windows 文件锁问题、**平台服务器开着也能跑**；`config/` 下平台库（auth/llm/聊天记录等）一律不碰。⚠️ 语义明示：**运行测试会清空本组全部业务数据**（测试环境初始化；需要数据时由主数据用例重建）。
3. **外部系统走 stub**：`os.environ.pop` 清掉 `LLM_*` 与 `SAP_BASE_URL`/`MOM_BASE_URL`/`WMS_BASE_URL`/`MDM_BASE_URL`/`APS_BASE_URL`/`CTCT_BASE_URL` → 出向适配器自动降级为本地 stub，无需真 SAP/APS/WMS。
4. **加载与自检**：`FdePlatform().load_all()`，断言用例涉及的应用全部加载成功。
5. **运行约束**：平台服务器可同开（清表初始化不动文件、无锁冲突），但**跑测试期间勿经平台 / Agent 操作该组数据**（写入会与测试互扰）；**勿并行**跑多个 verify 脚本（互相清数据）。

## 脚本结构（模板）

产物是**脚本集**（编排器 + 按生成批次拆分的 part），全部落 `app/<组>/tests/`：

```
app/<组>/tests/
├── verify_chain_<组>.py            ← 编排器（运行入口，平台静态骨架）
├── verify_chain_<组>_part1.py      ← §0+§1 主数据 用例语句体
├── verify_chain_<组>_part2.py      ← §2 主链（超大节自动 part3…；按用例块边界切，不劈单条用例）
└── verify_chain_<组>_partN.py      ← §3 分支 / 异常
```

```python
# ── 编排器 verify_chain_<组>.py（平台静态骨架）──
# 头部：docstring + 路径锚定（ROOT=向上查找 fde_platform/ + os.chdir）+ 清外部基址(stub) + GROUP/APPS
STEP = ""; STEP_RESULTS = []            # 逐例记录器
def step(name): ...                     # 打印 `→ name`、失败定位
def record(ok, note=""): ...            # STEP_RESULTS 追加 (步骤名, 是否通过, 备注)
def expect_err(fn, substr): ...         # 断言抛 FdeError 且含关键词
def clean(): ...                        # 清空本组各应用库全部表（保留库文件、只清数据）

def main():
    clean(); pf = FdePlatform(); pf.load_all()
    def call(app, svc, **kw): return pf.call(f"{GROUP}/{app}", svc, **kw)
    for name, label in PARTS:           # 按序执行各 part
        mod = importlib.import_module(f"verify_chain_{GROUP}_{name}")
        try: mod.run_part(call, step, expect_err, record)
        except Exception as e: record(False, f"[{label}] CRASH: …")   # 崩溃隔离：只记录、继续跑
    clean()
    # 打印逐例结果表 + 三态哨兵
if __name__ == "__main__":
    try: main()
    except Exception as e:              # 脚本级崩溃（非用例软失败）
        print(f"FAIL_STEP: {STEP}"); print("VERIFY_RESULT: CRASH"); sys.exit(1)

# ── 各 part verify_chain_<组>_partN.py（模型只写用例语句体）──
def run_part(call, step, expect_err, record):
    # 每条用例首行 step("<TC编号> <名称>")，随后该用例语句
    #   （数据准备 / call / assert / expect_err / 回执模拟调回写服务）
    # 每条用例由平台自动包 try/except：失败记原因后继续（软失败，不阻断）
```

**为什么拆**：超大组单脚本可达数千行——审阅难、修复粒度粗、脚本级崩溃连坐。拆分后：各 part
数百行、与生成批次一一对应（门禁失败 / 修复回路**定向重生成对应 part**）；part 脚本级崩溃只影响该
part（崩溃隔离，后续自包含用例照跑）；运行入口与语义不变——`python app/<组>/tests/verify_chain_<组>.py`，
一次清表初始化 + 一个 DB 生命周期内按序执行各 part，part 间共享变量与库状态（数据依赖由此消化）。

**三态 verdict（机器哨兵）**：`VERIFY_RESULT: PASS x/x`（全绿）/ `PARTIAL x/M`（M 例中 x 通过，失败例逐条记录原因）/
`CRASH`（脚本自身语法 / 运行时错）。**报告优先**：失败用例不中断执行——除 CRASH 外永远跑到尾、出逐例报告。

## 执行铁律

- **真实路由**：所有步骤经 `platform.call`，测的是真实联通（跨应用 `self.fde.call`、事务、状态机），不绕过平台直调应用方法。
- **数据字典只引用不新造**：§0 冻结标识贯穿全脚本；单据号一律从返回值捕获串联，禁止硬编码生成的单号。
- **入参以代码实际签名为准**：用 `ast` 抽公共方法签名校准入参名与必填项；用例 §4『待确认』项（如某服务入参结构、暂估价字段）**运行时按实际报错校准**。
- **分阶段执行**：
  - **Phase 1**：§1 主数据 + §2 主链——先把脊柱跑绿（主干不通，依赖它的用例会连环 fail，无从 triage）。
  - **Phase 2**：§3 分支——区分**自包含**错误校验（如坏父组织、余量不足，独立可跑）与**依赖主链状态**的分支（如「FO 已排产不可撤回」，复用 Phase 1 单据或单独造数）。
- **断言聚焦可靠信号**：优先断 `status` 与明确返回字段；对不确定的返回结构先 `print` 观察再固化断言，避免一开始就因键名猜错而误判。

## 失败 triage（首轮几乎不会全绿，须归类）

《测试用例.md》是**未运行**生成的，部分入参形态/必填字段为推断，故首跑必有出入。每个 FAIL 归两类：

1. **脚本 / 用例翻译错**——入参名不对、漏必填字段、返回键名不符、期望状态名不符 → **修脚本或回填用例**（并据实修正《测试用例.md》的 §4 待确认）。
2. **真实应用 bug**——生成的应用代码确有缺陷（校验缺失、状态机错、跨应用调用契约不符）→ **记录**，作为第③步代码质量反馈，不在本步擅自改应用代码。

报告须能逐条定位：失败在哪个 `step`、哪条用例、实际返回/报错是什么。

## 验收标准

- 脚本可独立运行：`python app/<组>/tests/verify_chain_<组>.py`。
- verdict 三态达标：`PASS`（全绿）或 `PARTIAL x/M`（失败例均已明确 triage 记录：脚本校准错 vs 应用 bug）；`CRASH` 必须修复至 PASS/PARTIAL。
- 分支用例覆盖 §3 的错误分支与外部失败路（`expect_err` 与回执失败路）。
- 清表初始化只影响**本组**应用库（`config/` 平台库不动）；运行即清空本组业务数据（测试环境语义，须明示执行者）。
- 报告含逐例结果表（用例 / 结果 / 备注）+ 输出尾部。

- **覆盖度门禁**：本步产出须经独立的覆盖度检查——对照本规格规定的上游输入，逐项验证覆盖完整性。覆盖度 < 100% 不得进入下一步。具体门禁条件见 `design-plus/工具链使用说明.md` 对应步骤的「完成门禁」段。

## 命名与边界

- 脚本落 `app/<组>/tests/verify_chain_<组>.py`（与《测试用例.md》同组，独立 `test/` 目录）。
- 本步**只翻译并运行测试**，不改应用代码；发现的应用 bug 另行反馈第③步。
- 测试设计**只来自《测试用例.md》**，不凭架构/详设另起用例（保持「生成与执行」单一数据源）。

## 平台化入口（第⑤步自动化任务）

平台 `/groupbuild` 页面 ⑦ 测试执行（任务 `kind="testexec"`，`fde_platform/groupbuild_runner.py`）
把本步产品化为一键任务：

- `gather`：预检 测试用例.md；ast 抽各应用**服务签名** + `_init_db` 建表字段 / 必填列（**数据契约**，消除入参形态误译）。
- `gen`（**harness 模式**）：编排骨架（初始化头部 / 助手 / part 循环 / 三态哨兵 / `__main__` 入口）为**平台
  静态代码**，模型只写用例语句体——**按 § 章节自适应分块**（§0+§1 / §2 / §3…，单块超
  `GROUPBUILD_CHUNK_MAX_CHARS`（默认 3 万字）按 TC 用例块边界再切；每批只投喂自己那节 + 共享的 §0
  字典 / 数据契约 / 签名），规避超大组单段撞 `max_tokens` 截断（`'{' was never closed`）与网关推理超时
  （HTTP 504）。**每批落一个 part 文件**（`verify_chain_<组>_partN.py`，`run_part` 包语句体），平台按
  `step()` 标记**逐例自动包 try/except**（软失败：失败记原因继续跑）；拼装后过静态门禁，未过**按问题
  文件归属定向重生成对应批**（非全量重出）。
- `run`：**真实树直跑**编排器（清表初始化；按序调各 part，part 级脚本崩溃只记录不阻断后续 part），
  三态 verdict；`write`：脚本集 + 报告 + 失败台账。

要点：

- **报告优先**：失败用例不中断执行；verdict 三态 `PASS / PARTIAL x/M / CRASH`——**仅 CRASH / 用例全败触发脚本修复回路**
  （≤3 轮，回喂输出尾部分段重生成；连续两轮错误签名相同 → 提前终止）。PARTIAL 即真实结果，直接出报告。
- **真实树直跑**：脚本落 `app/<组>/tests/verify_chain_<组>.py`，平台 subprocess 直接运行（cwd=项目根）。
  初始化走脚本内置 `clean()` 清表（保留库文件、只清数据）——**平台服务器同开也无文件锁冲突**；
  ⚠️ **运行会清空该组全部业务数据**（测试环境初始化语义；config/ 平台库不受影响）。
- **产出**：`app/<组>/tests/verify_chain_<组>.py`（符合本规格完整模板，可手动重跑）+ `app/<组>/tests/测试报告_<组>.md`
  （verdict / 逐例结果表 / 输出尾部）；有失败用例 → 追加 `BUGS_<组>.md` 台账（待 triage）。
  页面可下载脚本 / 报告、删除产物（不删 BUGS_<组>.md）、**终止运行中的任务**（协作式取消，秒级生效）。
- 调参：env `GROUPBUILD_TESTEXEC_REPAIR`（修复轮数，默认 3）/ `GROUPBUILD_TESTEXEC_RUN_TIMEOUT`
  （单轮运行超时秒数，默认 900）/ `GROUPBUILD_TESTEXEC_OUTPUT_TAIL`（回喂输出尾部字数，默认 6000）。
